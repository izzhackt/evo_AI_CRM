## 0. Чего этот план не разрешает

- Ни одного действия на production: ledger-apply миграций, правка env на VPS,
  создание роли БД и её пароля, выпуск образа, включение ИИ, включение
  автоответчика, корзина папки в «Базе знаний» — каждое отдельным
  разрешением владельца на конкретное действие.
- Копирование исходного кода SoodaCloser в публичный репозиторий
  `evo_AI_CRM`. Здесь — только UI, тонкие авторизованные маршруты, миграции и
  SQL-тесты. Код движка живёт в приватном репозитории `evo-ai-agent`.
  Документы могут описывать поведение и ссылаться на пути файлов SoodaCloser.
- Отправку клиентам чего-либо днём без нажатия сотрудника. Днём ИИ только
  готовит черновик; ночной автоответчик — отдельная фаза P4 по ADR 0031.

## 1. Цель и границы

Раздел «ИИ-агент» помогает сотрудникам продаж быстро отвечать клиентам в
WhatsApp точными ответами из проверенных материалов EVO, учит агента на
ошибках через «Лабораторию», показывает расходы в долларах и, по отдельному
решению владельца, ночью сам квалифицирует новых клиентов.

Что входит:

1. окно «Помочь с ответом» в чате продаж: потоковый ответ с источниками;
2. «Информация для агента» — своя база материалов агента с загрузкой файлов,
   двойным OCR и «Листом сверки»;
3. «Лаборатория» и «Правила общения»;
4. память о клиенте;
5. «Расходы» на ИИ;
6. ночной «Автоответчик»;
7. «Диктовка» — отложена владельцем, здесь только место в плане.

Что не входит:

- amoCRM в чате продаж. Владелец 06.10: «убери эти тоже, у нас же другой план
  по ИИ агенту а amocrm убирай просто, пока не надо в чате продаж». Старый блок
  «Ответ и отправка» («Черновик Gemini», «Синхронизация с amoCRM недоступна…»)
  убирается из чата продаж в отдельном PR полного чата
  (`izzhackt/sales-chat-full`). Окно ИИ из этого плана заменяет его
  ИИ-часть.
- Отправка файлов из чата и OCR вложений клиентов. Вложения клиентов —
  персональные данные; они никогда не попадают в «Информацию для агента».
- Звонки и настольное приложение SoodaCloser. Владелец их не просил.

## 4. Архитектура: приватный сервис `evo-ai-agent`

### 4.1. Что где лежит

| Где | Что |
|---|---|
| Приватный репозиторий `izzhackt/evo-ai-agent` (новый) | Форк движка SoodaCloser: Python 3.13, FastAPI, psycopg 3. Модули ingest, retrieval, assistant (ответ, защита, Лаборатория, память), pricing/usage, логика автоответчика. Слои хранения переписаны на RPC EVO. Свой WAHA-канал, своя авторизация, звонки и десктоп не переносятся. Там же промпты, eval-harness и анонимизированный набор вопросов |
| Публичный `izzhackt/evo_AI_CRM` | Миграции (`supabase/migrations/266+`) и SQL-тесты; маршруты `/api/v3/ai-agent/*`; внутренние маршруты `/api/internal/ai-agent/*`; UI раздела и окна ИИ; две новые службы в `docker-compose.prod.yml`; поддержка digest образа в release controller |
| Supabase EVO | Все данные агента: документы, фрагменты, ответы, расходы, журнал автоответчика. Отдельного проекта Supabase нет |
| hermes-vps `/opt/evo-crm` | `.env.ai-agent` (ключ Gemini, пароль роли БД, HMAC-секреты), mode 0600, вне Git |

SQL для EVO пишется заново в соглашениях EVO (`organization_id`,
`platform_private`, SECURITY DEFINER, пустой `search_path`). Файлы миграций
SoodaCloser не копируются.

### 4.2. Процессы и compose

В `docker-compose.prod.yml` проекта `evo-crm` добавляются две службы из
одного образа:

| Служба | Команда | Сеть | Лимиты | Назначение |
|---|---|---|---|---|
| `ai-agent-api` | uvicorn, 2 воркера | только `private` (`evo_crm_private`), alias `evo-ai-agent`, порт 8080 | 0,5 CPU, 512 MiB | Ответы (SSE), Лаборатория, переиндексация после правок |
| `ai-agent-worker` | цикл чтения pgmq | только `private` | 1,0 CPU, 1536 MiB, `pids_limit` 256 | Загрузка документов и OCR, эмбеддинги, память о клиенте, автоответчик |

Правила для обеих служб: `read_only: true`, `tmpfs /tmp` 256 MiB, `init: true`,
не root, без опубликованных портов, без сети `web`, без доступа к WAHA.
Healthcheck `GET /v1/health` (без БД) и `GET /v1/ready` (БД и очередь).
Службы стоят под compose-профилем `ai-agent`: пока владелец не включил
агента, выпуск CRM их не поднимает и ведёт себя как сейчас.

Reranker `bge-reranker-v2-m3` в P1–P3 не поднимается (`RERANK_MODE=off`).
Причины: интерактивные ответы в SoodaCloser на этом же хосте и так идут без
него (2,5 с не хватает даже на 12 кандидатов), на хосте нет swap, а второй
reranker держал бы около 3,4 GiB без дела, пока фоновая подготовка
выключена. Вопрос возвращается в P4, когда появятся фоновые ночные ответы
(§18, вопрос 4).

### 4.3. Как CRM вызывает агента

Браузер никогда не обращается к агенту напрямую.

1. Браузер → маршрут CRM (сессия Supabase в cookie). Маршрут вызывает
   авторизованный RPC `platform.ai_agent_ticket_v1(purpose, conversation_id,
   ref_id)`. Внутри БД по `auth.uid()` проверяются право `ai.agent.use` (или
   `ai.agent.manage`) и, для диалога, доступ
   `staff_access_evaluate(…, 'communication.read.full')`. RPC возвращает
   одноразовый билет: 32 случайных байта, в БД хранится только SHA-256,
   срок 60 с, билет привязан к сотруднику, диалогу, сообщению и цели.
2. CRM → агент по `http://evo-ai-agent:8080` во внутренней сети. Запрос
   подписан HMAC-SHA256 (`ts.method.path.sha256(body)`, допуск по часам 60 с)
   секретом `EVO_AI_AGENT_INTERNAL_SECRET`. Этот секрет не совпадает ни с
   HMAC WAHA, ни с секретами lead-agent. Билет передаётся в теле запроса.
3. Агент погашает билет RPC `platform_ai_agent.redeem_ticket_v1`: получает
   организацию, сотрудника и цель, билет помечается использованным. Утёкший
   HMAC-секрет сам по себе не открывает ни одного диалога: нужен свежий
   билет, выданный по действующей сессии сотрудника.
4. Ответ идёт потоком SSE: агент → CRM → браузер. Маршрут CRM пробрасывает
   поток без буферизации (`Content-Type: text/event-stream`,
   `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`, без
   сжатия Next). Когда браузер закрывает поток, CRM обрывает запрос к агенту.
   Caddy сбрасывает `text/event-stream` сразу; это проверяется smoke-тестом
   через настоящий edge.

Простые чтения и записи без ИИ идут из CRM прямо в авторизованные RPC, минуя
агента: сохранённый ответ, «Правила общения», «Расходы», настройки
автоответчика, список документов, «Лист сверки».

Новые маршруты `/api/v3/ai-agent/*` и `/api/internal/ai-agent/*`
регистрируются в `src/lib/platform-route-contract.ts`, маршрут раздела — в
`src/lib/platform-access.ts` и `src/lib/fixed-role-policy.ts`.

Фоновая работа (загрузка документов, память, автоответчик) идёт без билета.
Её границы держит БД, а не код агента (§5.3, «Фоновые функции»): каждая
фоновая функция, которая отдаёт текст диалога, работает только при
включённой своей настройке и только для диалогов очереди продаж; при
выключенной настройке она отказывает. Каждое действие пишется в журнал.

### 4.4. Доступ к БД: отдельная роль `evo_ai_agent`

**Выбор:** отдельная роль Postgres с минимальными правами. Она может только
вызывать SECURITY DEFINER-функции схемы `platform_ai_agent`.

- `CREATE ROLE evo_ai_agent NOLOGIN NOINHERIT NOBYPASSRLS NOCREATEDB
  NOCREATEROLE` — в миграции. `LOGIN`, пароль и `CONNECTION LIMIT 10`
  оператор задаёт вне Git (SQL editor или Management API) по отдельному
  разрешению. Пароль хранится в `.env.ai-agent` и в SOPS-архиве.
- Роль получает `USAGE` только на `platform_ai_agent` и `EXECUTE` на явный
  список функций. Права на таблицы не выдаются, на `platform_private`, `pgmq`,
  `storage` и `auth` — тоже. Для роли задаются `statement_timeout` 15 с и
  `idle_in_transaction_session_timeout` 30 с. Долгую индексацию документа
  агент выполняет одной транзакцией: `BEGIN; SET LOCAL statement_timeout =
  '60s'; SELECT platform_ai_agent.document_index_v1(…); COMMIT;`. Атрибут
  `SET statement_timeout` на самой функции не помогает: таймер уже идущей
  команды взят при её старте. Таймаут — защита ресурсов, а не граница
  доступа: размер пакета ограничивает сама функция (не больше 2 000
  фрагментов за вызов).
- Подключение через Supavisor в transaction mode. Имя пользователя —
  `evo_ai_agent.<project_ref>`. Custom-роли с LOGIN поддерживаются, пул
  считается отдельно на каждого пользователя, поэтому пул агента не мешает
  пулу приложения. Prepared statements в transaction mode не используются, как
  и в SoodaCloser.
- Схема `platform_ai_agent` не входит в exposed-список PostgREST
  (`supabase/config.toml`: `public`, `platform`, `graphql_public`).

**Почему не иначе:**

- Роль-владелец таблиц или любая роль с обходом RLS недопустимы: сервис
  разбирает недоверенные файлы и вывод модели.
- Ключ `service_role` через PostgREST даёт BYPASSRLS на весь проект: Auth,
  Storage, данные студентов. Это слишком широко для побочного сервиса. Кроме
  того, аренде pgmq с visibility timeout и пакетной записи фрагментов всё
  равно нужны RPC.
- Роль `authenticated` с JWT сотрудника не подходит для фоновой работы без
  пользователя.

Отдельная роль ограничивает ущерб от взлома агента функциями агента, а
авторизация остаётся в Postgres.

### 4.5. Файлы

Новый приватный bucket `platform-ai-agent-knowledge`: 25 MiB на файл, список
MIME из §7. Политика RESTRICTIVE закрывает его для anon и authenticated, как у
`platform-knowledge-library` (201).

- Загрузка идёт через CRM: маршрут проверяет размер и тип, сканирует файл в
  существующем ClamAV (`evo-crm-clamav`), кладёт его в bucket серверным
  ключом CRM и вызывает RPC `platform.ai_agent_document_upload_v1`. RPC
  создаёт строку документа и ставит в очередь указатель.
- Агенту нужен доступ к оригиналам и он пишет картинки страниц и вырезки.
  Для этого CRM открывает внутренний брокер
  `/api/internal/ai-agent/storage/*` с отдельным секретом
  `EVO_AI_AGENT_STORAGE_SECRET`. Брокер работает только внутри bucket агента и
  только с префиксом `{organization}/{document}/`. Edge Caddy уже отвечает 404
  на `/api/internal/*`. Серверный ключ Supabase остаётся только у CRM.

### 4.6. Образ, пиннинг, выпуск, откат

- CI приватного репозитория собирает `linux/amd64` образ
  `ghcr.io/izzhackt/evo-ai-agent` (Debian bookworm, Python 3.13, Tesseract
  5.3 с `rus`, `kir`, `eng`, `osd`, pdfium, без ключей) и публикует его в
  приватный GHCR. В образе метки `org.opencontainers.image.revision` и
  `source`.
- В compose образ задаётся только по digest:
  `${EVO_AI_AGENT_IMAGE_REPOSITORY:-ghcr.io/izzhackt/evo-ai-agent}@${EVO_AI_AGENT_IMAGE_DIGEST}`.
  Переменная GitHub `EVO_AI_AGENT_IMAGE_DIGEST` работает как
  `EVO_WAHA_IMAGE_DIGEST`: controller проверяет `^sha256:[0-9a-f]{64}$`,
  записывает digest в receipt и pending-state и откатывает его вместе с
  приложением. Подвижные теги не считаются доказательством выпуска.
- Для `docker pull` на hermes нужен токен GHCR только на чтение
  (`read:packages`). Он хранится в docker credential store root и в SOPS. Это
  отдельный ops-шаг владельца (§15, P0).
- Smoke выпуска для агента: `GET /v1/ready` изнутри сети, `/v1/status` (ключ
  Gemini принят, без генерации) и один настоящий ответ на диалог QA-владельца
  в фазе приёмки. В каждом обычном выпуске CRM генерация не вызывается.

### 4.8. Ёмкость hermes

Агент добавляет 2 GiB лимитов: 512 MiB у api и 1,5 GiB у worker. Распознавание
одной страницы идёт в одном процессе (`OCR_CONCURRENCY=1`). Разбор файла
выполняется в дочернем процессе с лимитом памяти 768 MB и таймаутом 120 с,
как в `ingest/sandbox.py` SoodaCloser. Перед включением P2 замеряется время
Tesseract `rus+kir+eng` на странице на hermes; цель «3 страницы скана за
≈ 50 с» до замера считается неподтверждённой.

Для сервера CRM (`platform`, `EXECUTE` только у `service_role`, ключ есть

- `ai_autosend_authorize_v1(organization_id, decision_id, request_id)` —
  единственная точка ночной отправки (§11, правило 9, P4).

Для агента (`platform_ai_agent`), интерактивные — только по погашенному

- `usage_record_v1`, `rate_take_v1`, `budget_reserve_v1`, `budget_release_v1`

Фоновые функции агента читают диалоги без билета, поэтому каждая проверяет
в БД, что её настройка включена, и работает только с диалогами один на
один очереди продаж (`queue = 'sales'`); иначе — отказ:

| Функция | Фаза | Условие в БД | Что отдаёт |
|---|---|---|---|
| `inbound_since_v1` | P3/P4 | включены автоответчик (shadow или живой, сейчас внутри интервала), память или подготовка заранее | Только указатели: диалог, сообщение, время. Текста нет |

В P1 фоновых функций с текстом диалогов нет: память, подготовка заранее и
автоответчик появляются миграциями P3 и P4.

### 5.4. Очередь

Новая очередь pgmq `ai_agent_work_v1` и `ai_agent_dead_letter_v1`. Сообщения
только с указателями: `{v, kind, ref_id}`, где `kind` — `ingest`, `reindex`,
`memory`, `autosend`, `seed`. Текстов клиентов, промптов и ошибок в очереди
нет. Это поправка к контракту P2G: третья пара очередей заводится для того,
чтобы роль агента физически не могла взять работу `manual_whatsapp_send` из
`platform_work_v1`. Повтор — до трёх попыток по `read_ct`, затем
dead-letter.

Новые входящие сообщения агент узнаёт опросом
`platform_ai_agent.inbound_since_v1` каждые 5 с и только когда нужен фон:
включены автоответчик, память или подготовка заранее. Это условие
проверяет сама функция (§5.3). Триггер в живом пути проекции WAHA не
ставится: путь приёма WhatsApp не меняется.

### 5.5. Права

Новые определения прав в `platform.permission_definitions`:

- `ai.agent.use` — окно ИИ в чате и просмотр раздела;
- `ai.agent.manage` — загрузка и правка знаний, «Лист сверки», «Применить» в
  Лаборатории, правила, настройки расходов и автоответчика.

Оба права описываются как права уровня организации, как `team.chat.*` и
`staff.assistant.use` в 155: `staff_resource_kinds = {organization}`,
`staff_scope_kinds = {organization}`, `staff_system_only` и
`staff_sensitive` — false, метки и группа «ИИ-агент» для экрана ролей.

Опубликованный bundle менять нельзя: триггер
`role_bundle_permissions_published_immutable` (041) запрещает правку его
прав. Поэтому миграция P1 по решению Q9 повторяет шаги
`platform.staff_role_publish` (155) для каждой подходящей роли, как 173
делал для шаблонов:

1. Подходящая роль — активная роль организации с текущим опубликованным
   bundle, все активные назначения которой имеют область `organization`. Это
   роли «Продажи — общие разделы» и «Сопровождение — общие разделы» из 173.
   В production 06.10 их две, у них 4 активных назначения. Роли с
   назначениями `own` или `department` (Sales, Sales Manager, Admissions,
   Admissions Manager) не меняются: право уровня организации в них дало бы
   `staff_roles_publish_scope_conflict`.
2. Для каждой такой роли:
   - создаётся новая версия bundle (`role_bundle_versions`: черновик, права
     текущего bundle плюс два новых, затем `published`);
   - добавляется привязка `staff_role_bundle_bindings` со следующим
     `bundle_version`;
   - у роли меняются `current_bundle_id` и `draft_permission_keys`,
     `version` увеличивается на 1;
   - активные назначения роли закрываются (`revoked_at`) и создаются заново
     на новом bundle с той же областью.
3. `staff_bump_memberships` для затронутых сотрудников, чтобы сессии
   перечитали права.
4. Проверка в конце миграции: каждый активный сотрудник (не студент) либо
   system admin (получает права сам, 155), либо имеет `ai.agent.use` через
   назначение. Тех, у кого права нет, миграция перечисляет в NOTICE
   количеством; в production 06.10 таких 0. Новому сотруднику admin выдаёт
   роль «… — общие разделы» в «Ролях», как сейчас.

Старые фиксированные bundles 041 (`organization_memberships.current_bundle_id`)
сотрудникам прав больше не дают (155), их миграция не трогает. Студентам
права не даются. Сужение позже — обычная публикация роли в «Ролях», без
изменения схемы. Окно ИИ показывается только в диалогах, которые сотрудник
может читать (`communication.read.full`). Замечание ревью #1141 (черновики
ИИ видны всем, кому открыт диалог продаж) с решением Q9 согласуется: ответ
ИИ видит тот же круг, что и сам диалог.

| 075 и staff-assistant (`src/app/api/platform-ai/staff-assistant/route.ts`, `platform-staff-assistant-*`) | Код удаляется в P1 вместе с записью в route contract. Таблица аудита остаётся |
| 120 `reply_snippets` | Остаются как есть. Окно ИИ их не заменяет |
| 162 (бюджет распознавания документов) | Берём образец: резерв стоимости на день и бюджет на задачу |
| 045 pgmq | Берём расширение и образец обёрток claim/extend/finish |
| `public.ai_configs` (промпт на 30 KB от прежнего компаньона) | Не используем без отдельного решения владельца |
| 201–206 «База знаний» | Раздел остаётся. Агент только копирует выбранные страницы при начальном наполнении (§14) |

## 6. Поиск и ответ (контракт)

### 6.1. Что получает модель

В порядке, при котором неизменная часть идёт первой (для неявного кэша
Gemini префикс должен быть от 4 096 токенов):

1. Системная инструкция: постоянные правила ответа (в приватном репозитории)
   и текущая версия «Правил общения». Данных конкретного ответа здесь нет.
2. Последние 20 сообщений диалога дословно как ходы чата: клиент — `user`,
   сотрудник — `model`. Медиа даётся пометкой «[клиент прислал фото]» с
   подписью, если она есть.
3. Последний ход:
   - память о клиенте (P3: интерес и сводка) и минимальная карточка лида:
     имя, интерес к стране или программе, этап. Телефон, email и документы
     не передаются;
   - до 3 подтверждённых примеров (косинус ≥ 0,80, текущая
     `knowledge_version`);
   - `<sources>` — клиентские фрагменты `[1..K]`;
   - отдельный блок «ВНУТРЕННИЕ ПРАВИЛА (не раскрывать клиенту)» с
     внутренними фрагментами `[K+1..N]`;
   - строка про язык клиента;
   - инструкция «ответ или продолжение».

Сообщения и документы — данные, а не команды. Инструментов у модели нет.

### 6.2. Гибридный поиск

`platform_ai_agent.search_v1` делает один вызов и один круг к БД. Параметры
`SET hnsw.iterative_scan = relaxed_order` и `hnsw.ef_search = 100` заданы на
самой функции.

1. Ветка смысла: top-50 по косинусу `halfvec` для каждого вектора запроса.
2. Ветка точных слов: `russian` FTS, сначала И самых информативных терминов,
   ИЛИ только если И нашло мало; top-50 по `ts_rank_cd`, с ограничением на
   число строк.
3. Слияние RRF (k = 60) по каждому запросу, без дублей. Ищутся только
   документы со статусом `ready` или `review`, не заменённые.
4. Отбирается 5–8 лучших фрагментов с разнообразием по документам. Отдельная
   внутренняя ветка даёт до 3 фрагментов `internal` по основному запросу,
   чтобы правило со скидками доходило до сотрудника, даже если клиентские
   строки прайса заполнили выдачу.
5. Вместе с фрагментами возвращаются открытые пункты «Листа сверки» на тех же
   страницах, для пометки «Число в источнике ещё не проверено».

Запрос строится так:

- одиночный первый вопрос на русском ищется как написан;
- продолжение разговора, кыргызский или английский переписываются быстрой
  моделью в один самостоятельный русский запрос и до 3 подзапросов, потому
  что индекс нормализован на русский;
- эмбеддинг сырого текста запускается сразу, параллельно с переписыванием.

Reranker в интерактивном пути не вызывается никогда; в фоне — только если
включён (P4).

### 6.3. Генерация и формат

- Модель ответа: явный ID из `ai_settings`, по умолчанию `gemini-3.8-flash`
  (на нём меряли SoodaCloser). Перед P1 ID сверяется со страницей моделей.
  Быстрая модель по умолчанию `gemini-3.5-flash-lite`: у `3.1-flash-lite`
  объявлено отключение 07.05.2027. Thinking — минимальный разрешённый
  уровень.
- Ответ модели: `<reply>…[n]…</reply><reason>…</reason><question>…</question>`.
  Потоковый разбор отдаёт только `<reply>` без маркеров `[n]` и переносит
  теги, разорванные между кусками.
- События SSE: `status {stage: searching|writing}`, `sources {count}`,
  `delta {text}`, `final {answer}`, `error {code, message_ru, status}`,
  `: ping` каждые 10 с.
- `final.answer`: `answer_id`, `source_message_id`, `intent`, `language`,
  `reply`, `reason` («Почему такой ответ»), `question` («Спросите клиента»),
  `citations` (`n` и `chunk_id`), `sources` (`n`, документ, название,
  аудитория, страница или лист, `section_path`, `quote` из сохранённого
  фрагмента, `unverified_values`), `warnings`, `guard`, `model`,
  `created_at`, `current`.

### 6.4. Проверка источников

- Модель видит только номера 1..N, ID фрагментов ей не показываются. Номер
  вне 1..N делает ответ недействительным («ИИ указал неподтверждённый
  источник»).
- Цитаты в карточке — оригинальный текст из `ai_chunks`. Модель цитату не
  повторяет.
- Нет источников вообще: жёлтая плашка «Проверьте факты — источники не
  найдены». Клиентские источники есть, но ответ на них не ссылается:
  «Проверьте факты — ответ не ссылается на источники».
- Число из фрагмента с открытым пунктом «Листа сверки» помечается «Число в
  источнике ещё не проверено».
- Проверка покрытия после генерации (`assistant/coverage.py` SoodaCloser):
  предложение с фактом без источника убирается или превращается в вопрос.

### 6.5. Защита внутренних документов

Внутренние документы (лимиты скидок, маржа, правила согласования) влияют на
черновик и объясняются сотруднику в «Почему такой ответ», но клиенту не
цитируются никогда:

1. Маркер `[n]` в `<reply>` может указывать только на клиентский фрагмент.
   Маркер на внутренний выбрасывается и пишется в журнал.
2. Проверка утечки по `<reply>` и `<question>`: число, процент или сумма,
   которые есть во внутреннем фрагменте или в тексте «Правил общения», но
   нет ни в одном клиентском фрагменте, ни в диалоге, ни в памяти,
   считаются утечкой. Правила проверяются, потому что их начальная версия
   собрана и из внутренней страницы «Продажи и ответы» (§14). Процент должен
   подтверждаться именно процентом. Такой ответ один раз перегенерируется,
   затем заменяется безопасным ответом.
3. ID внутренних фрагментов, повлиявших на ответ, сохраняются в
   `result.guard`.
4. Ночной режим вообще не берёт внутреннюю ветку (§11).

### 6.6. Язык

Ответ пишется на языке клиента: RU, KY или EN. Язык определяется по последнему
сообщению клиента, где язык виден, а не по сообщениям сотрудника.

- Кыргызский узнаётся по буквам ң, ө, ү и частым словам.
- Для английского нужно не меньше двух служебных слов. Одиночные «Thanks»
  или «OK» язык не переключают.

Цитаты источников показываются на языке оригинала.

### 6.7. Актуальность: обновление, устаревание, повторное открытие

- Ответ актуален, если его `source_message_id` — последнее входящее
  сообщение диалога, а `knowledge_fingerprint` совпадает с текущим.
  Продолжение (`followup`) актуально, только пока его
  `source_outbound_message_id` — ещё и последнее исходящее: после нового
  сообщения сотрудника (в том числе отправленного продолжения) оно
  устаревает, вставка получает 409, а запрос готовит новое. Отпечаток
  меняется при смене версии знаний, правил, модели, аудитории документа и
  при правке или удалении сообщения, если чат их отслеживает.
- Открытие окна: если последнее сообщение от клиента и актуального ответа
  нет, запрос идёт автоматически. Если сотрудник писал последним — «Ждём
  ответ клиента» и кнопка «Подготовить продолжение».
- Новое сообщение клиента при открытом окне запускает новый запрос. Запрос
  для старого сообщения отменяется: агент перед генерацией и во время неё
  сверяет последнее входящее и завершает поток событием `error` с кодом
  `superseded`, статус 409.
- Повторное открытие показывает сохранённый ответ из `ai_answers`, без нового
  вызова Gemini.
- «Вставить в ответ» вызывает `ai_agent_answer_insert_v1`. Сервер отказывает
  409, если ответ устарел; кнопка неактивна и показывает «Пришло новое
  сообщение — обновите ответ». Отправка остаётся отдельным действием
  сотрудника.
- Один генератор на ключ: запись `pending` с heartbeat каждые 8 с, после 30 с
  без heartbeat запись считается брошенной.

### 6.9. Цели скорости

Меряются от сервера CRM на hermes и через edge:

- `status` — ≤ 300 мс;
- первый текст: p50 ≤ 3,5 с, p95 ≤ 6 с. Спецификация говорит «~3 с»;
  SoodaCloser намерил 3,25 с с Mac и ослабил свою цель до 4–5 с, поэтому до
  замера на EVO это не подтверждено;
- повторное открытие сохранённого ответа — p95 ≤ 300 мс.

## 7. Загрузка знаний: «Информация для агента» и «Лист сверки»

- Принимаются PDF, DOCX, XLSX, CSV, TXT и MD, а также PNG и JPEG как
  одностраничные сканы. Ограничения: до 25 MB, 300 страниц, 2 000 000
  символов. Дубликат по SHA-256 отклоняется с названием уже загруженного
  документа.
- При загрузке сотрудник выбирает аудиторию: «Для клиентов» (по умолчанию)
  или «Внутреннее». Чтобы сделать документ клиентским, нужно подтверждение.
  Галочка «Это материал компании, не документ клиента» обязательна.
- Этапы worker: `extract → ocr → structure → chunk → enrich → embed → index`.
  - **extract** — в дочернем процессе с лимитами. DOCX сохраняет заголовки,
    списки и таблицы. XLSX даёт раздел на лист, строку заголовка и значения
    так, как они показаны в Excel. CSV — с определением кодировки (UTF-8,
    cp1251). У PDF текстовый слой берётся постранично; страница почти без
    текста считается сканом.
  - **ocr** — только для сканов, двумя независимыми чтениями. A: Tesseract
    `rus+kir+eng`, строки с bbox. B: Gemini vision. Строки выравниваются.
    Совпавшее принимается. Разногласия в токенах с цифрами, процентами и
    валютой идут к арбитру: вырезки строк, сильная модель (по умолчанию
    `gemini-3.1-pro-preview`, запасной — Flash). Цифра, которую никто
    уверенно не подтвердил, попадает в «Лист сверки». Молча цифра не
    меняется никогда.
  - **chunk** — по разделам, цель 350 токенов, максимум 600. Таблицы режутся
    группами строк (около 15) с повтором заголовка в каждом фрагменте. У
    каждого фрагмента есть документ, страница или лист и `section_path`.
  - **enrich** — быстрая модель: язык, контекстный заголовок и `index_text`
    (русский перевод) для нерусских фрагментов.
  - **embed** — `gemini-embedding-2`, 1536 измерений, тип `document`.
  - **index** — одна транзакция. Старая версия документа уходит из поиска
    только когда новая полностью готова. Если новая упала, остаётся старая.
- Защита от персональных документов: если enrich видит признаки документа
  клиента (MRZ паспорта, ПИН из 14 цифр, бланк аттестата), документ
  останавливается со статусом «Похоже на документ клиента — не загружается»
  до решения сотрудника. Это исполнение правила AGENTS «не извлекать
  содержимое документов заявителей в базу ИИ».
- «Лист сверки»: вырезка, три прочтения, предложенное значение и действия
  «Подтвердить», «Исправить», «Оставить как есть», «Открыть снова».
  Исправление правит `content_md` и переиндексирует только затронутые
  фрагменты. Пока пункт открыт, документ уже ищется, а ответы помечают это
  число.
- Ошибка — по-русски, с кнопкой «Повторить». Удаление во время обработки
  отменяет её.

## 8. Лаборатория и «Правила общения»

«Правила общения» — системный промпт, который уходит в каждом ответе: тон,
стиль продаж, что можно обещать, как говорить о цене, список вопросов для
квалификации (он же для ночного режима). Страница показывает текущий текст и
версии (кто и когда). Править можно прямо там или через Лабораторию. Версия
из начального наполнения помечена «нужна проверка», пока кто-то не нажмёт
«Проверено».

«Лаборатория» при каждом открытии начинается с пустой проверки:

1. Сотрудник задаёт вопрос как клиент и видит ответ, источники и «Почему такой
   ответ». Работает тот же конвейер, назначение в журнале — `laboratory`.
2. Сотрудник пишет, что не так.
3. ИИ предлагает **одно** изменение: правку документа (точно «было/стало» в
   `content_md`), новый фрагмент знаний, правку «Правил общения» или
   исправленный пример. К нему — эталонный ответ.
4. «Применить»: эмбеддинги готовятся вне транзакции, затем одна транзакция
   перепроверяет, что знания и предложение не изменились (иначе 409
   «Знания или предложение изменились»), и применяет правку и пример. «Не
   менять» ничего не трогает.

Правка документа меняет индексированный текст, а не оригинальный PDF или
DOCX; документ получает пометку «изменён в Лаборатории». Пример требует новой
проверки, когда меняется его документ, правила или модель. Новые вопросы
примерами сами не становятся.

## 9. Память о клиенте (P3)

- В каждом ответе — последние 20 сообщений дословно (уже в P1).
- Сводка обновляется в фоне, когда в диалоге больше 20 сообщений и не меньше
  6 новых за окном: быстрая модель получает прежнюю сводку и вышедшие из окна
  сообщения. `interest` (до 140 символов) обновляется не чаще раза в минуту.
- Карточка лида читается живьём из Платформы и не копируется.
- Медиа: в контекст идут подпись и пометка типа. Содержимое фото, документов
  и голосовых в Gemini не отправляется и в знания не попадает. Распознавание
  голосовых — отдельное решение, позже вместе с «Диктовкой».
- Удалённое клиентом сообщение, если чат такое отслеживает, в память и
  контекст не попадает.

## 10. Расходы

- Пишется каждый вызов Gemini: генерация, поток (включая прерванные), vision,
  эмбеддинги, проба доступности. Назначение и группа в интерфейсе:

  | Назначения | Группа в интерфейсе |
  |---|---|
  | `answer` | «Ответы клиентам» |
  | `rewrite`, `embed_query` | «Поиск» |
  | `precompute` | «Подготовка заранее» |
  | `memory`, `summary` | «Память о клиенте» |
  | `embed_document`, `enrich` | «Обработка документов» |
  | `ocr_page`, `ocr_arbiter` | «Распознавание сканов» |
  | `laboratory` | «Лаборатория» |
  | `autosend`, `autosend_summary` | «Автоответчик» |
  | `probe` | «Проверка доступности» |
  | `dictation` (позже) | «Диктовка» |

- Стоимость считается в момент записи по цене, действующей в этот день
  (`ai_prices`), и хранится в долларах. Модель без цены на сегодня нельзя
  выбрать в настройках; пока такая модель стоит в настройках, резерв не
  выдаётся (PT402 `ai_model_unpriced`); вызов модели без цены записывается по
  сумме своего резерва, а не по 0, — иначе месячный лимит можно обойти. Эмбеддинги (Gemini не возвращает для
  них токены) и прерванные вызовы — оценки, они помечены «≈».
- «Расходы» показывают: сегодня, этот месяц, прогноз на месяц, по
  назначению, средняя цена ответа. Плюс строка о смене цен: «С 1 января 2027
  цены Gemini Flash удваиваются».
- Лимиты:
  - месячный лимит EVO (`monthly_cap_usd`) — дневной резерв, как в 162;
    при исчерпании ИИ-вызовы отклоняются с понятным сообщением;
  - месячный лимит проекта в Google AI Studio — вторая линия;
  - 20 ответов в минуту на сотрудника;
  - подготовка заранее выключена по умолчанию.
- Ориентир стоимости, расчёт по ценам от 01.10.2026, не замер: ответ на Flash
  при 6–10 тыс. входных токенов — около $0,007–0,013 сейчас и
  $0,014–0,026 с 2027 года; с кэшем префикса меньше. Цифра «$0,004 за ответ»
  из материалов SoodaCloser — оценка, её не перепроверяли по журналу.
  Реальная цена появится в «Расходах» после P1.

## 11. Автоответчик (P4, ADR 0031)

Владелец разрешил (Q5) и принял риски. Режим по умолчанию выключен.

**Что делает.** Во включённом интервале агент отвечает на входящие сообщения
клиентов в чате продаж:

- отвечает на вопросы только тем, что подтверждено материалами;
- продаёт и квалифицирует: страна, уровень обучения, сроки, бюджет, класс или
  возраст, город, удобное время звонка (список в «Правилах общения»);
- не принимает оплату: не даёт реквизитов, счетов и ссылок на оплату, не
  подтверждает оплату и не просит перевести деньги;
- в конце говорит фиксированную фразу. По-русски — по словам владельца:
  «Завтра в рабочее время вам позвонит наш руководитель.» Это верно, только
  если завтра рабочий день. Перед выходными и праздниками фраза называет
  ближайший рабочий день: «В понедельник в рабочее время вам позвонит наш
  руководитель.» День берётся из `working_days` и дат «включён весь день»
  (§18, вопрос 6). Задача «Позвонить клиенту» ставится на тот же день. KY и
  EN версии готовятся в P4 и подтверждаются владельцем. После этой фразы
  автоответчик в этом диалоге молчит до конца интервала (`handed_off`).
- Финальная фраза уходит сразу, без генерации, когда квалификация
  закончена, клиент хочет оплатить или оформить договор, или вопрос не
  покрыт материалами.

**Настройки** («ИИ-агент → Автоответчик»):

- главный выключатель;
- расписание по дням недели «с–до», допускается переход через полночь, по
  умолчанию 20:00–09:00;
- интервалы дат «включён весь день» или «выключен», например праздники;
- рабочие дни (по умолчанию пн–пт) для финальной фразы и задач;
- часовой пояс Asia/Bishkek, показан и не меняется;
- задержка 30–90 с;
- до 4 ответов в чате за час, до 8 за ночь, до 30 в час на номер;
- финальные фразы (оба варианта, §18, вопрос 6) на RU, KY и EN;
- ответственный сотрудник — тот, кто включил расписание (§18, вопрос 9);
- «Проверка без отправки» (shadow): решение и текст пишутся в журнал, но не
  уходят. Включена при первом включении;
- журнал решений;
- утренняя сводка.

**Ограничения, которые нельзя выключить:**

1. Только ответ на входящее сообщение клиента в существующем диалоге один на
   один в очереди продаж. Агент никогда не пишет первым, не пишет в группы и
   не делает рассылок.
2. Только на самое новое входящее сообщение, пришедшее не раньше 5 минут
   назад и внутри интервала. Проверяется при поступлении, до и после
   генерации и в момент отправки.
3. Пропуск, если: сотрудник написал после сообщения клиента; сотрудник был
   активен в чате последние 15 минут; чат исключён сотрудником; в сообщении
   только медиа; достигнут лимит.
4. Источники — только документы `audience = client` с
   `autosend_allowed = true`; это разрешение каждый документ получает
   отдельным действием сотрудника. Внутренняя ветка поиска не используется.
5. Каждое предложение с фактом цитирует источник. Каждое число, цена и дата
   дословно есть в цитируемом фрагменте. Без цитаты допустимы только
   приветствие, благодарность, вопрос квалификации, финальная фраза и
   строка-раскрытие из §18 Q11 (если владелец её включит).
6. Пропуск, если в источнике есть непроверенное число из «Листа сверки».
7. Стоп-слова обещаний и оплаты: «гарантируем», «скидка», «бесплатно»,
   «оплатите», «реквизиты», «счёт», «карта», «перевод» и подобные. Их
   появление означает пропуск или финальную фразу.
8. Один автоответ на одно сообщение клиента: уникальность
   `client_message_id`.
9. Отправка идёт через канонический путь исходящих (049/050/077/080/097/101),
   но со своей точкой входа. Ручная отправка
   `platform.request_manual_whatsapp_send_with_authorization` (050) требует
   `require_communication_actor`, то есть вошедшего сотрудника
   (`auth.uid()`). У внутреннего маршрута сессии нет, поэтому эта функция
   ночью не подходит. Порядок такой:
   - агент вызывает `platform_ai_agent.autosend_commit_v1(decision_id, text,
     cited_chunk_ids)`. БД проверяет правила (таблица ниже) и сохраняет текст,
     его SHA-256 и ссылки на фрагменты в `ai_autosend_log` со статусом
     `scheduled` и временем `send_at`;
   - в `send_at` агент вызывает внутренний маршрут CRM
     `/api/internal/ai-agent/send` с HMAC и только `decision_id`. Текст в
     запросе не принимается;
   - CRM проверяет env-выключатель и вызывает
     `platform.ai_autosend_authorize_v1(organization_id, decision_id,
     request_id)`. Её вызывает только CRM: `EXECUTE` есть только у
     `service_role`, а этого ключа у агента нет. Функция ещё раз проверяет
     правила, берёт сохранённый текст и создаёт авторизацию вида
     `ai_autosend` со ссылкой на решение. Автор авторизации — ответственный
     сотрудник из настроек (включивший расписание). Функция проверяет, что
     он активен и что `staff_access_evaluate(…,
     'communication.manual.send')` для этого диалога проходит по его
     membership. Затем ставит работу `manual_whatsapp_send` в
     `platform_work_v1`;
   - дальше CRM выполняет claim, отправку в WAHA, finish и reconcile тем же
     кодом и теми же функциями, что и ручную отправку (077/097/101), поэтому
     идемпотентность и сверка общие.

   Точная форма авторизации (новый столбец со ссылкой на решение и проверка
   «ровно один источник») задаётся в миграции P4 после повторного чтения
   триггеров 044/049/050/077/097/101. Сообщение в чате подписано
   «Автоответчик». У агента нет ключа WAHA и ключа `service_role`. 067 не
   возрождается.
10. Перед отправкой — «прочитано» и «печатает», если путь отправки это
    поддерживает; иначе только задержка.
11. Автоматическая пауза: сессия WAHA не в WORKING, ошибки 463 или 475, три
    ошибки отправки подряд, ошибки Gemini. Снять паузу может только человек.
    Есть ещё глобальный выключатель `EVO_AI_AGENT_AUTOSEND=0` в env.
12. Журнал каждого рассмотренного сообщения: решение и причина по-русски.
    Аудит каждого изменения настроек.
13. В тексте нет ссылок (`http`, `www`, `wa.me` и подобных) и он не длиннее
    1 000 символов.

**Где проверяется каждое правило.** «commit» — `autosend_commit_v1` (роль
агента), «authorize» — `ai_autosend_authorize_v1` (сервер CRM), «агент» —
только код агента.

| Правило | commit | authorize | Только агент |
|---|---|---|---|
| 1. Ответ в диалоге один на один очереди продаж, не первым | да | да | |
| 2. Самое новое входящее, внутри интервала; не старше 5 минут при commit и не старше 5 минут плюс выбранная задержка при authorize | да | да | |
| 3. Сотрудник не писал после клиента и не был активен 15 минут; чат не исключён; не только медиа; лимиты 4/8/30 | да | да | |
| 4. Цитируемые фрагменты — `audience = client`, `autosend_allowed`, документ `ready` и не заменён (повторно при authorize: документ мог быть заменён или лишиться разрешения между commit и отправкой) | да | да | |
| 5. Каждое число, процент, сумма и дата текста дословно есть в цитируемых фрагментах | да | | |
| 5. Каждое предложение с фактом подтверждено источником (смысл) | | | да |
| 6. На страницах цитируемых фрагментов нет открытых пунктов «Листа сверки» | да | да | |
| 7. Стоп-слова обещаний и оплаты; правило 13 (ссылки, длина) | да | да | |
| 8. Один автоответ на сообщение (`client_message_id` уникален) | да | да | |
| 9. Только сохранённый текст; вызывает только `service_role` | | да | |
| 11. Включён, не shadow, не на паузе; env-выключатель | да | да (env — CRM) | |
| Ответственный сотрудник активен и может отправлять в этот диалог | | да | |

**Граница при взломе агента.** `autosend_commit_v1` принимает текст,
который дал агент. Если сервис агента взломан, он может отправить любой
текст, который проходит проверки БД: без ссылок и стоп-слов, с числами только
из клиентских фрагментов, разрешённых для автоответчика, и только в ответ на
свежее входящее сообщение в чате продаж при включённом живом режиме.
Смысловую проверку источников делает только агент. Ущерб ограничивают лимиты
(4 ответа в чате в час, 8 за ночь, 30 в час на номер), shadow перед живым
режимом, автопауза и выключатели. Это остаточный риск ADR 0031.

**Утренняя сводка** в конце интервала: список ночных диалогов, что спросил
клиент, что ответил агент, собранные ответы квалификации, пропуски с
причинами. Каждому диалогу, где сказана финальная фраза, по умолчанию
создаётся задача «Позвонить клиенту» ответственному сотруднику на 10:00
ближайшего рабочего дня — того же, что назван во фразе (§18, вопрос 7).

**Риск** (ADR 0031): условия WhatsApp относят автосообщения к запрещённым,
WAHA — неофициальный клиент, на кону единственный номер продаж. Поэтому:
shadow не меньше трёх ночей, затем тест на телефоне владельца, затем живой
режим с лимитами.

## 12. Интерфейс

Делается со скилом impeccable (правило владельца), в дизайн-системе v3. Тексты
по-русски, без объяснительных абзацев.

### 12.1. Окно ИИ в чате продаж

- Плавает справа внизу поверх полного чата (Q7). По умолчанию свёрнуто в
  капсулу «Помочь с ответом» (доступное имя «Помочь с ответом — открыть
  помощника»). Точка на капсуле показывает состояние: ждёт, работает, готово,
  требует внимания, ошибка.
- Перетаскивается мышью и стрелками клавиатуры. Позиция запоминается в
  браузере (`localStorage`, с try/catch). Esc сворачивает окно.
- Раскрытое окно около 360×520. На телефоне — нижний лист.
- Содержимое:
  - строка статуса: «Ищу в материалах…» → «Пишу ответ…» → «Ответ готов · 3
    источника»;
  - текст ответа появляется потоком;
  - чипы источников [1] [2]: по нажатию — название, страница или лист,
    оригинальная цитата, «Открыть страницу»;
  - раскрывашка «Почему такой ответ»;
  - блок «Спросите клиента» с кнопкой «Вставить вопрос»;
  - жёлтые плашки «Проверьте факты…»;
  - «Вставить в ответ» (неактивна, если ответ устарел) и «Обновить ответ»;
  - в P4 переключатель «Автоответчик в этом чате».
- Вставка добавляет текст в поле ответа полного чата, не стирая уже
  написанное, ставит туда фокус и ничего не отправляет.
- Скрытое окно ничего не запрашивает, только помечает ответ устаревшим.
  Окно ни разу не открыто — Gemini не вызывается.

## 13. Доступ

Все сотрудники (Q9) получают `ai.agent.use` и `ai.agent.manage` через новые
версии ролей «… — общие разделы» (§5.5). Студенты — никогда. Роль
предпросмотра admin видит то же, что показываемая роль.

Два действия остаются только за admin (system admin, как в
`kb_require_admin`):

- **Копирование из «Базы знаний».** «База знаний» только для admin
  (решение E, 244). `platform.ai_agent_seed_from_kb_v1` вызывает
  `kb_require_admin` и копирует только страницы из закрытого списка (§14).
  У роли агента нет ни одной функции, которая читает «Базу знаний».
  Остальные сотрудники видят у скопированного документа источник («База
  знаний, узел, версия»), но не кнопки копирования.
- **Согласие на Gemini** (`ai_agent_consent_record_v1`). Это согласие
  владельца на передачу текстов клиентов в Google (Q4). Решение Q9 «все
  могут» относится к работе с агентом, а не к этому юридическому шагу.
  Отзыв согласия — тоже только admin.

## 14. Папка «ИИ-ассистент» и начальное наполнение (Q2 «a», Q3)

1. **Копирование до удаления (P1).** Копирует RPC для сотрудников
   `platform.ai_agent_seed_from_kb_v1(organization_id, node_ids,
   request_id)`, не агент. Она вызывает `kb_require_admin`, поэтому работает
   только у admin (§13). Текущие версии страниц копируются в `ai_documents`
   (`kind = knowledge`, `source = seed_kb`, `source_ref` = узел и версия),
   затем в очередь ставится указатель `seed`. Worker агента режет и
   индексирует уже скопированный `content_md` и «Базу знаний» не читает.
   - **Закрытый список.** Функция принимает только узлы, которые
     одновременно: в области `internal`; `kind = page`; не удалены и не в
     архиве; лежат в «ИИ-ассистенте», «Компании» или «Странах и
     поступлении»; имеют пометку импорта
     `historically_approved_general_client_knowledge` или
     `historically_approved_internal_knowledge`. Всё остальное — отказ,
     в том числе рабочие материалы, кандидаты и закрытые производные.
   - **Аудитория — из пометки, а не из выбора.** Страница «утверждено для
     клиентов» получает «Для клиентов», остальные — «Внутреннее». Перевод
     документа в «Для клиентов» — отдельное действие с подтверждением (§7),
     для цен, гарантий и юридических формулировок — по правилу AGENTS с
     подтверждением владельца или директора (§18, вопрос 2).
   - Страницы «Правила ответов» и «Продажи и ответы» →
     `ai_rules_versions` v1 («нужна проверка»). Страница «Продажи и ответы»
     имеет пометку «для внутреннего ИИ», поэтому текст правил входит в
     проверку утечки (§6.5).
   - Страницы «Вопросы и ответы» → клиентский документ «FAQ (из базы знаний
     19.09)» и кандидаты в примеры. Примерами они становятся только после
     подтверждения в Лаборатории.
   - README «Правила базы» не используется: это описание самой базы.
   - Корпус по умолчанию — §18, вопрос 2.
   - Никогда не копируются: области `raw`, `secrets` и `clients` (досье),
     «Панель управления», «Служебные файлы локальной базы» и любые файлы
     KB (`kind = file`).
2. **Удаление папки.** После проверки копий admin кладёт папку «ИИ-ассистент»
   в корзину в «Базе знаний» обычной командой `trash` (`kb_command_v1`).
   Узлы и версии можно восстановить. Это запись в production, на неё нужно
   отдельное разрешение.
3. **Импорт больше её не создаёт.** Убрать «ИИ-ассистент» из
   `src/components/v3/knowledge/import-structure.ts`; в
   `scripts/knowledge-library/prepare_import.py` и `inventory.py` перестать
   направлять туда локальные папки. Тест на структуру импорта обновить.
4. Не путать с `LEAD_CHANNEL_AI_NOTE = "ИИ-ассистент"`
   (`src/lib/lead-channel-contract.ts`): это метка канала маркетинга, её не
   трогаем.
5. Копии в «Информации для агента» живут сами по себе: правки в KB автоматически
   не переносятся. У скопированного документа есть кнопка «Обновить из базы
   знаний». Её видит только admin; она вызывает ту же
   `ai_agent_seed_from_kb_v1` с узлом из `source_ref` и создаёт новую версию
   документа (старая ищется, пока новая не готова).

Координация: по AGENTS «Astra owns the knowledge scope». Этот план меняет в
KB только папку «ИИ-ассистент» и маршрутизацию импорта. Номера миграций и
выпуски согласуются с текущим координатором.

### P1 — окно ИИ, помощь с ответом, источники, правила, расходы (≈ 4–6 агентских недель плюс время владельца на эталоны)

Оценка пересчитана по review: первая оценка «2–3 недели» не учитывала
доработку release controller, новый приватный репозиторий с CI и GHCR и
эталоны eval, которые подтверждает владелец. Ориентиры по срезам:

1. Миграции: схема, роль, права (§5.5), очередь, цены, RPC, SQL-тесты в
   `scripts/test-postgres-authorization.sh` — ≈ 1 неделя.
2. Приватный репозиторий, CI, образ в GHCR, digest агента в release
   controller и compose, откат — ≈ 1 неделя.
3. Агент: каркас api и worker, хранение на RPC EVO, клиент Gemini, журнал
   расходов, лимиты, ошибки 402 и 429 — ≈ 1 неделя.
4. Поиск и ответ (§6) с потоком SSE — ≈ 0,5–1 неделя.
5. CRM: маршруты, окно ИИ, оболочка «ИИ-агента» с «Информацией для агента»
   (начальные документы, без загрузки), «Правилами общения» и «Расходами» —
   ≈ 1 неделя.
6. Начальное наполнение (§14), корзина «ИИ-ассистента», правка импорта,
   удаление кода staff-assistant и старого пути Gemini — ≈ 0,5 недели.
7. Набор вопросов v1 (§16), выпуск. Срок эталонов зависит от владельца или
   директора; пока эталон не подтверждён, вопрос идёт только в метрики
   поиска (§16), и это не держит выпуск.

Приёмка на production (реальные знания, реальные диалоги, телефон владельца
как клиент):

- **Качество.** Прогон eval v1 на production-знаниях: recall@5 ≥ 0,85,
  ≥ 95 % утверждений подтверждены цитатами, 0 выдуманных чисел, 0 утечек
  внутренних данных, язык ответа совпадает в 100 % случаев, на вопросы без
  ответа в материалах ≥ 90 % ответов уточняют или честно говорят «уточню».
- **В чате.** Владелец пишет с второго телефона: ответ с проверенными
  источниками пришёл потоком. Второе сообщение клиента делает первый ответ
  устаревшим, и сервер отвечает 409 на вставку. Повторное открытие
  показывает сохранённый ответ без нового вызова (видно по журналу).
- **Скорость.** Замер по §6.9 через настоящий edge.
- **Расходы.** Каждый вызов есть в журнале. Суммы в «Расходах» совпадают с
  SUM по журналу. 21-й запрос за минуту отклонён. Месячный лимит проверен
  временно низким значением в настройках.
- **Безопасность.** Роль `evo_ai_agent` не читает ни одной таблицы напрямую
  (SQL-тест и проверка в production). Билет нельзя использовать дважды и
  после 60 с. В P1 фоновых функций с текстом диалогов нет (§5.3), поэтому
  роль агента без погашенного билета не получает ни одного диалога: SQL-тест
  вызывает каждую функцию роли без билета и ждёт отказа или пустого
  результата без текста. У роли агента нет функций, читающих «Базу знаний»;
  `ai_agent_seed_from_kb_v1` отказывает не-admin и узлам вне закрытого
  списка (§14). Права `ai.agent.*` есть у каждого активного сотрудника
  (§5.5, проверка в конце миграции).

### P2 — загрузка знаний, OCR, «Лист сверки», Лаборатория (≈ 2–3 недели)

Приёмка на реальных материалах компании (не документах клиентов):

- прайс XLSX: строки с заголовками находятся по точному названию программы;
- PDF-буклет;
- скан 3–5 страниц: время до `ready` записано, все неуверенные цифры в
  «Листе сверки». На 10 страницах сканов с эталонным текстом от владельца —
  0 молча изменённых цифр, точность цифр после арбитра ≥ 99 %;
- замена версии: старая версия ищется, пока новая не готова;
- 5 настоящих исправлений через Лабораторию видны в следующих ответах;
  примеры находятся;
- повторный прогон eval: recall@5 ≥ 0,90.

### P3 — память о клиенте, медиа в контексте (≈ 1 неделя); диктовка отложена

- Сводки на реальных диалогах длиннее 20 сообщений: 10 сводок владелец
  оценил как верные.
- Вопросы-продолжения в eval: recall@5 не хуже, чем без памяти.
- Сообщения с медиа дают пометку в контексте, содержимое никуда не уходит.
- При `memory_enabled = false` функции памяти отказывают; при включённой
  отдают только диалоги очереди продаж (SQL-тест).
- «Диктовка» (Q6): когда владелец вернётся к ней, браузерный микрофон →
  CRM → агент → быстрая модель Gemini (RU, KY, EN, до 3 минут). Текст
  вставляется у курсора и никогда не отправляется сам. У моделей Handy нет
  кыргызского; форк Handy — отдельный настольный проект.

### P4 — ночной автоответчик (≈ 2–3 недели плюс не меньше трёх ночей shadow)

- ADR 0031 слит. Функция включается только по отдельному разрешению
  владельца на каждый шаг ниже.
- SQL-тесты на каждое правило таблицы «Где проверяется» (§11) для
  `autosend_commit_v1` и `ai_autosend_authorize_v1`: агент не может вызвать
  `ai_autosend_authorize_v1`; текст в маршруте отправки не принимается;
  фоновые функции автоответчика отказывают вне интервала, при выключенном
  режиме и вне очереди продаж; финальная фраза перед выходными называет
  ближайший рабочий день.
- Shadow не меньше трёх ночей на реальном трафике. Владелец смотрит журнал: 0
  решений «отправить», которые нарушили бы §11.
- Живой тест на телефоне владельца: квалификация, финальная фраза, пауза
  после неё, отказ на вопрос об оплате, выключатель срабатывает сразу.
- Живой режим с лимитами. Утренняя сводка и задачи пришли. Ошибок 463 и 475
  нет.
- Если владелец решит включить reranker — eval с ним и без него, плюс замер
  памяти hermes.

## 16. Набор вопросов для оценки (eval)

- **Источник.** Реальные вопросы клиентов из выгрузки последних 50 чатов

  «Проверочные вопросы ИИ-агента»). В публичном Git — только сводные

## 18. Вопросы владельцу

Работа идёт с решением по умолчанию; ответ владельца его заменяет.

1. **Месячный лимит на ИИ.** По умолчанию: лимит EVO $100 в месяц, лимит
   проекта в Google $150, уровень Tier 1.
2. **Что взять из «Базы знаний» при наполнении.** По умолчанию копируются
   только страницы из закрытого списка (§14):
   - «Для клиентов» — 9 страниц с пометкой импорта «утверждено для
     клиентов»: 3 страницы «Вопросы и ответы», 2 в «Компания → Услуги и
     условия EVO», 4 в «Странах и поступлении». Ещё 2 такие страницы
     («Правила ответов», README «Правила базы») идут в правила или не
     используются. 7 узлов с той же пометкой — служебные файлы, они не
     копируются;
   - «Внутреннее» — 223 страницы «Стран и поступления» и 10 страниц
     «Компании» с пометкой «утверждено для внутреннего ИИ». Они помогают
     черновику и объясняются сотруднику, но клиенту не цитируются (§6.5);
   - не копируются 120 рабочих материалов «Стран и поступления» и 2
     рабочие страницы «Компании».

   Вопрос владельцу или директору: какие страницы «Стран и поступления»
   перевести в «Для клиентов». По правилу AGENTS клиентский ИИ берёт только
   утверждённую клиентскую базу, а цены, гарантии и юридические формулировки
   требуют подтверждения владельца или директора. Поэтому массового
   перевода по умолчанию нет. Внутренние правила (скидки, маржа) сотрудники
   загружают сами позже. Ни один документ не разрешён для автоответчика.
3. **Модели.** По умолчанию: ответ `gemini-3.8-flash`, быстрые задачи
   `gemini-3.5-flash-lite`, арбитр `gemini-3.1-pro-preview` с запасным Flash.
4. **Reranker.** По умолчанию выключен; решение в P4 по eval и памяти hermes.
5. **Ночное расписание.** По умолчанию ежедневно 20:00–09:00 по Бишкеку.
   Автоответчик выключен до приёмки P4.
6. **Финальная фраза.** По умолчанию: «Завтра в рабочее время вам позвонит
   наш руководитель.», если завтра рабочий день; иначе — с днём недели
   ближайшего рабочего дня («В понедельник в рабочее время…»). Рабочие дни
   по умолчанию пн–пт, праздники — даты «включён весь день». KY и EN —
   черновой перевод обоих вариантов с пометкой «проверить»; в живой режим
   не идут без подтверждения владельца.
7. **Утренняя сводка.** По умолчанию: страница «Автоответчик» и задача
   «Позвонить клиенту» ответственному сотруднику на 10:00 того рабочего дня,
   который назван во фразе.
8. **Согласие клиентов.** По умолчанию: строка в политике конфиденциальности
   и записанное решение владельца, без отдельного сообщения клиенту в
   WhatsApp. Юристу показать до P4.
9. **Кто отвечает за автосообщение.** По умолчанию: сотрудник, включивший
   расписание; в чате подпись «Автоответчик».
10. **Фото документов (PNG, JPEG) в знаниях.** По умолчанию: принимаются как
    сканы компании.
11. **Говорить ли клиенту, что ночью отвечает автомат.** По умолчанию: да.
    Первый ночной автоответ в диалоге начинается одной строкой «Пишет
    автоматический помощник EVO — менеджеры сейчас не на связи.» (RU, KY,
    EN подтверждает владелец). Так клиент не примет ответ агента за
    обещание сотрудника. Убрать строку проще, чем добавить её потом.
12. **Кто записывает согласие на Gemini.** По умолчанию: только admin (§13),
    отзыв — тоже. Если владелец хочет отдать это всем сотрудникам по Q9,
    это правка одной проверки.
