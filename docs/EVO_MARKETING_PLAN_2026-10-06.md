## 0. Чего этот план не разрешает

План не разрешает ни одного действия на production. Каждый ledger-apply
миграции, правка env на VPS, установка systemd-юнитов на hermes-vps,
правка edge Caddy, выкат сайта, тестовая заявка в production и подключение
коннекторов с правом записи — отдельное разрешение владельца на конкретное
действие. Чтение production (шаг 0 в §9) — только агрегаты, без строк с
персональными данными.

## 1. Зачем

Главный вопрос руководства: **какой канал приводит людей, которые подписывают
договор и платят, и сколько стоит один такой клиент**. Охваты и подписчики
видны и в самом Instagram; ценность раздела — связка «маркетинг → заявка →
договор → оплата» внутри Платформы.

## 2. Исходное состояние (06.10)

Сайт `evoadmissions.com`:

- аналитики нет (ни GA4, ни Метрики, ни пикселя); cookie и localStorage сайт
  не использует; Google Fonts грузятся без согласия;
- `/robots.txt`, `/sitemap.xml`, `/privacy/` отвечают 404; Open Graph и
  JSON-LD нет ни на одной странице; подтверждений Search Console, Bing и
  Яндекса нет; `www` отвечает 200 без редиректа на основной домен;
- форма есть только на `/` и `/ru/`; 192 страницы университетов ведут на
  неё полной навигацией `/?university=…#apply`;
- форма отправляет только `requestId, name, phone, age, city, country,
  university, consent, website`; UTM, referrer и click-id не читаются;
  возраст принимается от 10 до 100.

Платформа:

- `platform.leads.source_key` — TEXT по регулярному выражению, неизменяемый
  после создания (guard в 084). Значения в коде: `website`, `whatsapp`,
  `office`, `phone_call`, `referral`, `other`, `platform_application` (180).
  Ручной список (143, `src/lib/v3/manual-lead-source.ts`): `office`,
  `phone_call`, `referral`, `website`, `other`; `instagram` и `whatsapp`
  исключены решением Э8.11 (28.09), потому что очереди «Заявки» (221/250)
  берут `source_key IN ('website','whatsapp')`;
- приёмник сайта (`src/lib/server/website-lead-intake.ts`, RPC
  `receive_website_lead`, 231/240) отвечает общим `400 invalid_request` на
  любой неизвестный ключ; лимит тела 8192 байт в приложении и `max_size 8KB`
  на edge; у RPC одна сигнатура (231: DROP + CREATE + повторный ACL);
  повторная заявка с телефоном открытого лида не создаёт новый лид, а
  привязывает квитанцию к существующему (240);
- события WhatsApp в Платформу пока не приходят (переключение WAHA
  отложено владельцем; прямой приём — #1137/#1139/#1141, слиты в main, они
  заняли миграции 259–261). Значит лиды из Instagram Direct и WhatsApp попадают
  в Платформу **только ручным добавлением** сотрудником;
- таблиц рекламных расходов нет; планировщика в БД нет (есть systemd-таймер
  базы знаний `deploy/knowledge/evo-knowledge-maintenance.*`, юниты ставятся
  на хост отдельно от образа); графики — собственные SVG
  (`TrendChart`, `Funnel`, `MetricCard`).

Instagram `@evo_admissions`: 14K подписчиков, 412 публикаций. Ссылка в
профиле → `evoadmissions.taplink.ws` → WhatsApp `api.whatsapp.com/send?
phone=996990407030&text=` с пустым текстом. Тип аккаунта (бизнес/автор) без
входа не виден — UNVERIFIED; реклама Meta с него идёт, значит аккаунт почти
наверняка профессиональный (для API подходят оба профессиональных типа).
Реклама: Meta Ads в Instagram, по оценке владельца ~$40 в день; куда ведут
объявления (Direct, WhatsApp, профиль, сайт) — не известно, вопрос в §10.

## 3. Модель источника: два измерения

### 3.1. Канал связи — `leads.source_key`

Как контакт до нас дошёл; неизменяем, как сейчас.

| Ключ | Подпись | Как появляется |
|---|---|---|
| `website` | Сайт | форма сайта или вручную |
| `whatsapp` | WhatsApp | автоприём (когда будет подключён) |
| `whatsapp_manual` | WhatsApp (вручную) | **новый**, ручной ввод; в «Заявки» не попадает |
| `instagram` | Instagram Direct | **новый**, ручной ввод; в «Заявки» не попадает |
| `office` | Офис | вручную |
| `phone_call` | Звонок | вручную |
| `referral` | Рекомендация | вручную |
| `platform_application` | Анкета на платформе | анкета кабинета |
| `other` | Прочее | вручную |

В разделе `whatsapp` и `whatsapp_manual` показываются одной строкой
«WhatsApp». Фильтры 221/250 не меняются, Э8.11 в части очереди «Заявки»
остаётся в силе. Подписи добавляются в `SOURCE` (`src/lib/v3/wording.ts`).

### 3.2. «Откуда узнал» — касания

Таблица `platform_private.lead_attribution_touches`: только добавление
(append-only и no-truncate триггеры), RLS без политик, `REVOKE ALL`; прямого
чтения нет ни у кого, только RPC.

| Поле | Значение |
|---|---|
| вид | `website_form` (с формы), `staff_manual` (сотрудник при создании), `staff_correction` (исправление в Lead 360), позже `whatsapp_first_message` |
| основание | `utm_tagged`, `referrer`, `message_code`, `staff_asserted` |
| выбор сотрудника | `instagram_ads`, `instagram`, `website_search`, `referral`, `other`, `unknown` |
| метки (только `website_form`) | `utm_source/medium/campaign/content/term/id`, `has_fbclid` (булево; сам `fbclid` не храним), `referrer_host`, `landing_path`, `seen_at` |

Подписи выбора: «Instagram — реклама», «Instagram — посты и профиль»,
«Сайт и поиск», «Рекомендация», «Другое», «Не известно».

**Правило канала** (одно SQL-представление; меняется без переписывания
данных):

1. Последнее `staff_correction` сильнее всего, в списке помечено
   «исправлено».
2. Иначе — **первое** касание по `seen_at`/времени записи.
3. Автоматическое касание: UTM → по таблице меток; без UTM — по хосту
   реферера: `instagram.com`, `l.instagram.com`, `taplink.ws` →
   «Instagram — посты и профиль»; `google.*`, `bing.com`, `yandex.*`,
   `duckduckgo.com` → «Сайт и поиск»; `chatgpt.com`, `perplexity.ai`,
   `gemini.google.com`, `copilot.microsoft.com`, `claude.ai` → «Сайт и
   поиск» с пометкой «ИИ-ассистент»; иначе и без реферера — «Не известно».
4. Повторная заявка сайта по существующему лиду добавляет касание (с признаком
   `is_repeat`), но канал не меняет — даже у лида, у которого до неё не было ни
   одного касания: он остаётся «Не известно», а повторная форма первой стать не
   может. Такие обращения видны отдельной строкой «повторные». Канал уточняется
   только словом сотрудника или исправлением.

В списке у канала всегда видно основание: «по метке», «по ссылке»,
«со слов клиента», «исправлено», «не известно». UTM — заявленное, не
доказанное значение, поэтому слово «доказано» не используется.

**Поле в ручной форме.** «Откуда узнал» обязательно, без значения по
умолчанию, «Не известно» — последним вариантом; при его выборе подсказка
«Спросите клиента». Значение пишет отдельный `platform.record_lead_touch`
сразу после создания лида; сигнатура и payload `create_manual_sales_lead`
не меняются (иначе повтор старой формы дал бы `manual_lead_request_conflict`,
а откат образа сломал бы форму). При ответе `duplicate` касание ставится на
существующий лид, если сервер его вернул; иначе сотрудник ставит его в
Lead 360. В Lead 360 — исправление (`staff_correction`), история
сохраняется.

**Права.** `record_lead_touch` — `staff_can_access(..., 'lead.sales.workflow
.manage', 'lead', id)`, то есть продажи на своих лидах и admin. Продажи
читают только проекцию (канал + основание) через RPC с проверкой доступа к
лиду; сырые метки, страницы входа и реферер видит только admin в
«Маркетинге».

**Ограничения, которые остаются.** Ручной лид требует телефон или email
(143): переписка в Direct без телефона в Платформу не попадает и до
получения номера видна только в агрегатах Instagram/Meta.

## 4. Раздел «Маркетинг»

Маршрут `/v3/marketing?view=…`, пункт «Маркетинг» в общей группе меню.
**Только admin:** каждый RPC проверяет положительно
`platform_role = 'admin'` реального JWT (как 071/084) или
`system_role = 'admin'` (как `kb_sealed_v1`, 202), а не разрешение вроде
`sales.register.read`; NULL-роль приглашённых сотрудников (244) отказывает.
Маршрут и серверные действия отказывают в режиме просмотра роли (как
`requireKnowledgeAdmin`). Новый ключ разрешения не вводится до возврата
роли маркетолога. Период — `resolvePeriod`/`PERIODS` из
`src/lib/v3/funnel-source.ts` (воронка «Сегодня»), время — Бишкек.

| Вкладка | Главный вопрос | Когда |
|---|---|---|
| Обзор | Сколько клиентов даёт каждый канал и во что это обходится? | М1 |
| Заявки | Кто пришёл, откуда и что с ним стало? | М1 |
| Instagram | Растёт ли аккаунт и какие публикации ведут к нам? | М2 |
| Реклама | Какие кампании дают переписки и заявки дешевле? | М2 |
| Подключения | Свежи ли данные, что не подключено, когда истекает токен? | М2 |
| Сайт и поиск | Находят ли нас и доходят ли до формы? | М3 |
| ИИ-видимость | Называют ли нас ChatGPT, Gemini, Perplexity, Алиса? | позже |

Вкладки без данных не рисуются.

**Обзор — два блока, они не смешиваются в одном отношении.**

1. «Заявки периода и что с ними стало на сегодня» (когорта по дате
   заявки): канал × заявки → квалифицированы → переданы → договор →
   оплатили; строка «Источник не известен — N из M»; строка «повторные».
2. «Продажи периода» (по дате договора `signing_date`): договоры и суммы по
   каналам; строка «без привязки к лиду»; строка сверки «по каналам + без
   привязки = Продажи отчёта», расхождение видно.

Расход и цены (ручной расход в М1, данные Meta с М2): цена заявки — по
когорте; цена договора и оплатившего — накопительно или по когортам старше
90 дней, не за короткий период. Строка сигналов наверху («расход есть,
заявок 3 дня нет», «источник не известен у >40% заявок», «токен Instagram
истекает через 7 дней») — только в интерфейсе, без рассылок.

**Заявки.** Список с именами: имя (ссылка в Lead 360), телефон, когда
пришёл, канал связи, откуда узнал + основание, кампания/метка, страница
входа, этап (для закрытых — «Отказ»/«В архиве»), договор (дата продажи),
оплата (сумма в своей валюте), ответственный. Фильтры: период, канал,
кампания, этап, «есть договор», «источник не известен» (это и очередь
дозаполнения: открыть лид → поставить «Откуда узнал»), «без
ответственного». Страница ≤ 50, курсор только `(created_at, id)`; имена и
телефоны не попадают в URL. В строке нет текстов переписок, заметок,
документов, данных дела и куратора. Экспорта нет.

**Ручной расход (М1).** Admin вводит расход за месяц или период: сумма,
валюта, кампания (необязательно), пометка «введено вручную». С М2 за дни,
где есть данные Meta, ручные записи не используются и помечаются
«заменено данными Meta».

**Instagram (М2).** Подписчики (ежедневный снимок), подписки/отписки,
просмотры, вовлечённые аккаунты, взаимодействия, сохранения, репосты,
переходы по ссылке профиля (`profile_links_taps` — вход в воронку Taplink →
WhatsApp), лучшие публикации и Reels (просмотры, охват, сохранения, среднее
время просмотра Reels). Охват за период не складывается из дней: берётся
отдельным запросом за период или не показывается.

**Реклама (М2).** Кампании/группы/объявления: расход, показы, клики по
ссылке, начатые переписки (по данным Meta), заявки CRM с меткой кампании;
цена переписки, цена заявки, цена договора. «Лиды» Meta без пикселя — «н/д»,
не 0. Часовой пояс рекламного аккаунта указан в подписи.

**Подключения (М2).** По каждому провайдеру: не подключено / работает /
устарело / ошибка / токен истекает; последняя загрузка; «данные по»; тип
токена («бессрочный» для системного пользователя Meta); с С4 — «с метками
N из M заявок сайта».

**Сайт и поиск (М3).** Сессии GA4 по источникам и страницам входа, лучшие
гайды, конверсия формы («не менее»: отказавшихся от cookie GA4 не видит),
заходы из ИИ-ассистентов; запросы Google (показы, клики, CTR, позиция) из
Search Console.

| Время до договора | Медиана дней от заявки до `signing_date` |

## 6. Правила честных чисел

- Знаменатель всегда виден: «7 из 23», не «30%». Единый порог: при N < 10
  — только количества, без долей и медиан.
- «Не известно» — отдельная строка, не ноль и не раздача по каналам.
- Цена заявки — три уровня, не одно число: «по метке», «со слов клиента»,
  «включая неизвестные»; рядом «по данным Meta: N переписок». Знаменатель 0
  → «—».
- «Не подключено», «не загружено», «ошибка», «н/д» — разные слова, никогда
  «0».
- Неполные последние дни (лаг GA4/Search Console) выделены и в итог не
  входят. Охват и пользователи по дням не складываются. Часовой пояс
  провайдера, если он не Бишкек, указан в подписи.
- Когорта по дате заявки и продажи по дате договора — разные блоки.
- «Привела реклама» — только при метке; иначе «со слов клиента» или «не
  известно».
- GA4 — выборка (после отказа от cookie); источник истины по заявкам —
  Платформа.

## 8. Сайт (репозиторий `evoadmissions-website`, отдельные PR)

Выкат — только `scripts/deploy.sh` по разрешению владельца на каждый выпуск.
Гайды и директории — через `head()`/`footer()` в
`generate-universities.mjs`; главная — рукописный `evo-admissions/index.html`
+ `scripts/locales/home.ru.json` (RU строится `generate-homepage.mjs`; любой
новый видимый текст требует перевода в `home.ru.json`); новый
`generate-site-files.mjs` — для sitemap и страниц политики. Генератор
главной запрещает непустые inline `<script>`/`<style>`: JSON-LD требует
отдельного правила (исключение для `application/ld+json` между маркерами
`<!--evo:seo:start/end-->`, запись в `docs/DECISIONS.md` сайта), gtag и
уведомление — внешними файлами `js/consent.js`, `js/analytics.js`.
Проверки: оба `--check` и `check-russian.py`.

- **С1 SEO (без юридической зависимости):** `robots.txt` (всё разрешено,
  строка `Sitemap:`, явные разрешения поисковым и ИИ-поисковым ботам);
  `sitemap.xml` (~198 URL, альтернативы en/ru/x-default, `lastmod` из
  `verifiedAt`); Open Graph/Twitter (гайды — существующие фото направлений,
  главная — одно новое изображение 1200×630 с проверенной лицензией);
  JSON-LD `ProfessionalService` (адрес, часы, телефон, `sameAs` Instagram)
  и `BreadcrumbList` на гайдах; мета-теги подтверждения из нового
  `scripts/site.config.json` (пустые не выводятся); `X-Robots-Tag: noindex`
  для `/globe-embed/*`. Без `llms.txt` как приоритета, без схем отзывов и
  рейтингов.
- **С2 правовое:** `/privacy/` и `/ru/privacy/`. Текст — черновик, в
  production не выходит до проверки юристом и данных владельца. Правовая
  база: Цифровой кодекс КР, заменивший закон 2008 года в феврале 2026;
  номера статей и точная дата взяты из вторичного источника (ICNL) и с
  текстом кодекса не сверены — в публичном тексте не цитируются до
  подтверждения юристом. Политика перечисляет все потоки: форма → Платформа
  (VPS, Supabase), WhatsApp/Instagram (Meta), AI-чат (вопросы уходят в Google
  Gemini), GA4 (после согласия), хранение выбора cookie в `localStorage`,
  метки источника заявки. Ссылка на политику — в согласии формы и во
  вступлении чата; текст согласия формы дополняется: «к заявке прикладывается
  источник перехода и страница входа». Шрифты Archivo и Montserrat
  локально вместо Google Fonts. Уведомление о cookies — тихая карточка,
  «Принять» и «Отказаться» равного веса, без блокировки страницы, выбор в
  `localStorage` (try/catch), повторный вопрос через 12 месяцев или при
  смене политики, ссылка «Настройки cookie» в подвале. Возраст: решение
  владельца с юристом (§10) — что форма показывает при возрасте < 14 и
  < 18.
- **С3 GA4 (после С2):** базовый режим согласия — `gtag.js` загружается
  только после «Принять»; отзыв согласия: `ga-disable-<ID>`, удаление
  `_ga*`, перезагрузка; срок cookie не больше срока хранения (14 месяцев);
  Google signals, персонализация рекламы, обмен данными с Google и
  «взаимодействия с формами» в расширенной статистике — выключены;
  `page_location` без параметров, кроме `utm_*`; события без персональных
  данных: `generate_lead` (направление, slug университета, язык),
  `click_whatsapp`, `click_telegram`, `click_phone`, `click_email`,
  `chat_open`. Без идентификатора `G-…` скрипт ничего не делает.
- **С4 метки формы (после М1 на production и С2):** необязательный ключ
  `attribution` = `{v, utm_source, utm_medium, utm_campaign, utm_content,
  utm_term, utm_id, has_fbclid, referrer_host, landing_path, seen_at}`.
  Валидация одинакова на сайте и сервере: значение отбрасывается при `@`,
  7+ цифрах подряд, длине > 100 или несоответствии
  `^[A-Za-z0-9_.:~-]+$` (кроме `utm_campaign/content/term`, где допустимы
  буквы и пробел, но те же запреты на `@` и цифры); `utm_id` — только цифры;
  `landing_path` ≤ 200 без `?` и `#`; `referrer_host` — только hostname ≤
  253; `seen_at` не в будущем и не старше 30 суток. Плохое значение
  отбрасывается, заявка принимается — 400 из-за меток не бывает. Метки
  живут в памяти страницы и переносятся в ссылки на форму с гайдов
  (`/?university=…&utm_…#apply`) без хранения; в `sessionStorage` — только
  после «Принять». Метки вне отпечатка повторной отправки. Если приёмник
  ответил `400`, а метки были, форма один раз повторяет отправку без них с
  тем же `requestId` — заявка не теряется при откате образа Платформы ниже
  М1. Одна константа выключает отправку меток. `INTAKE.md`/`DECISIONS.md`
  обновляются в том же PR.
- **Отдельное разрешение (edge Caddy Платформы на VPS):** редирект
  `www` → `evoadmissions.com`.

## 10. Что делает и решает владелец

Можно сразу, бесплатно:

- в Taplink — текст WhatsApp-ссылки с кодом: «Здравствуйте! Хочу узнать про
  обучение [IG-BIO]»; для других мест — свои коды (`TAP`, `WEB-BTN`,
  `AD-<кампания>`);
- в Meta Ads, поле «Параметры URL» объявлений, ведущих на сайт:
  `utm_source=instagram&utm_medium=paid_social&utm_campaign={{campaign.name}}&utm_term={{adset.name}}&utm_content={{ad.name}}&utm_id={{campaign.id}}`
  (макросы подтверждены вторичными источниками);
- посмотреть тип аккаунта: Instagram → Настройки → «Тип аккаунта и
  инструменты».

Вопросы:

- куда ведут объявления: Direct, WhatsApp, профиль или сайт;
- возраст в форме: что показывать при < 14 и < 18 (заявку подаёт родитель
  или законный представитель?) — с юристом;
- сроки хранения: лиды без договора, касания и метки, метрики — с юристом.

К С2/С3: юридическое название, ИНН, адрес; проверка текста юристом;
GA4-ресурс (часовой пояс Бишкек, хранение 14 месяцев, signals и обмен
данными выключены); Search Console (DNS TXT в Spaceship или мета-тег),
импорт в Bing, Яндекс Вебмастер.

К М2 (чем раньше, тем длиннее история Instagram): приложение Meta (тип
Business), токен Instagram Login для `@evo_admissions`; системный
пользователь с `ads_read` на рекламный аккаунт; валюта и часовой пояс
рекламного аккаунта. Токены вводятся на VPS, не в чат.

К М3: проект Google Cloud и сервисный аккаунт («Читатель» в GA4,
«Ограниченный» в Search Console); ключ вводится в Платформу на VPS и
удаляется с диска.

## 12. Проверки

Под каждый шаг — только изменённое поведение на реальном пути:

- SQL-тесты новых RPC: admin читает; продажи, куратор, студент и
  сотрудник с NULL-ролью получают 42501; режим просмотра роли отказывает;
  касания только добавляются; `record_lead_touch` — только на доступном лиде;
- приёмник: старый payload сайта принимается байт в байт; плохие метки
  отбрасываются без 400; худший по размеру payload проходит лимит edge;
  повтор с тем же `requestId` и другими метками — `accepted`;
- форма сайта: повтор без меток после 400; метки не попадают в отпечаток;
- typecheck/eslint изменённого; UI-путь раздела на изолированном локальном
  стеке с синтетическими данными;
- загрузчики — на реальных токенах владельца после их выдачи.

В production — ни одной тестовой заявки без разрешения владельца. Ничего не
помечается «готовым» по одному health check; отсутствие доступа
называется прямо.
