## Проблема и результат

Раздел9 исходного CRM/admissions-плана разделяет ошибку чтения, неизвестный
исход отправки и неизвестный исход удаления. Чтение уже исправлено #1005.
В `TeamChatMessageRow.tsx:94` удаление/модерация всё ещё выводят
`TEAM_CHAT_FAILURE_COPY` из `platform-team-chat.ts:47`: unavailable обещает
сохранённый черновик, хотя удаляется чужой/свой существующий текст. Composer
тоже использует общий неопределённый «результат», хотя операция известна.

После изменения сотрудник понимает, какое действие не подтверждено и как
повторить именно его. Удаление никогда не обещает сохранение черновика;
отсутствие ответа не представляется ни успехом, ни достоверной отменой.

## Минимальная реализация

- Оставить существующие server actions, SQL, requestId, expectedVersion,
  замороженный input/reason, retry target, onSaved/onFailure и поведение
  закрытия/возобновления неизменными. Никаких новых запросов/таймеров/кнопок.
- Добавить небольшой typed presenter по операции `post | edit | delete |
  moderate`, либо локальные таблицы если они проще. Не создавать общий
  framework ошибок. Read-error модуль уже имеет свой контракт и не меняется.
- Неизвестная отправка: «Не удалось подтвердить отправку. Повторите тот же
  запрос. Это не создаст дубликат сообщения.» Текст остаётся в существующем
  заблокированном поле; подсказка не обещает persistent storage. Неизвестная
  правка: «Не удалось подтвердить изменение. Повторите тот же запрос.»
- Неизвестное удаление/модерация: «Не удалось подтвердить удаление. Сервер
  мог уже удалить сообщение. Повторите тот же запрос, чтобы проверить
  результат.» Существующая кнопка «Повторить тот же запрос» сохраняется.
- Invalid/conflict/forbidden/not_found у удаления тоже должны соответствовать
  операции: не предлагать менять текст/упоминания или проверять «черновик».
  Не называть недоступное сообщение точно удалённым и не обходить права.
- Storage-error сообщение Composer остаётся единственным источником
  предупреждения о том, сохраняет ли браузер черновик. Saved не показывается
  как failed из-за запоздавшего фонового обновления.
- До реализации сверить точные тексты/операции с действующими error status и
  независимо проверить, что копия не обещает больше idempotency-контракта.

Разрешённые файлы: TeamChatComposer.tsx, TeamChatMessageRow.tsx, маленький
pure presenter в lib при необходимости, соответствующие docs. platform-team-chat
общую таблицу удалить только если все реальные callsites переведены; иначе
сохранить для остальных потребителей. Лента, rail, feed/seen, CSS, Auth,
repositories/commands и SQL остаются вне блока.

## Проверка

- Scoped lint/typecheck/diff и независимый exact-head review; побайтно
  сопоставить обработчики команд/формирование input/requestId с исходными.
  Не добавлять тесты, просто повторяющие новые строки. Если presenter получил
  реальное ветвление/инвариант, дать малые cases операции/status, не UI fixture.
- Существующие drafts/retry tests переиспользовать с точной ревизией, если
  код и входы неизменны; запускать заново только при затронутом контракте.
- После отдельного ROOT handoff один существующий актёр и ограниченная UI
  проверка. По реально имеющимся own/foreign сообщениям выбрать одну
  существующую delete/moderate форму. Вид/контекст/причина/фокус проверяются
  без подтверждения online. Отсутствующие варианты остаются gaps.
- Для нового error copy можно сделать строго один browser-offline negative
  submit уже открытой формы: сначала отсутствие pending network и настоящий
  offline, затем ordinary click и доказанный failed request. **Не отправлять
  повтор online**, не удалять реальные сообщения и не создавать fixture.
  После фиксации текста и сохранённого frozen payload unmount собственного
  UI, восстановить online и закрыть собственные ресурсы по reviewed packet.
  Если условия нельзя доказать, runtime error path остаётся gap, а не PASS.
- Отдельный отрицательный submit несохранённого Composer допустим только в
  явно утверждённом том же bounded packet; не расширять его на все команды.
  Positive send/delete/idempotent business acceptance не заявляется из copy QA.
- Финальные snapshots должны сохранить сообщения/версии/аудиты; допустимы
  только заранее связанный собственный seen и обычные собственные Auth effects.

Изменение принято, когда новое сообщение реально соответствует операции,
повтор сохраняет исходную попытку по source/сохранённому сетевому наблюдению,
изменённый UI проверен в доступном сценарии, CI и независимое review пройдены.
Это не закрывает весь пункт15 или issue708 real-staff acceptance.
