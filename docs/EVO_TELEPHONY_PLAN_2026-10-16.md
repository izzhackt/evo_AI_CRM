# EVO — телефония Beeline KG: план фазы 1 (16.10.2026)

Статус: план, запись до кода; версия после независимого review 16.10.2026
(две линзы: сверка с REST API ВАТС и вики вендора; сверка с репозиторием).
Это рабочий контракт для срезов T1–T12: что строим, где это живёт, по каким
правилам и как принимаем. Решения владельца, изменение объёма и итоги review —
в `docs/PLAN_CHANGES.md`, запись «2026-10-16 — Телефония Beeline KG: план фазы
1 (решения владельца)». Архитектурное решение —
[ADR 0033](adr/0033-integrate-beeline-kg-pbx-via-rest-api-without-recording-copies.md).
Этот план снимает отсрочку телефонии (DEC-019, DA-04) только для телефонии и
задаёт contract и acceptance, которых требует INT-018; пока приёмка (§15) не
пройдена, телефония нигде не показывается как рабочая.

Факты проверены 16.10.2026 только чтением:

- код `origin/main` `7f51a4c31` (миграции в main до 282 включительно);
- amoCRM — только GET-запросы к API v4, только агрегаты, без номеров, имён,
  текстов и ссылок на записи;
- кабинет ВАТС Beeline — через Chrome владельца, только просмотр, без нажатий
  на «Ваша CRM» и без изменения настроек;
- публичные страницы вендора платформы (вики тенанта Moldcell, та же платформа,
  включая три скриншота формы «Ваша CRM») и публичный PDF «REST API Облачной
  АТС», который отдаёт сам тенант EVO (121 104 байта, SHA-256 начинается с

## 0. Чего этот план не разрешает

- Ни одного действия на production: ledger-apply миграций, правка
  `.env.production`, установка таймера на VPS, создание подключения «Ваша CRM» в
  кабинете ВАТС, правка edge Caddy, включение выключателей и флагов, выпуск
  приложения, настоящий звонок через API — каждое отдельным разрешением
  владельца на конкретное действие.
- Изменений в настройках ВАТС и amoCRM: маршрут входящих, виджет, токены,
  настройки записи остаются как есть. EVO подключается отдельным соединением
  (§5.6) и не меняет подключение amoCRM.
- Копирования записей разговоров (решение 3, ADR 0033). Ни файла, ни
  потока в хранилище EVO, ни кэша. Ссылка на запись — секрет.
- Возврата старых маршрутов `/calls` и `/api/webhooks/telephony`. Они остаются
  скрытым 404 (`RETIRED_PLATFORM_ROUTE_ROOTS`, тесты
  `tests/p6b-supabase-runtime-cleanup.test.mjs` и
  `tests/e2e/supabase-staff-auth.spec.ts`). Новый код живёт на новых путях
  (§5.1, §12).
- Любой работы с WhatsApp. Wazzup остаётся как есть внутри amoCRM, возврат WAHA
  — позже и отдельным планом. Телефония не трогает приём WAHA
  (`/api/v2/whatsapp/inbound`).
- Расшифровки и пересказа звонков ИИ, номеров для отслеживания рекламы,
  отключения amoCRM (§4, «Позже»).

### Что подключение EVO всё же меняет

«Не меняем настройки» не означает «ничего не происходит». Проверка по форме
кабинета (скриншоты вики вендора, §3.2) и по PDF показывает четыре последствия.

1. **Новое подключение получает все звонки сразу.** В форме `history`
   (входящие и исходящие), `event` и `contact` (имя звонящего на экране
   телефона) у подключения «всегда подключены»; опционален только маршрут
   «звонки перенаправляются на ответственных менеджеров из CRM». Значит, с
   момента создания подключения каждый входящий на `+996 770 40-70-30` вызывает
   синхронный запрос `contact` к EVO. Что делает ВАТС, если EVO отвечает
   медленно, с ошибкой или не отвечает, не документировано. Это P1-блокер
   запуска (§17, риск 2): подключение создаётся только после ответа Beeline и
   замера на настоящих звонках (§14, шаг 8).
2. **`makeCall` из EVO виден в amoCRM.** ВАТС звонит менеджеру на его
   устройство; в фазе 1 это вкладка amoCRM с WebRTC. ВАТС шлёт `history` и
   `event` и подключению amoCRM: во вкладке всплывёт карточка звонка, звонок
   попадёт в историю контакта, а виджет по вики вендора умеет по неизвестному
   номеру создавать контакт, сделку и задачу.
3. **Входящий с неизвестного номера и сегодня создаёт в amoCRM контакт и
   сделку** (виджет, §3.3). Тестовые звонки приёмки (§15) оставят следы в
   amoCRM: владелец заранее выбирает номер, уже известный amoCRM, либо чистит
   следы после.
4. **EVO ничего не пишет в amoCRM и не читает из него.** Сверка по агрегатам
   amoCRM (шаг 10) — только чтение владельцем или агентом по отдельному разрешению.

## 1. Цель и границы

Цель владельца 16.10: продажи переходят из amoCRM в CRM EVO. Телефония — одна
из частей такого перехода. Когда менеджер звонит и ему звонят, это должно быть
видно в карточке лида, а пропущенный звонок не должен потеряться.

Что входит в фазу 1:

1. приём событий и итогов звонков из ВАТС (PBX → EVO) и сверка по истории
   ВАТС;
2. журнал звонков в EVO, привязка к клиенту и лиду по телефону;
3. прослушивание записи через сервер EVO без копий;
4. кнопка «Позвонить» (EVO → ВАТС `makeCall`);
5. пропущенный входящий → задача «Перезвонить» со сроком 15 минут рабочего
   времени; неизвестный номер → новый лид «Звонок» в «Заявках»;
6. результат звонка одним нажатием, «Недозвон» автоматически, следующий шаг;
7. отчёт по звонкам;
8. настройки, здоровье интеграции, права, аудит;
9. флаги включения: интерфейс, набор, разбор и автоматика по умолчанию
   выключены, срезы выпускаются по одному и ничего не открывают (§9.1, §14).

Что не входит:

- Перенос маршрутизации входящих и всплывающей карточки в EVO — это фаза 2.
- Встроенный в браузер телефон (WebRTC). В фазе 1 звонок идёт на устройство,
  которое у менеджера уже зарегистрировано в ВАТС (§8).
- Копирование или пересказ записей; перенос истории звонков и записей из
  amoCRM; Wazzup, WAHA; отключение amoCRM; call-tracking по рекламным каналам.
- Изменение работы продавцов в amoCRM: пока команда там работает, EVO только
  параллельно наблюдает (§4).

  Поэтому сегодня звонят только через WebRTC в виджете amoCRM.
- Один номер компании `+996 770 40-70-30`. Маршрут входящих 24/7:
  «Ответственный менеджер из amoCRM»; запасной — приветствие и группа «Отдел

- Запись: внешние и внутренние звонки включены, хранение 1 год, записи
  доступны с 22.10.2025. Уведомление о записи владелец включает сейчас

- Раздел «Интеграция с CRM»: amoCRM подключён; блок «Ваша CRM» разрешает
  несколько подключений по REST API. EVO подключается параллельно, второго
  подключения к amoCRM это не меняет (не нажималось).

### 3.2. REST API ВАТС

Документ публичный, формат проверен по PDF тенанта. Точка входа ВАТС:
`POST https://<тенант>/sys/crm_api.wcgp`. Только HTTPS. Авторизация — общий
ключ в теле запроса: `token` в запросах CRM → ВАТС и `crm_token` в запросах
ВАТС → CRM. Ключи создаются один раз при настройке и меняются на стороне CRM
и в кабинете. Подписи сообщений нет. Лимиты, повторы, таймаут ответа CRM и
кодировка тела (форма или JSON) в документе не описаны.

| Направление | Команда | Что даёт EVO |
|---|---|---|
| ВАТС → CRM | `event` | `type` = `INCOMING`, `ACCEPTED`, `COMPLETED`, `CANCELLED`, `OUTGOING`, `TRANSFERRED`; поля `phone`, `diversion` (номер компании), `user`, `groupRealName`, `ext`, `telnum`, `direction`, `callid` (общий для всех связанных ног звонка). В форме кабинета «всегда подключено» |
| ВАТС → CRM | `history` | после звонка: `type` in/out, `status` Success/Missed/Cancel/Busy/NotAvailable/NotAllowed/NotFound, `user`, `ext`, `groupRealName`, `telnum`, `phone`, `diversion`, `start` (UTC `YYYYmmddTHHMMSSZ`), `duration` (**общая** длительность звонка), `callid`, `link` (запись). В форме «всегда подключено» (входящие и исходящие) |
| ВАТС → CRM | `contact` | синхронный запрос при новом входящем: на вход `phone`, `callid`; ответ `{contact_name, responsible}`. В форме «всегда подключено» (имя на экране телефона); опционален только переключатель маршрута «на ответственного из CRM», который включается вручную |
| CRM → ВАТС | `accounts`, `groups` | сотрудники (`name`, `realName`, `ext`, `telnum`) и отделы — для сопоставления сотрудников |
| CRM → ВАТС | `makeCall` | `user` (логин, внутренний или прямой номер), `phone`; ВАТС сначала звонит менеджеру, потом соединяет с клиентом; ответ 200 — идентификатор звонка |
| CRM → ВАТС | `history` | CSV за период (`start`/`end` UTC или `period`, `type` all/in/out/missed, `limit`): `UID,type,client,account,via,start,wait,duration,record` |
| CRM → ВАТС | `subscribeOnCalls`, `set_dnd`, `get_dnd`, `subscriptionStatus` | приём звонков сотрудником — позже. В примерах PDF литералы `subscribeoncalls` и `subscribtionstatus` (с опечаткой), в заголовках `subscribeOnCalls` и `subscriptionStatus`; параметр `user` ссылается на режим `self_map`, который не описан. Точные литералы проверяются настоящим вызовом до использования, `self_map` — вопрос Beeline |

Форма кабинета (по скриншотам вики вендора, тенант Moldcell; для Beeline KG
ожидается то же, подтверждается в кабинете): у каждого подключения «Ваша CRM» свои
поля — «Имя вашей CRM», «Включить доступ к API», «Адрес АТС» (только чтение),
«Ключ АТС» (выдаёт кабинет), «Адрес вашей CRM» (в примере `domain.ru`, принимает ли
путь — не документировано), «Ключ для авторизации в вашей CRM» (вводится). На
демо-тенанте два таких подключения работают одновременно. Сценарий общий для всех
номеров (можно создавать отдельные по номерам); `history`, `event`, `contact`
(имя), `makeCall`, `accounts` «всегда подключены», переключается только маршрут
по CRM. Примеры ключей в форме — UUID.

Коды ответа CRM: 200; 400 `{"error":"Invalid parameters"}`; 401
`{"error":"Invalid token"}`. Ответ `makeCall` в PDF — «CallID» (голая строка или
JSON — не сказано). Ссылка на запись — это URL MP3 без подписи и без
query: любой, у кого есть ссылка, слушает запись (проверено HEAD-запросом, без
скачивания). Записи старше года на старом тенанте отдают 404, на текущем
тенанте записи возраста 343–353 дня ещё отдаются: правило «год» подтверждено
косвенно, удаление начнётся примерно с 28.10.2026.

Размер: около 2 КБ на секунду речи (16 кбит/с, моно). Это оценка для
потокового прокси, а не для хранения. На вики вендора администратору ВАТС
доступна выгрузка записей по FTP; для Beeline KG это не подтверждено (§7.5).

### 3.3. amoCRM (агрегаты)

- Живой виджет телефонии — `amo_beeline_kg`. Второй, `amo_beeline_business`,
  установлен, но звонков через него нет.
- С апреля 2025: 30 673 звонка, 91 % исходящие. Последние 12 месяцев — 27 927,
  последние 30 дней — 3 095. Звонят 5 человек. Нагрузка: около 91 звонка в
  рабочий день (медиана 86, максимум 187 за последние 90 дней), понедельник —
  суббота, 10:00–20:00 по Бишкеку.
- Исходящие отвечены в 56 %. Входящие: 2 804 за всё время, **без ответа 52 %**.
  Около 90 % звонивших на входящий уже были контактами в amoCRM (перезвоны
  тем, с кем уже общались); новых неизвестных звонящих — порядка 10–15 в
  месяц. Виджет сам создаёт для них контакт и лид.
- Поле «Результат звонка» не заполнено ни в одном звонке (0 %). Работа ведётся
  задачами «Связаться» (около 27 тысяч).
- Записей на текущем тенанте около 15,7 тыс. (около 650 часов разговора).

### 3.4. Репозиторий

- Телефонии в коде нет. Прежний вебхук и страница звонков удалены 04.09.2026
  (P6B); маршруты — скрытый 404. В спецификации: DEC-019 «Deferred», INT-018,
  DA-04 в бэклоге.
- Есть готовые части: приём вебхука WhatsApp (`platform-waha-webhook.ts`:
  ограничение тела, постоянное по времени сравнение секрета, выключатель env,
  доказательство события, очередь); сопоставление телефонов
  (`normalize_person_phone`, `admissions_direct_phone`, `person_phone_match_keys`,
  281); канонические клиент и лид (084); задачи (`staff_tasks`, 142/147, а для
  задач от системы — образец 275 `ai_autosend_call_tasks`); права (268);
  выдача медиа по разрешению (062); журнал `platform.audit_events`; источник
  лида `phone_call` (143/264).
- Чего нет: сущности звонка, сопоставления пользователя ВАТС и сотрудника,
  публичного маршрута для ВАТС, права на звонки, строки «Телефония» в
  настройках, учёта звонков в «Заявках» и ленте лида.
- Найдено при чтении: очередь `staff_requests_queue_v2` берёт лиды только с
  `source_key IN ('website','whatsapp')` (250), поэтому лид `phone_call` в
  «Заявках» сегодня не появился бы. Нужна новая версия очереди (§12, T9).
- Номер следующей миграции: main — 282; 283–286 заняты открытыми PR #1202,
  #1205, #1207 (план приложения студента v2). Первая телефонная миграция —
  **287**; один номер на один PR, номер подтверждается при слиянии по свежему

### 5.1. Приём: ВАТС → EVO

Путь: `POST /api/v2/telephony/beeline/inbound` (рядом с
`/api/v2/whatsapp/inbound`). Адрес в кабинете: §5.6. Маршрут добавляется в
`PLATFORM_PRIVATE_API_ALLOWLIST` (`src/lib/platform-route-contract.ts`): сам
проверяет токен, обходит cookie-сессию сотрудников. Тесты скрытых 404 для
`/calls` и `/api/webhooks/telephony` остаются зелёными.

Принцип: дешёвое первым; до успешной проверки токена база не вызывается и
значения полей нигде не пишутся.

1. Метод не POST → 405 с `Allow: POST`.
2. Нет или негоден `EVO_PLATFORM_TELEPHONY_CRM_TOKEN` (меньше 32 знаков,
   пробелы, управляющие знаки, знаки вне `[A-Za-z0-9-]`) → 503. Подключение в
   кабинете при этом существовать не должно (§14).
3. Заявленный `Content-Length` больше 32 КиБ → 413. Тип запроса сравнивается
   без параметров (`;charset=…` допускается); принимаются
   `application/x-www-form-urlencoded`, `application/json`,
   `multipart/form-data` и `text/plain` (JSON-объект или форма). Другой тип →
   415.
4. Чтение тела потоком с жёстким пределом 32 КиБ (как `readBoundedBody` у
   WAHA); превышение → 413 с отменой загрузки. Узкий плоский разбор: форма,
   один JSON-объект только со скалярными значениями, multipart стандартным
   `formData()` над уже прочитанным ограниченным буфером; не больше 32 полей,
   ключ ≤ 64 и значение ≤ 2 048 знаков, ссылка ≤ 1 024. Вложенность, повторы
   ключей, `__proto__` и тело, которое не разобрать → 400. Журнал приложения
   (stdout) получает только счётчики: код ответа, основной тип запроса (≤ 64
   знаков, без параметров), корзина длины тела (до 1 КиБ, до 4 КиБ, до 32
   КиБ), признак «разбор не удался». Тело и значения не логируются.
5. Постоянное по времени сравнение `crm_token` с текущим ключом и, если задан,
   со следующим (`…_CRM_TOKEN`, необязательный `…_CRM_TOKEN_NEXT` для ротации,
   §5.5): SHA-256 обеих сторон, затем `timingSafeEqual`. Неверный →
   `401 {"error":"Invalid token"}`. Токен после сравнения удаляется из объекта и
   нигде не сохраняется.
   Ограничитель неудач считает только запросы с неверным токеном или
   неразобранным телом: больше 20 в минуту с одного адреса — такие запросы
   получают 429 на минуту. **Запрос с верным токеном ограничитель никогда не
   останавливает**, поэтому поток чужих запросов не отрезает ВАТС. Адрес берётся
   только из заголовка `X-Evo-Telephony-Ip`, который ставит edge
   (`header_up X-Evo-Telephony-Ip {remote_host}`, §5.7); приложение игнорирует
   `X-Forwarded-For` и клиентские значения. Карта в памяти ограничена по размеру
   (LRU, 10 000 адресов) и сбрасывается при перезапуске.
6. Дальше запрос аутентифицирован:
   - `cmd=contact` → сразу `200 {}`: без базы, без проекции, без записи,
     меньше 200 мс, **независимо от `EVO_PLATFORM_TELEPHONY_ENABLED`**, пока
     ключ верный. Причина: ВАТС шлёт `contact` на каждый входящий, поведение при
     ошибке неизвестно, а подключение может жить, когда приём выключен
     (§0, §14). `503` на `contact` недопустим;
   - выключатель не ровно `"1"` → для остальных команд `503
     {"error":"telephony_unavailable"}`, ничего не пишется;
   - `cmd` не из списка `event`, `history`, `contact` → 400
     `{"error":"Invalid parameters"}`; в доказательство пишется запись формы
     (имена полей и длины, без значений) для диагностики;
   - `event` и `history` → пункты 7–8.
7. Запись доказательства **всегда**, для любого аутентифицированного `event` и
   `history` (хранить сначала, проецировать потом). Проверка полей мягкая: нет
   обязательных по PDF `user` (пропущенный звонок, который никто не взял, или
   группа), `phone` (анонимный звонящий) или `callid` (проба) — не повод для
   400, потому что неизвестно, повторит ли ВАТС запрос или отключит
   подключение, а звонок будет потерян. Доказательство получает
   `validation_state` = `ok` или `incomplete` с перечнем отсутствующих имён
   полей; проекция неполные сообщения пропускает или помечает
   `needs_review`, а сверка (§5.4) подбирает звонок по CSV. Неполное
   сообщение не создаёт ни задач, ни лидов (§9).
8. Постановка в очередь (§5.2) и встроенная проекция с бюджетом 500 мс (дольше
   — очередь), ответ `200 {}`.

Отличие от WAHA: у WAHA HMAC считается по сырым байтам до разбора, у ВАТС
подписи нет, токен лежит в теле. Поэтому до проверки токена допускается только
ограниченный плоский разбор тела размером до 32 КиБ, без обращения к базе, без
логирования содержимого. Это осознанное исключение из правила «неподписанное
тело не доходит до JSON.parse»; оно записано в ADR 0033.

Команды:

| `cmd` | Фаза 1 | Ответ |
|---|---|---|
| `event` | доказательство + состояние ноги (звонит, принят, завершён, отменён, исходящий, переведён) | 200 `{}` |
| `history` | доказательство + итог ноги: статус, общая длительность, ссылка на запись (прямо в строку ноги, §7.1) | 200 `{}` |
| `contact` | токен проверен; `{}` без `responsible`, без базы, всегда (пункт 6 выше). Маршрутизацию ВАТС по CRM для подключения EVO не включаем (§5.6). Задержку ВАТС и поведение на пустой ответ проверяем замером (§14, шаг 8). В фазе 2 ответ вычисляется без запроса в базу на каждый звонок | 200 `{}` |
| другое | запись формы | 400 |

Идемпотентность: ключ дедупликации — SHA-256 от канонической строки (`cmd`,
`type`, `callid`, `user`, `status`, `start`, `ext`, `phone`) без токена и
ссылки. Повтор того же сообщения возвращает 200 с `deduplicated`. Сообщения с
одним `callid`, но разными `user`, `status` и `start`, хранятся все: звонок и
его ноги собираются по правилам §6.1, а не «побеждает последнее сообщение». Повторы ВАТС
в документе не описаны, поэтому EVO отвечает 200 на любой принятый и
сохранённый пакет и не рассчитывает на повторную отправку: страховка — сверка
по `history` (§5.4). События приходят не по порядку, проекция это терпит.

Белый список адресов: если Beeline назовёт адреса источника, фильтр ставится на
edge (`remote_ip`, §5.7); слой приложения не дублирует. Без списка защита —
длинный случайный токен, ограничитель неудач и сверка.

### 5.2. Доказательство и очередь

Выбор: отдельные таблицы, а не `provider_webhook_events` и не
`durable_work_items`.

- `platform.communication_provider` = {waha, kommo, amocrm}, а у
  `provider_webhook_events` проверки формы привязаны к WAHA (044). Добавить
  значение enum можно (`ALTER TYPE … ADD VALUE`, отдельной миграцией), но
  правка проверок общей таблицы затрагивает горячий путь WhatsApp.
- `durable_work_items` связана проверками и внешним ключом с
  `provider_webhook_events` (045: проверки по видам работы, `source_webhook_event_id`);
  новый вид работы меняет их и общую функцию постановки. ИИ-агент свою
  очередь строит отдельно, на pgmq (план ИИ-агента §5.4).

Берём тот же протокол — аренда, число попыток, отсрочка, мёртвые письма — в
таблицах телефонии:

| Таблица (`platform_private`) | Назначение |
|---|---|
| `telephony_pbx_events` | append-only доказательство: время приёма, `cmd`, тип, `callid`, ключ дедупликации, SHA-256 сырого тела, очищенные поля (без токена и без ссылки на запись; ссылка заменена признаком `has_link`), `validation_state`, результат проверки токена; для отклонённых после токена — только форма (имена полей и длины) |
| `telephony_event_work` | исходящий «ящик»: статус, попытки, `next_attempt_at`, аренда, код последней ошибки. **Ссылка на запись здесь не хранится**, только `has_link` |
| `telephony_calls` | звонок (§6.1) |
| `telephony_call_legs` | нога звонка: участие одного сотрудника или группы; здесь, и только здесь, лежит ссылка на запись (§6.1, §7.1) |
| `telephony_call_events` | append-only хронология событий звонка (для времени ожидания и фазы 2) |

Функция приёма пишет доказательство и, если в сообщении была ссылка, кладёт её
**сразу в строку ноги в той же транзакции**, до проекции. Проекция идёт внутри
транзакции приёма через точку сохранения: если она не удалась, доказательство и
нога (со ссылкой) остаются, работа уходит в очередь, фоновый скрипт повторяет
(§5.3). Приём отвечает 503 только если не удалось сохранить доказательство.
Если транзакция приёма не прошла целиком, ссылку вернёт сверка из CSV
(столбец `record`). Решение об отдельных таблицах обсуждается на ревью T1a;
если ревью предпочтёт pgmq, меняется только слой очереди, не контракт маршрута.

### 5.3. Фоновая работа

Скрипт `telephony-maintenance.mjs` собирается в образ приложения в
`Dockerfile`, как `knowledge-maintenance.mjs`: `docker exec evo-crm-app-1 node
/app/telephony-maintenance.mjs`. Режимы внутри скрипта, срок следующего запуска
берётся из `telephony_runtime_state`:

1. повтор проекции из `telephony_event_work` (каждую минуту);
2. окно успокоения и тик SLA пропущенных (§6.1, §9) и «Недозвон» (каждую минуту);
3. сверка по `history` (§5.4, каждые 10 минут);
4. отметка истёкших записей (§7.5, раз в сутки).

**Production-артефакт: systemd-сервис и таймер на VPS.** Это отдельная
установка вне образа приложения. Файлы
`deploy/telephony/evo-telephony-maintenance.service` и `….timer` лежат в
репозитории по образцу `deploy/knowledge/*` (`Type=oneshot`,
`ExecStart=/usr/bin/docker exec evo-crm-app-1 node /app/telephony-maintenance.mjs`,
`OnUnitInactiveSec=1min`, `Persistent=true`, `TimeoutStartSec`; пересечения
запусков нет, пока предыдущий запуск не закончился). Устанавливаются шагом
§14 отдельным «давай» владельца; без установки не работают повтор проекции,
SLA, сверка и отметка истёкших записей, поэтому шаг стоит **до** включения
приёма. Скрипт при `ENABLED` не равном `1`, а также при выключенной проекции
или `outbound_paused` ничего не делает. Отдельного HTTP-маршрута для
планировщика нет. Контейнер приложения `read_only`, скрипт ничего не пишет на
диск.

### 5.4. Исходящий клиент: EVO → ВАТС и сверка

Серверный модуль (только сервер, `server-only`):

- адрес — `EVO_PLATFORM_TELEPHONY_PBX_URL` (`https://evoadmitions.ats.beeline.kg/sys/crm_api.wcgp`),
  только `https`, хост из белого списка, редиректы не выполняются;
- тело — форма `application/x-www-form-urlencoded` с `cmd` и `token`
  (`EVO_PLATFORM_TELEPHONY_PBX_TOKEN`);
- таймауты: соединение 5 с, весь запрос 10 с; для чтений (`accounts`, `groups`,
  `history`, `get_dnd`) до двух повторов с отсрочкой;
- `makeCall` не повторяется автоматически: двойной звонок опаснее потерянного.
  Ответ 200 в PDF описан как «CallID» (голая строка или JSON — не сказано):
  разбор принимает оба вида, настоящий вид записывается в шаге 9 и закрепляется
  тестом. Неоднозначный итог (таймаут, неразобранный ответ) помечается «не
  подтверждён», пользователь видит «Проверьте телефон», а сверка по `history`
  потом находит звонок;
- ответы разбираются по коду: 401 → в «Настройках» «Ключ ВАТС отклонён»; 400 →
  код ошибки; в журнал идут correlation id, команда, статус, время, без токена,
  без номера (только последние 4 цифры);
- перед `makeCall`: проверка права, флагов `dial_enabled` и `outbound_paused`,
  сопоставление пользователя, проверка номера и лимиты (§6.5), идемпотентность
  по `request_id`.

#### Сверка (`history`, CSV)

Сверка — страховка от потерянных вебхуков и источник того, чего нет в
вебхуке (время разговора, ожидание). Каждые 10 минут запрашивается окно от
последнего успешного курсора минус два часа до сейчас; раз в сутки — вчера
целиком. Курсор (`telephony_runtime_state`) сдвигается только после
успешного разбора всего ответа. Размер окна и `limit` подбираются по
настоящим данным: максимум `limit` в PDF не указан, и если число строк равно
`limit`, окно делится пополам.

Формат CSV (заголовок, разделитель, кавычки, формат `start` и `client`) в PDF не
описан. Разбор пишется только по настоящему образцу, снятому в шаге 8 (§14);
пока образца нет, сверка ничего не проецирует.

| Столбец PDF (`UID,type,client,account,via,start,wait,duration,record`) | Куда | Замечание |
|---|---|---|
| `UID` | `pbx_callid` | совпадение с `callid` вебхука — предположение по документу, проверяется в шаге 8; иначе связь по (клиентский номер, сотрудник, ±60 с) |
| `type` | направление и класс | `in` — входящий, `out` — исходящий, `missed` — пропущенный входящий (предположение). Как CSV показывает исходящий без ответа (`out` с `duration = 0` или иначе) — проверяется |
| `client` | `client_phone` | нормализация по 281 |
| `account` | нога и сотрудник | логин сотрудника, который говорил; имя группы или код `ivr`/`fax` — до сотрудника не дошло |
| `via` | `company_number` | номер, на который пришёл входящий, или АОН исходящего |
| `start` | `started_at` | UTC; формат по образцу |
| `wait` | `wait_seconds` | время ожидания на линии |
| `duration` | `talk_seconds` | время разговора (в вебхуке `duration` — общая длительность) |
| `record` | ссылка | в строку ноги, как секрет (§7.1); в памяти, не на диске, не в журнале |

Итог звонка по CSV. Поля `status` в CSV нет, поэтому `Busy`, `NotAvailable`,
`NotFound`, `NotAllowed` и `Cancel` из него не восстановить. Строка, созданная
сверкой (`created_via = 'reconcile'`), получает `outcome_source = 'csv'` и один
из трёх итогов: `answered` (`duration > 0` и `account` — сотрудник), `missed`
(входящий без сотрудника), `no_answer_unknown` (исходящий без разговора). В
интерфейсе такая строка подписана «исход неточный». Правила:

- по строке `outcome_source = 'csv'` не выставляются «Недозвон» и каденс, а
  задача «Перезвонить» создаётся только для входящего пропущенного не старше
  двух часов;
- если вебхук уже дал точный статус, CSV его не перезаписывает, а дополняет
  `wait`, `talk_seconds`, `via` и недостающую ссылку (и по CSV решается
  `answered`: `duration > 0` и `account` — сотрудник);
- пока звонку меньше 360 дней, сверка обновляет ссылку из `record` (§7.3);
- число расхождений за сутки показывается в «Настройках» и входит в критерий
  выхода из фазы 1.

#### Первичный импорт

При первом подключении тот же код сверки проходит назад суточными окнами до
22.10.2025 (начало доступных записей). Он:

- создаёт строки звонков (`created_via = 'backfill'`) только для номеров,
  которые уже совпали с клиентом EVO (`matched`); остальные строки отбрасываются
  без сохранения и без журнала;
- сохраняет ссылку на запись (это ссылка, не звук; решение 3 не нарушено);
- не создаёт клиентов, лидов, задач и «Недозвон»;
- запускается только после «да» владельца (вопрос 10) и как можно раньше, потому
  что каждый месяц промедления после первых удалений у Beeline теряет около
  1,4–1,8 тыс. ссылок (§7.5).

### 5.5. Секреты и env

Имена; значения в Git не попадают. Секреты бэкенда, не `NEXT_PUBLIC_*`.
Хранение: игнорируемый `/opt/evo-crm/.env.production` и SOPS-архив
(`Секреты и доступы ЭВО`; в реестре доступов строки «Beeline ВАТС» пока нет,
её добавляет владелец или агент при внесении ключа).

| Имя | Что | Формат |
|---|---|---|
| `EVO_PLATFORM_TELEPHONY_ENABLED` | выключатель приёма событий и итогов (`contact` отвечает независимо, §5.1) | `0` или `1` |
| `EVO_PLATFORM_TELEPHONY_CRM_TOKEN` | ключ, который EVO задаёт в подключении кабинета (`crm_token`) | случайная строка из `[A-Za-z0-9-]`, 32–64 знака: UUID v4 или 64 hex. Такой вид — как примеры ключей в форме кабинета и не требует кодирования в форме |
| `EVO_PLATFORM_TELEPHONY_CRM_TOKEN_NEXT` | необязательный, только на время ротации | тот же формат, не равен текущему |
| `EVO_PLATFORM_TELEPHONY_PBX_TOKEN` | «Ключ АТС» из подключения в кабинете (для запросов EVO → ВАТС, `token`) | значение из кабинета |
| `EVO_PLATFORM_TELEPHONY_PBX_URL` | адрес `sys/crm_api.wcgp` тенанта | https-URL |
| `EVO_PLATFORM_TELEPHONY_PBX_HOST` | хост тенанта для проверки адресов ссылок на записи | `evoadmitions.ats.beeline.kg` |

Группа `PBX_TOKEN` + `PBX_URL` + `PBX_HOST` — «всё или ничего»: пока её нет,
исходящие функции (`makeCall`, сверка, прокси записей) выключены и честно
показывают «Ключ ВАТС не задан». «Ключ АТС» выдаёт сам кабинет **после**
создания подключения, поэтому ключ приёма (`…_CRM_TOKEN`) вносится раньше, а
группа PBX — в шаге 8.

Токены должны отличаться друг от друга и от каждого другого секрета EVO.
Организация берётся из существующей конфигурации платформы (как у WAHA).
Если кабинет выдаёт один общий ключ вместо двух и тот же ключ используется
виджетом amoCRM, EVO не использует его без явного решения владельца и ответа
Beeline (§17, риск 1).

**Контракт env (срез T3).** Релиз проверяет env скриптом
`scripts/evo-app-env-contract.mjs`: любое имя из `deploy/env.production.example`,
которого нет в `.env.production`, роняет выпуск (`required_env_name_missing`),
если оно не в списках необязательных. Поэтому T3 вносит: пять имён и
`…_CRM_TOKEN_NEXT` в `deploy/env.production.example`; все новые токены,
URL и хост — в списки необязательных (функция выключена, пока значения нет;
выпуск шага 3 проходит до ключей); `EVO_PLATFORM_TELEPHONY_ENABLED` в
`validateFeatureFlags` (только пусто, `0`, `1`); правило «`1` принимается только
при заданном `…_CRM_TOKEN` (по формату выше, отличном от остальных значений)»;
правило «группа PBX — всё или ничего»; тесты в `tests/app-env-contract.test.mjs`.

**Ротация.**

- Ключ приёма (`crm_token`): 1) новое значение кладётся в `…_CRM_TOKEN_NEXT`,
  приложение пересоздаётся — принимаются оба; 2) владелец меняет «Ключ для
  авторизации в вашей CRM» в подключении кабинета; 3) после первого запроса с
  новым ключом значение переносится в `…_CRM_TOKEN`, `…_NEXT` очищается,
  приложение пересоздаётся. Окна, в которых ВАТС получает 401, нет (иначе
  сообщения окна теряются, а сверка только догоняет). При подозрении на утечку
  те же шаги выполняются сразу, автоматика выключается, а доказательства с
  момента подозрения просматриваются.
- «Ключ АТС» (`…_PBX_TOKEN`): перегенерируется только в кабинете. Порядок: 1)
  `outbound_paused = true` (набор, сверка и прокси записей останавливаются,
  «Настройки» показывают «ВАТС: ключ меняется»); 2) владелец перегенерирует ключ;
  3) новое значение кладётся в env, приложение пересоздаётся; 4) пауза
  снимается. Пропущенное окно догоняет сверка.

Настройки, которые меняются без пересоздания приложения, хранятся в базе
(`telephony_settings`, право `telephony.manage`): рабочие часы, срок перезвона,
флаги (§9.1), ответственный при отсутствии владельца лида, разрешённые префиксы
набора, лимиты, потолки автоматики, `outbound_paused`.

### 5.6. Подключение в кабинете ВАТС

Создаётся владельцем в день запуска в разделе «Интеграция с CRM» → «Ваша CRM»,
отдельным разрешением, в тихое время (§14, шаг 8). Форма описана по скриншотам
публичной вики вендора (тенант Moldcell, та же платформа); для Beeline KG
ожидается то же, подтверждается в кабинете без нажатий до разрешения:

| Поле формы | Что вносим |
|---|---|
| «Имя вашей CRM» | «EVO CRM» |
| «Включить доступ к API» | включено |
| «Адрес АТС» (только чтение) | `https://evoadmitions.ats.beeline.kg/sys/crm_api.wcgp` → `…_PBX_URL` |
| «Ключ АТС» (выдаёт кабинет) | → `…_PBX_TOKEN`; вносится в env после создания подключения |
| «Адрес вашей CRM» | `https://crm.evoadmissions.com/api/v2/telephony/beeline/inbound`. **Предположение:** в форме вики поле показано как `domain.ru`, принимает ли оно путь — не документировано (§17, риск 21; запасной вариант ниже) |
| «Ключ для авторизации в вашей CRM» | значение `…_CRM_TOKEN` |

Сценарий интеграции «для всех номеров»: `history` (входящие и исходящие),
`event`, `contact` (имя на экране телефона), `makeCall`, `accounts` — «всегда
подключено»; **выбрать «только `event` и `history`» форма не позволяет**.
Единственный переключатель — «Звонки от клиентов перенаправляются на
ответственных менеджеров из CRM»: для EVO он **выключен** до фазы 2. Следствие
— каждый входящий вызывает `contact` (§5.1, §0). Модель «своя пара ключей на
каждое подключение» (на демо-тенанте вики два подключения «Ваша CRM»
работают одновременно) — ожидание, не факт: подтверждается в кабинете Beeline.

**Запасной вариант адреса.** Если поле принимает только хост: отдельное имя хоста
для ВАТС (DNS и правка edge — отдельное «давай»); на нём edge принимает только
`POST /` и переписывает его на путь приёма (§5.7), всё остальное на этом хосте —
404. Первое действие шага 8 — проверить, что поле принимает путь.

**Запасной режим «только сверка».** Если push-подключение запускать нельзя (ответ
Beeline о `contact` неблагоприятен или замер показал задержку), а ключ ВАТС
можно получить без рабочего адреса приёма (вопрос Beeline), EVO живёт на
сверке: `history` каждые 5 минут. `event` и `contact` не нужны; пропущенный
звонок находится за 5–10 минут, что укладывается в срок 15 рабочих минут.
Контракт приёма и таблицы остаются; режим включает владелец.

Подключение amoCRM не затрагивается; в фазе 2 для EVO включается «Ответственный
менеджер из CRM», и маршрут переключается.

Если кабинет не позволяет два подключения, смена ключа ломает виджет amoCRM
или Beeline не подтверждает, что сбой `contact` не задерживает входящие,
запуск останавливается и возвращается к владельцу и Beeline (§17).

### 5.7. Edge Caddy

Маршрутизацию добавлять не требуется: любой путь, которого нет в `@private`
блока `(evo_app)`, уже идёт на приложение, а закрывает его само приложение.
Новый путь в `@private` не добавляется, `/api/internal/*` не используется
(ВАТС в Docker-сеть не попадает). Перед включением приёма нужна укрепляющая
правка (отдельное «давай» владельца, только `caddy validate` и `caddy reload`,
без перезапуска общего edge; в живом файле блоки расходятся с репозиторием, как
описано в `docs/runbooks/whatsapp-go-live.md`, C5). В ней:

- для пути `/api/v2/telephony/beeline/inbound`: только `POST`, предел тела
  32 КиБ (`request_body`), и только на хосте `crm.evoadmissions.com` (блок
  общий с `app.evoadmissions.com`, на хосте студента путь отвечает 404);
- `header_up X-Evo-Telephony-Ip {remote_host}` перезаписывает клиентское
  значение (образец — `X-EVO-Website-IP`); заголовок добавляется в список
  удаления из журнала Caddy рядом с `X-Evo-Website-Ip`;
- при известных адресах Beeline — `remote_ip`;
- иных заголовков с секретами в приёме нет; тело в журнал edge не попадает;
- для запасного адреса (§5.6) — отдельный блок хоста с `POST /` → путь приёма.

Правка записывается в репозиторный `Caddyfile.evo-edge` тем же PR, но живой файл
редактируется как в C5.

Для встроенного браузерного телефона (фаза 2, §8) edge уже отдаёт
`Permissions-Policy: microphone=(self)`; потребуется расширить `connect-src`
CSP адресом WSS. Сейчас CSP только в режиме Report-Only.

### 6.1. Звонок и его ноги

Один `callid` в PDF общий «для всех связанных звонков»: группа менеджеров,
`CANCELLED` для тех, чьё место занял другой, `TRANSFERRED`. Поэтому звонок — одна
строка на `pbx_callid` (`telephony_calls`), а участие каждого сотрудника или
группы — отдельная нога (`telephony_call_legs`). Сообщения по одному `callid`
не схлопываются в одну строку: «побеждающего последнего» сообщения нет.

Звонок (`telephony_calls`):

| Поле | Значение |
|---|---|
| `pbx_callid` | уникален в организации; у сообщения без `callid` — временный ключ из хэша (`start`, `phone`, `user`) и `needs_review` |
| `direction` | `in` / `out`, по первому событию или ноге |
| `state` | `ringing`, `answered`, `ended`; `ended` — только когда все известные ноги закончили |
| `outcome` | `answered`, `missed`, `cancelled`, `busy`, `unavailable`, `not_found`, `not_allowed`, `no_answer_unknown` (последний — только из CSV) |
| `outcome_source` | `webhook` или `csv`; у `csv` исход неточный (§5.4) |
| `started_at`, `answered_at`, `ended_at`, `settled_at` | UTC; `settled_at` — когда звонок считается завершённым для решений (правило 5) |
| `webhook_total_seconds` | общая длительность по вебхуку, с ожиданием и приветствием; **не время разговора** |
| `wait_seconds`, `talk_seconds` | из CSV `wait`/`duration`; до сверки `talk_seconds` пусто и в интерфейсе «—» |
| `client_phone` | нормализованный номер (E.164), персональные данные, наружу не отдаётся; в строках звонков сотрудники видят маску |
| `company_number` | `diversion`/`via` |
| `membership_id` | сотрудник, ответивший первым; пусто, если не ответил никто |
| `client_id`, `lead_id`, `match_state` | `matched`, `ambiguous`, `unmatched`, `created` |
| `result_code`, `result_by`, `result_at` | `reached`, `callback`, `not_interested`, `no_answer` (авто) |
| `recording_state` | сводное по ногам: `none`, `available`, `unavailable`, `expired` |
| `created_via` | `webhook`, `reconcile`, `backfill`, `dial` |
| `needs_review`, `dial_request_id` | признак ручной проверки; для исходящих из EVO |

Нога (`telephony_call_legs`):

| Поле | Значение |
|---|---|
| `call_id`, `pbx_user`, `extension`, `group_name` | как пришли |
| `membership_id` | сотрудник по сопоставлению (§6.3), может быть пусто |
| `state` | `ringing`, `accepted`, `completed`, `cancelled`, `transferred`, `missed` |
| `status` | `status` из `history` ноги |
| `leg_started_at` | `start` из `history` |
| `talk_seconds` | из CSV |
| `recording_link` | секрет, единственное место хранения (§7.1) |
| `recording_state`, `not_found_count`, `first_not_found_at` | §7.3 |

Ключ ноги — (`call_id`, `pbx_user`, `leg_started_at`). У `event` нет `start`:
событие привязывается к ноге того же `user` с ближайшим по времени приёма; точная
схема уточняется в T1a и проверяется на настоящих групповом звонке и переводе
(§15, строка 5).

Правила слияния ног в звонок (проверяются SQL-тестами T1b и настоящими звонками):

1. **«Ответил сотрудник».** Нога отвечена, если есть `ACCEPTED` с `user` —
   сотрудником (логин из `accounts`; имя группы, `ivr`, `fax` и пустое значение
   сотрудником не считаются), либо `history` со `status = Success`, `user` —
   сотрудником и ненулевой `webhook_total_seconds`. Окончательно решает сверка:
   `duration` из CSV > 0 и `account` — сотрудник. `Success` без сотрудника
   (звонящий дослушал приветствие или меню и положил трубку) — **не отвечен**.
   Не документировано, что ВАТС шлёт в `user` для такого звонка; проверяется
   настоящим звонком «только приветствие» (§15, строка 4).
2. **Ответ необратим.** После `answered` более поздняя нога `Missed` или `Cancel`
   итог не меняет (A ответил, перевёл на B, B не взял — итог `answered`).
3. Прочие итоги — по старшинству: `busy`, `unavailable`, `not_found`,
   `not_allowed`, затем `cancelled`, затем `missed`.
4. `CANCELLED` относится к ноге и звонок не завершает: звонок `ended`, когда
   закончили все известные ноги.
5. **Окно успокоения.** Решения, меняющие мир (задача «Перезвонить», лид
   «Звонок», «Недозвон»), принимаются после `settled_at`: все известные ноги
   закончили, а если ВАТС не прислала финальных сообщений — через 90 секунд после
   последнего сообщения по `callid`. Первый `history` с `Missed` решения не
   принимает.
6. `talk_seconds` звонка — сумма `talk_seconds` ответивших ног (переводы идут
   последовательно); `membership_id` — первый ответивший. Право слушать «свои»
   (§11) есть у сотрудника любой ноги звонка.
7. Направление — по первому событию или ноге.

### 6.2. Сопоставление с клиентом и лидом

`platform_private.telephony_match_phone(org, phone)` берёт ключи
`person_phone_match_keys(phone)` и ищет `platform.clients` по нормализованному
телефону:

- ровно один клиент → `matched`; лид — единственный открытый, иначе самый
  недавно обновлённый открытый; открытых нет — `lead_id` пуст, задача идёт
  последнему владельцу лида клиента, лид не создаётся (спорный случай, §18, 12);
- несколько клиентов → `ambiguous`: автоматической привязки нет, создаётся
  задача руководителю продаж «Проверить звонок», строка видна в отчёте как
  «без привязки»;
- ни одного → `unmatched`; при включённой автоматике (§9) создаётся клиент и
  лид `source_key = 'phone_call'` через `create_or_link_client` и
  `create_or_link_lead` (084), `match_state = created`.

Правило U2 канонической модели соблюдается: совпадение по одному телефону не
сливает клиентов, только прикрепляет запись звонка; создание нового клиента
по неизвестному номеру открывает кандидата в дубликаты как у других приёмников.
Внутренний звонок между сотрудниками (короткий `phone`: меньше 7 цифр или
совпал с внутренним номером) строки в `telephony_calls` не создаёт: считается
только счётчик в `telephony_runtime_state`, а в доказательстве номер пуст и
ссылка не сохраняется.

### 6.3. Сопоставление сотрудников (`telephony_extensions`)

Таблица: `pbx_user` (логин из `accounts.name`), `extension`, `pbx_display_name`
(как в ВАТС), `membership_id` (сотрудник EVO), `active`,
`last_seen_in_accounts_at`. Список приходит командой `accounts`, сотрудника
выбирает `admin` в «Настройки → Телефония». Пока пользователь не сопоставлен,
его звонки сохраняются без `membership_id`, а в «Настройках» горит счётчик
«не сопоставлено». ВАТС ограничена пятью пользователями; шестой сотрудник —
вопрос тарифа (§18). Имя группы, `ivr` и `fax` в этой таблице не хранятся:
сотрудником считается только логин из `accounts` (правило 1 §6.1).

### 6.4. Остальные таблицы

|---|---|
| `telephony_settings` | одна строка организации (§5.5): рабочие часы (по умолчанию пн–сб 10:00–20:00, `Asia/Bishkek`), срок перезвона (15 минут); **флаги** `ui_enabled`, `dial_enabled`, `projection_enabled`, `missed_task_enabled`, `unknown_lead_enabled`, все по умолчанию выключены (§9.1); `outbound_paused`; ответственный при пустом владельце (`escalation_membership_id`: функция принимает только администратора или держателя роли «Телефония — руководитель», §11); разрешённые префиксы набора; лимиты набора (§6.5); потолки автоматики (§9.1); каденс «Недозвона»; `reached_default_step_days` (пусто — выключено, §9.4) |
| `telephony_dial_requests` | `request_id` (идемпотентность), сотрудник, лид, ответ ВАТС, статус, код отказа; основа лимитов и аудита |
| `telephony_recording_grants` | выдача на прослушивание (§7): сотрудник, нога, срок, лимит обращений, счётчик |
| `telephony_task_links` | связь системных задач со звонком; частичный уникальный индекс: одна открытая «Перезвонить» на лид и вид |
| `telephony_runtime_state` | времена последних запусков, курсор сверки (§5.4), метки здоровья, счётчик внутренних звонков |

### 6.5. Телефония и деньги

`makeCall` стоит денег и может уйти на любой номер, а телефон на карточке
сотрудник может править. Поэтому:

- номер берётся на сервере из карточки клиента или лида, доступной сотруднику:
  браузер присылает идентификатор лида и `request_id`, не номер; ручного набора в
  фазе 1 нет;
- `POST /api/v3/telephony/dial` проверяет `sameOrigin` (403, как остальные
  POST-обработчики репозитория) и право внутри базы; повторный `request_id`
  возвращает прежний результат, второго звонка нет;
- номер приводится к E.164 и сверяется со списком разрешённых префиксов в
  `telephony_settings` (по умолчанию только `+996`: 99,7 % звонков в amoCRM идут
  на +996; админ добавляет другие страны, куда реально звонят). Короткие,
  служебные и платные диапазоны блокируются всегда;
- лимиты: на сотрудника не больше 150 в сутки (вся команда в среднем делает 91
  звонок в день, максимум 187) и не чаще одного набора в 5 секунд; на
  организацию не больше 60 в час и 400 в сутки; при 80 % лимита в «Настройках»
  предупреждение, при превышении набор отказывает;
- каждый набор и каждый отказ (с кодом причины) — в `telephony_dial_requests` и
  в журнале действий;
- `dial_enabled = false` или `outbound_paused = true` выключают набор целиком.

## 7. Записи разговоров: потоковый прокси

### 7.1. Принципы

- Копий нет: ни файлов, ни кэша, ни буфера дольше текущего запроса.
- Ссылка — секрет и лежит **в одном месте**: `telephony_call_legs.recording_link`.
  Она записывается туда прямо в транзакции приёма (или сверки) и не попадает в
  `telephony_event_work`, в доказательство, журналы, ответы API, аналитику,
  выгрузки и в браузер; в остальных таблицах вместо неё признак `has_link`.
  Ссылка из CSV сверки живёт только в памяти до записи в ногу.
- Браузер получает только `GET /api/v3/telephony/recordings/<legId>` на нашем
  домене и тело `audio/mpeg`.

### 7.2. Путь запроса

1. Сессия сотрудника и право. Обработчик вызывает от имени сотрудника
   `platform.telephony_recording_grant_v1(leg_id)`. В базе проверяются флаг
   `ui_enabled`, право (`telephony.recording.listen.all`, либо `…listen.own` и
   участие сопоставленного с сотрудником пользователя ВАТС в любой ноге звонка),
   `recording_state = 'available'` и лимит выдач (30 в час на сотрудника). RPC
   выдаёт разрешение со сроком 15 минут и числом обращений до 40 (аудио-плеер
   делает несколько Range-запросов) либо возвращает действующее. **В журнал
   `platform.audit_events` (`telephony.recording.listen`: кто, звонок, когда)
   запись пишется только при выдаче нового разрешения**, не при каждом
   Range-запросе: перемотка строк не добавляет.
2. Сервер вызывает функцию только для service role
   `telephony_recording_consume_v1(grant_id, membership_id)`: она проверяет срок,
   лимит и принадлежность и отдаёт ссылку серверу. Прямой вызов из браузера
   ссылку не вернёт: browser-вызываемая функция выдаёт лишь идентификатор
   разрешения (шаблон 062 `grant`/`consume`).
3. Проверка ссылки: `https`, хост ровно равен `EVO_PLATFORM_TELEPHONY_PBX_HOST`,
   путь по строгому шаблону (уточняется по настоящим ссылкам в T6), без
   редиректов, без обращения к частным адресам — защита от подмены ссылки через
   украденный токен ВАТС (SSRF).
4. Запрос к Beeline: `GET` без cookie и заголовков сотрудника, `fetch` с
   `cache: 'no-store'` и `redirect: 'manual'`, маршрут с `dynamic =
   'force-dynamic'` (в контейнере `/app/.next/cache` — записываемый tmpfs, кэш
   недопустим). `Range` передаётся только если это одиночный `bytes=…`.
   Таймауты: соединение 5 с, заголовки 10 с, простой 15 с. Единый предел тела
   16 МиБ (около двух часов разговора при 2 КБ/с; самый длинный звонок в amoCRM —
   40 минут, около 5 МиБ). Отмена клиента отменяет запрос к Beeline.
5. Ответ: тип источника должен быть `audio/mpeg`, иначе 502 без тела.
   Статус 200/206 как у источника; заголовки только из белого списка:
   `Content-Type: audio/mpeg`, `Accept-Ranges: bytes`, `Content-Range`,
   `Content-Length`; добавляются `Cache-Control: private, no-store, no-transform`,
   `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
   `Content-Disposition: inline`. Тело передаётся потоком без буферизации
   (`no-transform` защищает от сжатия edge).
6. Если источник игнорирует `Range` (200 вместо 206): запись целиком (в пределах
   тех же 16 МиБ) буферизуется в памяти запроса и отдаётся срезом; больше — 502.
   Поведение источника проверяется в T6 на настоящей записи.

### 7.3. Ошибки и состояния записи

Состояния ноги и звонка: `none` (ссылки нет), `available`, `unavailable`
(временно недоступна, ссылка сохранена), `expired` (ссылка обнулена).

Ответ 404 от Beeline не всегда означает «срок вышел»: запись может быть ещё не
загружена, тенант мог дать временный сбой, а ссылку невозможно получить заново
(копий нет). Поэтому ссылку обнуляет только достаточно старый звонок.

| Источник | Браузер | Действие |
|---|---|---|
| 404 или 410, звонку не меньше 360 дней | 410 | `expired`, ссылка обнуляется; в карточке «запись удалена по сроку хранения» |
| 404 или 410, звонок моложе 360 дней | 404 `recording_not_ready` | «Запись ещё не готова или временно недоступна»; ссылка **сохраняется**; растёт `not_found_count`; после трёх таких ответов на протяжении не менее 6 часов состояние `unavailable` («Запись недоступна, проверим позже»); сверка обновляет ссылку из CSV, пока звонку меньше 360 дней |
| 5xx, таймаут, сеть | 502 | «Запись временно недоступна»; состояние не меняется |
| тип не `audio/mpeg` | 502 | без тела |
| нет права или флаг `ui_enabled` выключен | 403 | без причины и без раскрытия существования записи |
| звонок не найден или нет записи | 404 | — |

### 7.4. Что видит сотрудник

В строке звонка в «Ленте» лида: значок, время, длительность, кто говорил и
кнопка «Слушать» (`<audio controls preload="none">`, без автозагрузки); у звонка
из нескольких ног с записями — «Запись 1», «Запись 2». Для чужого звонка
менеджеру кнопки нет, подпись «Запись доступна руководителю». Кнопка «скачать»
убрана из плеера, но это лишь удобство: человек с правом слушать может
записать звук; риск принят, прослушивание пишется в журнал.

### 7.5. Срок хранения у Beeline

Срок по условиям платформы — год. Для звонка не младше 365 дней суточная
отметка (§5.3) делает пробный `GET` с `Range: bytes=0-0` тем же клиентом и теми
же проверками хоста, что прокси: 404/410 → `expired` и ссылка обнуляется; 2xx →
повтор через 7 дней (записи возраста 343–353 дня ещё отдаются, жёсткая граница
неизвестна); ошибка → завтра. Звонку младше 365 дней проверка сама по себе
ничего не помечает: срок вышел только по ответу источника (§7.3).

Из решения 3 следует прямое последствие: записи старше года и записи,
удалённые у Beeline до первого импорта ссылок (§5.4), потеряны для EVO
навсегда. По оценке, удаление записей текущего тенанта начинается около
28.10.2026: к концу ноября 2026 уйдёт около 690 записей, дальше порядка
1,4–1,8 тыс. в месяц. Раньше этой даты подключение не будет готово, поэтому
владелец решает о первых удалениях осознанно: **на вики вендора администратору
ВАТС доступна выгрузка записей по FTP** (для Beeline KG не подтверждено,
вопрос Beeline); это делается вне EVO и не нарушает решение 3, EVO копий не
делает. Решение «сохранить» один важный звонок в EVO — позже, после
юридического решения; оно не вернёт уже удалённые записи.

## 8. Звонок из CRM: софтфон, WebRTC и запасные пути

### 8.1. Что установлено

- `makeCall` не набирает номер сам: ВАТС звонит сотруднику на его
  устройство(а) и после ответа соединяет с клиентом (документ REST API).
  Сотрудник должен иметь зарегистрированное и доступное устройство.
- У четырёх менеджеров и директора нет корпоративных SIM и личных номеров в
  ВАТС. Сегодня «устройство» — вкладка amoCRM с виджетом: по публичной вики
  платформы WebRTC запускается внутри виджета (браузер и гарнитура); вкладка
  закрыта — статус «Не в сети». Виджет работает по WebSocket (инструкции
  поддержки вендора просят смотреть вкладку WS в панели разработчика), то есть
  адрес WSS у платформы есть.
- **SIP-учётные данные у каждого сотрудника ВАТС есть, но не через REST API.**
  По вики вендора в карточке сотрудника: логин (его же вводят в настольный
  телефон и «Корпоративный мессенджер»), пароль, необязательный отдельный
  SIP-пароль («SIP-пароль, если он установлен, иначе обычный пароль»), сервер —
  адрес тенанта. REST API отдаёт только `name`, `realName`, `ext`, `telnum`.
- Устройства сотрудника работают параллельно (настольный телефон, софтфон,
  мобильное приложение, вкладка amoCRM одновременно, вики «Настольные
  телефоны»). Браузерный телефон EVO был бы ещё одним устройством того же
  сотрудника и **шестого места в тарифе не потребовал бы**.
- Чего нет в публичных источниках: адреса WSS для сторонних WebRTC-клиентов,
  разрешения ВАТС на такие клиенты, отдельных SIP-паролей у сотрудников Beeline
  KG. Без отдельного SIP-пароля SIP-логин — пароль кабинета, и EVO получил бы
  пароли кабинета сотрудников; так делать нельзя (§8.2, E).
- Устройства платформы (вики того же вендора, тенант Moldcell; для Beeline KG
  подтверждается): «Коммуникатор» (Windows 10+, macOS, вход логином сотрудника);
  «Корпоративный мессенджер» (чаты и софтфон, Windows, macOS, Linux);
  мобильное приложение (iOS/Android, вход логином или QR; в описании
  приложения Beeline KG в App Store упомянуты звонки из приложения); настольные
  SIP-телефоны и сторонние SIP-клиенты (UDP/TCP 5060, RTP UDP 10000–65535, G.711
  предпочтительно).
- Не проверено: звонит ли `makeCall` во вкладку amoCRM с виджетом, в
  «Коммуникатор», в «Корпоративный мессенджер», в мобильное приложение;
  поддерживает ли тенант Beeline KG те же приложения. Это проверяется
  настоящими звонками (§8.3).

### 8.2. Варианты

| Вариант | Работает без новых данных от Beeline | Что нужно | Замечания |
|---|---|---|---|
| A. «Позвонить» → `makeCall` на устройство менеджера (вкладка amoCRM, «Коммуникатор», «Корпоративный мессенджер» или приложение) | да, если устройство звонит по `makeCall` (§8.3) | менеджер и устройство сопоставлены | В фазе 1 основной путь. Пока вкладка amoCRM открыта, она остаётся телефоном, а звонок виден и в amoCRM (§0) |
| B. «Коммуникатор» или «Корпоративный мессенджер» | да | установка на компьютер, наушники | Для фазы 2 без WebRTC EVO; Windows/macOS (мессенджер и Linux) |

### 8.3. Точка решения G-SP

До выхода из фазы 1 (не до её начала): настоящий `makeCall` с открытой вкладкой
amoCRM, затем с «Коммуникатором», «Корпоративным мессенджером» и мобильным
приложением (§14, шаг 9; владелец рядом, 30 минут, звонок на номер владельца);
письмо Beeline с вопросом про WSS-адрес, разрешение на сторонние WebRTC-клиенты
и отдельный SIP-пароль (§18, вопрос 3 «г»). Рекомендация по умолчанию: если E
доступен — строить E; иначе B для сидящих за компьютером и C для остальных; F —
последний запас. Фаза 1 с вариантом A полезна уже сейчас и не зависит от
решения.

Если у сотрудника нет доступного устройства, `makeCall` вернёт ошибку или не
дозвонится до менеджера; в EVO сотрудник увидит: «Не удалось позвонить:
откройте приложение ВАТС». Клиенту при этом не звонят.

## 9. Пропущенные, неизвестные номера, результат

### 9.1. Включатели и потолки

Срезы выпускаются по одному (§14), и слияние кода не должно ничего открывать:
телефония нигде не показывается как рабочая, пока не пройдена приёмка (INT-018).
Автоматика, кроме того, не должна создавать работу, которую команда не видит:
продажи пока работают в amoCRM. Поэтому в `telephony_settings` есть флаги, все
по умолчанию **выключены**:

| Флаг | Что открывает | Когда включается |
|---|---|---|
| `projection_enabled` | разбор доказательств в звонки и ноги; без него только доказательства | шаг 9 §14 |
| `ui_enabled` | строки звонков в ленте лида, «Слушать», блок «Звонки» отчёта, вкладка «Звонки» в «Заявках», строка «Телефония» в здоровье для сотрудников | шаг 9, после строк A про приём и запись |
| `dial_enabled` | кнопки «Позвонить» и результат звонка | шаг 9, после строки A про `makeCall` |
| `missed_task_enabled` | задачи «Перезвонить» для пропущенных, «Недозвон» с каденсом, автозакрытие | шаг 11 |
| `unknown_lead_enabled` | лиды `phone_call` по неизвестному номеру | шаг 11 |

Каждый RPC и каждое место интерфейса проверяют нужный флаг внутри базы (и, где
уместно, здоровье интеграции); клиент не решает. Пока флаги выключены, право
`telephony.*` у сотрудников ничего не показывает, а «Настройки → Телефония»
видны только держателю `telephony.manage` и честно говорят «Выключено».

Потолки автоматики защищают от поддельных событий при утёкшем ключе (подписи
сообщений у ВАТС нет): не более 10 автосозданных лидов в час и 40 в сутки; не
более 30 автозадач в час и 120 в сутки. При превышении оба флага автоматики
выключаются сами, в «Настройках» горит предупреждение, событие пишется в журнал;
включает снова админ после проверки. Для сравнения: сегодня около четырёх
пропущенных входящих в рабочий день и около 0,5 новых неизвестных номеров в
день.

### 9.2. Пропущенный входящий → «Перезвонить»

Условия: `direction = in`, звонок закончен (`settled_at`, §6.1) без ноги, на
которую ответил сотрудник, включён `missed_task_enabled`.

- Ответственный: владелец лида; иначе сотрудник из `escalation_membership_id`
  (руководитель продаж, §11); иначе администратор.
- Срок — 15 рабочих минут: часы идут только внутри рабочего времени (по
  умолчанию пн–сб 10:00–20:00 Бишкек). Пропущено в 19:55 — срок завтра 10:10;
  пропущено в 03:00 — срок 10:15.
- Задача создаётся функцией, как `ai_autosend_call_tasks` (275): от имени
  системы, привязана к лиду и клиенту, видна в «Задачи» и «Сегодня» (источник
  `tasks` уже входит в очередь «Сегодня»).
- Одна открытая «Перезвонить» на лид и вид: повторные пропущенные не плодят
  задач, а увеличивают счётчик в её тексте.
- Автозакрытие: позже состоялся звонок на этот клиентский номер с итогом
  `answered` (отвеченный входящий или исходящий; именно итог `answered`, а не
  длительность вебхука, которая включает ожидание и приветствие). Задача
  закрывается системой со ссылкой на звонок. Неотвеченная попытка исходящего не
  закрывает.
- Если звонок сопоставлен неоднозначно (`ambiguous`): задача руководителю
  продаж «Проверить звонок».
- Сверка (§5.4) создаёт задачу только для входящего пропущенного не старше двух
  часов.

### 9.3. Неизвестный номер → лид «Звонок»

Условия: `match_state = unmatched`, `direction = in`, звонок закончен
(`settled_at`), включён `unknown_lead_enabled`. Создаётся клиент и лид через
`create_or_link_*` со `source_key = 'phone_call'`, этап `new`, без владельца,
источник канала «Откуда узнал» — `unknown` (подсказка «Спросите клиента»
остаётся). Дальше лид попадает в «Заявки» как «ждёт разбора».

Лид создаётся и для отвеченного, и для пропущенного звонка с неизвестного
номера. Для пропущенного дополнительно создаётся задача «Перезвонить»
руководителю продаж (владельца ещё нет). Повторный звонок того же номера
прикрепляется к созданному лиду, а не создаёт нового.

Нужна новая версия очереди: `staff_requests_queue_v2` берёт лиды только
`website` и `whatsapp`. Срез T9 добавляет `staff_requests_queue_v3` и вкладку
«Звонки» (`REQUEST_SOURCE_FILTERS`, `RequestLeadRow.source`, версия курсора),
а старая версия снимается по правилу replace-not-layer.

Исходящий звонок на неизвестный номер лид не создаёт: набор в фазе 1
возможен только по номеру из карточки.

### 9.4. Результат звонка

После отвеченного звонка в карточке лида (и в «Сегодня» для открытой задачи)
показывается строка из трёх кнопок одним нажатием:

| Кнопка | Что записывается |
|---|---|
| «Дозвонился» | `result_code = reached`. Следующий шаг сотрудник выбирает как сейчас на доске. Если шага нет, лид попадает в полосу «без шага» очереди «Сегодня» (существующее поведение) |
| «Перезвонить» + дата | `result_code = callback`; задача «Перезвонить» на выбранную дату (по умолчанию завтра 10:00); открытая системная «Перезвонить» заменяется |
| «Не интересно» | `result_code = not_interested`; открытая «Перезвонить» закрывается. Лид автоматически не закрывается (закрытие — отдельное действие с причиной, §18, 6) |

«Недозвон» ставит система: исходящий звонок с точным статусом вебхука
(`Missed`, `Busy`, `NotAvailable`, `NotFound`, `Cancel`) завершён без ответа
клиента. Строки, созданные сверкой (`outcome_source = 'csv'`), без
точного статуса «Недозвон» и каденс не получают (§5.4). Следующий шаг: задача
«Перезвонить» по каденсу `telephony_settings` (по умолчанию: +2 рабочих часа,
затем следующий рабочий день 11:00, затем +2 рабочих дня), одна открытая на
лид; после пяти недозвонов за семь дней руководителю продаж уходит подсказка
(не закрытие). Нажатие результата можно изменить в течение суток.

**Отклонение от решения владельца 5.** Решение говорит, что следующий шаг
создаётся автоматически; здесь это сделано для «Перезвонить» и «Недозвон». После
«Дозвонился» шаг, как сейчас на доске, выбирает сотрудник. Автозадача «Связаться»
через N дней после «Дозвонился» заложена как настройка `reached_default_step_days`
(по умолчанию выключено); включать ли её по умолчанию — вопрос владельцу
(§18, 14). Отклонение записано в `PLAN_CHANGES.md`.

В amoCRM поле результата не заполнялось ни разу (0 %). Чтобы в EVO этого не
повторилось, строка результата стоит прямо под звонком, без модального окна,
а процент звонков с результатом — одна из строк отчёта (§10).

## 10. Отчёт по звонкам

Место: «Отчёт продаж» (`/v3/main?view=sales`), блок «Звонки», за выбранный
период, часовой пояс Бишкек. Права `telephony.report.read.own` и `.all` (§11).
Данные — функция `platform.telephony_report_v1(from, to)`; внутренние звонки не
учитываются (они не хранятся). «Отвеченный» — итог `answered` по правилам §6.1
(ответил сотрудник), а не `Success` из вебхука; время разговора берётся из
сверки (§5.4), поэтому у звонка моложе 10 минут оно «—» и в сумму не входит.

| Показатель | Определение |
|---|---|
| Звонки | число клиентских звонков менеджера (входящие + исходящие), разбивка по направлению; звонок с несколькими ногами считается один раз, участники — по ногам |
| Доля отвеченных | отвеченные / все; отдельно исходящие и входящие |
| Время разговора | сумма `talk_seconds`; в часах и минутах; среднее на отвеченный |
| До первого звонка по новому лиду | для лидов, созданных в периоде: от `leads.created_at` до начала первого исходящего звонка любого сотрудника; также до первого отвеченного; медиана и доля уложившихся в 15 минут рабочего времени |
| Пропущенные без перезвона | входящие пропущенные, после которых нет отвеченного звонка на этот номер до конца следующего рабочего дня; число и список без привязки. Отдельно: перезвонили позже срока (15 рабочих минут) |
| Результат проставлен | доля отвеченных звонков с кнопкой результата |

Менеджер с правом `.own` видит только свои цифры, руководитель и admin —
всех. Выгрузка CSV — позже.

## 11. Права и роли

Новые определения в `platform.permission_definitions`, миграция T2 по шаблону
268 (определения, новая неизменяемая версия bundle подходящих ролей,
перепривязка, `staff_bump_memberships`, проверка в конце, `NOTICE` с числом
сотрудников без права). Все ключи — уровня организации
(`staff_resource_kinds = {organization}`, `staff_scope_kinds = {organization}`,
не системные, не чувствительные, группа «Телефония»), как `ai.agent.*` в 268.
Различие «свои» и «все» делает не область права, а сама функция в базе по
участию сотрудника в ногах звонка. Так не нужно расширять `staff_access_evaluate`
новым видом ресурса и не возникает конфликт областей при публикации роли.

| Право | Что открывает |
|---|---|
| `telephony.call.dial` | кнопка «Позвонить», результат звонка |
| `telephony.recording.listen.own` | слушать записи звонков, в которых участвовал сам сотрудник |
| `telephony.recording.listen.all` | слушать любую запись |
| `telephony.report.read.own` | блок «Звонки» отчёта, только свои цифры |
| `telephony.report.read.all` | блок «Звонки» отчёта по всем |
| `telephony.manage` | «Настройки → Телефония»: сопоставление, часы, флаги, префиксы, лимиты, здоровье |

**Как права раздаются (решение, а не отложенный выбор).** Шаблон 268 даёт ключ
каждой подходящей роли «… — общие разделы», которая есть у всех сотрудников, а
роли с областью `own`/`department` пропускает (`staff_roles_publish_scope_conflict`).
Различие из решения 3 («менеджер — свои, руководитель — все») таким способом не
выразить, а `listen.all`, `report.read.all` и `manage` не должны попасть всем
сотрудникам. Поэтому миграция T2 **не добавляет** эти три ключа в «общие
разделы», а создаёт две новые роли организационной области (новые bundle) и
выдаёт ключи только им и admin:

| Роль | Права | Кому назначает admin |
|---|---|---|
| «Телефония — менеджер» | `call.dial`, `recording.listen.own`, `report.read.own` | четыре менеджера |
| «Телефония — руководитель» | всё из роли менеджера плюс `recording.listen.all`, `report.read.all` | руководитель продаж |
| admin (существующая роль) | все шесть, включая `manage` | директор |

«Руководитель продаж» в этом плане — **держатель роли «Телефония —
руководитель»** (в EVO нет штатной роли с таким названием: `STAFF_ROLES` = admin,
sales, admissions). Назначенный в настройках получатель эскалаций
(`escalation_membership_id`, §6.4) должен быть администратором или держателем этой
роли: функция настроек проверяет это в базе, а не доверяет полю. Если admin-bundle
нельзя пополнить ключом (конфликт областей), создаётся третья роль «Телефония —
администратор» по тому же принципу. Состав существующих ролей и их области
сверяются чтением production перед написанием миграции: в этом документе они не
проверялись. Выбор записан в `PLAN_CHANGES.md`.

Видимость строки звонка в ленте лида следует `lead.read` по лиду, как у заметок
и переписки (решение владельца 06.10 «нет, все могут»), и открывается флагом
`ui_enabled`; ограничены только прослушивание и отчёт (решение 3).

Маршруты и права: `src/lib/platform-access.ts` (`CAPABILITY_PERMISSIONS`,
`staffCanAccessRoute`) и `src/lib/fixed-role-policy.ts` для новых страниц;
тест `tests/fixed-role-route-contract.test.mjs`. Каждый RPC повторяет право
сам; клиент не решает.

Аудит: `platform.audit_events` — прослушивание (`telephony.recording.listen`, при
выдаче нового разрешения), набор и отказ набора (`telephony.dial`), результат
(`telephony.result.set`), правка настроек, сопоставление, автоматическое
выключение автоматики по потолку. Чтобы эти события были видны в «Журнале
действий», миграция T2 расширяет серверный allowlist приёмом rename-and-union
(255) **и по действиям, и по типам объектов** (`telephony_call`,
`telephony_dial_request`, `telephony_settings`). Автоматические события приёма
в журнал не идут (как `work.*` и `communication.webhook.persist`).

## 13. Приватность и юридическое

Не юридическая консультация. Источник — публичная заметка ICNL о Цифровом
кодексе КР (февраль 2026) и вывод разведки 16.10.

- Голос и номер телефона — персональные данные. Цифровой кодекс КР
  (по заметке ICNL, действует с 05.02.2026) требует законного основания и, при согласии,
  осознанного, конкретного и доказуемого согласия; трансграничная передача —
  отдельные условия. Данные ВАТС и их хостинг не уточнены (вопрос Beeline).
- Уведомление о записи включено владельцем в ВАТС. Владелец проверяет, что
  уведомление звучит на обоих языках, которыми говорят клиенты, и входит в
  сценарий **до** запуска (включая вызовы, на которые отвечает группа).
- В политике конфиденциальности сайта нужна строка о записи звонков и
  обработке номера: PR в `evoadmissions-website`, только после «да»
  владельца и вычитки юристом КР (вопрос 9).
- EVO не хранит звук, но хранит номер, время, длительность, имя сотрудника и
  результат: это метаданные клиента того же класса, что переписка WhatsApp.
  Срок хранения метаданных звонка — срок хранения клиента (DEC-012 остаётся
  открытым); доказательства приёма — не дольше 12 месяцев (очистка отдельной
  контролируемой функцией в T11, пока её нет — не очищаются).
- Передача звука через сервер EVO при воспроизведении — транзит без записи;
  вопрос юристу: считать ли транзит трансграничной обработкой (место VPS и
  регион Supabase).
- Ни в Git, ни в чат, ни в журналы: токены, ссылки на записи, полные номера
  клиентов, имена сотрудников и клиентов. В журналах — последние 4 цифры.
- В строках звонков, в шапке чата и в журналах номер клиента скрыт (последние 4
  цифры), а набор получает номер на сервере по идентификатору лида. **Карточка
  клиента и лида показывает номер как сейчас** (`tel:`-ссылка, §3.4): полного
  скрытия номеров от менеджеров в EVO нет и этот план его не вводит. Если оно
  нужно как защита от выноса базы (в amoCRM есть похожая настройка
  `HIDINGPHONES`), это отдельное решение владельца и отдельный срез (§18, 15).
- Права слушать — только по §11, каждое прослушивание в журнале.
- ИИ (позже): отправка звука или расшифровки в Gemini требует отдельного
  согласия и решения владельца (ADR 0032, согласие Q4 относится к тексту
  чатов); в фазе 1 звук в ИИ не уходит.

## 14. Порядок выпуска

Правило проекта: ledger → приложение → подключение ВАТС → настоящий звонок.
Релиз не идёт во время чужого релиза; слияние в `main` во время выката срывает
выкат (согласовать с координатором).

**Срезы выпускаются по одному.** Каждый срез: PR → независимое review по точному
head → слияние → ledger-apply его миграции (иначе следующий выпуск остановится с
`schema_ledger_mismatch`) → выпуск приложения. Выпускаемый код ничего не
открывает: флаги `ui_enabled`, `dial_enabled`, `projection_enabled` и флаги
автоматики выключены (§9.1), приём выключен (`ENABLED=0`), права без флага
ничего не показывают. Открывают их только шаги 9 и 11 ниже; слияние не открывает.

| Шаг | Кто | Что | Готово, когда |
|---|---|---|---|
| 1 | агент | Срезы по порядку (§16), каждый — отдельное review и короткие PR-checks | PR слиты |
| 2 | держатель authority | После слияния каждого среза с миграцией: `evo-schema-ledger.yml` `mode=check`, затем `mode=apply` по порядку номеров | ledger production совпадает с репозиторием |

входящие. Только потом `ENABLED=0` или любые правки env и выпуск.
`projection_enabled = false` приостанавливает разбор; автоматика и флаги
выключаются в настройках. amoCRM всё это время работает и не затрагивается;

делает `contact` недоступным (§17, риск 23).

клиентские данные и не отправляет сообщений; успех телефонии заявляется только
после настоящего звонка (`AGENTS.md`).

## 15. Приёмка (настоящие звонки)

Приёмка — на настоящих звонках по настоящему тенанту. Номера: телефон
владельца как «клиент» и сопоставленные пользователи ВАТС как менеджеры.
Имитация вебхука curl'ом, юнит-тесты и локальные стенды — рабочие проверки
разработчика, но не приёмка.

Матрица делится на две части. Строки **A** проходят при выключенной автоматике
(шаги 8–9 §14), строки **B** требуют включённых `missed_task_enabled` и
`unknown_lead_enabled` и проходят в окне шага 11 на номерах владельца при
уведомлённой команде. Тестовые лиды и задачи архивируются штатным действием, не
удаляются.

**Следы в amoCRM.** Звонок на номер компании с неизвестного номера создаёт в
amoCRM контакт и сделку (виджет), а `makeCall` с вкладкой amoCRM в роли
устройства появляется в ней как обычный звонок (§0). Поэтому для строк 2, 3, 8,
15–18 владелец берёт номер, уже известный amoCRM, либо заранее соглашается
почистить следы после; после строк 8 и 17 он смотрит в amoCRM, что появилось, и
записывает это в квитанцию.

## 18. Вопросы владельцу

Работа идёт с решением по умолчанию; ответ заменяет его.

1. **Рабочее время и срок.** По умолчанию: пн–сб 10:00–20:00 Бишкек, срок
   перезвона 15 рабочих минут (по профилю звонков amoCRM; воскресенье почти не
   работает).
2. **Кто руководитель продаж и какие роли.** Получает пропущенные без владельца
   и подсказки по недозвонам, слушает все записи. В EVO нет штатной роли с таким
   названием, поэтому план вводит две роли («Телефония — менеджер» и «Телефония —
   руководитель», §11); руководитель продаж — держатель второй, получатель
   эскалаций выбирается в «Настройки → Телефония» только среди admin и держателей
   этой роли. По умолчанию: директор (admin) до назначения. Нужно подтвердить
   двухролевую схему и назвать человека (блокирует T2).
3. **Письмо Beeline** (одним сообщением, от владельца): (а) подключение «Ваша
   CRM» — один ключ или два, не ломает ли виджет amoCRM; (б) адреса источника
   вебхуков и нужно ли разрешать адрес VPS; (в) лимиты, повторы, таймаут;
   (г) WSS-адрес для WebRTC в своей CRM, разрешены ли сторонние WebRTC-клиенты и
   можно ли завести отдельный SIP-пароль на сотрудника, не равный паролю
   кабинета; (д) звонит ли `makeCall` в «Коммуникатор», «Корпоративный мессенджер»
   и мобильное приложение тенанта; (е) тариф: API, шестой пользователь, хранение
   записей; (ж) где хранятся записи; **(з) что делает ВАТС, если `contact` или
   `event` отвечают ошибкой, медленно или не отвечают (таймаут, повторы,
   отключение подключения), задерживает ли это входящие, и перекрывает ли имя из
   EVO имя из amoCRM на экране телефона (P1-блокер, §17, риск 2)**; (и) принимает
   ли поле «Адрес вашей CRM» путь, и одна ли пара ключей на подключение; (к) что
   ВАТС шлёт в `user` и `status` для звонка, на который отвечает только приветствие
   или группа; (л) смысл параметра `self_map` и точные литералы команд
   `subscribeoncalls`/`subscribtionstatus`; (м) есть ли у администратора ВАТС
   Beeline KG выгрузка записей по FTP.
4. **Внутренние звонки** (запись включена владельцем). По умолчанию: EVO их
   не хранит, считает только число.
5. **Звонки существующих студентов и родителей.** По умолчанию: ответственный —
   владелец лида клиента, иначе руководитель продаж, не куратор дела.
6. **«Не интересно».** По умолчанию: только запись результата и закрытие
   открытой «Перезвонить»; лид закрывается вручную с причиной.
7. **Каденс «Недозвона».** По умолчанию: +2 рабочих часа, затем следующий
   рабочий день 11:00, затем +2 рабочих дня; после пяти недозвонов за
   семь дней подсказка руководителю.
8. **Когда включать автоматику.** По умолчанию: после недели сверки и только
   когда команда реально ведёт лидов в EVO; решение «да» даёт владелец.
9. **Юрист КР.** Запись и транзит, строка в политике сайта, формулировка
   уведомления о записи на русском и кыргызском.
10. **Первичный импорт ссылок и метаданных за год** (только для клиентов, которые
    уже в EVO; звонки остальных номеров не сохраняются). По умолчанию: да, в T4a,
    сразу после подключения (шаг 9); записи не переносятся, переносятся только
    ссылки.
11. **Устройства менеджеров** (компьютеры Windows/macOS, телефоны, наушники) —
    для выбора варианта §8 (B/C/E).
12. **Известный клиент без открытого лида позвонил.** По умолчанию: задача
    последнему владельцу, новый лид не создаётся.
13. **Wazzup и WAHA.** Владелец: Wazzup остаётся как есть, WAHA позже. Когда
    начинать — отдельное решение; телефония от этого не зависит.
14. **Следующий шаг после «Дозвонился».** По умолчанию: шаг выбирает сотрудник,
    как сейчас на доске (отклонение от решения 5, §9.4); можно включить
    автозадачу «Связаться» через N дней (`reached_default_step_days`).
15. **Скрыть полный номер клиента от менеджеров** в карточке (как `HIDINGPHONES`
    в amoCRM). По умолчанию: нет, карточка показывает номер как сейчас; «да» —
    отдельный срез.
16. **Разрешённые страны набора и лимиты.** По умолчанию: только `+996`, 150
    звонков на сотрудника в сутки, 60 в час и 400 в сутки на организацию (§6.5).
    Какие ещё префиксы нужны (+7, +992, +998, +971…).
17. **FTP-выгрузка записей у ВАТС до удаления** (первые удаления около
    28.10.2026). Решение о выгрузке и хранении принимает владелец вне EVO и с
    юристом КР; EVO копий не делает (решение 3).
