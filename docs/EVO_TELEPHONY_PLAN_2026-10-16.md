# EVO — телефония Beeline KG: план фазы 1 (16.10.2026)

Статус: план, запись до кода. Это рабочий контракт для срезов T1–T12: что
строим, где это живёт, по каким правилам и как принимаем. Решения владельца и
изменение объёма — в `docs/PLAN_CHANGES.md`, запись «2026-10-16 — Телефония
Beeline KG: план фазы 1 (решения владельца)». Архитектурное решение —
[ADR 0033](adr/0033-integrate-beeline-kg-pbx-via-rest-api-without-recording-copies.md).
Этот план снимает отсрочку телефонии (DEC-019, DA-04) только для телефонии и
задаёт contract и acceptance, которых требует INT-018; пока приёмка (§15) не
пройдена, телефония нигде не показывается как рабочая.

Факты проверены 16.10.2026 только чтением:

- код `origin/main` `7f51a4c31` (миграции в main до 282 включительно);
- amoCRM — только GET-запросы к API v4, только агрегаты, без номеров, имён,
  текстов и ссылок на записи;
- кабинет ВАТС Beeline — через Chrome владельца, только просмотр, без нажатий
  на «Ваша CRM» и без изменения настроек;
- публичные страницы вендора платформы и публичный PDF «REST API Облачной
  АТС», который отдаёт сам тенант EVO (121 104 байта, SHA-256 начинается с
  `0d50ae10`). На тенанте проверена одна безтокенная проба `GET` к
  `/sys/crm_api.wcgp`: ответ `400 {"error":"Empty token"}`. Звонки не
  совершались, ничего не менялось.

## 0. Чего этот план не разрешает

- Ни одного действия на production: ledger-apply миграций, правка
  `.env.production`, создание подключения «Ваша CRM» в кабинете ВАТС, правка
  edge Caddy, включение выключателей, выпуск приложения, настоящий звонок через
  API — каждое отдельным разрешением владельца на конкретное действие.
- Любых изменений в ВАТС и amoCRM: маршрут входящих, виджет, токены, настройки
  записи остаются как есть. Подключение EVO к ВАТС идёт отдельным соединением
  (§5.6) и не трогает действующее.
- Копирования записей разговоров (решение 3, ADR 0033). Ни файла, ни
  потока в хранилище EVO, ни кэша. Ссылка на запись — секрет.
- Возврата старых маршрутов `/calls` и `/api/webhooks/telephony`. Они остаются
  скрытым 404 (`RETIRED_PLATFORM_ROUTE_ROOTS`, тесты
  `tests/p6b-supabase-runtime-cleanup.test.mjs` и
  `tests/e2e/supabase-staff-auth.spec.ts`). Новый код живёт на новых путях
  (§5.1, §12).
- Любой работы с WhatsApp. Wazzup остаётся как есть внутри amoCRM, возврат WAHA
  — позже и отдельным планом. Телефония не трогает приём WAHA
  (`/api/v2/whatsapp/inbound`).
- Расшифровки и пересказа звонков ИИ, номеров для отслеживания рекламы,
  отключения amoCRM (§4, «Позже»).

## 1. Цель и границы

Цель владельца 16.10: продажи переходят из amoCRM в CRM EVO. Телефония — одна
из частей такого перехода. Когда менеджер звонит и ему звонят, это должно быть
видно в карточке лида, а пропущенный звонок не должен потеряться.

Что входит в фазу 1:

1. приём событий и итогов звонков из ВАТС (PBX → EVO) и сверка по истории
   ВАТС;
2. журнал звонков в EVO, привязка к клиенту и лиду по телефону;
3. прослушивание записи через сервер EVO без копий;
4. кнопка «Позвонить» (EVO → ВАТС `makeCall`);
5. пропущенный входящий → задача «Перезвонить» со сроком 15 минут рабочего
   времени; неизвестный номер → новый лид «Звонок» в «Заявках»;
6. результат звонка одним нажатием, «Недозвон» автоматически, следующий шаг;
7. отчёт по звонкам;
8. настройки, здоровье интеграции, права, аудит.

Что не входит:

- Перенос маршрутизации входящих и всплывающей карточки в EVO — это фаза 2.
- Встроенный в браузер телефон (WebRTC). В фазе 1 звонок идёт на устройство,
  которое у менеджера уже зарегистрировано в ВАТС (§8).
- Копирование или пересказ записей; перенос истории звонков и записей из
  amoCRM; Wazzup, WAHA; отключение amoCRM; call-tracking по рекламным каналам.
- Изменение работы продавцов в amoCRM: пока команда там работает, EVO только
  параллельно наблюдает (§4).

### 3.2. REST API ВАТС

Документ публичный, формат проверен по PDF тенанта. Точка входа ВАТС:
`POST https://<тенант>/sys/crm_api.wcgp`. Только HTTPS. Авторизация — общий
ключ в теле запроса: `token` в запросах CRM → ВАТС и `crm_token` в запросах
ВАТС → CRM. Ключи создаются один раз при настройке и меняются на стороне CRM
и в кабинете. Подписи сообщений нет. Лимиты, повторы, таймаут ответа CRM и
кодировка тела (форма или JSON) в документе не описаны.

| Направление | Команда | Что даёт EVO |
|---|---|---|
| ВАТС → CRM | `event` | `type` = `INCOMING`, `ACCEPTED`, `COMPLETED`, `CANCELLED`, `OUTGOING`, `TRANSFERRED`; поля `phone`, `diversion` (номер компании), `user`, `groupRealName`, `ext`, `telnum`, `direction`, `callid` |
| ВАТС → CRM | `history` | после звонка: `type` in/out, `status` Success/Missed/Cancel/Busy/NotAvailable/NotAllowed/NotFound, `user`, `ext`, `groupRealName`, `telnum`, `phone`, `diversion`, `start` (UTC `YYYYmmddTHHMMSSZ`), `duration`, `callid`, `link` (запись) |
| ВАТС → CRM | `contact` | синхронный запрос при новом входящем: на вход `phone`, `callid`; ответ `{contact_name, responsible}`; ВАТС может направить звонок ответственному, если включить вручную |
| CRM → ВАТС | `accounts`, `groups` | сотрудники (`name`, `realName`, `ext`, `telnum`) и отделы — для сопоставления сотрудников |
| CRM → ВАТС | `makeCall` | `user` (логин, внутренний или прямой номер), `phone`; ВАТС сначала звонит менеджеру, потом соединяет с клиентом; ответ 200 — идентификатор звонка |
| CRM → ВАТС | `history` | CSV за период (`start`/`end` UTC или `period`, `type` all/in/out/missed, `limit`): `UID,type,client,account,via,start,wait,duration,record` |
| CRM → ВАТС | `subscribeOnCalls`, `set_dnd`, `get_dnd`, `subscriptionStatus` | приём звонков сотрудником — позже |

Коды ответа CRM: 200; 400 `{"error":"Invalid parameters"}`; 401
`{"error":"Invalid token"}`. Ссылка на запись — это URL MP3 без подписи и без
query: любой, у кого есть ссылка, слушает запись (проверено HEAD-запросом, без
скачивания). Записи старше года на старом тенанте отдают 404, на текущем
тенанте записи возраста 343–353 дня ещё отдаются: правило «год» подтверждено
косвенно, удаление начнётся примерно с 28.10.2026.

Размер: около 2 КБ на секунду речи (16 кбит/с, моно). Это оценка для
потокового прокси, а не для хранения.

## 5. Архитектура

```
 1. ВАТС ──(event, history, contact; crm_token в теле)──▶ edge Caddy ──▶ evo-crm-app
                                          POST /api/v2/telephony/beeline/inbound
                                          выключатель → тело → токен → поля
                                                              │
                                                              ▼
                                      Supabase: доказательство, очередь, звонки (RLS, RPC)
                                                              ▲   ▲
 2. браузер сотрудника ──(сессия)──▶ /api/v3/telephony/* ─────┘   │
    лента лида, «Заявки», «Сегодня», отчёт, «Позвонить»,          │
    «Слушать» (поток из ВАТС через сервер, без хранения)          │
                                                                  │
 3. ВАТС ◀──(accounts, groups, makeCall, history; token в теле)── evo-crm-app
                                   и фоновый скрипт telephony-maintenance.mjs
```

### 5.1. Приём: ВАТС → EVO

Путь: `POST /api/v2/telephony/beeline/inbound` (рядом с
`/api/v2/whatsapp/inbound`). Адрес в кабинете:
`https://crm.evoadmissions.com/api/v2/telephony/beeline/inbound`. Маршрут
добавляется в `PLATFORM_PRIVATE_API_ALLOWLIST`
(`src/lib/platform-route-contract.ts`): сам проверяет токен, обходит
cookie-сессию сотрудников. Тесты скрытых 404 для `/calls` и
`/api/webhooks/telephony` остаются зелёными.

Порядок проверок (дешёвое первым, ничего до токена не пишет в базу):

1. Метод не POST → 405 с `Allow: POST`.
2. Выключатель `EVO_PLATFORM_TELEPHONY_ENABLED` не ровно `"1"` → 503
   `telephony_unavailable`. Тело не читается, Supabase не вызывается.
3. Нет или негодный `EVO_PLATFORM_TELEPHONY_CRM_TOKEN` (меньше 32 байт, пробелы,
   управляющие символы) → 503.
4. Заявленный `Content-Length` больше 32 КиБ → 413; тип не
   `application/x-www-form-urlencoded` и не `application/json` → 415.
5. Чтение тела потоком с жёстким пределом 32 КиБ (как `readBoundedBody` у WAHA);
   превышение → 413 с отменой загрузки.
6. Узкий плоский разбор: форма или один JSON-объект только со скалярными
   значениями, не больше 32 полей, ключ ≤ 64 и значение ≤ 2 048 знаков,
   ссылка ≤ 1 024. Вложенность, повторы ключей, `__proto__` → 400.
7. Постоянное по времени сравнение `crm_token`: SHA-256 обеих сторон, затем
   `timingSafeEqual` одинаковой длины. Неверный → 401
   `{"error":"Invalid token"}`. Токен после сравнения удаляется из объекта и
   никогда не пишется ни в базу, ни в журнал. Порог неудачных попыток: больше
   20 в минуту с одного адреса → 429 на минуту (в памяти приложения; адрес
   берётся из заголовка edge).
8. Проверка полей по `cmd` → 400 `{"error":"Invalid parameters"}`.
9. Запись доказательства и постановка в очередь (§5.2), встроенная проекция с
   бюджетом 2 секунды → 200 `{}`.

Отличие от WAHA: у WAHA HMAC считается по сырым байтам до разбора, у ВАТС
подписи нет, токен лежит в теле. Поэтому до проверки токена допускается только
ограниченный плоский разбор тела размером до 32 КиБ, без обращения к базе, без
логирования содержимого. Это осознанное исключение из правила «неподписанное
тело не доходит до JSON.parse»; оно записано в ADR 0033.

Команды:

| `cmd` | Фаза 1 | Ответ |
|---|---|---|
| `event` | доказательство + состояние звонка (звонит, принят, завершён, отменён, исходящий, переведён) | 200 `{}` |
| `history` | доказательство + итог звонка: статус, длительность, ссылка на запись | 200 `{}` |
| `contact` | токен проверен; ответ `{}` без `responsible`. Маршрутизацию ВАТС по CRM для подключения EVO не включаем (§5.6). Поведение ВАТС на пустой ответ проверяется в наблюдении (§14, шаг 7) | 200 `{}` |
| другое | — | 400 |

Идемпотентность: ключ дедупликации — SHA-256 от канонической строки
(`cmd`, `type`, `callid`, `user`, `status`, `start`, `ext`, `phone`) без токена и
ссылки. Повтор того же сообщения возвращает 200 с `deduplicated`. Звонок —
одна строка на `callid` (`callid` общий для связанных плеч). Итог `history`
окончательный и перекрывает промежуточные `event`. События могут приходить
не по порядку, проекция это терпит. Повторы ВАТС в документе не описаны, поэтому
EVO отвечает 200 на любой принятый и сохранённый пакет и не рассчитывает на
повторную отправку: страховка — сверка по `history` (§5.4).

Белый список адресов: если Beeline назовёт адреса источника, фильтр
ставится на edge (`remote_ip`, §5.7); слой приложения не дублирует. Без списка
защита — длинный случайный токен, лимит попыток и сверка.

### 5.2. Доказательство и очередь

Выбор: отдельные таблицы, а не `provider_webhook_events` и не
`durable_work_items`.

- `platform.communication_provider` = {waha, kommo, amocrm}, а у
  `provider_webhook_events` проверки формы привязаны к WAHA (044). Добавить
  значение enum можно (`ALTER TYPE … ADD VALUE`, отдельной миграцией), но
  правка проверок общей таблицы затрагивает горячий путь WhatsApp.
- `durable_work_items` связана проверками и внешним ключом с
  `provider_webhook_events` (045: проверки по видам работы, `source_webhook_event_id`);
  новый вид работы меняет их и общую функцию постановки. ИИ-агент свою
  очередь строит отдельно, на pgmq (план ИИ-агента §5.4).

Берём тот же протокол — аренда, число попыток, отсрочка, мёртвые письма — в
таблицах телефонии:

| Таблица (`platform_private`) | Назначение |
|---|---|
| `telephony_pbx_events` | append-only доказательство: время приёма, `cmd`, тип, `callid`, ключ дедупликации, SHA-256 сырого тела, очищенный JSON (без токена и без ссылки на запись), результат проверки токена |
| `telephony_event_work` | исходящий «ящик»: статус, попытки, `next_attempt_at`, аренда, код последней ошибки; ссылка на запись временно хранится здесь до проекции и затем обнуляется |
| `telephony_calls` | звонок (§6) |
| `telephony_call_events` | append-only хронология событий звонка (для времени ожидания и фазы 2) |

Проекция идёт внутри транзакции приёма через точку сохранения: если она не
удалась, доказательство остаётся, работа уходит в очередь, фоновый скрипт
повторяет (§5.3). Приём отвечает 503 только если не удалось сохранить
доказательство. Решение обсуждается на ревью T1; если ревью предпочтёт pgmq,
меняется только слой очереди, не контракт маршрута.

### 5.3. Фоновая работа

Скрипт `telephony-maintenance.mjs` собирается в образ приложения в
`Dockerfile`, как `knowledge-maintenance.mjs` (`deploy/knowledge/*.timer`):
`docker exec evo-crm-app-1 node /app/telephony-maintenance.mjs`, таймер каждую
минуту. Режимы внутри скрипта, срок следующего запуска берётся из таблицы
`telephony_runtime_state`:

1. повтор проекции из `telephony_event_work` (каждую минуту);
2. тик SLA пропущенных (§9) и «Недозвон» (каждую минуту);
3. сверка по `history` (§5.4, каждые 10 минут);
4. отметка истёкших записей (§7.5, раз в сутки).

Отдельного HTTP-маршрута для планировщика нет. Контейнер приложения `read_only`,
скрипт ничего не пишет на диск.

### 5.4. Исходящий клиент: EVO → ВАТС и сверка

Серверный модуль (только сервер, `server-only`):

- адрес — `EVO_PLATFORM_TELEPHONY_PBX_URL` (`https://evoadmitions.ats.beeline.kg/sys/crm_api.wcgp`),
  только `https`, хост из белого списка, редиректы не выполняются;
- тело — форма `application/x-www-form-urlencoded` с `cmd` и `token`
  (`EVO_PLATFORM_TELEPHONY_PBX_TOKEN`);
- таймауты: соединение 5 с, весь запрос 10 с; для чтений (`accounts`, `groups`,
  `history`, `get_dnd`) до двух повторов с отсрочкой;
- `makeCall` не повторяется автоматически: двойной звонок опаснее потерянного.
  Неоднозначный итог (таймаут) помечается «не подтверждён», пользователь видит
  «Проверьте телефон», а сверка по `history` потом находит звонок;
- ответы разбираются строго; 401 → в «Настройках» «Ключ ВАТС отклонён»;
  400 → код ошибки; в журнал идут correlation id, команда, статус, время,
  без токена, без номера (только последние 4 цифры);
- перед `makeCall`: проверка права, сопоставление пользователя, лимит
  (§6.5), идемпотентность по `request_id`.

Сверка (`history`, CSV): каждые 10 минут — период с перекрытием два часа; раз в
сутки — вчера. Столбцы `UID,type,client,account,via,start,wait,duration,record`:

- звонок, которого нет в EVO, добавляется с `created_via = 'reconcile'`;
- у существующего звонка заполняются `wait`, `talk_seconds`, `via`, ссылка на
  запись, если их не было; длительность из CSV считается точнее вебхука
  (см. §17, риск 8);
- задачи и лиды (§9) создаются по сверке только для звонков не старше двух
  часов, чтобы пропавший вебхук не породил лавину старых задач;
- число расхождений за сутки показывается в «Настройках» и входит в критерий
  выхода из фазы 1.

Соответствие `UID` из CSV и `callid` вебхука считается одинаковым по
документу, но подтверждается на первых настоящих звонках (§14, шаг 7); так же
подтверждается, совпадает ли ответ `makeCall` с `callid` последующих событий.
Если нет, исходящие связываются по паре (пользователь, номер, окно ±60 с).

Имена; значения в Git не попадают. Секреты бэкенда, не `NEXT_PUBLIC_*`.
Хранение: игнорируемый `/opt/evo-crm/.env.production` и SOPS-архив
(`Секреты и доступы ЭВО`; в реестре доступов строки «Beeline ВАТС» пока нет,
её добавляет владелец или агент при внесении ключа).

| Имя | Что | Формат |
|---|---|---|
| `EVO_PLATFORM_TELEPHONY_ENABLED` | выключатель приёма; открывает маршрут только при ровно `1` | `0` или `1` |
| `EVO_PLATFORM_TELEPHONY_CRM_TOKEN` | ключ, который EVO задаёт в кабинете ВАТС (`crm_token`) | 32–128 байт, печатные знаки, случайный |
| `EVO_PLATFORM_TELEPHONY_PBX_TOKEN` | ключ ВАТС для запросов EVO → ВАТС (`token`) | значение из кабинета |
| `EVO_PLATFORM_TELEPHONY_PBX_URL` | адрес `sys/crm_api.wcgp` тенанта | https-URL |
| `EVO_PLATFORM_TELEPHONY_PBX_HOST` | хост тенанта для проверки адресов ссылок на записи | `evoadmitions.ats.beeline.kg` |

Токены должны отличаться друг от друга и от каждого другого секрета EVO.

Если кабинет выдаёт один общий ключ вместо двух и тот же ключ используется
виджетом amoCRM, EVO не использует его без явного решения владельца и ответа
Beeline (§17, риск 1). Ротация: новое значение кладётся в env, приложение
пересоздаётся, затем меняется значение в кабинете, старое снимается.

Настройки, которые меняются без пересоздания приложения, хранятся в базе
(`telephony_settings`, право `telephony.manage`): рабочие часы, срок перезвона,
включатель проекции, включатели автоматики (§9), ответственный при отсутствии
владельца лида, суточный лимит звонков.

### 5.6. Подключение в кабинете ВАТС

Создаётся владельцем в день запуска в блоке «Ваша CRM» (отдельным разрешением):

- адрес приёма — п. 5.1; ключ — `EVO_PLATFORM_TELEPHONY_CRM_TOKEN`;
- события: `event` и `history`; маршрутизация звонка по CRM — **выключена**;
- подключение amoCRM не затрагивается; в фазе 2 для EVO включается
  «Ответственный менеджер из CRM» и маршрут переключается.

Если кабинет не позволяет два подключения, или смена ключа ломает виджет
amoCRM, запуск останавливается и возвращается к владельцу и Beeline (§17).

### 5.7. Edge Caddy

Маршрутизация менять не требуется: любой путь, которого нет в `@private`
блока `(evo_app)`, уже идёт на приложение, а закрывает его само приложение.
Новый путь в `@private` не добавляется, `/api/internal/*` не используется
(ВАТС в Docker-сеть не попадает). Перед включением приёма нужна
укрепляющая правка (отдельное «давай» владельца, только `caddy validate` и
`caddy reload`, без перезапуска общего edge; в живом файле блоки расходятся с
репозиторием, как описано в `docs/runbooks/whatsapp-go-live.md`, C5):

- для пути `/api/v2/telephony/beeline/inbound`: только `POST`, предел тела
  32 КиБ (`request_body`), при известных адресах Beeline — `remote_ip`;
- заголовки с секретами в приёме не используются, список удаления из журнала
  Caddy не расширяется; тело в журнал edge не попадает.

Правка записывается в репозиторный `Caddyfile.evo-edge` тем же PR, но живой файл
редактируется как в C5.

Для встроенного браузерного телефона (фаза 2, §8) edge уже отдаёт
`Permissions-Policy: microphone=(self)`; потребуется расширить `connect-src`
CSP адресом WSS. Сейчас CSP только в режиме Report-Only.

## 6. Модель данных

Все новые таблицы — `platform_private`, организация в каждой строке,
`ENABLE` и `FORCE ROW LEVEL SECURITY`, политик нет, права отозваны у `PUBLIC`,
`anon`, `authenticated`, `service_role`; доступ — только через SECURITY DEFINER
функции с `SET search_path = ''`. Приём — функции только для service role;
сотрудники — `platform.telephony_*_v1` для роли `authenticated` после проверки
права внутри базы (шаблон 268, 156, 062). Append-only таблицы защищены
`block_append_only_mutation`. Точный DDL — в срезе T1; здесь контракт.

### 6.1. Звонок (`telephony_calls`)

| Поле | Значение |
|---|---|
| `pbx_callid` | уникален в организации |
| `direction` | `in` / `out` |
| `state` | `ringing`, `answered`, `ended` |
| `outcome` | `answered`, `missed`, `cancelled`, `busy`, `unavailable`, `not_found`, `not_allowed` (из `status` итога) |
| `started_at`, `answered_at`, `ended_at` | UTC; из `start` и событий |
| `wait_seconds`, `talk_seconds` | из CSV `wait`/`duration`; до сверки — из вебхука |
| `client_phone` | нормализованный номер (E.164), персональные данные, наружу не отдаётся; сотрудники видят маску |
| `company_number` | `diversion`/`via` |
| `pbx_user`, `extension`, `group_name` | как пришли |
| `membership_id` | сотрудник по сопоставлению (может быть пусто: звонок на группу не принят) |
| `client_id`, `lead_id`, `match_state` | `matched`, `ambiguous`, `unmatched`, `created` |
| `result_code`, `result_by`, `result_at` | `reached`, `callback`, `not_interested`, `no_answer` (авто) |
| `recording_state` | `none`, `available`, `expired`, `unavailable` |

Статус вебхука `Cancel` у входящего считается пропущенным; `Success` с нулевой
длительностью — не отвечен.

### 6.2. Сопоставление с клиентом и лидом

`platform_private.telephony_match_phone(org, phone)` берёт ключи
`person_phone_match_keys(phone)` и ищет `platform.clients` по нормализованному
телефону:

- ровно один клиент → `matched`; лид — единственный открытый, иначе самый
  недавно обновлённый открытый; открытых нет — `lead_id` пуст, задача идёт
  последнему владельцу лида клиента, лид не создаётся (спорный случай, §18, 12);
- несколько клиентов → `ambiguous`: автоматической привязки нет, создаётся
  задача руководителю продаж «Проверить звонок», строка видна в отчёте как
  «без привязки»;
- ни одного → `unmatched`; при включённой автоматике (§9) создаётся клиент и
  лид `source_key = 'phone_call'` через `create_or_link_client` и
  `create_or_link_lead` (084), `match_state = created`.

Правило U2 канонической модели соблюдается: совпадение по одному телефону не
сливает клиентов, только прикрепляет запись звонка; создание нового клиента
по неизвестному номеру открывает кандидата в дубликаты как у других приёмников.
Внутренний звонок между сотрудниками (короткий `phone`: меньше 7 цифр или
совпал с внутренним номером) строки в `telephony_calls` не создаёт: считается
только счётчик в `telephony_runtime_state`, а в доказательстве номер пуст и
ссылка не сохраняется.

### 6.3. Сопоставление сотрудников (`telephony_extensions`)

Таблица: `pbx_user` (логин из `accounts.name`), `extension`, `pbx_display_name`
(как в ВАТС), `membership_id` (сотрудник EVO), `active`,
`last_seen_in_accounts_at`. Список приходит командой `accounts`, сотрудника
выбирает `admin` в «Настройки → Телефония». Пока пользователь не сопоставлен,
его звонки сохраняются без `membership_id`, а в «Настройках» горит счётчик
«не сопоставлено». ВАТС ограничена пятью пользователями; шестой сотрудник —
вопрос тарифа (§18).

### 6.4. Остальные таблицы

| Таблица | Назначение |
|---|---|
| `telephony_settings` | одна строка организации (§5.5): рабочие часы (по умолчанию пн–сб 10:00–20:00, `Asia/Bishkek`), срок перезвона (15 минут), `projection_enabled`, `missed_task_enabled`, `unknown_lead_enabled`, ответственный при пустом владельце, суточный лимит звонков (по умолчанию 400), каденс «Недозвона» |
| `telephony_dial_requests` | `request_id` (идемпотентность), сотрудник, лид, ответ ВАТС, статус; основа лимитов и аудита |
| `telephony_recording_grants` | выдача на прослушивание (§7): сотрудник, звонок, срок, лимит обращений, счётчик |
| `telephony_task_links` | связь системных задач со звонком; частичный уникальный индекс: одна открытая «Перезвонить» на лид и вид |
| `telephony_runtime_state` | времена последних запусков сверки, метки здоровья |

### 6.5. Телефония и деньги

`makeCall` стоит денег и может уйти на любой номер. Поэтому набор идёт только
по номеру, взятому на сервере из карточки клиента или лида, доступной
сотруднику; ручного набора в фазе 1 нет; лимит звонков на сотрудника в сутки
(по умолчанию 400, максимум общей нагрузки сейчас 187 в день на всю команду);
не более одного набора на сотрудника каждые 5 секунд; все наборы — в
`telephony_dial_requests` и журнале.

## 7. Записи разговоров: потоковый прокси

### 7.1. Принципы

- Копий нет: ни файлов, ни кэша, ни буфера дольше текущего запроса.
- Ссылка — секрет. Хранится только в `telephony_calls.recording_link`, не
  попадает в доказательство, журналы, ответы API, аналитику, выгрузки и в
  браузер. В `telephony_pbx_events` ссылка заменена признаком «была».
- Браузер получает только `GET /api/v3/telephony/recordings/<callId>` на нашем
  домене и тело `audio/mpeg`.

### 7.2. Путь запроса

1. Сессия сотрудника и право. Обработчик вызывает от имени сотрудника
   `platform.telephony_recording_grant_v1(call_id)`. В базе проверяются право
   (`telephony.recording.listen.all`, либо `…listen.own` и звонок, в котором
   участвовал сопоставленный с сотрудником пользователь ВАТС),
   `recording_state = 'available'`, лимит выдач (30 в час на сотрудника). RPC
   выдаёт разрешение со сроком 15 минут и числом обращений до 40 (аудио-плеер
   делает несколько Range-запросов) или возвращает действующее и пишет в
   `platform.audit_events` действие `telephony.recording.listen` (кто, звонок,
   когда).
2. Сервер вызывает функцию только для service role
   `telephony_recording_consume_v1(grant_id, membership_id)`: она проверяет срок,
   лимит и принадлежность и отдаёт ссылку серверу. Прямой вызов из браузера
   ссылку не вернёт: browser-вызываемая функция выдаёт лишь идентификатор
   разрешения (шаблон 062 `grant`/`consume`).
3. Проверка ссылки: `https`, хост ровно равен `EVO_PLATFORM_TELEPHONY_PBX_HOST`,
   путь по строгому шаблону (уточняется по настоящим ссылкам в T6), без
   редиректов, без обращения к частным адресам — защита от подмены ссылки через
   украденный токен ВАТС (SSRF).
4. Запрос к Beeline: `GET` без cookie и заголовков сотрудника, `Range`
   передаётся только если это одиночный `bytes=…`; таймауты: соединение 5 с,
   заголовки 10 с, простой 15 с, лимит 25 МиБ; отмена клиента отменяет запрос к
   Beeline.
5. Ответ: статус 200/206 как у источника; заголовки только из белого списка:
   `Content-Type: audio/mpeg`, `Accept-Ranges: bytes`, `Content-Range`,
   `Content-Length`; добавляются `Cache-Control: private, no-store, no-transform`,
   `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
   `Content-Disposition: inline`. Тело передаётся потоком без буферизации
   (`no-transform` защищает от сжатия edge).
6. Если источник игнорирует `Range` (200 вместо 206): запись целиком
   (до 8 МиБ, это больше часа разговора) буферизуется в памяти запроса и
   отдаётся срезом; больше — 502. Поведение источника проверяется в T6 на
   настоящей записи.

### 7.3. Ошибки

| Источник | Браузер | Действие |
|---|---|---|
| 404 или 410 | 410 | `recording_state = 'expired'`, ссылка обнуляется; в карточке «запись удалена по сроку хранения» |
| 5xx, таймаут, сеть | 502 | «Запись временно недоступна»; состояние не меняется |
| нет права | 403 | без причины и без раскрытия существования записи |
| звонок не найден или нет записи | 404 | — |

### 7.4. Что видит сотрудник

В строке звонка в «Ленте» лида: значок, время, длительность, кто говорил и
кнопка «Слушать» (`<audio controls preload="none">`, без автозагрузки). Для
чужого звонка менеджеру кнопки нет, подпись «Запись доступна руководителю».
Кнопка «скачать» убрана из плеера, но это лишь удобство: человек с правом
слушать может записать звук; риск принят, прослушивание пишется в журнал.

### 7.5. Срок хранения у Beeline

Срок по условиям платформы — год. Когда `started_at + 365 дней` прошло, фоновая
отметка (§5.3) ставит `recording_state = 'expired'` и обнуляет ссылку, даже
если никто не открывал карточку. Остальные метаданные звонка остаются. Из этого
следует прямое последствие решения 3: записи старше года и записи, удалённые
у Beeline до запуска, потеряны для EVO навсегда. По оценке,
удаление записей текущего тенанта начинается около 28.10.2026: к концу ноября
2026 уйдёт около 690 записей, дальше порядка 1,4–1,8 тыс. в месяц. Решение
«сохранить» один важный звонок — позже, после юридического решения; оно не
вернёт уже удалённые записи.

## 8. Звонок из CRM: софтфон, WebRTC и запасные пути

### 8.1. Что установлено

- `makeCall` не набирает номер сам: ВАТС звонит сотруднику на его
  устройство(а) и после ответа соединяет с клиентом (документ REST API).
  Сотрудник должен иметь зарегистрированное и доступное устройство.
- У четырёх менеджеров и директора нет корпоративных SIM и личных номеров в
  ВАТС. Сегодня «устройство» — вкладка amoCRM с виджетом: по публичной вики
  платформы WebRTC запускается внутри виджета; вкладка закрыта — статус «Не в
  сети». Для сторонней CRM в REST API нет ни WebRTC, ни учётных данных SIP/WSS.
- Другие устройства платформы (вики того же вендора, тенант Moldcell; для
  Beeline KG подтверждается): настольное приложение «Коммуникатор» (Windows 10+,
  macOS 13+, вход логином сотрудника и паролем); мобильное приложение
  (iOS/Android, вход логином или QR; в описании приложения Beeline KG в App
  Store упомянуты звонки из приложения); настольные SIP-телефоны и сторонние
  SIP-клиенты (UDP/TCP 5060, RTP UDP 10000–65535, G.711 предпочтительно).
- Встроенный в браузер телефон EVO на JsSIP/SIP.js требует адрес WSS и
  SIP-учётки на сотрудника. Публично этого нет. Возможность и условия — вопрос
  Beeline/ITooLabs.
- Не проверено: звонит ли `makeCall` во вкладку amoCRM с виджетом, в
  «Коммуникатор», в мобильное приложение; поддерживает ли тенант Beeline KG те
  же приложения. Это проверяется настоящими звонками (S2, §8.3).

### 8.2. Варианты

| Вариант | Работает без новых данных от Beeline | Что нужно | Замечания |
|---|---|---|---|
| A. «Позвонить» → `makeCall` на устройство менеджера (вкладка amoCRM, «Коммуникатор» или приложение) | да, если устройство звонит по `makeCall` (S2) | менеджер и устройство сопоставлены | В фазе 1 основной путь. Пока вкладка amoCRM открыта, она остаётся телефоном |
| B. «Коммуникатор» | да | установка на компьютер, наушники | Для фазы 2 без WebRTC EVO; нужен компьютер Windows/macOS |
| C. Мобильное приложение ВАТС | да | телефон менеджера, вход по QR | Удобно для встреч и выездов |
| D. SIP-клиент/настольный телефон | да | SIP-данные, порты | Не в браузере |
| E. Встроенный в EVO WebRTC | нет | WSS-адрес, SIP-учётки, ответ вендора; правка CSP `connect-src` | Лучший сценарий фазы 2: ответ и сброс в карточке; оценка работы 2–3 недели после ответа Beeline; вкладка должна оставаться открытой, как у amoCRM |
| F. amoCRM только как телефон | да | оставить виджет WebRTC на 5 мест | Запасной путь, если E недоступен, а B/C не подходят; amoCRM не отключается полностью |

### 8.3. Точка решения G-SP

До выхода из фазы 1 (не до её начала): S2 (шаг 8 в §14) — один настоящий `makeCall` с
открытой вкладкой amoCRM, затем с «Коммуникатором» и мобильным приложением
(владелец рядом, 30 минут, звонок на номер владельца); письмо Beeline с
вопросом про WSS/SIP для WebRTC в своей CRM. Рекомендация по умолчанию:
если E доступен — строить E; иначе B для сидящих за компьютером и C для
остальных; F — последний запас. Фаза 1 с вариантом A полезна уже сейчас и не
зависит от решения.

Если у сотрудника нет доступного устройства, `makeCall` вернёт ошибку или
не дозвонится до менеджера; в EVO сотрудник увидит: «Не удалось позвонить:
откройте приложение ВАТС». Клиенту при этом не звонят.

## 9. Пропущенные, неизвестные номера, результат

### 9.1. Включатели

Автоматика не должна создавать работу, которую команда не видит: продажи пока
работают в amoCRM. Поэтому есть два включателя в `telephony_settings`:
`missed_task_enabled` (§9.2, §9.4) и `unknown_lead_enabled` (§9.3), по
умолчанию выключены. Журнал звонков, лента, воспроизведение, отчёт работают
сразу. Включатели включаются после недели сверки (§14, шаг 9) с отдельного
«да» владельца (шаг 10).

### 9.2. Пропущенный входящий → «Перезвонить»

Условия: `direction = in`, `outcome` — пропущен или отменён,
включён `missed_task_enabled`.

- Ответственный: владелец лида; иначе сотрудник, названный в настройках как
  руководитель продаж; иначе администратор.
- Срок — 15 рабочих минут: часы идут только внутри рабочего времени (по
  умолчанию пн–сб 10:00–20:00 Бишкек). Пропущено в 19:55 — срок завтра 10:10;
  пропущено в 03:00 — срок 10:15.
- Задача создаётся функцией, как `ai_autosend_call_tasks` (275): от имени
  системы, привязана к лиду и клиенту, видна в «Задачи» и «Сегодня» (источник
  `tasks` уже входит в очередь «Сегодня»).
- Одна открытая «Перезвонить» на лид и вид: повторные пропущенные не плодят
  задач, а увеличивают счётчик в её тексте.
- Автозакрытие: позже состоялся звонок на этот клиентский номер с
  `talk_seconds > 0` (отвеченный входящий или исходящий) — задача закрывается
  системой с ссылкой на звонок. Неотвеченная попытка исходящего не закрывает.
- Если звонок сопоставлен неоднозначно (`ambiguous`): задача руководителю
  продаж «Проверить звонок».
- Сверка (§5.4) создаёт задачу только для звонков не старше двух часов.

### 9.3. Неизвестный номер → лид «Звонок»

Условия: `match_state = unmatched`, `direction = in`,
включён `unknown_lead_enabled`. Создаётся клиент и лид через `create_or_link_*`
со `source_key = 'phone_call'`, этап `new`, без владельца, источник канала
«Откуда узнал» — `unknown` (подсказка «Спросите клиента» остаётся). Дальше
лид попадает в «Заявки» как «ждёт разбора».

Лид создаётся и для отвеченного, и для пропущенного звонка с неизвестного
номера. Для пропущенного дополнительно создаётся задача «Перезвонить»
руководителю продаж (владельца ещё нет). Повторный звонок того же номера
прикрепляется к созданному лиду, а не создаёт нового.

Нужна новая версия очереди: `staff_requests_queue_v2` берёт лиды только
`website` и `whatsapp`. Срез T9 добавляет `staff_requests_queue_v3` и вкладку
«Звонки» (`REQUEST_SOURCE_FILTERS`, `RequestLeadRow.source`, версия курсора),
а старая версия снимается по правилу replace-not-layer.

Исходящий звонок на неизвестный номер лид не создаёт: набор в фазе 1
возможен только по номеру из карточки.

### 9.4. Результат звонка

После отвеченного звонка в карточке лида (и в «Сегодня» для открытой задачи)
показывается строка из трёх кнопок одним нажатием:

| Кнопка | Что записывается |
|---|---|
| «Дозвонился» | `result_code = reached`. Следующий шаг сотрудник выбирает как сейчас на доске. Если шага нет, лид попадает в полосу «без шага» очереди «Сегодня» (существующее поведение) |
| «Перезвонить» + дата | `result_code = callback`; задача «Перезвонить» на выбранную дату (по умолчанию завтра 10:00); открытая системная «Перезвонить» заменяется |
| «Не интересно» | `result_code = not_interested`; открытая «Перезвонить» закрывается. Лид автоматически не закрывается (закрытие — отдельное действие с причиной, §18, 6) |

«Недозвон» ставит система: исходящий звонок завершён без ответа (`Missed`,
`Busy`, `NotAvailable`, `NotFound`, `Cancel`). Следующий шаг: задача
«Перезвонить» по каденсу `telephony_settings` (по умолчанию: +2 рабочих часа,
затем следующий рабочий день 11:00, затем +2 рабочих дня), одна открытая на
лид; после пяти недозвонов за семь дней руководителю продаж уходит подсказка
(не закрытие). Нажатие результата можно изменить в течение суток.

В amoCRM поле результата не заполнялось ни разу (0 %). Чтобы в EVO этого не
повторилось, строка результата стоит прямо под звонком, без модального окна,
а процент звонков с результатом — одна из строк отчёта (§10).

## 10. Отчёт по звонкам

Место: «Отчёт продаж» (`/v3/main?view=sales`), блок «Звонки», за выбранный
период, часовой пояс Бишкек. Права `telephony.report.read.own` и `.all` (§11).
Данные — функция `platform.telephony_report_v1(from, to)`; внутренние звонки не
учитываются (они не хранятся).

| Показатель | Определение |
|---|---|
| Звонки | число клиентских звонков менеджера (входящие + исходящие), разбивка по направлению |
| Доля отвеченных | отвеченные / все; отдельно исходящие и входящие |
| Время разговора | сумма `talk_seconds`; в часах и минутах; среднее на отвеченный |
| До первого звонка по новому лиду | для лидов, созданных в периоде: от `leads.created_at` до начала первого исходящего звонка любого сотрудника; также до первого отвеченного; медиана и доля уложившихся в 15 минут рабочего времени |
| Пропущенные без перезвона | входящие пропущенные, после которых нет отвеченного звонка на этот номер до конца следующего рабочего дня; число и список без привязки. Отдельно: перезвонили позже срока (15 рабочих минут) |
| Результат проставлен | доля отвеченных звонков с кнопкой результата |

Менеджер с правом `.own` видит только свои цифры, руководитель и admin —
всех. Выгрузка CSV — позже.

## 11. Права

Новые определения в `platform.permission_definitions`, миграция 288 по
шаблону 268 (определения, новая неизменяемая версия bundle подходящих ролей,
перепривязка, `staff_bump_memberships`, проверка в конце, `NOTICE` с числом
сотрудников без права). Состав и области ролей сверяются чтением production
перед написанием миграции: в этом документе они не проверялись.

Все ключи — уровня организации (`staff_resource_kinds = {organization}`,
`staff_scope_kinds = {organization}`, не системные, не чувствительные, группа
«Телефония»), как `ai.agent.*` в 268. Различие «свои» и «все» делает не область
права, а сама функция в базе по `membership_id` звонка. Так не нужно расширять
`staff_access_evaluate` новым видом ресурса и не возникает конфликт областей
при публикации роли.

| Право | Что открывает | По умолчанию |
|---|---|---|
| `telephony.call.dial` | кнопка «Позвонить», результат звонка | продажи, руководитель продаж, admin |
| `telephony.recording.listen.own` | слушать записи звонков, в которых участвовал сам сотрудник | менеджеры |
| `telephony.recording.listen.all` | слушать любую запись | директор, руководитель продаж, admin |
| `telephony.report.read.own` | блок «Звонки» отчёта, только свои цифры | менеджеры |
| `telephony.report.read.all` | блок «Звонки» отчёта по всем | руководитель продаж, admin |
| `telephony.manage` | «Настройки → Телефония»: сопоставление, часы, включатели, здоровье | admin |

Видимость строки звонка в ленте лида следует `lead.read` по лиду, как у
заметок и переписки (решение владельца 06.10 «нет, все могут»); ограничены
только прослушивание и отчёт (решение 3).

Опубликованный bundle неизменяем (041): если у роли продаж с областью
`own`/`department` нельзя добавить ключ уровня организации (`staff_roles_publish_scope_conflict`),
как в 268, срез T2 выбирает один из двух путей и записывает выбор в
`PLAN_CHANGES.md`: ключи получают роли «… — общие разделы», которые уже
есть у всех сотрудников, либо создаётся роль «Телефония». Решение зависит от
фактического состава ролей и принимается по чтению production.

Маршруты и права: `src/lib/platform-access.ts` (`CAPABILITY_PERMISSIONS`,
`staffCanAccessRoute`) и `src/lib/fixed-role-policy.ts` для новых страниц;
тест `tests/fixed-role-route-contract.test.mjs`. Каждый RPC повторяет право
сам; клиент не решает.

Аудит: `platform.audit_events` — прослушивание (`telephony.recording.listen`),
набор (`telephony.dial`), результат (`telephony.result.set`), правка настроек,
сопоставление. Чтобы прослушивание и набор были видны в «Журнале действий»,
миграция 288 расширяет allowlist приёмом rename-and-union (255). Автоматические
события приёма в журнал не идут (как `work.*` и `communication.webhook.persist`).

Название переменных в коде не использует `phone` как источник сообщения
WhatsApp (`WhatsAppMessageOrigin.phone` уже занято смыслом «с телефона
отправлено»); для звонков — `call`, `pbx`.

## 13. Приватность и юридическое

Не юридическая консультация. Источник — публичная заметка ICNL о Цифровом
кодексе КР (февраль 2026) и вывод разведки 16.10.

- Голос и номер телефона — персональные данные. Цифровой кодекс КР
  (по заметке ICNL, действует с 05.02.2026) требует законного основания и, при согласии,
  осознанного, конкретного и доказуемого согласия; трансграничная передача —
  отдельные условия. Данные ВАТС и их хостинг не уточнены (вопрос Beeline).
- Уведомление о записи включено владельцем в ВАТС. Владелец проверяет, что
  уведомление звучит на обоих языках, которыми говорят клиенты, и входит в
  сценарий **до** запуска (включая вызовы, на которые отвечает группа).
- В политике конфиденциальности сайта нужна строка о записи звонков и
  обработке номера: PR в `evoadmissions-website`, только после «да»
  владельца и вычитки юристом КР (вопрос 9).
- EVO не хранит звук, но хранит номер, время, длительность, имя сотрудника и
  результат: это метаданные клиента того же класса, что переписка WhatsApp.
  Срок хранения метаданных звонка — срок хранения клиента (DEC-012 остаётся
  открытым); доказательства приёма — не дольше 12 месяцев (очистка отдельной
  контролируемой функцией в T11, пока её нет — не очищаются).
- Передача звука через сервер EVO при воспроизведении — транзит без записи;
  вопрос юристу: считать ли транзит трансграничной обработкой (место VPS и
  регион Supabase).
- Ни в Git, ни в чат, ни в журналы: токены, ссылки на записи, полные номера
  клиентов, имена сотрудников и клиентов. В журналах — последние 4 цифры.
- Маска номера в интерфейсе и серверное разрешение номера для набора
  (никто из менеджеров не видит полный номер в EVO) — защита от выноса базы;
  в amoCRM есть похожая настройка скрытия номеров.
- Права слушать — только по §11, каждое прослушивание в журнале.
- ИИ (позже): отправка звука или расшифровки в Gemini требует отдельного
  согласия и решения владельца (ADR 0032, согласие Q4 относится к тексту
  чатов); в фазе 1 звук в ИИ не уходит.

## 14. Порядок выпуска

Правило проекта: ledger → приложение → подключение ВАТС → настоящий звонок.
Релиз не идёт во время чужого релиза; слияние в `main` во время выката срывает
выкат (согласовать с координатором).

| Шаг | Кто | Что | Готово, когда |
|---|---|---|---|
| 1 | агент | Срезы T1–T12, независимое review каждого по точному head, короткие PR-checks | PR слиты |
| 2 | держатель authority | `evo-schema-ledger.yml` `mode=check`, затем `mode=apply` по порядку номеров | ledger production совпадает с репозиторием |
| 3 | держатель authority | Выпуск приложения «exact-main» с `EVO_PLATFORM_TELEPHONY_ENABLED=0` (маршрут отвечает 503) | проверка выпуска, маршрут 503, лента лида без звонков |
| 4 | владелец/агент | Ключи в `.env.production` и SOPS: `EVO_PLATFORM_TELEPHONY_CRM_TOKEN`, `…_PBX_TOKEN`, URL, хост (значения не показываются) | `settings-health`: «Ключ задан» |
| 5 | владелец (отдельное «давай») | Укрепление edge (§5.7), `caddy validate` и `caddy reload` | внешняя проба: без токена 401, чужой метод 405, большое тело 413 |
| 6 | держатель authority | `ENABLED=1` через штатное пересоздание приложения; `projection_enabled = false` (только доказательства) | маршрут отвечает 401 на пустой запрос |
| 7 (S1, наблюдение) | владелец | Подключение в кабинете ВАТС (§5.6); один настоящий исходящий и один входящий звонок | в «Настройках» видны события; формат тела, `callid`/`UID`, `duration`, реакция на пустой `contact` проверены по очищенным доказательствам; парсер исправлен |
| 8 (S2, устройства) | агент + владелец | `projection_enabled = true`; настоящий `makeCall` на вкладку amoCRM, «Коммуникатор» и мобильное приложение (§8.3), письмо Beeline отправлено; матрица приёмки §15 | записано, какие устройства звонят; все строки матрицы пройдены |
| 9 | агент + владелец | Неделя сверки при выключенной автоматике: число звонков EVO против `history` ВАТС и против агрегатов amoCRM (только чтение) | расхождение объяснено |
| 10 | владелец («да») | Включить `missed_task_enabled` и `unknown_lead_enabled` | задачи и лиды появляются по правилам §9 |

Откат: подключение выключается в кабинете ВАТС (владелец) или
`ENABLED=0` (пересоздание); `projection_enabled = false` приостанавливает
разбор; автоматика выключается в настройках. amoCRM всё это время работает
и не затрагивается; накопленные данные остаются.

Правила проекта сохраняются: релиз не меняет настройки провайдера, не пишет
клиентские данные и не отправляет сообщений; успех телефонии заявляется только
после настоящего звонка (`AGENTS.md`).

## 15. Приёмка (настоящие звонки)

Приёмка — на настоящих звонках по настоящему тенанту. Номера: телефон
владельца как «клиент» и сопоставленные пользователи ВАТС как менеджеры.
Имитация вебхука curl'ом, юнит-тесты и локальные стенды — рабочие проверки
разработчика, но не приёмка.

| № | Проверка | Ожидание |
|---|---|---|
| 1 | Приём закрыт | без токена и с неверным токеном 401; при `ENABLED=0` 503; метод GET 405; тело больше 32 КиБ 413; публичный `POST /api/webhooks/telephony` и `/calls` — 404 |
| 2 | Исходящий отвеченный из amoCRM (WebRTC) на телефон владельца | в EVO одна строка звонка: направление, сотрудник, время, длительность близки к `history`, `talk_seconds` из сверки |
| 3 | Входящий отвеченный на `+996 770 40-70-30` | маршрут прежний (ответственный из amoCRM), в EVO строка с клиентом |
| 4 | Входящий пропущенный | пропущенный записан; при включённой автоматике: задача «Перезвонить» ответственному, срок = 15 рабочих минут; вне часов — срок следующего утра |
| 5 | Затем отвеченный звонок на тот же номер | задача закрыта системой со ссылкой на звонок |
| 6 | Неизвестный номер (второй номер владельца) | при включённой автоматике: клиент и лид `phone_call` в «Заявках», вкладка «Звонки» |
| 7 | Запись | менеджер слушает свой звонок; чужой — кнопки нет, прямой запрос 403; руководитель слушает любой; перемотка работает (Range); в журнале по записи на каждое начало прослушивания; DevTools: ни одного запроса на хост Beeline из браузера |
| 8 | Запись, удалённая у Beeline | технический QA по разрешению владельца: тестовая строка звонка с помеченной ссылкой на хост своего тенанта и несуществующим номером записи (удаляется после проверки); 404 приходит настоящий от Beeline; карточка «запись удалена по сроку хранения», ссылка обнулена. Это не приёмка провайдера |
| 9 | «Позвонить» из карточки | `makeCall` звонит на выбранное устройство; после ответа соединяет с телефоном владельца; строка звонка в ленте появляется из событий; повторный клик в течение 5 с не звонит второй раз |
| 10 | Результат одним тапом | три кнопки пишут `reached`/`callback`/`not_interested`; «Перезвонить» создаёт задачу на дату |
| 11 | Исходящий без ответа (телефон владельца не берёт трубку) | «Недозвон», задача по каденсу |
| 12 | Потеря вебхука | владелец на время одного настоящего звонка отключает подключение в кабинете ВАТС (или `ENABLED=0`), затем возвращает: сверка по `history` добавляет звонок в течение 10 минут (`created_via = reconcile`), задача по старому звонку не создаётся |
| 13 | Отчёт | цифры совпадают с `history` ВАТС за те же сутки в пределах разницы тестовых звонков |
| 14 | Права | менеджер без права видит ленту и не видит отчёт руководителя; чужие цифры — нет |
| 15 | Неверный ключ ВАТС | подмена `…_PBX_TOKEN` в тесте ведёт к «ВАТС отклонила ключ» в «Настройках»; `makeCall` не уходит |

Что не считается приёмкой: любые проверки на подставных данных; отсутствие
ошибок в журналах; один health check.

Точечные проверки на срез (AGENTS «Fast Execution And Validation»): тесты SQL
отказов (RLS-запрет всех ролей, идемпотентность приёма, область `own` и
`organization`, срок и лимит выдачи, неоднозначное сопоставление),
контрактные тесты маршрутов (старые пути остаются скрытым 404, новые пути в списках),
проверка маски номера. Полный набор не запускается автоматически.

## 18. Вопросы владельцу

Работа идёт с решением по умолчанию; ответ заменяет его.

1. **Рабочее время и срок.** По умолчанию: пн–сб 10:00–20:00 Бишкек, срок
   перезвона 15 рабочих минут (по профилю звонков amoCRM; воскресенье почти не
   работает).
2. **Кто руководитель продаж.** Получает пропущенные без владельца и подсказки
   по недозвонам, слушает все записи. По умолчанию: директор (admin) до
   назначения; в EVO нет отдельной роли с таким названием, поэтому назначается
   в «Настройки → Телефония».
3. **Письмо Beeline** (одним сообщением, от владельца): (а) подключение «Ваша
   CRM» — один ключ или два, не ломает ли виджет amoCRM; (б) адреса источника
   вебхуков и нужно ли разрешать адрес VPS; (в) лимиты, повторы, таймаут;
   (г) WSS-адрес и SIP-учётки для WebRTC в своей CRM; (д) звонит ли `makeCall`
   в «Коммуникатор» и мобильное приложение тенанта; (е) тариф: API, шестой
   пользователь, хранение записей; (ж) где хранятся записи.
4. **Внутренние звонки** (запись включена владельцем). По умолчанию: EVO их
   не хранит, считает только число.
5. **Звонки существующих студентов и родителей.** По умолчанию: ответственный —
   владелец лида клиента, иначе руководитель продаж, не куратор дела.
6. **«Не интересно».** По умолчанию: только запись результата и закрытие
   открытой «Перезвонить»; лид закрывается вручную с причиной.
7. **Каденс «Недозвона».** По умолчанию: +2 рабочих часа, затем следующий
   рабочий день 11:00, затем +2 рабочих дня; после пяти недозвонов за
   семь дней подсказка руководителю.
8. **Когда включать автоматику.** По умолчанию: после недели сверки и только
   когда команда реально ведёт лидов в EVO; решение «да» даёт владелец.
9. **Юрист КР.** Запись и транзит, строка в политике сайта, формулировка
   уведомления о записи на русском и кыргызском.
10. **Перенос метаданных за год** (только для клиентов, которые уже в EVO). По
    умолчанию: да, в T11; записи не переносятся.
11. **Устройства менеджеров** (компьютеры Windows/macOS, телефоны, наушники) —
    для выбора варианта §8 (B/C/E).
12. **Известный клиент без открытого лида позвонил.** По умолчанию: задача
    последнему владельцу, новый лид не создаётся.
13. **Wazzup и WAHA.** Владелец: Wazzup остаётся как есть, WAHA позже. Когда
    начинать — отдельное решение; телефония от этого не зависит.
