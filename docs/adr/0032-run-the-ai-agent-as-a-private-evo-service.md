# 0032 — ИИ-агент как приватный сервис EVO рядом с CRM

- Статус: принято 2026-10-06 (решение владельца Q1 «B»). Контракт —
  [план «ИИ-агент»](../EVO_AI_AGENT_PLAN_2026-10-06.md).
- Владелец решения: владелец продукта EVO.
- Частично заменяет: ADR 0021 «One human-reviewed Gemini Flash adapter» в
  части места адаптера (теперь это отдельный сервис, а не код Next) и
  жёсткого `gemini-3.7-flash`. ID моделей становятся данными настроек, по
  одному явному ID на назначение.
- Сохраняет: одну Платформу и один Supabase (0020, 0024, 0027); дневной режим
  0021 (ИИ только готовит черновик, решение и отправка — сотрудник; нет
  второго провайдера; отказ провайдера — честное «недоступно»);
  replace-not-layer.
- Ночная автоотправка — [ADR 0031](0031-allow-bounded-night-whatsapp-autoreply.md).

## Контекст

У владельца есть свой продукт SoodaCloser (приватный репозиторий, Python,
свой Supabase), в котором сделано почти всё, что нужно разделу «ИИ-агент»:
помощь с ответом и источниками, двойной OCR, Лаборатория, журнал расходов,
автоотправка. Переписывать его на TypeScript в CRM — 9–13 агентских недель.
Запустить его как есть нельзя:

- вторая авторизация;
- персональные данные EVO в чужом Supabase;
- доступ к БД, рассчитанный на отдельный проект, а не на границы
  Платформы EVO;
- второй канал WAHA;
- связь между проектами на VPS.

Публичный репозиторий `evo_AI_CRM` не может хранить приватный код
SoodaCloser.

## Решение

1. **Сервис.** Приватный репозиторий `izzhackt/evo-ai-agent`: форк движка
   SoodaCloser, Python. Две службы — `ai-agent-api` и `ai-agent-worker` — в
   compose-проекте `evo-crm`, только в сети `evo_crm_private`, без портов
   наружу и без доступа к WAHA. Образ берётся из приватного GHCR только по
   digest (`EVO_AI_AGENT_IMAGE_DIGEST`); release controller проверяет и
   откатывает его так же, как digest WAHA.
2. **Данные.** Только в Supabase EVO: таблицы `platform_private.ai_*`, RLS
   включён без политик, права отозваны. Сотрудники работают через
   `platform.ai_agent_*_v1` (SECURITY DEFINER, проверка права и доступа к
   диалогу). Сервис подключается отдельной ролью `evo_ai_agent` (NOINHERIT,
   без BYPASSRLS). Ей разрешён только `EXECUTE` на функции схемы
   `platform_ai_agent`, без прав на таблицы, Storage, Auth и pgmq.
   Подключение через Supavisor, у роли свой пул. Пароль задаётся вне Git.
   Интерактивные функции роли отдают диалог только по погашенному билету.
   Фоновые функции (память, подготовка заранее, автоответчик) работают
   только при включённой своей настройке и только с диалогами очереди
   продаж; это проверяет БД (план, §5.3). «Базу знаний» роль не читает:
   копирование страниц делает admin через `platform.ai_agent_seed_from_kb_v1`
   из закрытого списка (план, §14).
3. **Связь с CRM.** Браузер говорит только с CRM. CRM получает в БД
   одноразовый билет от имени сотрудника (`auth.uid()`, право и доступ к
   диалогу, срок 60 с) и вызывает сервис по внутренней сети с
   HMAC-подписью. Сервис погашает билет. Файлы сервис читает и пишет через
   внутренний брокер CRM, который ограничен bucket агента. Серверный ключ
   Supabase и ключ WAHA остаются только у CRM.
4. **Публичный репозиторий.** Здесь только UI, тонкие маршруты, миграции,
   SQL-тесты, compose и поддержка выпуска. Ни кода движка, ни промптов
   SoodaCloser.
5. **Провайдер.** Только Google Gemini, платный проект EVO с billing и
   месячным лимитом (Q4). Перед первым вызовом в системе записывается
   согласие владельца на передачу текстов клиентов в Gemini. В промпт не
   передаются телефоны, email, документы и вложения клиентов.
   Explicit caching, Files API и grounding не используются.
6. **Внутренние документы.** Лимиты скидок, маржа и правила согласования
   влияют на черновик сотрудника и объясняются ему, но клиенту не
   цитируются никогда; есть проверка утечки после генерации.
   - Это уточнение правила AGENTS «клиентский ИИ использует только
     утверждённую клиентскую базу». Черновик, который проверяет и отправляет
     сотрудник, клиентским ИИ не считается.
   - Проверка утечки смотрит и на текст «Правил общения»: его начальная
     версия собрана и из внутренней страницы.
   - Ночной автоответчик (0031) использует только документы для клиентов,
     отдельно разрешённые для него.
7. **Прежние поколения ИИ.** Сервис заменяет staff-assistant API и UI
   «Подготовить черновик». Их код удаляется в P1. Таблицы 030, 054, 065–067,
   075 и 091 не удаляются: на 065 и 067 ссылаются живые функции WhatsApp и
   read-model входящих.

## Последствия

- Движок переносится как есть и проверен в SoodaCloser. Остаётся переписать
  хранение на RPC EVO и собрать новый набор вопросов для оценки.
- Появляется второй runtime (Python) с отдельным образом, digest и
  секретами. Выпуск и откат CRM учитывают его.
- Авторизация остаётся в Postgres. Взлом сервиса ограничен функциями
  агента. Интерактивно без свежего билета сотрудника он диалогов не читает.
  Фоновые функции читают диалоги очереди продаж без билета, но только пока
  включена память, подготовка заранее или автоответчик. Пока они выключены
  (так в P1), взломанный сервис не получает ни одного диалога. При
  включённом живом автоответчике он может отправить текст, прошедший
  проверки БД; ущерб ограничивают лимиты ADR 0031.
- Исправления в SoodaCloser и EVO нужно переносить вручную; модули без БД
  держим близкими к оригиналу.
- Права EVO на форк приватного продукта владельца подтверждает владелец.
