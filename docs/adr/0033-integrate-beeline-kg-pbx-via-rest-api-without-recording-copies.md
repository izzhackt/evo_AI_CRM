# 0033 — Телефония: Beeline KG ВАТС через REST API, записи без копий

- Статус: принято 2026-10-16 (решения владельца 1–8 того же дня; поправки
  после независимого review 16.10 — в том же ADR до слияния). Контракт —
  [план телефонии, фаза 1](../EVO_TELEPHONY_PLAN_2026-10-16.md).
- Владелец решения: владелец продукта EVO.
- Заменяет: DEC-019 «Deferred» в `docs/specs/EVO_PLATFORM_TZ.md` **только в
  части телефонии** (платёжный шлюз, email-провайдер и подача в вуз остаются
  отложенными) и отсрочку DA-04 в бэклоге для телефонии. Тексты спецификации и
  бэклога не переписываются (append-only): поправкой служат этот ADR и запись
  в `docs/PLAN_CHANGES.md` от 2026-10-16.
- Выполняет, не отменяет: INT-018 (провайдер не показывается как рабочий без
  contract и acceptance). Contract — план, acceptance — §15 плана на настоящих
  звонках.
- Сохраняет: одну Платформу и один Supabase (0020, 0024, 0027); решение
  владельца 2026-08-09 не копировать сырые записи без юридического решения
  (теперь закреплено как правило); приватность WAHA и lead-agent; скрытый 404
  старых маршрутов `/calls` и `/api/webhooks/telephony` (P6B). Не затрагивает
  ADR 0018 и 0019 об amoCRM: перенос продаж из amoCRM шире телефонии и
  оформляется отдельно, здесь только телефония.

## Контекст

EVO звонит клиентам через «Виртуальную АТС Beeline Бизнес» (Beeline
Kyrgyzstan), тенант `evoadmitions.ats.beeline.kg`: пять пользователей, один
номер компании, запись разговоров включена, хранение один год. Менеджеры
звонят из WebRTC-виджета amoCRM. С апреля 2025 в amoCRM записано 30 673
звонка (91 % исходящие), поле результата не заполнено ни разу, больше половины
входящих остаётся без ответа.

В CRM EVO телефонии нет: старый вебхук и страница звонков удалены 04.09.2026
(P6B) без преемника, спецификация откладывает телефонию (DEC-019). Владелец
16.10.2026 поставил цель перенести продажи из amoCRM в CRM EVO в два шага:
сначала параллельно, затем переключить маршрутизацию и всплывающую карточку.

Факты платформы ВАТС (проверено чтением 16.10):

- Тенант отдаёт публичный PDF «REST API Облачной АТС»: двусторонний HTTPS-обмен
  с общим ключом в теле запроса (`token` к ВАТС, `crm_token` к CRM), без
  подписи сообщений. ВАТС шлёт `event`, `history` (с ссылкой на запись) и
  синхронный `contact`; CRM может вызывать `makeCall`, `accounts`, `groups`,
  `history` (CSV) и другие команды. Лимиты, повторы, таймаут и кодировка
  тела не описаны. `callid` общий для всех связанных ног звонка (группа,
  перевод); `duration` вебхука — общая длительность, `duration` CSV — время
  разговора.
- В кабинете блок «Ваша CRM» допускает несколько подключений по REST API, то
  есть EVO можно подключить параллельно amoCRM. По форме на вики вендора
  (тенант Moldcell, для Beeline KG подтверждается) `history`, `event` и
  `contact` (имя звонящего) у подключения «всегда подключены»; опционален
  только маршрут «на ответственных менеджеров из CRM». Значит, каждый входящий
  вызывает синхронный `contact` к EVO, и поведение ВАТС при сбое EVO неизвестно.
- Ссылка на запись — URL MP3 без подписи: любой владелец ссылки слушает запись.
  Записи удаляются у Beeline примерно через год; первые удаления с текущего
  тенанта ожидаются около 28.10.2026. На вики вендора администратору ВАТС
  доступна выгрузка записей по FTP (для Beeline KG не подтверждено).
- У каждого сотрудника ВАТС есть SIP-логин и пароль (необязательный отдельный
  SIP-пароль), устройства сотрудника работают параллельно и шестого места не
  требуют; REST API их не отдаёт. WebRTC-виджет платформы работает по
  WebSocket, но публичного адреса WSS и разрешения для сторонних WebRTC-клиентов
  нет. Без отдельного SIP-пароля SIP-логин равен паролю кабинета.

## Решение

1. **Интеграция через REST API ВАТС, параллельно amoCRM.** EVO подключается
   отдельным подключением «Ваша CRM» с собственным ключом и принимает `event` и
   `history`; маршрутизация звонков по CRM для этого подключения выключена до
   фазы 2. Форма не позволяет выключить `contact`, поэтому подключение
   создаётся только после ответа Beeline и замера задержки входящего на
   настоящих звонках (P1-блокер); запасной режим — «только сверка» (pull
   `history`). Действующее подключение amoCRM, маршрут входящих и виджет не
   меняются, но ВАТС рассылает звонки и подключению amoCRM, поэтому `makeCall` из
   EVO и тестовые звонки оставляют следы в amoCRM, о чём владелец предупреждён.
   Если подключение требует общего ключа с amoCRM или ломает виджет, запуск
   останавливается.
2. **Приём — публичный маршрут с тремя защитами.** `POST
   /api/v2/telephony/beeline/inbound` (новый путь; `/calls` и
   `/api/webhooks/telephony` остаются скрытым 404). Выключатель
   `EVO_PLATFORM_TELEPHONY_ENABLED`; жёсткий предел тела 32 КиБ; постоянное по
   времени сравнение `crm_token` (текущий и следующий ключ для ротации без
   окна отказов) до любого обращения к базе. Так как подписи у ВАТС нет, а токен
   лежит в теле, до проверки токена допускается только ограниченный плоский
   разбор тела (форма, JSON, multipart, `text/plain`, с параметрами типа): это
   осознанное исключение из правила «неподписанное тело не доходит до
   JSON.parse», принятое для этого провайдера. Токен не попадает в базу и
   журналы; до токена в журнал идут только счётчики. После токена: `contact`
   отвечает `200 {}` сразу, без базы и независимо от выключателя; `event` и
   `history` сохраняются всегда (мягкая проверка полей: пустые `user`, `phone`,
   `callid` не повод для 400); 400 только для неизвестного `cmd`. Ограничитель
   неудачных попыток не останавливает запросы с верным токеном. Идемпотентность
   по ключу сообщения; повтор ВАТС не предполагается, страховка — периодическая
   сверка командой `history` (CSV) с курсором.
3. **Звонок состоит из ног.** Один `callid` общий для связанных ног (группа,
   перевод, `CANCELLED`), поэтому звонок — строка `telephony_calls`, а участие
   каждого сотрудника — нога `telephony_call_legs`. «Ответил сотрудник» — только
   нога с сотрудником из `accounts` (приветствие и группа сотрудником не
   считаются); ответ необратим; решения (задача, лид, «Недозвон») принимаются
   после окна успокоения. Итоги, созданные только сверкой (в CSV нет `status`),
   помечаются как неточные и не запускают «Недозвон».
4. **Отдельные таблицы доказательства и очереди.** Таблицы
   `platform_private.telephony_*` (RLS без политик, append-only для доказательства, исходящий
   «ящик» с арендой и попытками). Не расширяем `communication_provider`,
   `provider_webhook_events` и `durable_work_items`: их проверки и внешние
   ключи привязаны к WAHA, а общая таблица — горячий путь WhatsApp. Выбор может
   быть пересмотрен на ревью первого среза (замена слоя очереди, например на
   pgmq, не меняет контракт маршрута).
5. **Записи без копий.** EVO хранит метаданные звонка и непрозрачную ссылку на
   запись как секрет: одна колонка в строке ноги, пишется в транзакции приёма,
   не в таблице работы, не в доказательстве, не в журналах, не в браузере.
   Воспроизведение — серверный потоковый прокси с `Range`: право проверяет
   база (`telephony.recording.listen.own` для своих звонков, `.all` для
   остальных), разрешение выдаётся на 15 минут, выдача (а не каждый
   Range-запрос) фиксируется в журнале действий, ссылка погашается только
   серверной функцией, адрес проверяется по хосту тенанта и строгому пути
   (защита от подмены ссылки), редиректы не выполняются, ответ без кэша, тип
   `audio/mpeg`, единый предел 16 МиБ, тело не буферизуется. Ответ 404 обнуляет
   ссылку только у звонка старше 360 дней (`expired`, «запись удалена по сроку
   хранения»); у более молодого сохраняется («запись ещё не готова»), потому что
   ссылку заново получить нельзя. Сохранение отдельного звонка и расшифровка ИИ
   — только по отдельному решению после юридической оценки. Первичный импорт
   ссылок за год (только для клиентов, которые уже есть в EVO) идёт сразу после
   подключения, чтобы ссылки не терялись.
6. **Звонок из CRM — `makeCall` на устройство сотрудника.** ВАТС звонит
   сотруднику на зарегистрированное устройство и затем соединяет с клиентом.
   Номер берётся на сервере из доступной сотруднику карточки; ручного набора
   нет; проверка `sameOrigin`; разрешённые префиксы (по умолчанию `+996`);
   лимиты на сотрудника и организацию; идемпотентность по `request_id`; повтор
   `makeCall` не выполняется автоматически. Встроенный в браузер телефон
   (WebRTC) не входит в фазу 1: ему нужны адрес WSS, разрешение для сторонних
   клиентов и отдельный SIP-пароль на сотрудника (не пароль кабинета), которые
   должен подтвердить Beeline/ITooLabs. Точка решения G-SP (вкладка amoCRM,
   «Коммуникатор» или «Корпоративный мессенджер», мобильное приложение,
   встроенный WebRTC, amoCRM только как телефон) закрывается до выхода из фазы 1.
7. **Выпуск по срезам за флагами.** Каждый срез выпускается отдельно (слияние →
   ledger-apply → выпуск). Слияние ничего не открывает: флаги `ui_enabled`,
   `dial_enabled`, `projection_enabled` и флаги автоматики по умолчанию
   выключены, каждый RPC и экран проверяет их в базе. Автоматика (задачи, лиды) —
   отдельные флаги: пропущенный входящий → задача «Перезвонить» (15 рабочих
   минут), неизвестный номер → лид `phone_call`, «Недозвон» и следующий шаг,
   автозакрытие при отвеченном звонке (итог `answered`, не длительность). Они
   включаются после недели сверки с отдельного «да» владельца, под потолками
   автосозданного (лиды и задачи в час и сутки, автоотключение), чтобы
   поддельные события при утёкшем ключе не завалили «Заявки». Лид `phone_call`
   в «Заявках» требует новой версии очереди `staff_requests_queue_v3` (v2 берёт
   только `website` и `whatsapp`).
8. **Права, роли и аудит.** Шесть прав уровня организации
   (`telephony.call.dial`, `telephony.recording.listen.own|all`,
   `telephony.report.read.own|all`, `telephony.manage`) по шаблону 268;
   «свои»/«все» решает функция в базе по ногам звонка, а не область права.
   Шаблон 268 раздаёт ключи всем ролям «общие разделы», поэтому `.all` и `manage`
   выдаются только двум новым ролям («Телефония — менеджер», «Телефония —
   руководитель») и admin; «руководитель продаж» — держатель второй роли.
   Журнал: прослушивание (при выдаче), набор и отказы, результат, правки
   настроек; allowlist журнала расширяется и по действиям, и по типам объектов.
   Номер телефона клиента скрыт в строках звонков, шапке чата и журналах;
   карточка лида показывает номер как сейчас (скрытие номеров — отдельное
   решение владельца).
9. **Секреты.** Только в игнорируемом env и SOPS-архиве:
   `EVO_PLATFORM_TELEPHONY_CRM_TOKEN` (и необязательный `…_NEXT` для ротации),
   `…_PBX_TOKEN`, URL и хост тенанта (группа PBX — «всё или ничего»). Ключ
   приёма — UUID или hex длиной 32–64 знака. Токены не повторяют друг друга и ключ
   amoCRM. Env-контракт релиза (`scripts/evo-app-env-contract.mjs`) расширяется
   вместе с маршрутом. Подключение «Ваша CRM», установка systemd-таймера, правка
   edge, ledger, выпуск и включение приёма — отдельными разрешениями владельца.
10. **Фаза 2** (ответ на `contact` с ответственным, всплывающая карточка,
    переключение маршрута, отключение виджета amoCRM) — отдельным планом после
    выхода из фазы 1.

## Последствия

- Звонки, записи (ссылки), результаты и отчёт по ним появляются в EVO без
  копирования звука. Вместе с решением владельца это означает: записи, которых
  к моменту первого импорта ссылок уже нет у Beeline, и записи старше года
  потеряны для EVO; обратного хода нет. Владелец знает про возможную выгрузку по
  FTP вне EVO.
- EVO получает публичный маршрут с токеном в теле. Его поверхность атаки
  ограничена выключателем, пределом тела, ограничителем неудачных попыток
  (адрес из заголовка edge, неверные токены только), длинным случайным токеном,
  правкой edge (только `POST`, предел тела, только хост CRM, при известных
  адресах — `remote_ip`) и тем, что до проверки токена нет обращений к базе.
- Новое подключение получает каждый входящий звонок через `contact`. Пока Beeline
  не подтвердил, что сбой EVO не задерживает входящие, а замер не пройден,
  подключение не создаётся; откат — сначала выключить подключение в кабинете,
  потом править env; выпуски при живом подключении — вне рабочих часов.
- Нужна отдельная очередь, фоновый скрипт (`telephony-maintenance.mjs`) и
  systemd-таймер на VPS (повтор проекции, окно успокоения, сверка, отметка
  истёкших записей); таймер — отдельный production-артефакт. Контейнер
  приложения остаётся `read_only`.
- EVO и amoCRM параллельно получают одни и те же события, а звонки из EVO и
  тестовые звонки оставляют следы в amoCRM. До включения автоматики дублей
  задач и лидов нет; после — двойная работа менеджеров возможна, пока команда
  не перешла в EVO; это решение владельца о моменте включения.
- Метаданные звонка (номер, время, сотрудник, результат) — персональные
  данные клиента того же класса, что переписка. Юридическая оценка записи,
  транзита звука через сервер EVO и строки в политике сайта (Цифровой кодекс
  КР) остаётся за юристом КР; уведомление о записи включает владелец.
- Новые миграции (ориентир 287–298, один номер на PR) нумеруются при слиянии по
  свежему `origin/main` и ledger: 283–286 заняты открытыми PR приложения
  студента.

## Не решается этим ADR

- Отключение amoCRM и перенос истории звонков и записей из amoCRM.
- Wazzup и WAHA: Wazzup остаётся как есть, WAHA возвращается отдельным планом.
- Расшифровка и пересказ звонков ИИ; номера под рекламные каналы.
- Тариф Beeline (API, шестой пользователь, хранение).
- Скрытие полных номеров клиентов от менеджеров в карточке.
