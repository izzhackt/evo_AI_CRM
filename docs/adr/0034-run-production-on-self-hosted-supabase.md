# 0034 — Рабочая база EVO: self-hosted Supabase вместо облачного проекта

- Статус: принято 2026-10-20 (решение владельца в тот же день: «переключению
  можно и сразу делать … давай сразу делай»). Выполнено в окне
  00:35:03–00:47:26 UTC, рабочая с 00:47:25 UTC. Порядок и итог —
  [runbook](../runbooks/selfhosted-cutover.md) и запись
  `docs/PLAN_CHANGES.md` от 2026-10-20.
- Владелец решения: владелец продукта EVO.
- Заменяет: [ADR 0024](0024-use-managed-supabase-for-the-evo-production-successor.md)
  «Use managed Supabase for the EVO production successor» **только в части
  места базы**: рабочий Supabase — не облачный проект, а self-hosted на
  `hermes-vps`. Слова «managed Supabase» в названии ADR 0027 и в его строке
  «Retains: ADR 0024 managed-Supabase authority» читаются как «Supabase» в этом
  же смысле; сами тексты не переписываются.
- Сохраняет: всё остальное из ADR 0024: один Supabase-фундамент (Postgres,
  Auth, приватный Storage, RLS, нужные Realtime и очереди), корневой
  `supabase/` как единственный источник миграций, Supabase Auth как единственный
  вход сотрудников, replace-not-layer; ADR 0027 (V3 как единая поверхность)
  и ADR 0032 (ИИ-агент ходит в ту же базу ролью `evo_ai_agent` через Supavisor).

## Контекст

ADR 0024 (2026-09-02) выбрал управляемый облачный Supabase, чтобы не
поднимать заново готовые управляемые возможности. С 19.10 рядом с рабочей CRM
на `hermes-vps` стоял self-hosted Supabase как копия
([карта инфраструктуры](../runbooks/infrastructure-map.md), раздел 5); 19–20.10
на нём прошли две репетиции переключения, а код выпуска, ledger миграций и
контракт env получили режим `EVO_SUPABASE_TARGET` (#1272). 2026-10-20 владелец
решил сделать self-hosted рабочей базой и не удалять облачный проект.
Мотивы владельца в записи не приведены; этот ADR фиксирует решение и его
границы, а не объясняет его.

## Решение

1. **Где база.** Рабочие Postgres, Auth, приватный Storage, Realtime, Vault и
   Supavisor — self-hosted Supabase на `hermes-vps` (`/opt/evo-supabase`,
   compose-проект `evo-supabase`). Публичный адрес —
   `https://supabase.evoadmissions.com` через edge, открыты только `/auth/v1`,
   `/rest/v1`, `/storage/v1`, `/realtime/v1`. Приложение работает на нём с
   2026-10-20 00:47:25 UTC (выпуск `v3-r39349222695-a1-c200eef9`).
2. **Как выбирается.** Переменная GitHub `EVO_SUPABASE_TARGET` (`selfhosted`
   с 2026-10-20 00:41 UTC; не задана = `cloud`) выбирает базу для выпуска,
   ledger и контракта env. Код один, второго пути данных нет. Если self-hosted
   недоступен в режиме `selfhosted`, выпуск останавливается; тихого перехода
   на облако нет.
3. **Облачный проект** `iosckaqtovbbnssqcpde` не удаляется (запрет владельца) и
   не меняется нашими действиями: используется только на чтение как источник
   отката и историческая справка. Откат без потери данных возможен лишь до
   первой записи пользователя на self-hosted (runbook, шаг 14); обратного
   переноса из self-hosted в облако нет. Технической блокировки записи в
   облаке нет: сборки iPhone и операторские скрипты, нацеленные на облако,
   продолжают в него писать, пока не пересобраны.
4. **Миграции.** Корневой `supabase/` остаётся единственным источником
   миграций. На self-hosted их применяет и проверяет `EVO schema ledger` по
   SSH (`scripts/selfhosted-schema-ledger.mjs`); на момент решения ledger 310
   из 310.
5. **Резервные копии.** Нет — решение владельца 20.10 («бекапы пока не
   делаем»); когда делать, он скажет сам. ADR не вводит политику копий и не
   считает их сделанными.

## Последствия

- Эксплуатация базы переходит к EVO: обновления образов, диск и память
  `hermes-vps` (16 ГБ, swap нет), сертификат, домен `evoadmissions.com`
  (автопродление без способа оплаты, срок 2027-01-24). Подробности —
  [карта инфраструктуры](../runbooks/infrastructure-map.md).
- Пока копий нет, записи после 00:47:25 UTC существуют только на `hermes-vps`;
  облако их не получает.
- Ветки `cloud` в CI, ledger, контракте env и манифесте образа остаются на время
  отката. Удаление облачного пути в коде — #1271, срок 14 дней после приёмки,
  отдельным PR; облачный проект при этом не удаляется.
- `AGENTS.md` называет проект `iosckaqtovbbnssqcpde` историческим облачным и
  источником отката; рабочая база — self-hosted с `EVO_SUPABASE_TARGET=selfhosted`.
- Сессии, выданные облаком, недействительны (вход заново, пароли прежние);
  письма, отправленные облаком, ведут на облачный адрес и не работают.

## Не решается этим ADR

- Резервные копии и проверка восстановления (решает владелец).
- Удаление облачного пути в коде (#1271) и самого облачного проекта (запрещено).
- Сборка iPhone с адресом self-hosted, ключ Resend для писем Auth, отключение
  старых JWT-ключей облачного проекта, сессия WhatsApp `crm_primary`
  (`FAILED` с 12.10) — открытые пункты записи PLAN_CHANGES от 20.10.
- Мониторинг, второй сервер, высокая доступность.
