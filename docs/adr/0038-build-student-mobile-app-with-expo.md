# 0038 — Мобильное приложение студента: один код на Expo (React Native) для iPhone и Android

Статус: принято 2026-11-09 (решение владельца в чате: «мы делаем один код для
iPhone и Android», «да, React Native»). Заменяет пункт 1 «Клиент — нативный
SwiftUI» и отклонение «React Native/Expo» в ADR 0030. Серверная часть ADR 0030
остаётся в силе.

## Контекст

- ADR 0030 выбирал клиент только для iPhone. Теперь владелец хочет приложение
  ещё и для Android. Нативный путь означал бы три интерфейса: веб, SwiftUI и
  Kotlin. Каждую функцию и каждый редизайн пришлось бы делать трижды.
- Довод 0030 «Expo не переиспользует веб» больше не так силён. Кабинет написан
  на React и TypeScript, и мобильное приложение может брать у него без
  копирования:
  - строки RU/KY (`src/lib/portal/i18n.ts`);
  - статический контент (`src/content/**`, библиотеки фото и геоточек, список
    стран);
  - чистые модули правил (группировка вузов, разбор путей).
  Сейчас всё это заново написано на Swift.
- Новый дизайн кабинета (#1412) пока есть только в вебе, и iPhone-версию всё
  равно пришлось бы перерисовывать. Пересобирать экраны на новом стеке
  выгоднее сейчас, а не после переноса дизайна в SwiftUI.
- Проверено 2026-11-09:
  - Expo SDK 58 (React Native 0.88.1, React 19.3.0, New Architecture всегда
    включена) собирается для симулятора iPhone в Xcode 26.5 на этом Mac (BUILD
    SUCCEEDED).
  - Сервер не меняется. Те же RPC `platform.*` с публичным ключом и токеном
    студента вызываются из `supabase-js`. Опись: `docs/mobile/reference/`.

## Решение

1. **Клиент — Expo SDK 58 + Expo Router, TypeScript strict.**
   - Папка `mobile/` в этом репозитории, npm без workspaces.
   - Нативные каталоги `mobile/ios` и `mobile/android` генерирует
     `expo prebuild` (CNG), в Git они не хранятся.
   - Сборка, подпись, отправка в магазины и обновления по воздуху идут через
     EAS, аккаунт владельца `izzhackts-team`. Вход в EAS выполняет владелец.
2. **Общий код с вебом без копий.**
   - Metro `watchFolders` читает из `src/` только чистые модули: JSON-контент,
     строки и функции без `next`, `server-only`, `react-dom` и DOM.
   - Это проверяет скрипт-страж в `mobile/` (падает при запрещённом импорте).
   - Цвета, шрифты (Golos Text, JetBrains Mono), радиусы и отступы
     генерирует скрипт из `src/app/(portal)/portal.css`. Источник у веба и
     телефона один.
3. **Стили — `StyleSheet` с этими токенами.** NativeWind v4 поддерживает
   только Tailwind v3, а v5 пока в стадии RC. Тема светлая или тёмная по
   выбору студента, как в вебе.
4. **Данные.**
   - Используем `@supabase/supabase-js` v2. Сессия хранится в зашифрованном
     хранилище по документированной Supabase схеме LargeSecureStore (ключ в
     SecureStore, шифротекст рядом).
   - Обновление токена следует состоянию приложения (`AppState`).
   - Сохраняются все инварианты iPhone 1.1: клиентский `p_request_id`,
     повтор с тем же замороженным запросом, никакие ответы, вердикты и тексты
     ошибок сервера в журнал не попадают.
5. **Сервер — точечно, как в ADR 0030.** Узкие маршруты `/api/portal/*` с
   `Authorization: Bearer` или публичные с собственной защитой:
   - вход по логину «имя.фамилия»;
   - восстановление пароля с проверкой членства сотрудника (#1287);
   - установка своего пароля после временного;
   - регистрация только по личной ссылке с согласиями текущей версии;
   - bearer-ветка скачивания договора и чеков.

   Универсального шлюза поверх RPC нет. Service-role остаётся только на
   сервере.
6. **Структура приложения повторяет кабинет #1412.**
   - Нижняя панель на 4 вкладки (Главная, Поступление, Документы, Входящие)
     и меню ☰ с разделами по уровню доступа.
   - Известные ошибки структуры кабинета (#1355–#1363) в приложение не
     переносятся. Веб исправляется теми же решениями, чтобы продукт оставался
     одним.
7. **SwiftUI-клиент `ios/` заморожен.** Новых функций в нём нет. Он остаётся
   справочником поведения: экраны, 416 тестов, файлы сверки. Удаляется
   отдельным PR после того, как Expo-приложение займёт его место в App Store,
   с подтверждением владельца. Bundle id `com.evoadmissions.app` сохраняется.

## Отклонённые варианты

- **Оставить SwiftUI и писать отдельный Android (Kotlin):** каждую функцию и
  каждый дизайн пришлось бы делать дважды, навсегда.
- **Обёртка веб-кабинета (Capacitor или TWA):** доводы ADR 0030 остаются в
  силе. Это риск отказа Apple 4.2, вымывание cookie в WebKit, слабые
  нативные файлы и доступность.
- **Flutter:** один код, но язык Dart, и с вебом ничего не делится.
- **NativeWind v5 и Tamagui:** первый пока RC, второй — отдельная система
  компонентов поверх React Native. Обычные токены надёжнее.

## Последствия

- В репозитории появляется вторая сборочная экосистема (Metro, EAS, CocoaPods
  и Gradle). Проверки `mobile/` (typecheck, lint, Jest) запускаются, только
  когда меняется `mobile/` или общие модули.
- Обновления по воздуху (EAS Update, политика `runtimeVersion: fingerprint`)
  исправляют JS без проверки в магазине. Новые нативные модули по-прежнему
  требуют сборки и проверки.
- Установленные приложения обновляются не мгновенно, поэтому прежнее правило
  репозитория остаётся: RPC-контракты расширяются только добавлением полей,
  новые версии получают `_vN`.
- Для магазинов нужен владелец:
  - Apple: Team ID, App Store Connect, письмо-доверенность;
  - Google Play Console: взнос 25 $; для нового личного аккаунта ещё
    закрытый тест (12 тестировщиков, 14 дней);
  - публичная страница удаления аккаунта для Google.
