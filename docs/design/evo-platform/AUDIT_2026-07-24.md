## What the handoff contains

The archive contains four interactive `.dc.html` references, an icon asset, a
local helper script and a developer README:

- project index and architecture overview;
- staff workspace with seven role views;
- mobile-first student portal;
- EVO design-system catalogue;
- eight representative end-to-end flows.

The seven staff personas shown in the prototype are not the current production
role model. The real root application has five staff roles (`admin`, `sales`,
`curator`, `visa`, `finance`) plus the student `client` role. “Руководство” and
“Оператор Inbox” remain design viewpoints until a separate authorization
decision is approved and implemented server-side.

The design correctly preserves the most important product boundaries:

- amoCRM owns lead/contact identity and sales stage;
- the operational student stage is separate from the sales stage;
- AI customer replies are drafts that a person must review and send;
- Lead Agent has no user-facing workspace;
- broad automation and mass messaging are outside v1.

## Browser-verified strengths

- The 1440x1024 staff dashboard, sales funnel, Lead 360, Student 360, document
  review, finance, Inbox, role switcher and no-access state render coherently.
- The Inbox flow exposes an AI draft as “requires review / not sent” and does
  not silently send it.
- Role switching leads to a real restricted-access view rather than only
  hiding a menu item.
- Document, payment, admission, visa and student-next-action concepts are
  represented in connected prototype flows.
- The design system documents brand tokens, type scale, status vocabulary and
  core overlay/feedback patterns.

## Must-fix gaps before implementation can be called complete

### P0 — responsive failure

- At 834x1194 the staff sidebar remains 250px wide and several dashboard/KPI
  regions overflow beyond the viewport.
- At 390x844 the staff Inbox is effectively unusable: the desktop sidebar
  consumes most of the width and the conversation is clipped.
- The student “desktop” mode is a widened phone shell with a mobile status bar
  and bottom navigation, not a true desktop application layout.
- The student “390x844” reference is itself placed inside a phone bezel below a
  marketing header, so it is not a real 390x844 application viewport.

### P0 — inaccessible interaction contract

- Primary navigation items, rows and task cards frequently use clickable
  `div` elements without native keyboard behavior or an accessible role/name.
- Drawers, sheets and modals lack `dialog` semantics, focus entry/trapping,
  Escape behavior and focus return.
- Tabs have no `tablist`/`tab`/`tabpanel` semantics or arrow-key behavior.
- Data tables and kanban lanes are mostly generic layout containers, so
  screen-reader row/column relationships are absent.
- Several checkboxes, radios, switches and upload targets are visual shapes
  rather than labelled native inputs.

### P1 — states are catalogued but not all connected

The index claims loading, empty, no-results, approval-required, offline,
reconnecting, integration-missing and recovery states. Several exist only as
static design-system examples and cannot be reached inside the application
flows. Completion must require a real route/component state, not only a label.

### P1 — bundle is not self-contained

`support.js` loads React, ReactDOM and Babel from `unpkg.com`, and the HTML files
load Google Fonts. The local bundle therefore fails without network access and
is unsuitable as production source.

### P1 — content/data consistency

The “Аттестат + перевод” review drawer displays an AI hint that identifies the
file as a passport and mentions a missing MRZ line. This is mismatched demo copy
and must not be carried into the real frontend.

### P2 — overclaiming and placeholder evidence

- Project-index links cover major sections and flows, not every internal state.
- Document previews are placeholders.
- Local mutations and success toasts demonstrate intent only; they do not prove
  amoCRM, WAHA, Supabase, AI, telephony or persistence.
- The typographic logo recreation must be checked against the committed EVO
  logobook before production use.

## Implementation decision

The real frontend will be built in the root Next.js CRM application. Existing
server-side authentication, roles and read models will remain in place.
Interactive behavior will be implemented in focused Client Components rather
than turning whole data pages into client-only applications.

EVO Inbox is a UX and data-adapter source for conversations, not the canonical
application shell. Physical database/runtime consolidation is a later
architecture decision and is not inferred from the unified design.

The first frontend implementation of `/whatsapp` continues to use the root
CRM's existing `wa_*` shadow records and guarded actions. It must not be
described as a live read of EVO Inbox Supabase. A real cross-runtime read bridge
is a separate backend/integration task.
