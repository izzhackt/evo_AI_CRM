## Решение: модель доступа (PORT-1)

Разведка authority-модели (main `4a6c061f`) показала: разделение «одобрен» и
«сопровождение» уже заложено в данных — обе ветки (staff-одобрение анкеты в
180 и invite `cabinet_pending` в 185) сходятся к одному и тому же:
`student_cases.state='pending'`, `portal_activated_at` установлен, куратора
нет. Read-модели сопровождения (заявки/виза/финансы) уже отгорожены
`state IN ('active','closed')` и для pending честно пусты — это документированное
решение 180, не случайность.

Решение (минимальное корректное разделение, план §8.4):

1. **Pending-case = состояние «одобрен». Case-less уровень не строим.**
   Различение из одной и той же строки кейса:
   `approved` = `state='pending'` (куратора нет), `assisted` =
   `state IN ('active','closed')`. Переход active⇄pending уже происходит
   in-place (182), кейс не пересоздаётся — аккаунт и данные сохраняются.
2. **Производный `accessTier: "approved" | "assisted"`** добавляется в
   `VerifiedStudentPortalAuthority` (чистый TS-вывод, без миграции) — единая
   проверяемая граница для веба и iPhone вместо рассыпанных
   `caseState==='pending'` по экранам.
3. **Один пере-гейт в БД (миграция №192, изначально резервировалась как 195):** `case_help_workspace_v1` /
   `create_case_help_request_v1` (146) сегодня доступны pending-кейсу, а по
   диаграмме плана §4 «Общение» — уровень сопровождения. Студентская ветка
   `require_case_operations_actor` получает условие
   `state IN ('active','closed')`. По production-данным затронуто 0 аккаунтов
   (оба живых кейса active); существующие треды остаются читаемыми. Для
   approved-пользователя канал обращения — «Запрос консультации» (PORT-5), не
   case-help. (Отмечено для пост-ревью владельца как снятие возможности,
   которой по плану быть не должно.)
4. **Защитное ужесточение документов** в той же миграции: явное
   `state IN ('active','closed')` в предикатах чтения/загрузки документов —
   сегодня pending-безопасность держится лишь на том, что чек-лист сеется
   только active-кейсу (структурная случайность, не инвариант).
5. **Каталог, тесты, уведомления, профиль, избранное** — ноль изменений БД:
   уже корректно работают для approved (гейт по роли/permission, не по
   состоянию кейса).
6. Семейство invite-RPC (`claim/finalize/resolve…`, 126) — service_role-only и
   остаётся серверно-опосредованным: для iPhone инвайт идёт через universal
   link в web `/auth/callback` (ADR 0030), не через прямой PostgREST.
7. Обязательный boundary-тест уровня `platform_student_assessments_boundary.sql`
   на новую границу: pending-актор получает 42501/пусто на case-help и
   документы, approved-возможности работают, active-кейс не деградирует.
   TS-контракт: «ждёт решения» остаётся отдельным механизмом
   (`own_student_application_v1`/invite-receipt), не поддельным кейсом.

## Решение: мобильный стек

SwiftUI + supabase-swift поверх существующих `platform.*` RPC; bearer-резолвер
только для документных route handler'ов; узкие endpoints для анкеты/инвайта;

## Решение: состав первого учебного модуля (план §6, полномочие Fable)

«Английский. Модуль 1 — старт» (уровень: с нуля/basic, соответствует полосе
basic english36):

1. Приветствие и знакомство. 2. Алфавит, звуки, spelling своего имени.
3. Числа, даты, время. 4. Рассказ о себе и семье. 5. Школа и учёба.
6. Простые вопросы (who/what/where/when). 7. Быть и делать: базовые
конструкции настоящего времени. 8. Повседневные ситуации: кафе, транспорт,
покупки. 9. Чтение коротких текстов. 10. Слова об учёбе и планах.
11. Страна и город: рассказать, откуда ты и куда хочешь. 12. Повторение
модуля (собирается из ошибок уроков 1–11).

- Урок: цель → микро-объяснение (RU/KY) → 8–10 заданий → мгновенный разбор
  ошибки → итог. Типы заданий v1: выбор, сопоставление, короткий ответ,
  чтение. Аудирование — не в модуле 1: реальная запись и её пайплайн — модуль 2,
  чтобы не блокировать старт аудио-инфраструктурой.
- Механика повторения: банк ошибок ученика + урок-повторение №12 и кнопка
  «повторить ошибки»; без XP/лиг/стриков (план §6).
- Контент: оригинальный EVO, версионируемый JSON → генератор → immutable
  миграция (форк пайплайна assessment-content, с колонками locale ru/ky —
  текущий CHECK 'ru'-only расширяется миграцией). Без CEFR-меток.
- Переписка с приёмной комиссией и интервью сознательно НЕ старт (план §6);
  они становятся модулем 3+ по мере роста уровня.

## Решение: покрытие профессий (план §6, полномочие Fable)

- Стартовый набор: **24 карточки**, покрывающие все интересовые шкалы ORVIS
  (~2–3 на шкалу), каждая обязана иметь: рабочий день, среду, навыки,
  интересные/сложные стороны, пробное мини-задание, связанные направления и
  ссылки на реальные программы каталога (143 вуза дают материал для связей).
- Зарплаты и работодатели — только при надёжном актуальном источнике с
  провенансом; это необязательные поля, пустыми не публикуются.
- Число 24 — рабочее решение PORT-0, а не квота: карточка без содержательного
  наполнения не публикуется, готовые сверх набора — публикуются.
- Атрибуция ORVIS/IPIP (CC BY 4.0) сохраняется на всех связанных экранах.

## Решение: каталог, карта, избранное, фото

- Карта — MapLibre GL JS; тайлы — свободный источник с проверкой условий и
  атрибуции на этапе PORT-3 (решение по конкретному тайл-провайдеру — в
  дизайн-контракте PORT-2/3). Список остаётся полноценным равноправным
  представлением; сбой карты показывается явно.
- Координаты — новое nullable-поле контента с собственным
  `sourceUrl`/`verifiedOn` (паттерн провенанса поля), миграция по образцу
  150/151; вуз без координат не получает точку, фиктивных пинов нет.
- Избранное v1 — на уровне вуза (id программ внутри JSONB нестабильны между
  версиями публикации); таблица student-owned + RPC add/remove/list +
  batch-by-ids чтение карточек; та же RPC-only изоляция, что у каталога.
- Фото: миграция с hotlink Wikimedia на управляемое хранение (Supabase
  Storage) с сохранением атрибуции CC — лицензии это разрешают; выполняется в
  PORT-3 с перепроверкой лицензии каждого файла.

## Решение: локализация

- Механизм `getLocale()/getT()` расширяется до неймспейсных словарей портала;
  «en» в портале не предлагается (план §2: английский — содержание обучения).
- Язык — персистентное поле профиля в БД (синхронизация между веб и iPhone),
  cookie остаётся быстрым request-time умолчанием.
- Русскоязычные статус-словари `wording.ts` для портала параметризуются по
  локали отдельным портальным слоем, staff-словарь не трогается.
- Полные RU/KY-словари — обязательная часть каждого портального PR, не
  финальная «полировка» (портал сегодня локализован на 0%).

## Релизная дисциплина Portal

- Любая правка якорей smoke (`student-portal-shell`, «Разделы кабинета»,
  «Моё поступление», заголовки /portal/documents, `#staff-email` и пр.) — в том
  же PR обновляются `scripts/evo-production-browser-smoke.mjs` и
  `tests/production-browser-smoke.test.mjs`. Новые ключевые портальные экраны
  добавляют свои якоря в smoke — названная, а не молчаливая зона покрытия.
- Порядок production-изменений: миграция в main → `evo-schema-ledger.yml`
  (mode=apply) → сверка ledger → dispatch `evo-platform-ci.yml`
  (proof_revision=exact main SHA) → авто `evo-fast-release.yml` → acceptance →
  disarm. Точечный smoke изменённой функции обязателен; RPC-расширения — только
  аддитивно или `_v2`.
