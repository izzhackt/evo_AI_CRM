## Пять подтверждённых пробелов

1. **Money пока не один рабочий поток.** `tabs.tsx:426-441` выводит `CaseAgreementBlock`, затем `:451-483` старый бюджет, `:485-509` план платежей, `ProfileFinanceControls` и `FinanceEntryWorkspace`. Отдельный `Profile.tsx:248-255` продолжает выводить технический договор. `ContractDraftReportWorkspace.tsx:600-601,714` показывает `provider claims`, `plain-text draft`, hash в обычном интерфейсе. Следствие: сотрудник выбирает между несколькими способами читать/изменять финансовые факты. Сначала составить карту операций, перенести их в последовательность стоимость → договор → транши → оплаты/чеки → остаток; затем убрать конкурирующие точки входа. Скрыть старый ledger без переноса возвратов/исправлений нельзя. Наличие стоимости не доказывает подпись; загруженный договор не доказывает существующее решение по draft.

2. **Docs скрывает ошибку чтения доступных шаблонов требований.** `Documents.tsx:63-78` перехватывает любой отказ `listCaseBaselineChecklistOptions` и превращает его в пустой массив; `ProfileDocumentsClient.tsx:696-704` тогда прячет применение требований. Сотрудник не различает «шаблонов нет» и «не удалось загрузить». Нужно отдельное состояние загрузки/ошибки с повтором, не выдуманный пустой успех. При этом требуемое различие «требования не назначены» уже существует (`:718-731`); не переписывать его как новую функцию. Загрузки/отсутствующие файлы выводятся отдельно по `presence`.

3. **Подготовка программы не привязана к устойчивым program/intake IDs.** `ApplicationCreateDialog.tsx:53-70` создаёт `preparation`, но поле программы — `program_name`; `platform-admissions-actions.ts:359-376` передаёт `p_catalog_institution_id` и `p_program_name`, без program/intake ID. Это достаточная основа ручной записи, но не общий выбор одной программы/набора из каталога со своей редакцией требований и сроком (§11.4). Расширить существующую application/preparation связь и общую операцию; сохранить старые свободные названия, доказанные сроки, несколько вариантов и историю. Повтор выбора — тот же объект, не дубль; сотруднический и Student входы одинаковы по результату.

4. **Upload сейчас одновременно публикует документ на проверку.** `ProfileDocumentsClient.tsx:636-665` вызывает `/api/v2/document-slots/:id/versions`, а `src/lib/server/platform-document-storage-route-handlers.ts:628-643` принимает подтверждение только с `published_slot_status === "submitted"`, verified integrity и clean malware. Отдельной UI-кнопки недостаточно: нужна общая серверная семантика сохранённой версии и явной отправки, в том числе portal upload handler. Сохранить Storage preflight/scanning, контроль версии и idempotency. Загруженный файл без отправки не должен попадать в новую review-очередь.

5. **Существующий «пакет» — проверенный export, не новая первая отправка в EVO.** `src/lib/document-package.ts:177-238` проверяет редакцию/хеш правил, scope, актуальность версий, доступность, источники и approved review (`:222-226`); `src/lib/server/document-package-export.ts:113-168` готовит/создаёт/сохраняет export artifact. `StudentProfileExportHistory.tsx:37-56` отображает ZIP/draft/final и скачивание. Его нельзя использовать как первую отправку по §11, которой предварительный staff approval не нужен, или ослаблять ради неё final-export safeguards. Требуется отдельное бизнес-событие отправки с зафиксированными program/intake, редакцией требований и ссылками на конкретные версии, idempotency и решением по комплекту. Повторно используются те же файлы, без бинарных копий. University `submitted` остаётся внешним этапом, не следствием «Отправить пакет в EVO».

## Что обязательно сохранить

- **Навигация и правильные данные.** `?case=` и `?id=` — разные канонические идентичности; URL-вкладки, refresh/Back/прямые ссылки и `section=docs`. Куратор из дела отдельно от продавца; единый `PlatformAccessCard`; `#sale-conditions` снова открывает действующий редактор. Назначения, регистрации, права и список студентов не меняются побочно.
- **Полные денежные операции.** `CaseAgreementBlock.tsx:65-101` различает неизвестную стоимость, несовпадение сумм и смешанные валюты; `:110-155` сохраняет текущий договор и скачиваемую историю; `:158-190` — транши/сроки/редактирование/архивирование только допустимых; `:194-224` — оплаты, возвраты, авторов, даты, чеки. `FinanceEntryWorkspace.tsx:16-27` содержит создание обязательства, оплату, возврат и историю; `ProfileFinanceControls` — финансовый stop/release. Все права брать из сервера. `financeSummary` (`profile-source.ts:184-227`) скрывает нулевые агрегаты, поэтому перед удалением этой проекции проверить явное различие 0 / неизвестно / разные валюты на едином блоке.
- **Технический договор содержит полезные действия.** `ProfileContractWorkspace.tsx:31-40,208-219`: создание/утверждение/вывод версии шаблона, генерация/review draft, post-contract items/report/review; handoff context и amoCRM command section. Перед удалением вкладки определить служебное место этих действий и сохранить их доступность/историю/права. Не выдавать plain-text за подпись или отправку.
- **Документные пункты и история.** `ProfileDocumentsClient.tsx:106-199` показывает удалённые пункты и версии с автором/датой/просмотром/скачиванием; `:245-335` связывает один пункт с несколькими application/visa targets; `:336-607` применяет версию базового checklist, добавляет/переименовывает/убирает пункт с optimistic version и историей. Статус accepted не обходить ради замены; новую корректировку проектировать как новую версию с сохранённым старым решением.
- **Точная проверка файла.** `DocumentReviewForm.tsx:41-64` отправляет case, slot, конкретный `document_version_id`, request ID и фиксированный payload при неопределённом результате; `:74-107` запрещает принятие недоступного файла, требует причину возврата/отклонения и даёт восстановление после stale. Это разные решения по файлу, не отказ в поступлении.
- **Анкета/OCR/формы/экспорт.** `StudentProfileFields.tsx:57-67,220-244` сохраняет confirmed fields, source conflicts, unsaved/stale guards, revision, draft/final export; `UniversityFormExportPanel.tsx:67-73` сверяет template version/mapping/review; `DocumentRecognitionJobs.tsx:73-91,110-123` сохраняет consent на provider operation, привязку source version/profile revision, историю/повтор той же неопределённой команды. OCR даёт кандидаты на review, не автоматически подтверждённые факты. `StudentProfileExportHistory` сохраняет историю artifact, reconcile и разрешённое скачивание. В этом аудите OCR, экспорт и скачивание private files не выполнялись.

| Срез | Конкретный результат | Прямые зависимости |
|---|---|---|
| A. Money | Одна читаемая последовательность и один набор повседневных действий; служебные договорные операции вынесены без потерь | Инвентаризация двух finance surfaces и contract actions; общие DTO не менять ради вёрстки |
| B. Docs states/navigation | Ясные ошибки требований, отсутствие требований/файлов, проверка конкретной версии; короткий путь анкета → требования → файлы → готовая форма | Текущие Docs/profile fields/export; отдельный подтверждённый UI-проход |
| C. Shared preparation contract | Один идемпотентный выбор program/intake для staff/web/iPhone, немедленная подготовка; требования и сроки конкретной программы | Один владелец RPC/DTO/миграции; согласование с Fable до правок Portal/iPhone |
| D. Save/submit/snapshot/review | Сохранённый файл отдельно от отправленного; неизменяемая отправка набора версий; review очередь, возврат, повторная отправка изменённого | Сначала shared server contract, потом CRM и оба клиента; сохранённые export правила не ослаблять |
| E. Feedback/queue | Уполномоченная очередь с case/program/deadline; неназначенные дела не теряются; Student получает замечание с deep link к документу | Реальные recipients/assignment, существующие notification/refresh механизмы; без task на каждый файл |

Для новой простой программы стартовые «Фото»/«Загранпаспорт» — требования EVO, не утверждение о требованиях всех вузов. Существующие подробные перечни сохраняются. Готовность считается по обязательным пунктам выбранной программы; общий счётчик наличия файлов `Documents.tsx:54-57` не переименовывать в готовность пакета. Не обещать live-sync без его отдельного доказательства.

## Матрица приёмки на реальном пути

Пока это план проверок, не выполненные проверки. Использовать существующие реальные сессии/чтения; записи — только в отдельно разрешённом QA-сценарии, не создавать реальные продажи/чеки/письма для скриншота.

| Путь | Что доказать | Минимальный набор состояний |
|---|---|---|
| CRM дело → Money → стоимость | Правильная case identity; ссылка ведёт к доступной форме; после подтверждения согласованное чтение | До/после handoff; null ≠ 0; закрытое дело; preview и запрещённая роль |
| Договор/транши/оплата/возврат | Текущий файл + история; операция ровно одна; чек доступен нужной роли; одинаковые суммы в CRM/Student | Без файла/истории; пустые транши; paid/partial/refund; mixed currency; stale/uncertain retry |
| EVO Docs → требования | «Не назначены», «есть пункты, нет файлов» и ошибка чтения различаются; retry не создаёт пункт | 0 требований, 1+ отсутствующих, existing version, unavailable |
| Сохранить → отправить один файл | Storage/scanner подтверждает сохранённую версию; очереди нет до явной отправки; после неё правильные version/time/actor | invalid file, network retry, concurrent replacement, закрытое дело, другая org/Student denied |
| Staff и Student выбирают программу | Оба входа открывают ту же preparation с program/intake IDs и теми же требованиями/сроками | Повтор без дубля; две программы; самостоятельный пользователь denied; accompaniment без лишнего approval |
| Отправить пакет → CRM review → исправить | Первая отправка без предварительного approval; нет доступа/обязательного файла — конкретная причина; snapshot неизменяем; review изменённой части | Shared passport, разное essay; replacement после submission; новая редакция требований; unassigned case в queue |
| Web ↔ iPhone ↔ CRM | Та же версия/отправка/замечание после refresh, рабочий deep link, правильный проект iPhone | Нестабильная сеть, возврат на экран, другой Student denied, staff не видит private tests |
| Анкета → OCR/готовая форма/export | Старые функции и источники сохраняются, revision/mapping/source version отражены в реальном artifact | Только при затронутой зависимости и отдельной provider/QA authority; иначе явно unverified |
| Desktop + 393px/320px | Клавиатура, focus return, читаемые деньги/имена/ошибки, видимое действие и локальное переполнение | Light/dark, длинные названия, error/loading/empty; один проход + одно исправление |
