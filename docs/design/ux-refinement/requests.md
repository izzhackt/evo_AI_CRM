## Задача страницы и сохраняемые различия

Сотрудник должен увидеть доступные обращения, различить их смысл, открыть каноническую запись, выполнить именно разрешённое действие и вернуться к тому же отбору/странице. `request kind` и `intake source` — разные оси:

| Вид записи | Идентичность / источник | Существующее действие и authority |
|---|---|---|
| Регистрационная анкета | application ID; `platform_application`; опциональный `canonicalLeadId` | Одобрить доступ в кабинет/отклонить с причиной. RPC сохраняет отдельную scope/permission модель; это не продажа, handoff или назначение куратора |
| Обращение-лид | lead ID; `website` или `whatsapp` | Открыть Lead 360 через `?id=`. Информационная строка, не кнопка регистрационного одобрения |
| Консультация кабинета | consultation request ID; кабинет; optional institution ID | `requested → handled`, кто/когда обработал, conflict. Не создавать lead/application/case и не открывать сопровождение автоматически |
| Будущая отправка пакета §11 | Ещё не существующая в этом queue запись | Зависимость отдельного admissions-контракта. Не показывать её как реализованный request kind или автоматически применять решения анкеты/консультации |

Сохранить ключи `${kind}:${id}`, канонические UUID и явные связи, не объединять по имени/email. Анкета может ещё не иметь lead; текущий UI тогда показывает ответы (`requests/page.tsx:114-140`). Консультационный DTO имеет только request/institution IDs, не содержит безопасного case/lead target (`requests-source.ts:137-147`): нельзя строить ссылку на дело по догадке. Если нужен переход, добавить разрешённую сервером связь отдельно.

## Четыре основных пробела

1. **Фильтр источника после cap теряет подходящие записи; продолжить чтение нельзя.** `requests-source.ts:91-107` сначала собирает website/WhatsApp вместе и оставляет 100, `:121-122` фильтрует уже этот набор. Страница вызывает load без source (`requests/page.tsx:89,100`). Например, более 100 новых website записей вытеснят более старую WhatsApp запись, и WhatsApp выглядит пустым. Upstream `pipeline-source.ts:18-25,171-216` читает до 40×100 всех доступных лидов, не передавая source, после чего requests снова режет до 100. `requests/page.tsx:154-155` лишь сообщает об усечении, без следующей страницы. Анкеты независимо ограничены 100 в SQL177 `:368-371`, а их truncation вовсе не отражён. Объединённый `byRecency` (`requests-source.ts:66-67`) сортирует только по timestamp, без устойчивого tie-breaker. Консультации имеют SQL `ORDER BY is_open,created_at,id`, но `OFFSET 50` (SQL197 `:215-235`) смещается при обработке/добавлении записи. Нужны filter-before-limit и серверная cursor pagination каждого вида/общей проекции; увеличение cap не устраняет проблему.

2. **«Все» не включает консультации и смешивает вид с источником.** `requests/page.tsx:61-85` читает consultations только в отдельной ветке `source=portal_consultation`; `loadRequestsQueue` (`requests-source.ts:70-74,109`) читает только applications+leads. Навигация имеет aria-label «Источник заявки» (`requests/page.tsx:24-38`), хотя «Кабинет: консультации» выбирает другую сущность с другим действием. Свести доступные типы в одну read-проекцию для «Все», сохранять явный вид записи и оригинальный source. Не объявлять все остальные kinds доступными, если их permission/read не подтверждён.

3. **Счётчики и ошибки не передают точный охват.** `student-application-source.ts:66-79` уже возвращает серверный `pendingCount`; requests игнорирует его и пишет `pendingApplicationCount: applicationRows.length` (`requests-source.ts:112`), максимум 100. `requests/page.tsx:103-108` показывает count текущих строк, но рядом глобально звучащее «На рассмотрении»; при выборе website оно всё ещё относится к анкетам, при application outage превращается в 0. Любой rejected promise превращается в boolean unavailable (`requests-source.ts:116-117`), хотя typed application error различает forbidden/unavailable (`student-application-source.ts:45-51`). Затем любая ошибка анкет объявляется отсутствием прав (`requests/page.tsx:148-150`), даже технический отказ. При пустом частичном результате сначала показано «Заявок пока нет» (`:107-108`), ниже — alert неполного охвата. Нужны отдельные ready-empty / ready-filtered-empty / forbidden / unavailable / partial состояния и счётчики с scope: «На странице», «Анкет ожидают решения», «Открытых консультаций». Не суммировать unknown как ноль; настоящее total считать на сервере для того же actor/filter.

4. **Контекст теряется в recovery и переходах.** Source-фильтры уже URL-backed и browser Back сохраняет их (`requests/page.tsx:32-46`), это сохраняем. Но общий retry ведёт на `/v3/requests`, сбрасывая source (`:95,152`), консультационный retry/конфликт сбрасывает offset (`:79`, `PortalConsultations.tsx:42`); lead link несёт только `?id=` (`requests/page.tsx:115`), без явного безопасного возврата в отфильтрованную очередь. Consultation next-page существует (`PortalConsultations.tsx:100-109`), previous/возврат к текущему состоянию не выражены. Ввести общий builder URL для kind/source/cursor/returnTo; сбрасывать cursor только при изменении фильтра, не при retry. Return target разрешать только внутренний route с валидированными query. Не считать отсутствие явного returnTo доказательством сломанного browser Back.

## Роли и команды, которые нельзя ослабить

- Consultation read/handle: SQL197 `:188-195,239-268` требует live actor, non-Student, `lead.read`, org scope. Server action `platform-portal-consultation-actions.ts:24-44` дополнительно блокирует preview и сохраняет PT409/42501/22023; revalidate после подтверждённого receipt (`:46-51`). UI показывает «Обработано» только requested, сохраняет автора/время handled (`PortalConsultations.tsx:83-95`). UI сейчас сводит forbidden/invalid/unavailable к общей failed-подсказке — при обновлении раскрыть безопасное точное объяснение, не выдавать успех.
- Application read/review использует отдельную triad `profile.read.full`, `profile.manage`, `case.curator.assign` и направление (`177_platform_public_student_applications.sql:280-299`); миграция180 review продолжает `student_application_staff_org`/`student_application_visible` (`180_platform_unified_intake_access.sql:216,229`). Общая queue не даёт Sales новые review права. Существующий доступ к вкладке не равен доступу ко всем строкам.
- `ApplicationDecision` сохраняет `application_id`, `expected_revision`, `request_id`, причину отказа, draft при ошибке и safe retry (`StudentApplications.tsx:43-84`). Одобрение открывает кабинет без назначения куратора/платежа/handoff (`student-application-actions.ts:16-38`). Не менять эту семантику под видом унификации.
- История консультации и одобрения остаётся в собственных сущностях. Права проверяются RPC; UI должен получать честные per-kind/per-row capabilities, а не выводить их из общего «Admin» или наличия строки. Student-private assessment fields не добавляются в queue DTO.

## Узкий план реализации

1. **Read contract до вёрстки.** Выбрать стабильный порядок очереди и курсор `(sort timestamp, kind, canonical id)` либо отдельные источниковые cursors в одном валидированном DTO; определить semantics timestamp (ныне lead.updatedAt и application.submittedAt различаются). Сервер фильтрует kind/source и actor scope до LIMIT, отдаёт hasNext/cursor, независимое состояние доступности видов, точные count labels/values. Не ломать shared pipeline/dashboard reader ради requests. Один согласованный владелец migration/RPC, без самостоятельного schema apply.
2. **Объединить read, оставить команды отдельными.** Добавить consultation variant к RequestsRow и рендер по kind, «Все» включает все разрешённые варианты. Старый URL `source=portal_consultation` сохранить как совместимый alias/переход к фильтру консультаций. Регистрационные/лидовые/консультационные IDs и handlers не менять.
3. **Вывести честные состояния и навигацию.** Явный вид обращения на строке, источник отдельно; серверные счётчики с названиями, next/previous/back/retry, отсутствие результатов с сохранёнными фильтрами. Частичный отказ не обещает полное «нет заявок». Текущие shell/brand/положение основных элементов сохраняются; пустой экран уже не требует декоративного наполнения.
4. **Точечная приёмка и independent exact-head review.** Сначала настоящие server read сценарии, затем UI desktop/mobile и разрешённые QA mutations отдельно. §11 добавляется после существования его отдельного shared contract, не блокирует исправление CRM03.

В этом planning-проходе проверены исходники, diff между версиями requests и реальные снимки пустого состояния. Продуктовые тесты/БД mutations не запускались. Изучены существующие проверки: `tests/portal-consultation.test.mjs:78-101` закрепляют staff DTO/permission и нынешнюю отдельную consultation ветку; `tests/platform-unified-intake-access-migration.test.mjs` — access-only approval, canonical link и сохранение исторических форм; `tests/student-public-application.test.mjs` — registration/account authority.
