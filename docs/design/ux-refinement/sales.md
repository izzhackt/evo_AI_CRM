## Пять доказанных групп пробелов

### 1. Поиск и восстановление контекста списка не завершены — P1

В `SalesReportQuery` нет поиска (`SalesRegisterView.tsx:14–17`), источник/RPC принимает только период, manager, direction, review и archive (`sales-register-source.ts:17–35`; migration `144_platform_finance_entry_and_report.sql:60–85`). Искать имя/телефон/договор по всем доступным записям сейчас невозможно. Направление — произвольная строка «Как в записи» (`SalesRegisterView.tsx:90`); сброса фильтров нет. При нулевом результате предлагается сменить месяц, даже когда причина — активный продавец/направление (`:128–130`).

`href()` переносит период и фильтры, но не текущий offset (`:51–59`); переход к record и backHref используют его без offset (`:75–78`, `:138`, `:143`). Открытие строки со второй страницы теряет номер страницы при возврате. Сохранение позиции прокрутки также не реализовано этим контрактом. Фильтры уже применяются ДО LIMIT/OFFSET в SQL (`144:80–95`) — это полезное поведение сохранить, добавив поиск на этом же уровне, а не фильтруя 50 строк клиента.

### 2. Просмотр записи зависит от права редактирования — P1

Любой record-query объявляется `editing`, но карточка рендерится только при `canManage` (`SalesRegisterView.tsx:61`, `:74–79`); иначе пользователь вновь видит список, хотя ссылки «Открыть» доступны всем читателям (`:138`, `:143`). Для редактора открывается большая изменяемая форма сразу, без краткого просмотра (`SalesRegisterForms.tsx:148–222`). #935 меняет write gate и добавляет сообщение об ограничении, но отдельного read-only detail не вводит.

Нужен универсальный разрешённый просмотр исторического снимка; явное действие «Исправить запись» запускает edit только по write authority. Текущие условия клиента открываются в общей карточке, историческая коррекция не должна незаметно выглядеть их редактированием. Источник/архив и причина сохраняются. В текущем DTO нет истории изменений (`platform-sales-register-contract.ts:4–25`): не изображать timeline из `updatedAt`; проверить существующий audit-read и добавить минимальный защищённый projection только если необходим.

### 3. Список визуально отодвинут; мобильная запись разорвана горизонтальной прокруткой — P2

До таблицы идут шесть равнозначных фильтров и кнопка, большой раздел итогов, возможный отдельный блок денежных поступлений (`SalesRegisterView.tsx:80–126`). На предоставленном desktop-снимке первая запись начинается у нижней границы экрана; на mobile 390×844 первый экран заканчивается итогами, до строк пользователь ещё не доходит. Ошибка access RPC из pending 208 увеличивает высоту этого конкретного снимка; это отдельная известная зависимость, не новый UI-баг.

Таблица имеет `min-w-[960px]`, мобильного вертикального представления нет (`:133–145`). Родитель подтвердил отсутствие общего page overflow (document 380 / viewport 390); проблема именно в разделении имени и сумм внутри широкого scroll region, а не в доказанном нарушении reflow всей страницы. При этом native controls, 44px высота основных действий, фокусируемая таблица, scope заголовков и разделение валют уже полезны.

Оставить desktop-first плотность: заголовок/главное действие → период/поиск/продавец → дополнительные фильтры → короткие итоги → строки. На телефоне имя, дата, продавец, стоимость, оплачено и валюта одной записи читаются вертикально; таблица остаётся на подходящей ширине, при необходимости с sticky первой колонкой/шапкой. Не переносить шум в новые декоративные карточки. Для основного текста/сумм использовать уже принятые Golos 14–16 px и табличные цифры, 12 px только для вторичных метаданных. Сохранить оригинальный EVO logo, нейтральные токены, красный акцент и обе темы.

### 4. Охват итогов, месяц и уточнения недостаточно выражены — P2

`totalCount` и денежные итоги относятся к отфильтрованным строкам (`144:80–95`), а target — отделу; в UI они стоят под общим «Итоги периода», с «Записей продаж» и «План месяца» (`SalesRegisterView.tsx:98–113`). Ошибочного процента выполнения сейчас нет — не заявлять его существование. Нужны ясные «Найдено по фильтрам» и «План отдела», без нового KPI/ratio. В годовом списке `reportMonth` не отображается (`:136–143`), поэтому дата продажи не даёт весь контекст исторического месяца.

`needsReview` выводится только общим «Нужно уточнить» (`:142`), хотя missing date/currency/manager могут быть определены из реальных полей; причины нельзя домысливать. Исторические raw amount и notes сохранять. Импорт находится в ежедневном отчёте (`:154–156`) и должен перейти в существующий permission-gated management surface.

Важно: текущий исходный код НЕ подтверждает отдельно новую ошибку finance authorization. `SalesRegisterView.tsx:38–47`, `finance-entry-source.ts:15–28` используют full permission как hint; затем `platform-finance-entry-contract.ts:69–82` требует live pair. Access RPC проверяет `finance.read.full` + organization (`156:156–170`), а data RPC исправлен на ту же пару (`156:1312–1315`). Установить точную причину отсутствия сводки по реальному access/totals read и snapshot deployed functions, прежде чем менять guard. Не выдавать отсутствие блока на одном Admin-снимке за доказанный DB/RLS баг и не расширять всю Sales-роль.

### 5. Соседняя главная считает прежнюю когорту вместо текущей воронки — P1, CRM-01

`readPeriodDashboard` сначала отбирает лидов по createdAt (`funnel-source.ts:224–231`, `:423–429`); handed означает `linkedStudentCaseCount > 0` (`:215–220`), qualified — когда-либо доказанный вход в qualified (`:234–247`). Это накопительное продвижение когорты, не текущие люди на этапах и не подтверждённый факт продажи. UI по-прежнему называет блок «Воронка поступления», показывает период (`main/page.tsx:168–179`) и проценты (`Funnel.tsx:93–95`, `:204–219`, `:232–258`). Свежий main-снимок подтверждает старое название, период и процент.

Для CRM-01 сохранить визуальный путь и существующие этапы, но дать источнику точную текущую семантику и название «Воронка продаж»; убрать процент/конверсию. Период соседней динамики не фильтрует current funnel. Нельзя просто заменить числа, оставив условное скрытие всей области по нулевой когорте (`main/page.tsx:102–107`), или вывести текущие этапы через невозрастающую геометрию, подавляющую независимые количества (`Funnel.tsx:64–82`). Сохранить путь, сделать геометрию честной для текущего распределения. Продажа требует разрешённого реестрового факта; imported unlinked rows не порождают фиктивных лидов. Полнота чтения остаётся обязательной: `funnel-source.ts:17–25` отвергает truncated canonical read.

## Инварианты и реальная приёмка

- Сохранить tenant/record-scoped read, preview read-only, отдельные manage/import/target/finance права. Разрешённый читатель видит деталь; пользователь вне scope не получает строку через прямой record ID. Admin без нужной sales_manager authority не может создать/исправить продажу; UI hiding само по себе не доказательство.
- Сохранить snapshot, sourceKind/raw/source provenance, ручные исторические месяцы, оригинальные импортные имена, валюты отдельно, unknown как unknown. Служебную запись исключать только по подтверждённому ID/назначению; не чистить по имени.
- Использовать существующие разрешённые реальные записи и Auth-сессии. Для поиска выбрать существующую запись за первой страницей, проверить имя/нормализованный телефон/договор; cross-scope поиск ничего не раскрывает. Если таких записей нет, отметить непроверенный сценарий, не создавать fake data ради демонстрации.
- Проверить сочетания year/month/all, seller, direction, archive, review; query counts/totals равны тому же разрешённому набору ДО пагинации. Сброс оставляет период; open/back на offset≥50 возвращает ту же страницу и позицию; годовой список показывает reportMonth. Empty-filter и empty-period дают разные действия.
- На существующей записи read-only пользователь открывает все разрешённые snapshot поля; writer сначала видит просмотр и явно выбирает исправление. Полноценные correction/archive/restore/stale/idempotency сценарии выполнять только в отдельно авторизованном реальном QA пути; не править customer facts ради скриншота. - Finance: read-only сравнение разрешённого access RPC/data RPC и состава событий за месяц в Asia/Bishkek, отдельно payment/refund/currency. Нельзя включить summary лишь по union permissionKeys или объединить paid snapshot с cash.
