## Безопасность просмотра сейчас

Открытие `/v3/team-chat`, выбор канала, поиск, открытие сообщения/обсуждения **не вызывают запись chat business state по проверенному коду**. Page вызывает только `readV3TeamChat` (`src/app/(v3)/v3/team-chat/page.tsx:25`); RPC чтения `team_chat_read_page`/`team_chat_channels` STABLE (`supabase/migrations/141_platform_team_chat.sql:122,151`). `markRead` (`TeamChat.tsx:220`) вызывается только явной кнопкой «Отметить канал прочитанным» (`:306`). Подписка Realtime вызывает чтение changes при подключении/online/возврате видимости, а не read-команду. Возможен обычный refresh Auth-сессии. Вывод привязан к этому SHA, не к неизвестной live-версии.

Для screenshots безопасны открытие, чтение, поиск, навигация; не нажимать отправку, подтверждение удаления, модерацию, сохранение редактирования, отметку прочитанным и создание задачи. После реализации требуемого auto-read открытие видимой ленты уже будет менять состояние прочтения — эту гарантию нельзя переносить на будущую версию.

## Пять подтверждённых разрывов с согласованным результатом

1. **Ответы скрыты от общей хронологии.** SQL latest/before возвращает только `parent_message_id IS NULL` (migration 141:202–209), клиент ещё раз фильтрует roots (`TeamChat.tsx:26,84–90`); «Ответить» открывает второй feed/второй composer (`:169–188,317–333`). Server post разрешает parent только root (migration 171:71–75). Старые ответы нельзя вернуть изменением одной вёрстки. Нужны read projection всех сообщений, цитата и один composer; исходные message rows/ID/createdAt/author/parent не переписывать.

2. **Текущий учёт прочтения не выражает пропуски.** Отметка канала поднимает единственный `read_sequence` до выбранного сообщения (migration 171:103–112); unread считается как весь диапазон выше курсора (migration 141:135–142). Сейчас это явное массовое действие, не скрытое auto-read, но подключать его к viewport нельзя: прыжок к новым сообщениям погасит непросмотренную середину. Нужен дополнительный учёт конкретно увиденных ID и сохранение исторического cursor как уже прочитанной базы.

3. **Чат зависит от задач при каждом чтении.** `readV3TeamChat` получает `team_chat_task_links` для всех загруженных сообщений и при его ошибке роняет snapshot (`src/lib/v3/team-chat-source.ts:13–27`). В rows показываются «Задача создана ↗» и «Создать задачу» (`TeamChatMessageRow.tsx:47,56–57`). §9 прямо требует убрать UI и runtime enrichment. Сами задачи, source_message_id, их история/обратные ссылки и ручные URL из текста сохраняются.

4. **Поиск не даёт контекст и обратный путь.** SQL `message` возвращает только root и target (migration 141:186–190). Клиент очищает search, target-reply открывает thread (`TeamChat.tsx:198–205`); сохранённых результатов/scroll для возврата нет. В row нет search highlighting (`TeamChatMessageRow.tsx:37–39`). Нужен bounded around-message window с соседями в общей ленте; target — видимый фокус; «К результатам» сохраняет запрос, страницу и позицию. Search result/quote не должны вызывать seen исходного сообщения.

5. **Лента и ввод остаются избыточными, а состояния каналов неполными.** Каждая реплика повторяет имя/аватар/ряд действий (`TeamChatMessageRow.tsx:30–60`, CSS:40–56); textarea имеет rows=1, ручной `resize: vertical`, но нет autosize (Composer:86–98, CSS:68). Большой поиск ищет три названия, а preview доступен только выбранному каналу; когда последняя запись — reply, даже этот preview исчезает, потому что поиск идёт в roots (`TeamChat.tsx:238–257`). Время последнего сообщения не выводится. Любое changes-событие, включая правку/удаление, включает «Новые сообщения», без учёта нахождения внизу (`:96,307`). Нужны авторские группы с границами дня; вторичные действия hover/focus и явное mobile-меню; реальная последняя запись/время каждого доступного канала; autosize 1→5–6 строк→внутренняя прокрутка; переход вниз по реальному положению/новым сообщениям. Это вывод из кода, визуальные размеры следует подтвердить в одном desktop/mobile проходе.

Отдельно учесть в этих срезах: общая ошибка `unavailable` сейчас обещает сохранённый черновик даже для загрузки/удаления (`platform-team-chat.ts:42–47`). Нужны согласованные в §9 action-specific «Не удалось загрузить сообщения» / «Не удалось подтвердить отправку» / «Не удалось подтвердить удаление», реальная сверка и тот же idempotency key.

## Сохранение данных и функций

- Использовать те же message rows как плоский поток в `sequence_id`-порядке; даты разделять по существующему `PLATFORM_ORGANIZATION_TIMEZONE`. Не копировать/пересылать историю и не сбрасывать старые курсоры. Обновить индекс, который сейчас частичный только для roots (migration 141:30–31), и пагинацию/catch-up для общего feed.
- Старый `parent_message_id` остаётся ссылкой цитаты. Для ответа на бывший reply сервер должен разрешать точный target того же канала/организации, а не молча заменять его root. Новая запись ссылается только на существующую более раннюю запись. Старую thread-структуру сохраняем в данных; новый UI её не показывает. Quote read разрешён теми же grants; удалённый target показывает tombstone, никогда старый удалённый текст. Не сохранять копию body как способ обойти удаление.
- Не менять audit, author ownership, expectedVersion, receipt input equality, request/channel locks, scoped mentions и приватную Realtime invalidation. Последняя передаёт только refresh, а тело получается через повторно авторизованное чтение (migration 171:32–45,116–130).
- Draft migration: обнаруживать только старые ключи текущих organization/member/channel (`Composer:26–35`); дать восстановить канал/бывший thread с его цитатой через одно поле, не перетирать конфликтующие тексты. Черновики edit также сохранить. Неизвестно отправленный draft сохраняет исходные requestId и retryInput (`:44–65`); нельзя превратить его в «новую отправку» при миграции ключа или автоматически отправлять.
- Для sparse read минимально добавить scoped записи seen конкретных ID поверх исторического read_sequence. Auto-read не повышает общий cursor. Считать unread по исторической базе плюс подтверждённым seen; пропуски остаются. API принимает ограниченный список IDs, сервер перепроверяет membership/channel. Observer работает только для реально видимого основного feed в активной вкладке; search snippets и цитаты не участвуют. UI badge обновляется после подтверждения, с безопасным повтором. Согласовать совместимость с предыдущей сборкой и rollback до выпуска.
- Выдавать channel preview/time сервером для каждого разрешённого канала; отсутствие доступного preview не трактовать как пустоту. Ничего не придумывать про участников или online.

## Связи с задачами и календарём, без их аудита

Прямые связи чата с задачами: указанные row links/enrichment; `/v3/tasks?create=staff&message=…&channel=…`; task page читает исходное сообщение с канальной authority, получает его version для создания (`src/app/(v3)/v3/tasks/page.tsx:57–67,116–124`). У уже существующей задачи остаётся разрешённая обратная ссылка через `readStaffTaskChatSource` (`:98–100`). FK/source metadata — migration 142:7,139–168. Удаление кнопок в чате не повод удалять задачи, исторические связи, старые URL или обратную навигацию из Tasks.

Прямого вызова календаря в team-chat компонентах/read path нет. Проверенный calendar source читает admissions task queue и проецирует dueOn/dueAt (`src/lib/v3/calendar-source.ts:103–153`), а не chat messages. Этот срез не доказывает, что любая staff-задача из чата попадает в календарь. Для §9 не требуется менять календарь или дедлайны задач. Любые ручные ссылки на tasks/calendar в message body остаются как обычные безопасные ссылки.

## Узкие срезы реализации и фактическая приёмка

1. **Контракт чтения/история:** additive migration + TS contract/repository: chronological feed, bounded context, безопасные quotes и preview/time. Сверить старые root+reply rows до/после по ID/author/date/version/parent, показать каждый ровно раз. Проверить пагинацию >50, reply от старого root, tombstone quote, старый deep link и edit/delete catch-up без потерь. Не назначать номер миграции до координации владельцем.
2. **Единый UI и сохранение черновиков:** убрать thread UI/reply counts/task UI/enrichment, добавить quote composer и управляемое восстановление drafts; сохранить mentions, правку, deletion confirmation, модерацию, safe links, клавиатуру. На реальном разрешённом Auth/API пути подтвердить post/reply/edit/delete на согласованном QA-контексте; при неизвестном ответе сверить сообщение и повторить тот же requestId без дубля. Если write authority нет, это конкретный открытый gate, не повод отправлять рабочим сотрудникам.
3. **Поиск и навигация:** запрос только по каналу, подсветка, bounded around-window, return-to-results/scroll, firstUnread; новый контент не сдвигает чтение. Проверить поиск старого reply и удалённого исходника, URL на reply, переход вниз и обратно; результаты/цитаты не учитываются как исходное чтение.
4. **Sparse read:** отдельный маленький серверный/клиентский срез; реальный Auth/persistence: показать A, пропустить B, показать C → B остаётся unread; hidden tab, search snippet, quote не гасят unseen; перезагрузка сохраняет результат; legacy reads не сбрасываются; второй пользователь/другая организация/закрытый канал не доступны. Обычный page-open после этого среза является write, нужна разрешённая QA-сессия.
5. **Компактность и восстановление:** один batched desktop + 393px light/dark осмотр; максимум один подтверждающий проход после исправлений. Проверить группы/даты/44px controls, focus и IME, длинную реплику и URL, рост/сжатие ввода и reset только после saved, возврат мобильной навигации, канал без preview, ошибку/повтор/reconnect. Проверить ошибку task-links больше не блокирует чат, потому что вызова уже нет.

Зафиксировать exact SHA, реальные проверенные действия и ограничения. Проверки выбирать по этим рискам; общий тяжёлый suite не нужен. Независимое exact-head review, protected short checks и managed release остаются. Planning-only срез завершён без изменений репозитория и без live acceptance.
