## Задача, актёры, действия

| Актёр/состояние | Сохранить | Добавляемый путь |
| --- | --- | --- |
| Одобренный самостоятельный пользователь (`approved`) | Читать каталог и программы, источники/фото/даты; избранное; существующая консультация | Не давать подготовку/документы из одного факта регистрации; честный существующий путь обращения в EVO без lock-teaser, новой оплаты или повторной регистрации |
| Клиент с сопровождением (`assisted`, сервер подтвердил конкретное дело/действие) | Всё чтение и обычные возможности каталога | Выбрать программу и конкретный набор/период → сразу открыть подготовку в своём существующем деле; выбранное видно сотруднику, отдельного approval нет |
| Тот же клиент с уже выбранной программой | Сохранить несколько вариантов и историю | «Открыть подготовку» ведёт к той же записи; повтор из веба/iPhone не создаёт дубль |
| Разрешённый сотрудник из существующего дела | Текущие варианты, manual/free-text исторические записи и внешний application workflow | Каталожный выбор создаёт тот же ресурс подготовки, что клиентский вход; не связывать старый free text с программой по совпадению названия |

Избранное, консультация, регистрационная анкета, подготовка и отправка в университет остаются разными действиями. Любое количество уже существующих вариантов сохранить; новый лимит не вводить. Мутация выбора должна возвращать подтверждённый идентификатор подготовки/дела и состояние, а не просто показывать toast.

## Доказанная карта пробелов

### U1. Идентичность набора отсутствует; свободная программа CRM не закрывает §11 — P1

`UniversityProgram.id` — строковый slug, уникальный лишь внутри одного массива публикации (`src/lib/platform-university-catalog.ts:16–18,55–56`). `UniversityIntake` не содержит ID (`:10–15`); веб рендерит его по index (`src/components/portal/universities/Detail.tsx:142–143`), iPhone — по offset (`ios/EVOAdmissions/Views/UniversityDetailView.swift:327`). Список меняет порядок при новой публикации, поэтому index нельзя сохранять как выбранный набор. Native DTO тоже не имеет intake ID (`ios/EVOAdmissions/Services/PortalModels.swift:103–125`).

Staff-форма принимает `program_name` свободным текстом и позволяет заполнить позже (`ApplicationCreateDialog.tsx:67–71`); action передаёт institution ID, program name и ручной university deadline, но не program/intake IDs (`platform-admissions-actions.ts:359–377`). Это полезный существующий путь, однако он не даёт точную связь с требованиями набора.

Контракт до UI: стабильная catalog identity института/программы/набора, сохранение выбранной версии источника и связь с одним case preparation. Совпадающие названия/slug другого университета — не одна сущность. Перестановка или перепубликация набора не перепривязывает уже выбранное. Idempotency по повтору команды плюс business uniqueness одной и той же подготовки в деле; разные наборы/программы остаются отдельными вариантами. Не массово преобразовывать старый free text.

Отдельно определить в общем контракте §11 выбор программы без подтверждённого опубликованного набора (в существующих карточках такие программы есть). Отсутствие дедлайна само по себе не должно блокировать подготовку; нельзя выдумать дату/период, тихо выбрать первый intake или вводить новое одобрение сотрудником. Вернуть только подтверждённую сервером идентичность; этот сценарий не отменяет правило #729 о скрытии неподтверждённых наборов и редакторских пометок в публичном просмотре.

### U2. Нет выбора, tier-aware состояния и перехода к общей подготовке — P1

Web route получает actor, но передаёт в Detail только университет, locale, favorite и consultation (`portal/universities/[id]/page.tsx:27–31,64–76`); Detail содержит чтение/избранное/консультацию/внешние ссылки (`Detail.tsx:178–239`). iPhone Detail принимает institutionId/initialItem и рендерит тот же каталог с консультацией (`UniversityDetailView.swift:39–75,143–160`). Ни один вход не имеет подготовку/selection state. `MyAdmissionView` сейчас строит очередь из overview+finance и входов документов/оплаты/уведомлений/сообщений (`MyAdmissionView.swift:3–9,26–45`), без нового перечня подготовок по выбранным программам.

Навигационный accessTier уже есть: web — verified authority (`src/lib/supabase/student-portal-authority.ts:21–30`), native — `caseState` mapping (`PortalModels.swift:57–66`). Использовать его для presentation, но разрешение на создание повторно проверять сервером в собственном деле. `closed` также мапится в assisted: не расширять write lifecycle только из-за видимого tab. Конкретные допускаемые case-state операции обязан определить общий контракт §11.

Нужны состояния на каждой программе/наборе: доступно выбрать; выбор сохраняется; уже выбрано; запись получена — открыть; ошибка сохранения с безопасным retry; каталог изменился/снят; нет подтверждённого набора; доступ изменился. После успешного выбора — сразу требования/подготовка, без очереди одобрения выбора. Никаких фиктивных «подано» или «принято».

### U3. Реальный срок нельзя брать из общей ближайшей даты университета — P1 для выбора

Detail web и iPhone корректно различают startDate/startMonth/deadline, выводят время и timezone при их наличии (`Detail.tsx:64–89`; `UniversityDetailView.swift:416–438`). Их status helpers вычисляют закрытие в timezone конкретного intake (`src/lib/portal/universities.ts:90–116`; `PortalModels.swift:140–164`). Это сохранить.

Но соседний `nearestUniversityIntake` сворачивает все программы университета в одну дату, сравнивает только UTC day и возвращает лишь kind/value (`src/lib/portal/universities.ts:130–165`; `PortalModels.swift:168–192`). Он может показывать сегодняшний уже закрывшийся по времени intake как ближайший и теряет принадлежность к программе/набору. Это source-level риск, не наблюдённый live сбой. Не использовать его для карточки выбранной подготовки или её CTA; при изменении соседнего summary передавать program/intake context и тот же timezone-aware статус.

Неизвестная/неподтверждённая дата не становится датой закрытия или процентом готовности. Показать абсолютную подтверждённую дату; публичный просмотр сохраняет правило #729 о скрытии неподтверждённых наборов и редакторских пометок. Обновлённый дедлайн не должен переписывать историю уже отправленного комплекта. Допустимые опубликованные сведения о проверке, источник подтверждённого срока и выбранная версия сохраняются.

### U4. Видимость наборов и примечаний требует сверки web/iPhone с контрактом #729 — P2

Web фильтрует `unknown`/`needs_reconfirmation` intake целиком (`Detail.tsx:112–115`), native отображает все и подписывает статус (`UniversityDetailView.swift:327–330,406–413`). RPC отдаёт content публикации без этой фильтрации (`148_platform_university_catalog_publication.sql:212–232`); это разница клиента, а не доказанное расхождение DB.

Веб не выводит `content.notes`, `content.verifiedOn` и `intake.note`: весь detail (`Detail.tsx:64–98,178–239`) содержит даты/ссылки, но эти поля не использует. Native их показывает (`UniversityDetailView.swift:163–169,189–191,388–390`). Само наличие поля не доказывает, что всё его содержание допустимо публиковать: substantive сведения и редакторские пометки требуют семантической проверки. `intake.verifiedOn` сейчас не показан ни там, ни там.

Это расхождение клиентов, а не автоматическое доказательство недостающей функции веба. Действующее владельческое правило #729 в `DESIGN.md:258–263` исключает из публичного просмотра unknown/неподтверждённые наборы и редакторские «нужно уточнить»/«не подтверждено». Согласовать оба клиента с этим правилом, сохранив подтверждённое закрытие набора, реальные факты, официальные ссылки и допустимую provenance. Не предлагать публичную плашку «Срок уточняется» взамен скрытого набора. Восстанавливать только подходящие опубликованные содержательные примечания после проверки смысла; не публиковать notes целиком. Программа без подтверждённого набора следует общему selection-контракту §11 без выдуманной даты/набора и нового approval gate.

### U5. Новый write-путь должен учитывать текущие различия загрузки и восстановления — P2

Web route различает недоступное чтение и отсутствующую карточку; отказ favorites скрывает toggle вместо ложного false, отказ консультаций скрывает блок вместо ложного отсутствия заявки (`page.tsx:35–63`). Native держит initialItem, отдельно обновляет карточку и показывает refresh-failed (`UniversityDetailView.swift:21–35,48–59,131–138`), favorites умеет ошибку/откат, консультация — самостоятельный sheet. Эти полезные формы восстановления сохраняются.

Native при `cardMissing=true` и наличии initialItem всё ещё попадёт в content-first ветку (`:27–31,48–59`), а предупреждение content реагирует только на refreshFailed (`:131`). Сейчас это чтение; добавляя выбор, нельзя позволить старому snapshot выглядеть готовым к действию после снятия публикации. Сервер повторно проверяет current publication/access, UI явно сообщает stale/missing; данные не стираются до понятного восстановления. То же относится к смене программы/набора и поздним async ответам: ответ старого выбора не меняет текущий selection.

## Ограниченный implementation brief

1. **Общий контракт §11, до кнопок.** Один schema/API owner фиксирует stable identity/версии, idempotent selection, доступ assisted+case lifecycle, read списка выбранных вариантов и одного workspace подготовки. Staff и student write-entry используют общую доменную операцию, но свои права. Реальные требования и подтверждённые сроки идут из того же ресурса. Фото/паспорт — начальные требования EVO для простой программы; существующие полные checklist не сокращать и не зашивать два поля в UI.
2. **Web detail и вход в preparation.** Сохранить Atlas hero/атрибуцию, заголовок/место/favorite, факты, официальные ссылки и консультацию. Добавить рядом с конкретным program/intake одно главное действие assisted: «Выбрать программу» → pending → подтверждённая подготовка; повтор — «Открыть подготовку». Если подтверждённых наборов несколько — явный компактный выбор перед записью, без скрытого первого значения. Добавить быстрый якорь «Программы и наборы» с реальным числом; сверить видимость notes/verification с #729 и восстановить только подходящие опубликованные содержательные сведения после семантической проверки. Не раскрывать редакторские пометки и неподтверждённые наборы. Web mobile перестраивает action/факты вертикально; фильтры/позиция каталога при возврате сохраняются. Новый маршрут подготовки уточнить в общей route map, не изобретать здесь отдельную систему заявок.
3. **iPhone parity после фиксации API.** Сохранить #925 title-first, program-count jump, attribution DisclosureGroup, один фон программы, native Link/heart/consultation sheet, inline nav title и theme fix. Program picker/action — SwiftUI control; detail preparation — native push, self-contained выбор при необходимости sheet. Session/access и receipt обновляют тот же shared state; open-after-save не требует перезапуска app. Использовать текстовые стили/Dynamic Type, 44pt hit regions, safe areas; не копировать размеры/DOM веба и не редизайнить общий tab bar в этом срезе.
4. **Связанный workspace «Моё поступление».** Добавить фактический перечень выбранных программ с их набором/сроком/следующим действием и переходом к требованиям. Несколько вариантов сохраняются. Это зависимость общих документов/комплектов §11, а не локальная копия catalog state. Выбор сразу виден разрешённому сотруднику; приложение в университет и «Отправить пакет в EVO» остаются разными состояниями.

Не расширять каталог новым содержанием, рейтингами, картами, маркетинговыми блоками, лимитами выбора, оплатой/договорами или повторной регистрацией. Не перепубликовывать данные/фото и не менять лицензии ради UI. Текущий manual staff entry и старые application IDs сохранить.

## Реальная приёмка и пределы

- **Read и сохранность:** существующий университет/программа с реальными публикациями; одинаковые identity/version и допустимые опубликованные факты на desktop, mobile web и iPhone. Фото/автор/license/crop disclosure, официальный сайт, program page, источник подтверждённого срока, подходящие содержательные примечания, сведения о проверке и favorites/consultation остаются достижимыми. Проверить скрытие неподтверждённых наборов и редакторских пометок по #729 в обоих клиентах; подтверждённое закрытие и реальные факты сохраняются. Отправку консультации не выполнять ради read-smoke.
- **Право:** существующие approved и assisted Auth identities. Approved читает/сохраняет избранное/обращается в EVO, но прямой selection write запрещён. Assisted получает только своё дело; чужой ID, отозванный доступ и недопустимый lifecycle отклоняются сервером. Сам факт approved никогда не даёт документы. Admin preview не заменяет Student proof.
- **Выбор:** на отдельно авторизованном реальном QA деле выбрать существующие программу и набор → сразу preparation с теми же ID в CRM/web/iPhone. Повтор в том же клиенте, сеть после server commit и одновременный второй клиент не создают дубликат. Другая программа/набор добавляется рядом, не перезаписывает прежнюю. Staff exact selection и student selection сходятся в тот же ресурс; free text остаётся free text.
- **Сроки:** реальный опубликованный intake с date-only, date+time+TZ, startMonth и неизвестностью; не подменять дату старта дедлайном. Если реальных комбинаций нет — явно отметить непроверенные случаи, не создавать fake dataset для скриншотов. Осмысленные pure tests проверяют границы времени и DTO, но не называются живой бизнес-приёмкой. Изменение публикации не меняет identity ранее выбранного intake.
- **Ошибки:** real unavailable/expired Auth/stale publication/late response состояния дают правильный исход без fallback success. Публикацию не снимать в managed DB ради теста; сценарий требует своего authorized QA. Существующий catalog snapshot можно читать при refresh error, но он не даёт ложную запись.
- **UI:** web desktop + 320/390px, light/dark, RU/KY, keyboard/focus/zoom; программа, выбранный набор, срок и CTA читаются вместе, возврат восстанавливает каталог. iPhone simulator portrait на заявленном устройстве + большой Dynamic Type/light/dark/RU/KY; проверка нового push/back/выбора без перестройки #925. VoiceOver и hardware жесты/сеть требуют отдельной фактической проверки; не объявлять их пройденными по снимку. Один пакет осмотра и максимум одно исправление/подтверждение.
- **Проверки:** scope-local web typecheck/lint/contracts и iOS build; новую семантику выбора/идемпотентности проверить meaningful contract tests. Повторять неизменённую #925-проверку целиком не нужно; дополнительно проверить только прямые регрессионные риски новых action/navigation/state веток. Ни новый server write, ни shared §11 E2E пока не выполнен: нужные общие API на проверенном main отсутствуют.

Источник актуальности: все текущие утверждения о поведении основаны на исходниках данного SHA; визуальные сведения iPhone — явно переиспользованный receipt с совпадением view blob. Свежих web detail/нового iPhone runtime снимков у этого агента нет. Внешние университетские сведения сейчас не исследовались и не обновлялись.
