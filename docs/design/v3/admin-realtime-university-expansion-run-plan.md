## Холодное продолжение

Прочитать `AGENTS.md`, `CONTEXT.md`, `DESIGN.md`, текущий раздел
`docs/EVO_LAUNCH_PLAN.md`, последнюю запись `docs/PLAN_CHANGES.md`, затем этот файл.
Сверять GitHub, рабочую ветку и принятую сервером версию независимо друг от друга.
Не переисполнять миграции 001–148, импорт продаж или уже опубликованные пять вузов.
Не трогать чужой dirty checkout. После проверки — точный reviewed SHA, PR, обычные
защищённые CI/schema/release gates, подтверждение реального контейнера и туннеля.

## Что одобрено и что остаётся неизменным

- Admin выполняет работу Sales и Admissions под собственной личностью и может
  быть ответственным. Это не подмена роли и не обход условий договора/оплаты.
- Auth, активность сотрудника, организация, разделение данных и журнал автора
  остаются обязательными. Приватные ответы/результаты Student не открываются staff.
- Чат остаётся существующим внутренним чатом сотрудников с тремя каналами.
  WAHA, номера, рассылки, amoCRM и lead-agent этим проходом не активируются.
- Каталог расширяется по материалам EVO с проверкой публичных фактов. Личные
  документы абитуриентов, переписка, мусор и внутренние условия не публикуются.
- Одна постоянная Supabase-база, обычный вход и preview того же сервера через SSH.
  Новая резервная копия по прежнему решению владельца не запускается; остальные
  release gates не отключаются, сохранённые recovery-артефакты не удаляются.
- Использовать реальные входы и реальные пути исполнения. Не создавать фиктивных
  сотрудников, лидов, оплат или сообщений для доказательства работы. Отсутствие
  настоящего входа/разрешения отмечать как ограничение, не заменять симуляцией.

### A1 — Admin как полноценный сотрудник

Отдельный исполнитель владеет forward migration **149** и непосредственно
затронутыми назначениями/UI. Перед созданием ещё раз проверить свободный номер.
Аудировать последнюю действующую цепочку RPC, а не только исходную миграцию:
Sales eligibility/создание/назначение/claim/реестр; Admissions handoff/подтверждение,
назначение куратора, замещение, finance stop-factor и выбор исполнителей задач.
Проверки уже включающие Admin не переписывать. Не редактировать применённый SQL.
Общее правило: активный Admin допустим там, где нужен Sales или curator, без
расширения Student-доступа. Роли и аудит фактического автора остаются Admin.

Приёмка: настоящий Admin виден в форме создания лида и в доступных назначениях;
проверки команд согласованы со списками. Полный путь создания/передачи требует
реального лида/дела: если их нет, не объявлять этот путь проверенным.

### A2 — чат обновляется сам

Исполнитель владеет `TeamChat.tsx` и его узкими вспомогательными файлами.
Аудит подтвердил existing private Broadcast → changes RPC, reconnect/visibility/
online catch-up и периодическую догрузку. Надпись «Обновления подключены» означает
соединение, а не доказанную доставку. На здоровом соединении показать
«Сообщения появляются автоматически», ручное восстановление — при ошибке.

Дизайн: спокойный рабочий чат, одна область сообщений и один composer; соблюдаем
EVO `DESIGN.md`, цели 44 px, клавиатуру и мобильную ширину. Не перегружаем статусами.
Историю при чтении не прокручивать принудительно, черновик не терять.
Дополнительные поведенческие исправления только после реального воспроизведения.

Настоящая доставка проверяется в двух вкладках текущего Admin разрешённым рабочим
сообщением. Состояние второй вкладки читается до её активации и раньше 30 секунд,
иначе visibility/таймер могут скрыть отсутствие Broadcast. Это не доказательство
двух сотрудников, unread или межролевого доступа. Разрешение на одно служебное
сообщение в «Общий» запрошено один раз; без ответа не отправлять.

Исследователь владеет reviewed-content JSON, новым source memo и photo manifest/
типами, плюс forward migration **150** только для расширения существующего
допустимого списка фотографий (номер проверить; migration148 не менять).
Начальная партия:
Taylor’s, INTI, UCSI, City, Xiamen Malaysia, Monash Malaysia; SCUT, ZJUT, GDUT,
China University of Petroleum (East China), Ocean University of China, ECUST.
Если подтверждений недостаточно, вуз остаётся неопубликованным с точной причиной.

Инвентаризировать найденные институциональные заметки EVO, но не объявлять весь
архив обработанным. Каждая карточка: официальное название/кампус, страна/город,
понятное описание, проверенные программа/язык/даты либо явное «уточнить», URL и
дата проверки. Intake не равен дедлайну; старые цены/рейтинги не переносить как
актуальные. Фото именно этого кампуса, разрешённое использование и атрибуция.
Не выдавать наличие заметки за партнёрство EVO. Публичный DTO — только допустимые
проверенные сведения. Сохранить текущую ясную композицию карточек с реальными фото.

Root проверяет источники и staged preview, затем публикует через существующий
Admin approval путь; direct SQL/service-role publication не используется.
Уже опубликованные APU/Sunway/MMU/XJTLU/UNNC не дублировать. Пробелы фото указывать.

## Проверка, release и честный итог

Работать параллельно по трём изолированным владельцам, интегрировать одним root.
Проверять типы/сборку, затронутые реальные команды и UI; не устраивать повторную
широкую проверку провайдеров. Не заменять protected gates и не представлять
технические fixtures/CI как фактический бизнес-проход. До release — независимое
ревью точного head, затем сверка current main, schema/release evidence и runtime.
Если gate требует недоступного реального входа или дополнительной власти,
зафиксировать точный blocker, не обходить его.

Для компиляции SQL разрешён только временный технический schema-only sandbox:
`evo_admin_schema_compile_20260910` в уже работающем локальном
`supabase_db_evo-platform-local`. Копируются реальные определения схемы, не строки
клиентов/Auth; используются настоящие миграции, без mock bootstrap. Это не вторая
база продукта и не доказательство бизнес-прохода. Не менять существующие базы;
после проверки удалить только созданную этим проходом техническую базу.

При передаче перечислить: merged SHA, deployed SHA, миграция, URL production и
localhost, фактические UI-доказательства, число опубликованных вузов, фото и
непроверенные реальные сценарии. Закрывать этап только по его доказательствам.
