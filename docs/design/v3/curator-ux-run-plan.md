### Небольшие исполнимые части

- [ ] **UX-2 — рабочие права куратора.** Изменять срок и приоритет только своей
  назначенной операционной задачи в доступном ему деле; видимость студенту,
  исполнитель, финансовые полномочия и университетские дедлайны не меняются.
  «Внутренний срок» здесь означает срок операционной задачи, а не обязательно
  `student_visible=false`. Править не только форму: запрет находится и в RPC
  из migration 110. Использовать reviewed forward migration, существующие
  `platform-admissions-task-actions.ts` и `calendar/TaskControls.tsx`.
  Приёмка: реальное разрешённое изменение, durable readback и audit с причиной;
  чужая задача, изменение исполнителя/видимости и stale version отклоняются.
  Сохранить различие date-only/time и организационную зону Asia/Bishkek.
- [ ] **UX-3 — принятие передачи.** Текущий назначенный куратор подтверждает
  ознакомление либо просит конкретное уточнение; состояние и следующий шаг
  видны в существующей карточке. Это отдельное подтверждение поверх уже
  атомарного handoff, не откат договора/дела и не повтор starter tasks.
  Не закрывать доступ до принятия и не ставить выдуманный срок первого контакта:
  использовать согласованную дату. Начать с `platform-student-handoff.ts`,
  migration 088 и `profile/ProfileSalesTransition.tsx`.
  Приёмка: реальное принятие текущим владельцем и запрос уточнения сохраняются;
  повтор команды не дублирует события; посторонний не подтверждает. Admin не
  выдаёт своё действие за принятие куратором. При смене владельца сохранять
  прежнюю историю, но не приписывать его подтверждение новому куратору.
- [ ] **UX-4 — история в существующем профиле.** Расширить `caseTimeline()` в
  `src/lib/v3/profile-source.ts`, начав с `staff_student_case_activity`
  (migration 089). Соединить разрешённые события передачи, задач, заявок,
  документов, платежей и переписки; краткая строка ведёт к исходной записи.
  Не отдавать raw audit payload, не копировать переписку во второе хранилище.
  Словарь, стабильный порядок, дедупликация и пагинация едины. События изменения
  только срока/приоритета взять из реального audit: task transition stream
  их сейчас не содержит. Приёмка: видны существующие реальные события и новые
  события UX-2/3/6, без дублей; роли получают только разрешённые сведения.
  Не открывать полную Admissions-историю Sales/студенту; прежний запрет
  показывать автора/время приложения документа отдельно не отменён.
- [ ] **UX-6 — нагрузка и замещение.** Добавить компактное представление Admin
  в существующую поверхность: активные дела, открытые задачи и ближайшие сроки
  по кураторам; без выдуманного процента занятости, рейтинга и HR-модуля.
  Минимальный вариант замещения — один канонический владелец, временное
  переназначение Admin с причиной/сроком и явным возвратом; не параллельный
  доступ двух владельцев и не новый автоматический scheduler.
  Переиспользовать `assign_student_case_curator` и invoker-wrapper из 117.
  До изменения показать Admin затронутые дела и открытые задачи: нынешняя
  смена владельца сама задачи не переносит. Закрытые задачи/историю не менять.
  Приёмка: агрегаты сверяются с реальными доступными данными; при действительно
  необходимом замещении меняются ownership, scope/access version и выбранная
  открытая работа, возврат подтверждён. Нет частично успешного сообщения,
  осиротевших задач, доступа у неактивного заместителя или скрытого расширения прав.
- [ ] **UX-8 — ясный кабинет студента.** В `portal/OverviewView.tsx` оставить
  компактные ответы: что требуется от студента, что делает EVO, какой следующий
  шаг и срок; далее прямой переход к существующему документу/задаче.
  `student_portal_overview_v1` и `portal-source.ts` остаются источниками истины.
  Не угадывать исполнителя по тексту: если его нет в проекции, сначала добавить
  разрешённое каноническое поле. Ожидание извне показывать лишь когда оно
  подтверждено данными, без нового механизма ожиданий из неутверждённого №5.
  Приёмка: реальный student login, совпадение шага/даты с источником, рабочая
  ссылка и честное пустое состояние; внутренние задачи/заметки и чужие файлы
  не раскрываются. Нет parent portal, нового reminder engine или рассылок.
  Live invite/SMTP proof остаётся отдельным gate, не обещанием от UI-правки.

### UX/UI: критерии для этой волны

Лёгкая коррекция существующих экранов, **не большой редизайн**. Применить ко всем
изменяемым формам, карточке/истории, представлению замещения и portal overview;
общие компоненты поправить один раз. Не запускать отдельный тотальный аудит
или миграцию UI-библиотеки. Сохранить [frontend rules](frontend-rules.md).

1. **Понятный статус.** Видимые загрузка/сохранение/успех/ошибка/пустота;
   «Сохранено» только после подтверждённой записи. Не показывать бесконечный
   spinner вместо ошибки или старые данные как свежие. При ошибке поля сохраняются.
2. **Знакомый язык.** «Принять дело», «Перенести срок», «Нужно уточнить», а не
   RPC/enum/UUID. Использовать существующий `wording.ts`; технические детали
   не превращать в постоянные поясняющие баннеры.
3. **Контроль и свобода.** Явные «Отмена»/«Назад», предсказуемое закрытие формы,
   сохранение контекста списка. Undo только для действительно обратимых действий;
   для необратимых — понятное предупреждение/подтверждение, не фиктивная отмена.
4. **Последовательность.** Те же токены, формы, названия, кнопки и состояния
   на всех затронутых экранах. Существующий светлый V3, не новый визуальный мир.
5. **Защита от ошибок.** Проверка полей рядом с вводом, понятная причина запрета,
   защита от двойного submit и конфликта версий. Перед сменой куратора — точный
   состав переноса; подтверждение не требуется для каждого безобидного клика.
6. **Фиттс: удобно попасть.** Частые действия рядом с объектом, главная кнопка
   заметна и имеет подпись. Ориентир для частых touch-controls — 44×44 CSS px;
   не сжимать всё ради плотности. Keyboard focus и доступное имя обязательны.
7. **Хик: не перегружать выбором.** Одно главное действие на активную форму,
   вторичные — спокойнее; редкие настройки раскрываются по запросу. Не прятать
   ежедневное действие в цепочку меню и не убирать нужные возможности ради числа.
8. **До трёх понятных переходов для частых задач.** Цель: от контекстного
   списка открыть нужную форму/информацию без блуждания. В приёмке записать
   старт, переходы и полный путь включая ввод/подтверждение; не выдавать
   сокращённый navigation count за весь процесс. Три клика — целевой ориентир,
   не универсальный закон и не основание убрать важное подтверждение.
9. **Не dense.** В обзоре только статус и следующий шаг, детали — в существующих
   разделах. Не собирать все таблицы/метрики/формы в одну панель; не дублировать
   вкладки, не уменьшать шрифт/отступы, чтобы всё вместить. Иерархия и свободное
   пространство сохраняются на desktop и 393px; нет горизонтального overflow,
   мелких безымянных иконок и действий, доступных только при hover.

Методические источники проверены 08.09: [Nielsen heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/),
[Fitts](https://www.nngroup.com/videos/fittss-law-links-buttons/),
[ясное различие вариантов](https://www.nngroup.com/articles/explicit-differences/),
[ограничения правила трёх кликов](https://www.nngroup.com/articles/3-click-rule/),
[W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).
44px — наш ориентир удобства, не утверждение о минимуме WCAG: SC 2.5.8 задаёт
24×24 CSS px либо предусмотренные исключения. Присланные владельцем статьи
сохранены в product.md как происхождение его требований.
Pending/error-поведение реализовывать существующими form actions; актуальная
официальная основа проверена через Context7:
[useActionState](https://react.dev/reference/react/useActionState) и
[useFormStatus](https://react.dev/reference/react-dom/hooks/useFormStatus).

### Быстрый порядок и честная проверка

1. Один docs-only PR фиксирует выбор, UX-правила и границы. Текущая работа
   заканчивается этим планом, не выдаёт новые функции за уже реализованные.
2. До реализации определить контракты событий/видимости и переноса открытых
   задач. UX-2 и UX-3 можно вести независимо; UI-правки идут в той же небольшой
   части. Миграционные номера и merge координирует один исполнитель.
3. UX-4 собирает события UX-2/3; UX-6 добавляет свои события в ту же проекцию.
   UX-8 можно вести параллельно после фиксации разрешённой student-проекции.
   Не держать готовые права/формы до готовности всей истории и замещения.
4. Для docs — classifier, whitespace, links, short `Release contracts` и
   независимое exact-head review. Для реализации — затронутые реальные
   RPC/Auth/browser пути, повторное чтение записи и роль-отказы; один desktop
   и mobile проход по изменённым сценариям с keyboard/состояниями/скриншотами.
   Не повторять full Supabase/build/browser suite на каждую правку; новые
   forward migrations получают соответствующую реальную DB-проверку.
5. Нет настоящего аккаунта Admissions/student, реального дела или разрешённого
   бизнес-действия — назвать точный пробел проверки. Не создавать synthetic
   users/cases/files или mock-success ради зелёного результата; Admin preview
   не доказывает права другого реального actor. Production данные, migration
   apply, deployment и отправки остаются отдельными gates. QR не запрашивать.
