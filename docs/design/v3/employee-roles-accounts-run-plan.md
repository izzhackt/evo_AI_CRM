# Команда EVO: роли, отделы и личные аккаунты

## Подготовка пилотного подключения (2026-09-15)

**Сделано:** в действующей production-базе через обычный Admin-интерфейс
`/v3/settings?section=staff&view=roles` сохранены четыре редактируемых черновика.
`localhost:3000` — SSH-доступ к этому же production, не отдельная база.

| Черновик | Разрешений | Предлагаемая область при назначении |
| --- | ---: | --- |
| Продажи — свои записи | 15 | `own` — собственные записи |
| Продажи — общие разделы | 11 | `organization` — общие разделы |
| Сопровождение — свои дела | 27 | `own` — назначенные куратору дела |
| Сопровождение — общие разделы | 11 | `organization` — общие разделы |

После перезагрузки все четыре остались черновиками с нулём сотрудников;
повторное открытие редакторов подтвердило количество сохранённых разрешений.
Опубликованных прав у них нет, журнал приглашений пуст. Публикация, назначения,
создание аккаунтов и письма **не выполнялись**. На начальной проверке список
сотрудников содержал только действующего Admin, отделы ещё не настроены.

Две роли на человека нужны из-за существующих областей доступа: каталог,
знания, чаты и создание командных задач работают на уровне организации;
лиды/дела и личные задачи — только в разрешённой области. Это конфигурация
существующей системы, не роли, зашитые в код. `own` не означает все дела Китая.
Для доступа по стране потребуется отдельное согласованное назначение;
личные командные задачи нельзя включать в роль с областью `direction`.

Продажи: свои лиды/клиенты, краткое дело и финансы, договоры, чтение переписки,
реестр продаж и задачи. Сопровождение: анкета, полное дело, документы,
маршрут, заявления, визы, решения и задачи. Общие роли: рабочее пространство,
каталог, утверждённые знания, шаблоны договоров/ответов, общий и профильный чат,
создание задач. Финансовые подтверждения, защищённые исключения, Admin,
внешние отправки и команды провайдерам не добавлялись.
`document.validation.attest` — служебное действие проверки файлов, не право
куратора; его отсутствие не обходить. Независимая проверка исходников
подтвердила необходимые права обычного пути анкета/бланк/ZIP; это ещё не
подтверждение первого входа реального сотрудника.

**Осталось для подключения:**

1. Подключить почтового отправителя. Проверка живого Supabase Dashboard
   15 сентября показала built-in email и предложение Set up custom SMTP.
   Встроенная почта отправляет только адресатам команды проекта Supabase;
   она не подходит для рассылки найденному списку сотрудников.
   [Официальные ограничения SMTP](https://supabase.com/docs/guides/auth/auth-smtp).
   У владельца запрошены адрес отправителя и сервис; пароль в чат не нужен.
2. Сверить существующие Auth-пользователи перед созданием. Живой исходный
   справочник содержит 12 сотрудников, но имена/адреса не копируются в Git;
   использовать ранее указанную ссылку на справочник. Он не является финальным
   согласованием полномочий. Не превращать должность CEO/IT в Admin автоматически.
3. Одним списком согласовать конкретных адресатов, роли и области доступа;
   опубликовать нужные роли после просмотра влияния и начать с одного приглашения.
   Неопределённую отправку сверять по тому же запросу, не дублировать письмо.
4. Сотрудник сам задаёт личный пароль и выполняет первый и повторный вход.
   Проверить его реальные разрешённые действия и ограничения. Только тогда
   считать onboarding подтверждённым и подключать согласованную остальную группу.

Связанный P1: владелец ещё выбирает клиента для проверки анкета → бланк → ZIP.
В просмотренном списке Admissions нет доступных дел. При создании заявления
обнаружена отдельная UI-недоработка: каталог не подключён к форме, хотя
серверный путь уже есть. Исправление описано в `docs/EVO_LAUNCH_PLAN.md`,
но ещё не выполнено. Старые тестовые дела Docs не восстанавливать.

Следующие записи сохраняют историю предыдущих выпусков, а не текущие версии
production или команды повторить уже завершённые операции.

### Открытые условия подключения команды

- **Отдельно с командой:** сверка аккаунтов, подтверждение получателей/прав,
  настоящее письмо и первый вход. Такие письма этим запуском не отправляются;
  production, provider и Storage acceptance не подтверждены локальным onboarding.

Текущий контракт recovery/Admin-preview и browser-inventory proof использует
`schemaVersion: 2` и `systemRole: admin | staff`; Sales/Admissions — сценарии
или представления Admin, не отдельные системные роли. API `staff_access_snapshot`
и workspace ролей сохраняют `schemaVersion: 1`. Это описание исходного кода
([recovery](../../../scripts/test-v3-managed-supabase-recovery-orbstack.mjs),
[inventory](../../../scripts/platform-provider-runtime-inventory.mjs)), а не новый
результат этих recovery/inventory suites и не изменение исторического S1/D1 proof.

## Результат

Один сотрудник — один личный аккаунт на его Gmail, собственный пароль и несколько
назначений ролей при необходимости. Admin меняет отделы, должности, роли и области
доступа через интерфейс. Новая бизнес-роль не требует релиза; новое действие,
которого ещё нет в продукте, требует реализации и включения в каталог прав.
Gmail здесь означает адрес входа, не отдельный проект Google OAuth.

## Границы модели и начальные настройки

- **Должность ≠ отдел ≠ роль доступа.** Начальные шаблоны: руководство,
  руководитель Sales, Sales, руководитель Admissions, куратор, ассистент,
  маркетинг, бухгалтерия. Они редактируемые, не новые значения enum.
- Руководитель видит разрешённую командную работу; исполнитель — назначенные
  записи. Внешний вид CEO/IT-должности сам по себе не выдаёт Admin или доступ к
  персональным данным/финансам. Итоговые назначения подтверждаются перед выдачей.
- Admissions: Китай, Малайзия, Европа и ОАЭ имеют сотрудников в источнике;
  Турция остаётся без назначенного владельца. Один куратор может вести несколько
  направлений. Не создавать недостающих сотрудников или назначения из догадки.
- Проверять **право и область одного назначения вместе**. «Admissions: Китай»
  плюс «Sales: вся организация» не означает Admissions по всем направлениям.
- Admin остаётся защищённым системным уровнем и функциональным superset для staff;
  последнего активного Admin нельзя снять/заблокировать. Student — отдельная
  защищённая граница. Личные ответы/результаты тестов не открываются сотрудникам.
  Отдельные чувствительные подтверждения сохраняют текущие персональные grants.
- Публикация изменённой роли показывает затронутых людей и изменение доступа;
  архивирование используемой роли требует выбора замены. История не удаляется.
  Отзыв прав использует живую серверную проверку/`access_version`, не ждёт нового JWT.
- Существующий Auth без связи, Student-email и членство другой организации требуют
  явного разрешения конфликта с доказанной принадлежностью; не менять пароль,
  не присоединять и не пересоздавать аккаунт автоматически.
- Для приглашений сохранить request-id, ограничения повторов и reconcile после
  неизвестного результата. Отозванная ссылка не должна активировать доступ.
  Состояния запроса, доставки и первого входа — разные факты; недоказанное не
  показывать как успешное. Не считать `auth.resend` готовым API повторного invite.
