# D2 — проверенные поля и анкета Student Profile

Статус: D2 реализован и проверен локально на синтетическом деле; не выпущен и не
принят на реальном клиенте. Прежний Auth/browser proof: база `ce404b87`, с
незакоммиченными изменениями во время проверки, не immutable commit.
Текущая интеграция включает main `561aa920`: новый SQL-порядок158→159–161 проверен,
полная Auth/DB/browser-проверка итогового main ещё требуется.
Результаты и границы: [локальное доказательство D2](references/2026-09-13-student-profile-fields-local-proof.md).
Родитель: [единая EVO Docs](evo-docs-unification-run-plan.md), этап D2;
[ADR0028](../../adr/0028-unify-document-automation-inside-evo-platform.md).
Этот документ нужен исполнителю для продолжения работы без прежнего чата.

## Результат для куратора

В существующем деле открыть «Анкета» → при необходимости «Начать анкету» →
заполнить/проверить поля рядом с оригиналом → скачать черновик или готовый
EVO Student Profile. Один профиль на дело; второй студент, вход или база не нужны.
Не требовать заранее заполненную анкету или применённый список документов.
Оригинальный файл не изменяется. Ничего не отправляется университету или Gemini.

## Одна модель данных

1. Расширить `platform.student_profiles` из migration053, сохранив identity,
   связи с организацией/делом, уникальность, revision и ограничения непустых значений.
   Девять фактов допускают NULL: preferred_display_name, communication_language,
   citizenship_country, residency_country, current_education_summary,
   academic_summary, language_summary, budget_band, next_step.
   Не подставлять имя из строки дела, контакты покупателя, «неизвестно» или выдуманный бюджет.
2. Явная команда создания использует действующее `require_case_operator` и
   `profile.manage`, request_id и блокировку дела. expected_profile_revision=0
   означает отсутствие профиля; создание даёт revision1. Повтор одного запроса
   идемпотентен, конфликт другого редактора виден пользователю. Чтение ничего не создаёт.
   Начальные consent=not_recorded, evidence=NULL, decision_participant_labels=[].
3. Staff/Student snapshot допускает существующий частичный профиль без checklist.
   Тройка applied requirement ID / checklist revision / required fields согласована:
   без применённого требования первые два NULL, fields=[]; иначе все проверяются.
   Отсутствие профиля отличается от пустого профиля. Права S2/migration156 не ослаблять.
4. Сохранить полный существующий upsert как полный контракт. Требуемая дата рождения
   должна присутствовать; необязательная, но проверенная дата допускается.
   Экспорт договоров и другие потребители по-прежнему проверяют нужные им факты.
5. Перенести реестр 61 поля и шесть групп из исходного `src/shared/profile.ts`.
   `date_of_birth` хранится в одноимённой канонической колонке;
   `nationality` означает гражданство и хранится в citizenship_country;
   `country_of_residence` — в residency_country. Остальные 58 — расширения профиля.
   Не хранить второе текущее значение трёх общих полей. Русские подписи интерфейса,
   оригинальные ключи и пределы шаблона сохраняются.
6. Отдельно хранить историю предложений и метаданные проверки: источник, точная
   версия документа, страница, ограниченный фрагмент, confidence при наличии,
   extracted/needs_review/conflict/confirmed. Предложение не меняет подтверждённый факт.
   Подтверждённое человеком пустое значение тоже является решением; будущая обработка
   не заполняет его молча. Противоречия разрешает человек, не последний ответ AI.
7. Все изменения поля/проверки/конфликта используют одну revision профиля и аудит.
   Обычный полный upsert при `IS DISTINCT FROM` общего значения снимает подтверждение
   только соответствующего поля. Реализовать это на общей границе БД, не только в UI.
   Клиент не может объявить предложение результатом Gemini; provider ingestion — D3.

## Доступ и экспорт

- Чтение полной анкеты/источников: действующие права дела и `profile.read.full`.
  Изменения: `profile.manage`. Не предоставлять доступ к личным тестам Student.
- Отдельный серверный POST экспорта требует `profile.read.full` и `document.download`
  для того же дела, ожидаемую revision и режим draft/final. Не переиспользовать grant
  скачивания загруженного оригинала для сгенерированного DOCX.
- Данные, путь и hash шаблона выбирает сервер. Экспорт читает подтверждённый snapshot,
  проверяет формат/длину и повторно проверяет полномочия и revision перед ответом.
  Не принимать произвольные значения анкеты или путь шаблона из браузера.
- Черновик содержит только подтверждённые значения и явную отметку «Черновик».
  Финальная анкета требует девять обязательных полей из реестра и отсутствие
  неподтверждённых непустых/невалидных полей и любых конфликтов, включая пустые optional.
  Гражданство/страна могут иметь120 символов в модели, но60 в шаблоне:
  показать конкретное препятствие экспорта, не обрезать данные молча.
- Переносится штатный hash-pinned шаблон и ограниченный DOCX renderer, не Express,
  SQLite, второй Auth или весь старый runtime. Форматы загружаемых оригиналов
  PDF/JPEG/PNG не расширяются этим исходящим экспортом.
- Аудит экспорта фиксирует попытку с profile revision/template hash и исходом
  формирования, не утверждает получение файла человеком. Постоянные артефакты,
  университетские формы, ZIP и история пакетов принадлежат D4.

## Срезы реализации и следующий gate

После резервирования158 для S2 актуальные номера D2 —159–161. Прежний локальный
proof158–160 сохраняется как история; новый SQL-порядок проверен отдельно,
а полный browser gate итоговой версии остаётся открытым.

1. D2a: migration159 — частичная каноническая анкета, явное создание и согласованные
   snapshots; DTO и существующие потребители реализованы.
2. D2b: migration160 — реестр, история предложений/проверок и команды; компактный
   UI шести групп в существующей «Анкете», TS-реестр и реальные server actions.
3. D2c: migration161 — серверный аудит попытки/исхода; штатный DOCX renderer,
   POST экспорта и интерфейс готовности/скачивания. Оба RPC блокируют организацию
   до request/membership/profile; проверка revision и неизменяемость исходов сохранены.
4. Положительный путь через реальные локальные Auth/БД/браузер пройден: пустая
   анкета без checklist, общие и расширенные поля, подтверждённая пустота,
   черновик и финальный DOCX, конфликт двух редакторов без потери черновика
   и посторонних подтверждений. Это синтетическое, не клиентское доказательство.
5. Далее: независимое exact-head ревью и обычный PR; полный CI только на
   замороженном main перед выпуском. D2 не включать в параллельный выпуск S2.
   Managed-миграции, выпуск и реальная клиентская приёмка остаются открытыми.

Следующие этапы не исчезают: D3 — реальный разрешённый файл/Gemini и устойчивые
задания; D4 — университетские формы/пакеты; D5 — согласованное сопоставление и перенос
всех доменов; D6 — сквозная приёмка и точечное выключение старого приложения.
Непустые исходные данные, история и действующие сервисы сохраняются.

## Согласованный интерфейс D2a/D2b

- `start_student_profile(p_organization_id, p_student_case_id,
  p_expected_profile_revision, p_reason, p_request_id)` — явное создание.
- `staff_student_profile_fields(p_student_case_id)` — STABLE JSON snapshot:
  student_case_id, profile (null либо id/revision), can_initialize/can_review/can_export,
  fields (field_key, value, review_state, reviewed_at, source_document_version_id,
  source_page, proposals). Группы и русские подписи берутся из TS-реестра.
  Страны читаются без потери канонических120 символов; предел60 проверяет экспорт.
- `review_student_profile_field(p_organization_id, p_student_case_id, p_field_key,
  p_decision, p_value, p_proposal_id, p_source_version_id, p_source_page,
  p_expected_revision, p_reason, p_request_id)` — единая мутация.
  Решения: confirm (непустое значение), clear (NULL, подтверждённая пустота),
  reject_proposal (отклонить конкретное предложение без смены канонического факта).
  Выбор предложения получает значение/источник из БД; ручное исправление не
  притворяется ответом AI. Отклонение предложения само не разрешает конфликт.
- Текущие review states: extracted/needs_review/conflict/confirmed; существующее
  каноническое поле без проверки D2 читается как needs_review. Отсутствующая
  необязательная строка и явное confirmed NULL различаются.
- История предложений и решений неизменяема; текущая запись содержит дополнительное
  значение только для58 unmapped полей. Для трёх mapped-полей такое дублирование
  запрещено ограничением. Хранимая история прежнего значения не является вторым
  текущим источником.
- D2b не публикует вызов создания «AI proposals». Действительный ingestion и
  проверенный job context добавляет D3. Приватная подготовка схемы не разрешает
  чтение или отправку настоящих клиентских файлов провайдеру.

## Проверенные основания

### D2c — исторический серверный экспорт и аудит (заменён в D4)

Ниже описан выпущенный D2c, не активный путь нового D4-кандидата. После реальной
проверки сохранения/истории в0cc1f5c7 transient route и handler удалены, а forward164
закрывает grants двух старых RPC. Migration161 и история попыток сохранены.
Текущий путь: [сохранённые файлы и скачивание](evo-docs-export-artifacts-contract.md).

- POST `/api/v3/student-cases/[studentCaseId]/profile-exports` принимает только
  `mode`, `expected_revision` и `request_id`. Actor, значения и шаблон выбирает
  сервер; обычная сессия пользователя читает существующий snapshot. Admin preview
  не экспортирует. Проверка Origin повторяет действующий export-handler проекта.
- Migration161: begin/complete RPC доступны только `service_role`, не public,
  anon или authenticated. Сервер передаёт проверенную связь authUser/membership/org;
  БД повторно проверяет живую identity и оба права в одном деле. Ключ остаётся на
  сервере; служебный клиент не используется для чтения значений анкеты.
- Begin связывает попытку с делом, actor, revision, mode, hash шаблона и request ID.
  Повтор точного запроса возвращает прежнюю попытку без повторного формирования,
  новый ID — только новое явное действие. Другой fingerprint с тем же ID — конфликт.
  Pending означает неизвестный исход: без таймерного перехвата или слепого retry.
  После terminal outcome повторное скачивание требует нового явного экспорта;
  файлы в D2 не сохраняются. UI не называет прежний generated доставленным файлом.
- Complete сохраняет hash/размер сформированного файла либо фиксированную ошибку.
  Перед generated повторно проверяются живые права и revision. Изменение доступа
  или анкеты сохраняет failed outcome, а не откатывает запись через исключение;
  ответ не содержит DOCX. Неизвестный/недоступный результат аудита — ошибка без файла.
- Route входит в действующий API allowlist, штатный DOCX — в tracing standalone
  сборки. Данные, исходники документов и готовые файлы в аудит не попадают.

Исходная модель: migration053 и `src/lib/platform-student-profile.ts`;
новые права: migration156. Источник шаблона/реестра: отдельный EVO Docs main
`6e7cf741`, `src/shared/profile.ts`, `src/shared/profile-readiness.ts`,
`server/docx-template.ts`. Персональные файлы для этого проектирования не читались.
