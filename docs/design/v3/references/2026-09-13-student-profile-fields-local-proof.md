# D2 Student Profile — локальная проверка

Дата: 2026-09-13. D2 реализован и проверен на синтетическом деле в изолированном
Supabase `evo-local-4c16e7aa83b2eb24`. Это не production release и не приёмка
реального клиента. Продолжение: [контракт D2](../evo-docs-profile-fields-contract.md)
и [единый план D0–D6](../evo-docs-unification-run-plan.md).

## Что проверено

В существующей вкладке «Анкета» работают явное создание частичного профиля,
61 поле в шести компактных группах, ручное подтверждение/очистка и DOCX export.
Три общих поля остаются в канонических колонках; ещё 58 хранятся как расширения.
Источники и предложения не принимаются автоматически, Gemini не вызывается.

Реальный локальный Admin Auth и обычные Sales-команды создали синтетическое дело
через canonical handoff. Затем браузер подтвердил:

- отсутствие профиля без checklist и его явное создание без придуманных данных;
- девять обязательных полей и дополнительное поле, подтверждённую пустоту после
  повторного чтения, одну анкету с итоговой revision14;
- конфликт устаревшего сохранения с сохранением черновика редактора и других
  подтверждений; корректную identity страницы и отсутствие framework overlay;
- скачивание отмеченного черновика и готовой анкеты через настоящий серверный POST.

`acceptance.json`: `synthetic=true`, `businessAcceptance=false`,
`browserErrorCount=0`, `browserWarningCount=1`. Нулевая warning count не заявляется.
SQL отдельно подтвердил replay, canonical invalidation, audit и исходы
`profile_changed`/`access_changed` без выдачи файла после изменения revision/прав.
После исправления порядка блокировок migration160 эта SQL-проверка повторена.

## Что остаётся

Нужны независимое ревью замороженного D2 commit, PR, соответствующие managed
миграции и один exact-main release proof. В полный configured-путь добавлен один
вызов того же D2 browser-сценария после прежних проверок: без второй базы, повторного
применения миграций или provider-вызовов. Следующий release proof должен содержать
`STUDENT_PROFILE_FIELDS_BROWSER_VERIFIED`; локальный focused PASS выше не доказывает
эту новую интеграцию в полный запуск. Порядок подключения проверен регрессией:
RED `01a09b2243477352bf4690fd7440bbc6`, затем 11 PASS
`01a09b22966c7892b87d8bdef89969bf`.

Реальная анкета требует выбранного
разрешённого дела и человеческой проверки результата; этот отчёт её не заменяет.
D3 — реальные разрешённые документы/Gemini и устойчивые задания; D4 — формы,
пакеты и постоянная история; D5 — согласованное сопоставление всех доменов;
D6 — сквозная приёмка и точечное выключение standalone. Исходные данные,
старый runtime и provider-настройки этим локальным доказательством не изменены.
