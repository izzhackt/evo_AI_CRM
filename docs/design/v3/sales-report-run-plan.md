## Результат для отдела

Один раздел «Отчёт продаж» на существующей главной V3: год, месяц или весь
год, короткие итоги и список продаж. Создание и исправление записи выполняются
в платформе. Исходную Google-таблицу не изменяем. Импорт — начальный перенос,
а не постоянная двусторонняя синхронизация; после перехода EVO хранит рабочие
записи. Не создавать новую CRM, роли, Auth, бухгалтерию или parent portal.

Владелец разрешил самостоятельно выбрать минимальные продуктовые решения и
развернуть результат в production для своей проверки. Приёмка кураторских
сценариев на настоящих делах отложена из-за отсутствия дел, не объявлена успешной.
Техническая проверка и независимый review остаются обязательными.

  четыре фактические даты находятся вне месяца вкладки. Не использовать дату

- «Стоимость» и «Оплачено» — снимок сумм в источнике. «Оплачено» не содержит
  дат транзакций и не становится подтверждённым финансовым ledger или первым
  платежом для handoff. Не менять существующие financial evidence grants.
- Деньги считать отдельно по валютам, без выдуманного курса. Разрешён только
  однозначный разбор суммы/валюты. Смешанные валюты, пояснения, неоднозначные
  суммы сохраняются с исходным текстом и признаком «Нужно уточнить»; не включать
  их в денежные итоги как ноль. Пустой статус не означает «Не оплачено».
- Исторический менеджер — исходное имя, не текущий владелец лида. Связь с
  действующим сотрудником/клиентом необязательна и устанавливается явно;
  не создавать фиктивные аккаунты, клиентов или дела ради импорта.
- Оригинал и полное происхождение сохраняются приватно. В рабочие поля входят
  заявитель/телефон, страна, вуз, программа, направление, intake, договор,
  суммы и менеджер. Родительские контакты/ИНН не превращаются в новый продукт
  или общедоступную выдачу; исходный защищённый файл остаётся местом их хранения.

## Минимальный контракт платформы

Канонический модуль в `platform`/`platform_private`, root migration 134.
Реестр продаж — самостоятельный факт отчётности, не вторая customer identity
или копия payment ledger. Опциональная связь ведёт к существующему клиенту/лиду.
Source snapshot хранится отдельно от редактируемых значений, с checksum,
sheet/row, стабильным import key. Повторный импорт не создаёт дублей и никогда
не перезаписывает последующие ручные изменения.

Admin читает/редактирует отчёт организации. Sales читает/меняет только записи,
явно закреплённые за его действующим membership; новые собственные записи
закрепляются сервером. Исторические строки без такого соответствия доступны
Admin до явного назначения. Не выдавать отделу чужую финансовую информацию
только на основании существующего `sales.read`. Curator/student доступа нет.
Использовать существующую Auth, cookie-bound RPC, строгие DTO, серверную
валидацию, tenant checks, `expected_version`, request id и audit без raw PII.

Операции: добавить, исправить, архивировать ошибочную запись и восстановить.
Архивирование исключает запись из текущих итогов, но сохраняет историю.
Исправление сумм имеет явный статус сверки. Не называть остаток бухгалтерским
долгом: это разница стоимости и оплаченного по сопоставимым отчётным данным.
План продаж хранится отдельно как целевое количество по месяцу/менеджеру,
если такая цель указана; факт рассчитывается из записей, а не копируется из
ручной итоговой ячейки. Расхождение с исходным «Факт» показывать при переносе.
Причина ручного изменения сохраняется в приватной истории команд, связанной
с request ID. Общий audit получает тип/версию/ссылку на команду, не произвольный
текст с возможными персональными данными. Не запрашивать объяснение и затем
безвозвратно отбрасывать его.

## Завершение воронки автоматически попадает в отчёт

Дополнение владельца 08.09: последний успешный этап существующей воронки
должен сам добавлять продажу. В коде это колонка «Переданы» (`handed_off`),
производная от завершённой передачи Sales → Admissions, не произвольная смена
`stage_key`. Не добавлять второй словарь этапов и не обходить gate договора/
первого платежа. Отказ или незавершённая квалификация не считаются продажей.

Создание записи привязать в той же транзакции к канонической записи
`platform.sales_admissions_handoffs`, только к завершённому handoff. Уникальность
`organization_id + lead_id` и стабильный source key защищают от повторов.
Повтор передачи, обновление страницы и повтор команды не создают новую строку
и не затирают ручные исправления. Покрыть существующие завершённые передачи
идемпотентным backfill, не создавая сами передачи и не связывая старые строки
Google с людьми нечётким сравнением имён.

Отчётный месяц — фактический момент передачи в Asia/Bishkek. Сохранять реальные
client/lead IDs, имя/телефон, исходного Sales-владельца, доступные поля программы.
Не выдавать время подтверждения договора за дату его подписания. Стоимость и
полная накопленная оплата не выводятся из суммы первого платежа: если полного
снимка нет, оставить неизвестными и показать необходимость дополнить запись.
Admin override также не создаёт выдуманные денежные факты. Кнопка из записи
ведёт в существующий профиль, не новый customer dossier.
Отчётная проекция не должна отклонять допустимую каноническую передачу из-за
более строгого лимита текста. Длинные имя/подпись менеджера можно отображать
ограниченным фрагментом с явной отметкой; непригодный телефон не обрезать до
другого номера. Если пригодного имени нет, хранить неизвестное значение и
показать «Имя не указано», не создавать выдуманную личность. Исходные данные
остаются в каноническом профиле; приватная provenance фиксирует факт ограничения
и IDs. Ручные и импортируемые записи по-прежнему требуют имени.

## UI без перегруза

Спокойная светлая рабочая поверхность существующего V3, те же шрифты/отступы.
Ссылки «Обзор» / «Отчёт продаж» на `/v3/main?view=sales`, query для года/месяца.
Сначала период и одно действие «Добавить продажу», затем итоги и записи.
Не превращать страницу в мозаику карточек; подробные поля — в отдельной форме.
Pending, success, ошибки и пустое состояние различаются. Черновик сохраняется
при ошибке/stale, повтор возможен только после явной сверки актуальной версии.
На mobile нет горизонтальной прокрутки всей страницы и крошечных кнопок.
Использовать обычные переходы/раскрытие деталей; новых анимационных зависимостей нет.
