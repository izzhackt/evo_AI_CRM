# Student Portal: завершение рабочих сценариев

Дата: 2026-09-11. Статус: согласованные функции реализованы, проверены
изолированно и опубликованы в принятой версии `4e35b896`;
реальная Student-приёмка открыта. [Подтверждение публикации](references/2026-09-11-student-portal-workflow-release.md).
Основание: владелец поручил завершить функциональный чек-лист и прямо исключил
редактирование email и самостоятельное восстановление пароля.

## Объём

Один согласованный блок: завершить существующий цикл работы с документами и
обращениями в текущих staff и Student интерфейсах. Сохранить компактный дизайн,
реальную Supabase Auth, серверные полномочия и единую модель данных.
Отметки ниже фиксируют реализацию, не прохождение бизнес-приёмки.

- [x] Куратор / Admin принимает последнюю доступную проверенную версию документа,
  возвращает её на исправление или отклоняет; причина обязательна для двух
  отрицательных решений. Использовать существующую команду проверки, её
  idempotency, аудит и уведомление Student. Проверять полномочия, текущую версию,
  доступность файла и допустимость решения на сервере.
- [x] Форма сохраняет ввод при ошибке/неопределённом результате, не показывает
  успех до подтверждения и сообщает об изменении версии другим сотрудником.
- [x] Ответ куратора создаёт уведомление только владельцу обращения в его деле.
  Повтор той же команды не создаёт дубликат; текст staff-only данных не попадает
  в Student DTO. Отметка прочтения сохраняется штатной командой.
- [x] Уведомление открывает нужный ответ. Уже открытые Student страницы получают
  изменения без обязательного ручного обновления; обновления ограничены видимой
  вкладкой, не стирают ввод и не открывают Student данные в Admin preview.
- [x] Новые заполненные формы и ответы прошли изолированный E4 на 320/393 px;
  проверены перенос текста, сохранение ввода и действия без горизонтального
  переполнения. Клавиатурная навигация и закрытие мобильного меню проверены.
- [ ] Повторить новые формы/ответы на настоящем деле с клавиатурой и на экранах
  320/393 px. Технический browser-сценарий не закрывает эту бизнес-приёмку.

Не входят: email editing, forgot-password, хранение/показ исходного пароля в CRM,
новая регистрация, платёжный эквайринг, кабинеты родителей/партнёров, доступ staff
к приватным тестам, автосообщения внешним адресатам, расширение каталога или
переустройство инфраструктуры. Сбор email и выдача доступов остаются процессом
EVO. Supabase Auth продолжает владеть аутентификацией.

## Реализация и проверка

1. Использовать существующие review RPC, V3 source adapters и формы. Новые
   изменения SQL — только forward migration в корневом `supabase/migrations`.
2. Расширить существующий Student notification feed и read-receipt, сохранив
   действующие document/overdue события и owner/case фильтрацию. Не создавать
   вторую ленту или внешний канал рассылки.
3. Выполнить lint, настоящую сборку и DB/Auth/browser проверки на точной версии.
   Владелец 2026-09-11 явно разрешил изолированные тестовые данные для обязательных
   проверок публикации. Использовать настоящий PostgreSQL/Auth и приложение с
   техническими fixtures в отдельной тестовой среде; не создавать их в production
   и не выдавать технические проверки за приёмку на настоящем деле студента.
4. Независимый reviewer проверяет реализацию, соответствие этому плану и
   достоверность доказательств. После проверки отправить изменения в GitHub;
   существующие защищённые проверки и порядок публикации не обходить.

Актуальная документация проверена 2026-09-11. Context7 сообщил об исчерпании
месячной квоты; прочитаны официальные первоисточники и bundled Next.js docs:

- [Next.js revalidatePath](https://nextjs.org/docs/app/api-reference/functions/revalidatePath):
  обновление серверных данных после подтверждённой команды.
- [Next.js useRouter](https://nextjs.org/docs/app/api-reference/functions/use-router):
  `router.refresh()` запрашивает новое серверное представление, сохраняя
  незатронутое клиентское состояние; он не заменяет серверную инвалидацию.
- [Supabase database functions](https://supabase.com/docs/guides/database/functions):
  ограниченные execute grants, явный `search_path` и проверка пользователя для
  privileged database functions.

## Оставшаяся приёмка на настоящем деле

Эти пункты не разрешают придумывать клиента, файл, вопрос, ответ, оплату или
оценку. Выполнять только с настоящим выбранным делом и действующим доступом.

- [ ] Студент получает доступ и видит только своё дело.
- [ ] Этап, требования, сроки и видимые задачи соответствуют реальному плану.
- [ ] Настоящий документ: загрузка → мотивированное исправление → новая версия
  → принятие; студент видит решения и скачивает нужную версию.
- [ ] Изменения заявки/визы отражаются у студента с правильной историей.
- [ ] Настоящие частичная/полная оплата и возврат дают правильный остаток.
- [ ] Настоящее обращение → ответ назначенного сотрудника → уведомление →
  открытие ответа → сохранённая отметка прочтения.
- [ ] Оба теста: собственные ответы студента → выход → продолжение → завершение
  → сохранённый результат; чужие результаты недоступны.
- [ ] Те же разрешённые действия на телефоне, включая файлы и формы.

Для каждого выполненного пункта записывать реальное доказательство без личных
данных и секретов. Если нет выбранного дела, подходящего рабочего события или
Student сессии, назвать точный недостающий вход; не ставить отметку о готовности.
