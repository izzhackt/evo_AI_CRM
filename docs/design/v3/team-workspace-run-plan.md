## 3. Решения, предлагаемые по умолчанию

### Корпоративный чат — нативно в EVO, WhatsApp отдельно

Базовый вариант — существующая Supabase Auth + Postgres + private Realtime.
Аккаунт сотрудника автоматически является его аккаунтом чата; рабочий телефон
не является паролем, идентификатором доступа или обязательным условием входа.
Из Slack берём понятные каналы, ответы, непрочитанное и поиск, а не его полный
набор функций, плотность или оформление.

| Канал | Кто видит и пишет по умолчанию |
| --- | --- |
| `#общий` | Все активные сотрудники |
| `#продажи` | Sales и Admin |
| `#поступление` | Admissions и Admin |

Student, неактивный сотрудник и человек без Platform membership не допускаются.
Admin видит все три канала, но пишет от собственного имени. Не создаём отдельные
логины чата или новую роль «менеджер». Один staff role задаёт отдел на старте;
несколько отделов у одного человека — отдельное будущее расширение.

WAHA session — подключённый WhatsApp-аккаунт/номер, **не аккаунт сотрудника EVO**.
Если нужен только чат внутри платформы, WAHA не требуется. Если те же сообщения
должны приходить в WhatsApp, понадобится отдельный мост: сотрудник, его номер,
сессия, разрешённая группа, права, синхронизация и подтверждение доставки.
Одна общая сессия отправляет от одного WhatsApp-аккаунта, а не от всех сотрудников.
Для отправки именно от личного рабочего номера нужна привязка соответствующего
аккаунта; один сотрудник не получает управление чужой сессией.
В этот запуск нативный чат входит; мост W2 — отдельный предложенный вариант,
не скрытая зависимость и не автоматически разрешённая внешняя отправка.

### Минимальный чат первого выпуска

- Три фиксированных канала; история с пагинацией, текст, ответы в обсуждении
  одного уровня, упоминание конкретного участника, поиск внутри доступного канала.
- Непрочитанные сообщения и переход к первому непрочитанному; можно приглушить
  канал. Никаких массовых `@everyone`, push/email/WhatsApp-уведомлений по умолчанию.
- Правка своего сообщения с отметкой; удаление своего сообщения оставляет
  заглушку, ответы не теряются. Admin moderation — явное действие с аудитом.
- Статусы «Отправляется / Отправлено / Не отправлено», сохранение текста при
  ошибке и повтор с тем же request ID. «Прочитано всеми» без доказательств не показывать.
- «Создать задачу» из сообщения, предварительный просмотр задачи до сохранения.
  Смена статуса дела не происходит от фразы в чате.
- Файлы, личные сообщения, звонки, голосовые, emoji reactions, сложный редактор,
  пользовательские каналы, online/typing и AI-бот в корпоративном чате отложены.
  Это ограничения MVP, а не пункты, которые можно молча объявить готовыми.

### Задачи: единый интерфейс, разные границы данных

1. **Задача по студенту:** переиспользовать существующие `case_tasks` и команды,
   включая version/reason/coverage guards. Общая форма в календаре и деле студента;
   серверный поиск с пагинацией вместо первых 100 дел. Без расширения прав Sales
   на закрытые части дела и без изменения видимости Student по умолчанию.
2. **Рабочая задача сотруднику:** отдельный staff-only домен `platform.staff_tasks`
   в той же БД; не снимать NOT NULL с `case_tasks.student_case_id` ради быстрого insert.
   У case-task events тоже обязательная связь с делом, RLS зависит от дела,
   календарь делает INNER JOIN, coverage wrappers блокируют дело/куратора.
   Расширение всех этих путей опаснее небольшого отдельного домена.
3. Общие UI и утилиты срока/статусов/валидации/command receipts/audit используются
   повторно. Список `/v3/tasks` объединяет разрешённые case/staff задачи с явным
   типом; запись идёт в соответствующую единственную каноническую команду.
   Не копировать case-task engine, не создавать вторую копию задачи по студенту.

Поля новой staff-задачи: название, ответственный, срок (необязателен),
описание (необязательно), статус; приоритет — в дополнительных настройках.
Без дела студента и без `student_visible`. Creator, assignee и Admin видят задачу;
остальные сотрудники не получают её автоматически из-за общей роли/канала.
Создатель назначает себе или активному коллеге своего отдела; Admin — любому
активному сотруднику. Изменять содержание/назначение может creator/Admin,
состояние — также assignee. Определить ожидаемую версию и аудит каждого изменения.

Связь с сообщением — provenance, не выдача новых прав: проверить канал и
допустимого исполнителя до создания, не копировать закрытый текст в уведомление.
При потере доступа к каналу ссылка не раскрывает содержание. Обратная метка
«задача создана» не раскрывает детали участникам канала без доступа к задаче.

Уведомления сотрудникам: назначили задачу, изменили его задачу, упомянули в чате.
Для просрочки — живая выборка «Просрочено», не новый scheduler ради MVP.
Текущие `platform.notifications` привязаны к делу и обслуживают Student;
не превращать их в staff inbox через ослабление Student RLS. Добавить узкое
staff-only хранилище событий/прочтения, общую кнопку уведомлений и дедупликацию
по событию+получателю. Не рассылать сообщения во внешние сервисы.

## 4. Волны и параллельная работа

| Блок | Результат | Зависимости / владелец | Готово, когда |
| --- | --- | --- | --- |
| R0 | Этот план, подтверждённый остаток, UX и границы | Координатор | Docs reviewed/pushed; реализация отдельно |
| R1 | «Настройки → Сотрудники»: список, приглашение, роль, блокировка, восстановление входа | Backend/identity исполнитель | Реальный сотрудник принял разрешённое приглашение; повтор не дублирует membership; blocked теряет доступ; последний Admin защищён |
| R2 | `/v3/tasks`, общий task adder, case shortcuts, staff tasks, «Мои / Назначенные мной», просрочено | Tasks исполнитель после R1 authority contract | Реальная задача создаётся без студента и доступна исполнителю; case-команды не ослаблены |
| R3 | `/v3/team-chat`, три канала, сохранение/обновления/ответы/поиск/упоминания | Chat исполнитель параллельно R2 после R1 | Два настоящих сотрудника обмениваются сообщением; история сохраняется; нет доступа чужому отделу/Student |
| R4 | Задача из сообщения, staff notifications, навигация и короткая сквозная проверка | Координатор после R2+R3 | Сообщение → одна задача → уведомление → выполнение; нет утечки текста, дублей и недоступных назначений |
| R5 | Один общий релиз, same-server tunnel, handover и открытый остаток | Координатор после review/gates | Exact image/schema/health подтверждены, новый интерфейс открыт владельцу; live ограничения названы |

Параллельность — не три агента, меняющих одну таблицу. Координатор единолично
распределяет следующие номера миграций после свежего main, владеет `AppShell`,
`navigation.ts`, route/role contracts, общим notifications contract и интеграцией.
Tasks владеет task-domain/UI; Chat — chat-domain/UI. R1 сначала фиксирует общие
staff authority/read contracts; чтение и проектирование R2/R3 можно делать раньше,
но их активные UI нельзя выдавать за рабочие до реального backend. Отдельный
независимый reviewer не является соавтором проверяемого блока.

R1 не создаёт новый каталог пользователей: переиспользовать migrations 083/087,
существующие staff actions/RPC. Supabase Auth invite выполняется только сервером
после проверки действующего Admin; создание Auth identity не выдаёт роль.
Применение membership требует действующего Admin actor, не service-key обхода.
Состояния приглашения/частичного сбоя и безопасное продолжение обязательны;
не повторять неясную отправку вслепую. Пароли в UI администратора не показывать.
Номер телефона — необязательные внутренние контактные данные, не автоимпорт
адресной книги. Новые реальные адреса и получатели должны быть подтверждены.

R3 хранит историю в `platform`, а не в Realtime. Для приватных обновлений —
проверенная Realtime authorization и минимальные сигналы изменения без текста
сообщений; чтение содержимого всегда повторно проверяет активного сотрудника и
канал в Postgres/RPC. Realtime проверяет права при подключении: блокировку/смену
отдела надо доказать также на уже открытом соединении, не только после logout.
После reconnect/refresh читать пропущенное по устойчивому курсору, не терять
сообщения и не создавать дубли. Сбой обновлений виден пользователю; история из
БД — основной путь, а не молчаливая подмена сломанного транспорта. Не вводить
свой WebSocket-сервис, Redis, отдельный chat SaaS или дополнительные public endpoints.

## 5. UX/UI: продолжить выбранный вариант 2

- **Продажи:** Воронка, Отчёт, «Клиентские сообщения» (существующий Inbox).
  Admissions сохраняет разрешённые клиентские разговоры: перенос пункта меню

- **Поступление:** Рабочий список, Сводка. Страны внутри списка, не пять меню.
- **Общее:** Задачи, Командный чат, Календарь для разрешённых ролей, База знаний.

- **Настройки:** Сотрудники и существующие настройки; аккаунт внизу.
- Чат: компактный список трёх каналов + просторная переписка; обсуждение в правой
  панели только после открытия. На телефоне один слой за раз с понятным «Назад».
- Одна заметная кнопка «Создать задачу»; в форме сначала название/исполнитель/срок,
  остальное по раскрытию. В деле Student контекст уже выбран.
- Белые поверхности, оригинальный EVO logo, текущие шрифты/токены и красный акцент.

## 6. Проверки — короткие, но настоящие

Для docs-only R0: проверка ссылок/границ/фактов, `git diff --check`, независимый
review и выбранные classifier-ом PR checks. Не запускать product build/browser/БД
ради текста. Не менять CI ради пропуска обязательного контекста.

Для реализации проверять риск изменённого блока, не весь продукт после каждого
коммита. Node22.23.1, существующие зависимости и инструменты; production build
уже выполняет TypeScript, отдельный дублирующий tsc не нужен. Каждый файл теста
исполняется один раз на выбранном gate; полный `EVO platform CI` — один раз на
замороженном exact-main кандидате, повтор только после изменения кандидата.

Минимальные реальные исходы:

1. Staff приглашение → вход → роль/отдел; заблокированный сотрудник теряет права,
   другой staff не может выдавать себе Admin. Не блокировать единственного
   реального Admin ради теста; подтверждать такой запрет на безопасном реальном пути.
2. Сообщение между двумя разрешёнными staff → второй браузер → refresh/reconnect;
   один текст в БД. Повтор запроса, ошибка сети, конфликт правки не теряют draft.
3. Запрет Student/чужому отделу на чтение, поиск, запись, подписку и прямую ссылку;
   смена отдела/блокировка при открытой вкладке не раскрывает новые сообщения.
4. Задача без дела → исполнитель → уведомление → выполнено → повторное открытие.
   Из сообщения создаётся ровно одна задача, actor/source permissions перепроверены.
5. Case task через прежнюю команду → календарь/дело; отсутствует в Student при
   закрытой видимости; coverage/version restrictions сохранены. Общие staff tasks
   и сообщения никогда не попадают в portal/assessment результаты.
6. Один desktop/mobile/keyboard проход по реально изменённым экранам, затем
   реальная миграционная/RLS проверка затронутых доменов и обязательный release gate.

Новые mock/fake/demo пользователи, сообщения, заглушки API и поддельные receipts
не разрешены этим планом. Для многопользовательской приёмки нужны реальные
подтверждённые участники; старая узкая fictional Student QA-разрешённость не
расширяется на корпоративный чат. Если данных/сессии/адресата нет — отметить
конкретный непроверенный исход, продолжить независимые блоки и не писать PASS.
Production-бизнес-статусы не продвигать фиктивно до прибытия ради проверки.

## 7. Не ставить внешние блокеры на критический путь

**W1 — рабочий Sales Inbox и Lead Agent.** Сначала read-only проверить точную
`crm_primary`, действующий webhook и runtime controls. Healthy container не
означает WORKING session, WORKING не означает доставку. Исторически pairing
был отклонён владельцем. При необходимости телефона остановить только W1;
не запрашивать QR и не перезапускать сессию без нового разрешения. Затем при
согласованном адресате доказать реальное inbound → один lead/диалог → черновик
агента → одобренный человеком ответ → provider receipt. Ровно один inbound
owner; никакого legacy worker или параллельной записи amoCRM. Агент не читает
корпоративные каналы и сам не отправляет сообщения. Это отдельная активация,
не побочный эффект переноса Inbox в меню.

**W2 — WhatsApp-мост корпоративного чата, если владелец выберет его.** Перед кодом
подтвердить, требуется зеркалирование трёх групп или отправка от каждого рабочего
номера; проверить установленный WAHA engine/tier и допустимость числа сессий.
Только отдельные employee bindings и allowlist конкретных групп; не читать
личные чаты/все контакты и не использовать sales `crm_primary` для сотрудников.
Затем входящие/исходящие, webhook signature, event-ID дедупликация, echo-loop
защита, reconcile неопределённой доставки, блокировка ушедшего сотрудника и
явные статусы EVO/WhatsApp. Без утверждённых номеров, групп, доступа к телефонам
и разрешения внешней отправки W2 остаётся неактивным. Никакого нового billed
сервиса/лицензии без согласования. Нативный чат работает без W2.

**B — принятие прежнего продукта.** При появлении настоящих дел пройти реальный
Sales → handoff → Curator → Portal путь в пределах фактического этапа студента,
проверить отчёт. Не повторять импорт. Не обещать рабочую production-интеграцию
amoCRM без свежей отдельной проверки. English calibration и проверка понимания
русской ORVIS — улучшение качества методики, не выдуманный сертификат CEFR.

**D — отложено:** страны EU/AE/TR по регламентам, partner/parent accounts,
контроль личных тестов кураторами, сравнение офферов, полноразмерный Slack clone.
[#687](https://github.com/izzhackt/evo_AI_CRM/issues/687) удаляет временные portal
rollback exceptions только после отдельного owner acceptance. Не удалять старую
Auth identity, записи, backup или рабочие worktree по старому TODO.

  подтверждены в [O6](business-operations-universities-run-plan.md#проверки-и-выпуск)
