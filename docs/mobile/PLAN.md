# План: мобильное приложение студента на Expo (iPhone и Android)

Решение: ADR 0038 (2026-11-09). Справочники лежат в `docs/mobile/reference/`:

- `web-portal-spec.md` — экраны, RPC и дизайн кабинета;
- `ios-app-inventory.md` — поведение и тесты iPhone 1.1;
- `expo-research.md` — версии и правила магазинов;
- `open-problems.md` — ошибки, которые надо закрыть.

Владелец 09.11 сформулировал задачу так: «один код для iPhone и Android, новый
дизайн, сразу новые обновления, исправить ошибки, сделать полностью».

### Контракт сервера: согласия при входе (миграция 356)

Обе команды вызываются с JWT студента, схема `platform`, EXECUTE только у `authenticated` (anon и service_role отказ `42501`). Личность определяет сервер (`auth.uid()`), в аргументах её нет. Работают для студента кабинета и для заявителя анкеты; сотруднику отказ.

**Чтение: `platform.portal_consent_status_v1()`** без аргументов. Ответ (ровно шесть полей):
`{ policyVersionCurrent: "2026-11-07", policyAcceptedVersion: string|null, aiStatus: "granted"|"declined"|null, aiPolicyVersion: string|null, aiPolicyVersionCurrent: "2026-10-25", needsDecision: boolean }`.
`needsDecision = true`, если Политика не принята по текущей версии ИЛИ выбор об ИИ не сделан по текущей версии. Решение об ИИ «declined» по текущей версии (позднее «Отозвать») - это решение, `needsDecision = false`. Политика считается принятой и без записи, если анкета студента подана с галочкой текущей версии. Показывайте экран только при `needsDecision = true` И если `policyVersionCurrent` / `aiPolicyVersionCurrent` равны версиям, зашитым в сборку (иначе принятие будет отвергнуто и экран нельзя закрыть); при несовпадении или сбое чтения кабинет не запирать (доступ ИИ к данным без согласия закрывает база).

**Запись: `platform.portal_consents_accept_v1(p_policy_version text, p_ai_policy_version text, p_source text, p_request_id uuid)`**. Аргументы: `p_policy_version = "2026-11-07"`, `p_ai_policy_version = "2026-10-25"`, `p_source = "ios"` или `"android"` (допустим и `portal_web`), `p_request_id` - UUID, создаётся один раз при показе экрана и повторяется при повторе после сбоя сети. Одной транзакцией принимает Политику и записывает «разрешено» для ИИ (внутри та же `portal_ai_consent_set_v1`). Ответ - то же состояние, что у чтения; успех, когда `needsDecision = false`, `policyAcceptedVersion = "2026-11-07"`, `aiStatus = "granted"`. Повтор с тем же `p_request_id` и теми же аргументами возвращает прежний итог без нового события журнала; тот же `p_request_id` с другим источником - конфликт.

**Коды ошибок** (SQLSTATE: текст сообщения): `42501: consent_unavailable` (нет входа, сотрудник, нет студента); `22023: consent_invalid_request` (нет `p_request_id`); `22023: consent_invalid_source`; `22023: consent_policy_version_mismatch`; `22023: consent_ai_policy_version_mismatch`; `55000: consent_request_conflict`; `54000: consent_rate_limited` (не больше 20 изменений Политики в час); от внутренней записи ИИ могут прийти `ai_consent_*` (в том числе `ai_consent_rate_limited`, `ai_consent_request_conflict`). При любой ошибке ничего не записано (Политика и ИИ откатываются вместе). Для экрана достаточно: сбой записи - «Не удалось сохранить, повторите» с тем же `p_request_id`.

Порядок в приложении: вход (S3) -> при временном пароле смена пароля -> чтение `portal_consent_status_v1` -> при `needsDecision` экран -> запись -> дальше. Строки взять из веб-словаря `PORTAL_DICTIONARIES.consentGate` (RU/KY, `src/lib/portal/i18n.ts`). Ссылка на Политику одна на обе локали.

## Раздел W — тот же порядок в веб-кабинете

Веб и приложение должны оставаться одним продуктом, поэтому решения #1355–#1363
переносятся и в веб. Каждое идёт отдельным небольшим PR, после того как
соответствующий срез приложения закрепит решение:

#1355.

## Проверки

- **Каждый срез:**
  - `npx tsc --noEmit`, `npx expo lint`, Jest в `mobile/`;
  - ручной проход изменённого экрана на симуляторе iPhone 17 Pro и на
    эмуляторе Android на локальном синтетическом стенде.
- **Без записи в production.** Production-сессия студента нужна только для
  итоговой проверки M8 и только с разрешения владельца.
- **Серверные S1–S5:** собственные тесты маршрутов и проверка
  `scripts/release/evo-production-browser-smoke.mjs`, если затронут вход.
- **CI:** проверки `mobile/` встраиваются в существующий workflow «Fast
  checks» и включаются только при изменении `mobile/` или общих модулей.
  Требуемые проверки ветки main не меняются.

## Что нужно от владельца

1. Пройти первый запуск Android Studio (лицензии Google) — нужно для эмулятора.
2. Перед первой облачной сборкой: `npx eas-cli login` в терминале
   (аккаунт `izzhackts-team`).
3. Team ID Apple (developer.apple.com → Membership details).
4. Google Play Console (25 $, личный или на компанию).
5. Текст «как платить» для «Оплаты» (#1359).
6. Разрешение на удаление `ios/` после замены в App Store.
