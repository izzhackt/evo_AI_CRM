# EVO student web cabinet: specification for the Expo (React Native) app

Worktree: рабочая копия `mobile-expo`
HEAD: `2218479ee` (includes #1412 "вид кабинета по образцу Акылмана", #1417, #1418).
Paths are relative to the worktree root. `lib/...` means `src/lib/...`.

## 0. Read this first (headline findings)

1. **Almost every student read and write is a direct `platform.*` RPC on the user-session Supabase client** (publishable key plus the user's JWT). The web "server actions" are thin wrappers (validate, then the same RPC). A mobile app can call all of them directly via `supabase.schema('platform').rpc(name, args)`. This is the transport decision in `docs/adr/0030-portal-iphone-swiftui-supabase-transport.md` and what the shipped native app in `ios/` does. The ADR rejected React Native/Expo, but the server contract is identical.
2. **A native iOS client already exists in `ios/EVOAdmissions` (about 10k lines of Swift in `Services/`).** It is the best ground truth for the wire shapes of each RPC (`ios/EVOAdmissions/Services/*Models.swift`). It calls about 45 distinct RPCs; the list is in section 2.7.
3. **Things a mobile client cannot do with the publishable key** (service-role or cookie/CSRF-bound; section 2.8): login by `имя.фамилия`, registration (account creation), registration via personal link, email-confirmation exchange, forgot-password completion, first-login "set your own password", case-file (contract/receipt) download, `/api/portal/updates` poll with bearer (the RPC behind it is callable directly).
4. **Bearer-token HTTP exists only for 4 routes** (`Authorization: Bearer <access_token>`): student document upload and download, the program-application document upload and download, and `invite-acceptance`. Everything else under `/api/portal/**` is cookie-only or anonymous.
5. **Policy gap:** `POST /api/portal/registration` (the native sign-up route) calls `beginStudentSignup(..., invite=null)`, which skips the "personal link only" rule (341) the web form enforces. The route also accepts exactly the keys `email,password,questionnaire` and cannot carry a link token. So the app cannot do "registration by personal link" without a server change, and as written the route lets anyone register without a link. See 1.3.
6. **Content (timelines, CSCA overview, study countries, photo and geo libraries, English cover images) is static JSON/WebP** and importable by another TS project. Portal i18n (`lib/portal/i18n.ts`, 3028 lines) is a pure TS file whose only import is a type (`import type { Locale }`).

## 1. Auth model

### 1.1 Sessions
- Supabase Auth, email + password. Web: `@supabase/ssr` cookies (`lib/supabase/server.ts`), client created with `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (validated in `lib/supabase/config.ts`). Mobile uses `@supabase/supabase-js` with the same two values and persists the session in secure storage.
- "Session-only cookie": at login, checkbox `remember_device` (default checked). Unchecked sets httpOnly cookie `evo_session_only=1` (`lib/session-cookie.ts:8`, `lib/staff-auth-actions.ts:~96-108`), and the Supabase auth cookies are then written without `maxAge`, so the session dies on browser close. Mobile equivalent: a local preference; if unchecked, do not persist the session (or clear on app exit). Label copy is in the login page `COPY` (section 1.2).
- Locale cookie `locale` (ru|ky|en, default ru), theme cookie `theme`, rail cookie `portal_rail` are request-time defaults only (`lib/i18n.ts`, `lib/theme.ts:10`, `lib/portal/rail-choice.ts`). Persistent language is DB: `platform.set_own_portal_language_v1`.
- Logout: `logoutStudentPortalAction` (`lib/student-portal-auth-actions.ts:~218`) is `client.auth.signOut({scope:"local"})` then redirect `/login`. Mobile: `supabase.auth.signOut({scope:'local'})`.
- Hosts: students `https://app.evoadmissions.com`, staff `https://crm.evoadmissions.com` (`lib/platform-public-origin.ts:9-10`). Hosts are routing hints only; authority is in the DB.

### 1.3 Login algorithm (what the app must reproduce)
`loginStaffAction` (`lib/staff-auth-actions.ts:51-171`):
1. Trim `login`. If it contains no `@` (and is not the staff alias `admin`), it is a **student login** of the shape `имя.фамилия` (Latin, ICAO transliteration; `lib/student-login.ts`: regex `^[a-z][a-z0-9]*(\.[a-z0-9]+)+$`, 3-64 chars, parts up to 24 chars; collisions get suffix `base2`, `base3`...). The server resolves the login to the auth email through **service-role RPC `platform.student_login_email_v1(p_login)`** (`lib/server/student-login.ts`); the migration `supabase/migrations/340_platform_student_logins.sql:92-131` revokes it from everyone except `service_role`. Unknown login answers like a wrong password.
2. `signInWithPassword({email, password})`.
3. `auth.getClaims()`; staff-vs-student check, in this order:
   - `readVerifiedPlatformAuthority` (RPC `platform.current_actor_authority`) → staff → web goes to `/` (the app must **refuse staff**: sign out and show `staffAccessDenied`).
   - else `readVerifiedStudentPortalAuthority` → **student with portal** → `/portal`.
   - else if a student invite receipt says `accountPending` → `/auth/account-pending`.
   - else `resumeStudentApplication`: application saved → `/apply/status`, none → `/apply`; unverified → sign out, `staffAccessDenied`.
4. If `app_metadata.evo_temporary_password === true` (`lib/student-account-contract.ts:12`, `hasTemporaryPassword`) → redirect to `/auth/new-password` before anything else (also enforced in `src/app/(portal)/layout.tsx:~41` and `/apply`).
Accounts created by an admin without an email get a technical email `*@students.evoadmissions.invalid` (`TECHNICAL_STUDENT_EMAIL_DOMAIN`); these users can **only** sign in by login name (the email is never shown).
**Mobile consequence:** `signInWithPassword` works only with a real email. Login by `имя.фамилия` requires a **new server endpoint** that maps login to email server-side (or a login-to-token exchange); today it exists only inside a Next server action. The shipped iOS app is email-only (`ios/EVOAdmissions/Services/SupabaseService.swift:32`).

### 1.4 Student authority (staff vs student detection, tiers)
- `resolveStudentPortalActor` (`lib/student-portal-auth.ts`) = `auth.getClaims()` plus two RPCs: `platform.current_actor_authority()` (must be exactly one row with `platform_role == 'student'`; fields `auth_user_id, profile_id, membership_id, organization_id, display_name, platform_role, platform_access_version`) and `platform.student_portal_cases()` (one row: `case_id, case_state ∈ {pending,active,closed}, portal_activated_at`). Decoder: `lib/supabase/student-portal-authority.ts:~85-150`. JWT claims also needed: `sub`, `email`, `platform_bundle_id`, `platform_bundle_version`.
- **accessTier** (derived, never stored): `approved` = `case_state == 'pending'` (activated portal, no curator); `assisted` = `active | closed`. It gates the UI (below) and DB (migration 192/195).
  - approved sees: Главная, Поступление (Университеты tab, Программы tab), Университеты, Профессии, Английский, CSCA, Тесты, Профиль. No Документы, Оплата, Входящие (nav `tiers`), no "Что нового", no AI-consent home card, no case-help.
  - assisted sees everything.
- Guard outcomes (`lib/student-portal-guard-policy.ts`): anonymous → `/login`; authority unavailable → `/login?error=auth_unavailable`; invalid/staff → `/login?error=session_invalid`.
- Sign-out and refresh: after approval of an application the web calls `auth.refreshSession()` then re-reads authority (`lib/student-signup-actions.ts` `refreshStudentApplicationAction`).
- Bearer variant: `resolveStudentPortalBearerActor(accessToken)` (`lib/student-portal-auth.ts:~131`): `getClaims(jwt)` then the same two RPCs on a client carrying the token.

### 1.5 Registration and application ("анкета") flows (all pre-portal)
Route map: `/apply` (wizard, `src/app/apply/page.tsx`), `/apply/status` (`src/app/apply/status/page.tsx`), `/auth/signup-confirmation` (email-OTP landing), `/auth/account-pending`, `/auth/callback` (invite and recovery tokens), `/auth/new-password`, `/auth/forgot-password`, `/auth/reset-password`, `/auth/account-deleted` (route handler), `/auth/staff`, `/platform-pending`.

**Personal registration link ("invite", 341).** URL `https://app.evoadmissions.com/apply?invite=<token>`; token = 32 chars base64url (`lib/server/student-registration-link.ts:13`), only its sha256 is stored. `/apply` without a signed-in confirmed user and without a valid token renders `RegistrationInviteRequired` (statuses `unknown|used|expired|unavailable`; `src/components/student-application/RegistrationInviteRequired.tsx`). A valid link pre-fills the first/last name from `display_name` (`check_student_registration_link_v1`, service-role only; `consume_student_registration_link_v1` marks it used after the user is created). The web action `registerStudentAction` (`lib/student-signup-actions.ts:~35`) rejects with `status:"invite"` if no token. **Mobile: needs a server route that accepts the token** (see headline 5).

**Wizard (9 steps)**, `src/components/student-application/ApplicationWizard.tsx` (292 lines), step keys `countries, intake, education, fields, levels, nationality, english, budget, account`; strings namespace `apply` (`lib/portal/i18n.ts:1973` ru, plus ky). Draft is saved to `sessionStorage` key `evo-application-draft-v1` (per user+revision when signed in). Draft schema (`lib/student-application-contract.ts`, exact key set, `schemaVersion:1`):
`requestId(uuid), firstName(≤60), lastName(≤60), phone(7-15 digits, regex ^\+?[0-9 ()-]{7,40}$), destinationCountries[1..15] (CN MY AE TR IT CZ or single "UNDECIDED"; legacy DE FR ES NL PL HU AT GB CY accepted by server only), intakeSeason(spring|summer|autumn|winter|undecided), intakeYear(2026..2036), educationLevel(secondary|high_school|foundation|diploma|bachelor|master|phd), averageGrade(0..gradeScale), gradeScale(100|5|4|10|20), studyFields[1..10 strings ≤100], studyLevels[1..6] (foundation|bachelor|master|phd|diploma|language), nationality(ISO list, constant STUDENT_APPLICATION_NATIONALITIES), english = {mode:"exam", exam: ielts|toefl|toefl_120|pte|duolingo, score(range+step per exam)} | {mode:"self", level: beginner|intermediate|advanced|fluent}, tuitionBudget(under_5000|5000_10000|10000_20000|20000_30000|over_30000|undecided), fundingSource(family|savings|scholarship|loan|employer|undecided), consent:true, consentVersion:"2026-11-07"` (legacy "2026-09-18" accepted by the server). Last step also needs the **AI-assistants consent** box (`ai_consent=granted`) plus the Privacy Policy tick (345). Extra fields on the last step: email, password (≥12 chars, ≤72 bytes).
Presentation helpers: `lib/student-application-presentation.ts` (exam ranges, study-field options, country labels). Name pre-fill sources: invite `display_name`, admin `user_metadata.evo_name_prefill`.
**Sign-up (anonymous, new account):** the native-capable route is `POST /api/portal/registration` (section 2.6). Creates `auth.users` (unconfirmed) with the draft in `user_metadata.student_application_draft` and the AI consent in `user_metadata.student_ai_consent_choice`, sends an email with a link to `/auth/signup-confirmation#cap=<envelope>&otp=<digits>`; resend via `POST /api/portal/registration/resend`.
**Confirmation:** the web landing page posts a server action (CSRF cookie `evo_student_signup_confirmation_csrf`, Origin check) that runs `verifyStudentSignup` and sets the cookie session (`lib/student-signup-confirmation-actions.ts`). **There is no bearer/JSON endpoint for confirmation**, so the app needs a universal link into the web page or a new endpoint.
**Signed-in submit** (anketa after confirmed email): direct RPC `platform.submit_student_application_v1(p_request_id, p_questionnaire, p_expected_revision)` (`lib/v3/student-application-source.ts:~60`), then `client.auth.updateUser({data:{student_application_draft:null}})` and AI consent write (`portal_ai_consent_set_v1`). Status: `platform.own_student_application_v1()` returns null or `{id,status(pending|approved|rejected),revision,email,questionnaire,submitted_at,decided_at,decision_reason,student_case_id,admissions_direction,canonical_lead_id}`.
**`/apply/status`**: title by status (pending: statusPendingTitle/Lead; approved: statusApprovedTitle with "enter portal" button that does refreshSession then goes to `/portal`; rejected: statusRejectedTitle plus `decision_reason` and link "fix application" `/apply?edit=1`), list of answers (`localizedApplicationAnswers`, `lib/student-application-answers.ts`), own login line ("Логин: …", `platform.own_student_login_v1()`), logout, account-deletion panel (1.7). A pending account with an admin-opened cabinet but not yet activated: `/auth/account-pending`.
**Invite email flow (admin-invited students):** email link → `/auth/callback?...` (`src/app/auth/callback/page.tsx`, `StudentInviteCallback`, token_hash in query, CSRF cookie `STUDENT_INVITE_CSRF_COOKIE`). Native path in ADR: universal link into this page, or `POST /api/portal/invite-acceptance` (bearer; after native `supabase.auth.verifyOtp`) which returns `{status:"accepted", intakeFlow, accountPending, displayName}`; errors `401 authentication_required`, `409 mismatch`, `503 unavailable`.

### 1.6 Forgot / reset / set own password
- `/auth/forgot-password`: email only. Action `requestStudentPasswordRecoveryAction` → `auth.resetPasswordForEmail(email, {redirectTo})` (server, isolated client, per-address rate limit, 60 s resend; staff addresses get a neutral answer). Status states: `idle|sent|invalid_email|rate_limited|unavailable` (`lib/student-password-recovery-contract.ts`). Strings: `lib/portal/password-recovery-i18n.ts` (188 lines, ru+ky+en).
- Email link → `/auth/callback?type=recovery&token_hash=...` → interstitial → `verifyOtp({token_hash,type:'recovery'})` on the server, recovery session stored in httpOnly cookie `evo-student-recovery` (path-limited, 15 min) → `/auth/reset-password` form (new + confirm; min 12 chars, ≤72 bytes; states `mismatch|too_short|too_long|same_password|rejected|expired|staff_refused|sign_in_required|unavailable|done`). **Cookie-bound; not completable from the app without a universal link or new endpoint.** A native app could instead call `supabase.auth.resetPasswordForEmail` itself and finish `verifyOtp` + `updateUser({password})` on device if the Supabase email template/redirect is configured for a deep link (not configured today).
- `/auth/new-password` (temporary password from an admin, 342): form password + password_confirm → `setOwnStudentPasswordAction` (`lib/student-new-password-actions.ts`): **service-role `auth.admin.updateUserById` sets the password and clears `evo_temporary_password`** (cannot be done with a user token; a plain `updateUser({password})` would leave the flag set). Then re-sign-in with the new password, redirect `/apply` (dispatcher).
- Change password inside the cabinet (Profile): `changeStudentPasswordAction` → `lib/server/student-password-change.ts`: signs in an isolated client with the current password, `updateUser({password:new})`, signs out that client, re-signs the product session; status `wrong_current|same_password|rejected|rate_limited|unavailable|sign_in_required|done|mismatch|too_short|too_long`. A mobile client can do the same two calls with the publishable key (`signInWithPassword` to verify the current password, `updateUser`), minus the server rate-limiter.

### 1.7 Consents
1. **AI-assistants consent** (`lib/portal/ai-consent.ts`, `ai-consent-rpc.ts`, UI `src/components/portal/consent/AiConsent.tsx`, `AiConsentSlot.tsx`, strings namespace `aiConsent`). Policy version constant `"2026-10-25"`, source label `portal_web` (iOS sends `ios`, the Expo app on Android sends `android`, migration 355), privacy URL `https://evoadmissions.com/ru/privacy/`. RPC `platform.portal_ai_consent_get_v1()` → `{status: granted|declined|null, policyVersion, decidedAt, currentPolicyVersion}`; `platform.portal_ai_consent_set_v1(p_status, p_policy_version, p_source, p_request_id)` (idempotent per `request_id`; the answer must echo the chosen status and current version). Rule: decision on an older policy version = "undecided, ask again". Where shown: Home card and Overview slot (assisted only, until a decision exists for the current version); Profile row (approved and assisted: grant/decline/revoke); registration step (required, written after first sign-in from `user_metadata.student_ai_consent_choice`).
2. **Registration consent** (privacy policy + processing): `consent:true` plus `consentVersion` in the draft (`"2026-11-07"`).
3. No separate cookie/marketing consent in the portal.

### 1.8 Account deletion (App Store 5.1.1(v))
- Component `src/components/account-deletion/AccountDeletionPanel.tsx`; strings namespace `accountDeletion` (`lib/portal/i18n.ts:2888`); placed in Profile (`look="portal"`), `/apply` (signed in), `/apply/status`, `/auth/account-pending`.
- Read: RPC `platform.own_account_deletion_request_v1()` → `{requestId,status: requested|processing,requestedAt,dueAt}` or null (parser `lib/account-deletion-contract.ts: parseOwnAccountDeletion`).
- Request: RPC `platform.request_account_deletion_v2(p_request_id uuid)` (idempotent; staff are refused by the DB). Processing window **30 days** (`ACCOUNT_DELETION_DAYS`). UI states: idle (description + "kept note" + action) → confirm group (question, note, confirm "yes", cancel) → requested/processing (dates: `requested`, `due`) ; errors `unavailable`, `error`.
- After deletion by staff, a stale session is detected by `auth.getUser()` error code `user_not_found` → route `/auth/account-deleted` signs out and redirects `/login?notice=account_deleted`.

## 2. Data access

### 2.1 Conventions
- All RPCs: `client.schema('platform').rpc(name, args)`; reads are marked `{get:true}` in several places (STABLE functions: `student_portal_overview_v2`, `student_portal_documents`, `student_portal_case_files_v1`, `student_portal_finance_v2`, `student_portal_notifications_v2`, `portal_case_chat_page_v1`, `student_portal_poll_v1`). Do not pass `null` args in GET mode (they become the text "null"); omit them (see the comment in `lib/portal/messages-source.ts:~20`).
- Writes carry a client `p_request_id` UUID for idempotency; keep it stable across retries. Notification-read uses a deterministic UUIDv5 (`lib/server/student-portal-notification-command-id.ts`, namespace `73f89df8-d811-5352-9a97-a87652d591c1`, name `notification-read:{org}:{case}:{membership}:{authUser}:{notificationId}`); any fresh UUID works for the RPC, the v5 only makes retries replay-safe.
- RPC result shapes: portal read-models return `snake_case` rows (portal-source), profile/country-choice/chat/consultation return strict `camelCase` objects (parsers in `lib/portal/*.ts`, exact-key checks). Use `ios/EVOAdmissions/Services/*Models.swift` as a second reference.
- Errors: Postgres `42501` = forbidden/not found (treat as 404), `22023` = invalid, `40001`/`23505`/`PT409` = conflict.
- Dates: shown in `Asia/Bishkek`; `ru-RU` formatting (`src/components/portal/admission/presentation.ts`). Money: minor units; KGS printed as "сом" (`formatPortalMoney`).

### 2.5 Storage buckets, uploads and downloads
- **Bucket `platform-documents`** (private; constant `BUCKET_ID` in `lib/server/platform-document-storage-route-handlers.ts:33` and `platform-case-agreement-storage-route-handlers.ts`). Students never get direct bucket access: bytes go through the Next route handlers, which use the **service-role client** to upload, scan (ClamAV), finalize and sign URLs. Max file 25 MB (`MAX_FILE_BYTES`), types `application/pdf`, `image/jpeg`, `image/png`. Object names are server-generated (reservation RPC); the client never sees a path.
- **Bucket `portal-university-photos`** (public read; `UNIVERSITY_PHOTO_BUCKET_NAME`, `lib/university-photo-url.ts`): `<SUPABASE_URL>/storage/v1/object/public/portal-university-photos/<objectPath>`; resized: `/storage/v1/render/image/public/portal-university-photos/<path>?width=W&height=2500&resize=contain&quality=70`. Country/city photos: path pattern `geography/(countries|cities)/<slug>-<12 hex>.(jpg|png|webp|avif)` comes in the index RPC (`photo.path`). University photos: key `photoKey` → entry in `lib/university-photo-library.json` (149 entries: `path` (hotlink, e.g. thumb.wikimedia.org), `author`, `title`, `caption`, `sourceUrl`, license fields); the managed bucket copy is used only when `scripts/portal/university-photos-manifest.json` has `migrated:true` for that key (file `<photoKey>.<ext>`), otherwise hotlink. Server module is `server-only` and imports the manifest, so replicate the logic with the two JSON files.
- **Upload (checklist slot)** `POST /api/portal/document-slots/{documentSlotId}/versions`:
  - Auth: cookie, **or `Authorization: Bearer <access_token>`** (a present header always wins and never falls back to cookies; header must match `^[A-Za-z0-9_-]+\.…\.…$`, ≤16384 chars; `studentPortalDocumentRouteTransport`, handlers lines 893-975, 1663-1685).
  - Headers: `Content-Type: multipart/form-data; boundary=…`, `Idempotency-Key: <uuid>` (required, keep the same on retry), `Accept: application/json`.
  - Body: multipart with **exactly one field `file`** (extra fields rejected; filename ≤255 chars, 1 byte..25 MB, MIME must be one of the three).
  - Success `201 {"document":{documentSlotId,documentVersionId,versionNumber,originalFilename,declaredMimeType,byteSize}}`. Error mapping used by the web UI (`PortalDocumentControls.tsx:uploadFailureMessage`): 400/415 bad file; 403 forbidden; 409 conflict; 413 too large; 422 failed scan; 429 too many; others unavailable. JSON error body `{error:"<code>"}` (codes: `invalid_idempotency_key`, `file_too_large`, `multipart_required`, `invalid_multipart`, `invalid_document_slot`, `storage_unavailable`, `storage_*_unconfirmed`, ...).
  - Choreography (server): student scan-admission RPC → preflight → reservation RPC → upload to storage → read-back → scan → finalization RPC; resumable (TUS) transport is used server-side for files above `STANDARD_UPLOAD_MAX_BYTES`.
- **Download (checklist slot)** `GET /api/portal/document-versions/{versionId}/download`: cookie or bearer; grant RPC (user session) then consume RPC (service role) then signed URL; answers **`307`** (student policy `STUDENT_DOWNLOAD_POLICY`) with `Location: <signed url>` and `Cache-Control: no-store`. Mobile: perform the request with `redirect: 'manual'` or follow with a downloader; open the signed URL for the share sheet.
- **Program-application documents:** `POST /api/portal/application-document-uploads` (header `X-EVO-Upload-Intent: <base64url JSON>` (≤8192 chars, ≤6144 bytes decoded) with protocol version 1, target (studentCaseId, applicationId, requirementsRevisionId, requirementItemId, documentSlotId) and file metadata (originalFilename, declaredMimeType, byteSize string, sha256Hex), `Idempotency-Key`, multipart with one file part named `upload` (`APPLICATION_DOCUMENT_TRANSPORT_FILENAME`); success `201 {"upload": receipt}`, errors `{error:{code,resolution:'retain'|'not_written'}}` with codes of `ApplicationDocumentFailure`). `GET /api/portal/application-document-downloads?documentVersionId=…&studentCaseId=…&applicationId=…&requirementsRevisionId=…&requirementItemId=…&documentSlotId=…` → `302` to signed URL. Both accept bearer. Client helpers: `lib/portal/application-documents-upload.ts` (header encode, sha256, `freezeApplicationDocumentUploadIntent`).
- **Case files (contract/receipts):** `GET /api/portal/case-files/{contract|receipt|pending_receipt}/{fileId}/download`: **cookie only** (it calls `resolvePlatformActor()` and `createSupabaseServerClient()`; there is no bearer branch); RPC `student_portal_case_file_target_v1(p_file_kind,p_file_id)` then service-role `createSignedUrl(…, 60, {download:true})` then `307`. Not callable from the app until a bearer branch is added (small change next to the others).
- **Light poll** `GET /api/portal/updates[?s=<section>]`: cookie only (`createSupabaseServerClient`), query key only `s`; use the RPC `student_portal_poll_v1(p_section)` directly instead.

## 7. Gaps and recommended server work before/while building the Expo app
1. **Login by login name:** add a JSON endpoint (e.g. `POST /api/portal/login-resolve` returning a session via server-side `signInWithPassword`, or returning the email behind rate limit and constant-time behaviour), because `student_login_email_v1` is service-only. Without it, admin-created cabinets with the technical email cannot sign in from the app.
2. **Registration by personal link:** extend `POST /api/portal/registration` with an optional `invite` token (and enforce "link required", closing the current bypass), plus a link pre-check endpoint (`check_student_registration_link_v1` is service-only) to show `RegistrationInviteRequired` states and pre-fill the name.
3. **Email confirmation and password recovery completion** need either universal/app links into `/auth/signup-confirmation`, `/auth/callback`, `/auth/reset-password`, or new JSON endpoints that exchange `cap+otp` / `token_hash` for a session and a new password. Today they are cookie/CSRF-bound.
4. **Temporary-password first login:** needs a bearer endpoint (service-role `updateUserById` clearing `evo_temporary_password`); the web gate runs in `(portal)/layout.tsx` and `/apply`, and the app must detect `app_metadata.evo_temporary_password` from the JWT claims.
5. **Case-file (contract/receipt) download:** add the bearer branch (like the other four document routes).
6. **Rate limits:** the web's password-change limiter (`lib/server/student-password-change.ts`) and recovery limiter are server-side; direct client `updateUser` bypasses it (Supabase Auth's own limits still apply).
7. Photo URLs: reproduce `lib/university-photo-url.ts` logic in the app (manifest + library JSON, public bucket base from the Supabase URL); there is no RPC that returns ready photo URLs for universities (country/city photos do carry `path`).
8. Realtime: none. Web uses 60 s visible-tab polling (`student_portal_poll_v1`); mirror it with foreground polling or add push later.
9. Release safety: RPC contracts evolve additively or by `_v2`; installed apps lag. Keep exact-key parsers tolerant on the app side or version-check (`ios` uses strict parsers, copied from web).
10. Known stale doc: `docs/design/portal/design-contract.md` palette/radii. Existing parity reference: `docs/design/portal/functional-parity.md` (web vs iPhone, 295 lines).
