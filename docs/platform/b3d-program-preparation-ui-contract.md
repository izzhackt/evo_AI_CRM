# B3d — выбор программы и подготовка в CRM, портале и iPhone

Статус: pre-code, 2026-09-21. Исходная база `c803d393` (PR #964 merged).
Это контракт следующего ограниченного UI-среза, не подтверждение UI или релиза.
Root согласовал направление; реализация ждёт независимого review этого контракта
и принятия root. B writer window освобождён; новые QA-записи требуют окна root.
Новая миграция не нужна: используются существующие 214/218 и same-case Docs.

## Задача и граница

Клиент с сопровождением и сотрудник выбирают конкретные вуз, программу и набор,
сразу открывают сохранённую подготовку, видят её документы и переходят к файлам
того же дела. Дополнительного одобрения выбора нет. Самостоятельному пользователю
сохраняются каталог, избранное и консультация; одобрение регистрации само по себе
не даёт сопровождение. CRM сохраняет прежнее ручное создание заявки.

214 отвечает за binding/application и неизменяемые сведения выбора; 218 — за
неизменяемый стартовый состав и текущую доступность связанных материалов. Одна
application, одно дело, существующие версии файлов: копии сущностей не создаются.
Поддерживаемые страны: CN, MY, AE, TR, IT, CZ. Остальные остаются доступны для
просмотра, избранного и консультации. SQL остаётся конечным источником прав.

Полный редактор требований программы, принятие и сопоставление старых перечней,
разделение загрузки и отправки, версии пакетов, очередь проверки и исправления
остаются обязательными следующими блоками исходного admissions-плана. Этот UI
не объявляет их выполненными. Два стартовых пункта не заменяют полный перечень.

## Impeccable: рекомендация → решение → проверка

Применены `shape` и `operate` из Impeccable; исходные решения владельца уже заданы,
новое интервью о стиле не требуется. Режим Operate, refinement существующего EVO.
Это разбор поведения по исходникам, не завершённый визуальный `critique` или аудит.
До UI-изменений нужен реальный baseline целевых экранов с ordinary QA session.
После реализации — одна совместная проверка web desktop/mobile и iPhone,
исправление найденного одним пакетом, максимум одна подтверждающая проверка.

| Наблюдение по исходникам | Решение для пользователя | Реальная проверка |
| --- | --- | --- |
| В карточке есть программы/наборы, но нет входа в 214 | Одно действие у конкретного набора: «Начать подготовку»; для существующего выбора — «Открыть подготовку» | Выбор ведёт к сохранённой application; повтор/обновление не создаёт дубль |
| CRM создаёт прежнюю ручную заявку | Отдельный явный выбор из каталога в текущем разделе «Университеты»; ручной путь сохраняется | Сотрудник видит конкретные программу/набор до подтверждения; старый путь доступен |
| Overview/AdmissionHub зависят от Finance | Список подготовок и их ошибки читаются независимо | Ошибка несвязанного блока не превращается в пустой список подготовок |
| Старт218 — два пункта с неподтверждённой полнотой | «Стартовые документы» и короткое пояснение об уточнении полного списка; без процента готовности | Экран не обещает полный пакет или одобрение выбора |
| Текущая загрузка сразу отправляет на проверку | До перехода/выбора файла явно сообщать об отправке на проверку | Нет ложного «черновика» или неработающего отдельного «Отправить» |
| Неопределённый ответ может спровоцировать повторный выбор | Сохранять намерение; показать повтор того же действия и чтение сохранённой подготовки | Не менять request ID после потери ответа; не рисовать оптимистический успех |

Сохраняются «Атлас», фото/источники каталога, Golos и текущие web-токены, нативный
системный текст iPhone. Главная иерархия: программа/набор → текущий статус и срок →
следующее действие → документы. Не добавлять hero, новую гарнитуру, декоративную
анимацию, дублирующий глобальный навбар или технические ID во фронтенд. Короткие
RU/KY строки портала/iPhone, текущий язык staff CRM. Клавиатурный focus, доступное
имя, состояние pending/error, перенос длинных названий, минимум44pt touch targets,
Dynamic Type и сохранение фокуса после ошибки входят в изменяемый путь.

## Команды и восстановление

1. Перед новым выбором успешно прочитать актуальную карточку и подготовки этого
   дела. Найти существующий binding по case/institution/program/intake, без
   publicationVersion в ключе совпадения. Ошибка чтения не означает «ничего нет».
2. Существующий выбор открывается из карточки и отдельного списка даже после
   закрытия набора, обновления/исчезновения карточки или terminal application.
   Новая selection для открытия не вызывается. Название, программа, набор и сроки
   берутся из сохранённого `content`; статус — из текущего214 reader.
3. Для нового выбора пользователь явно нажимает действие. До сетевого запроса
   фиксируются полный214 intent и requestId. Двойной клик блокируется. После
   подтверждённой selection читается218; только `uninitialized` и текущие права
   допускают явную инициализацию в цепочке этого клика с отдельным218 intent.
   GET, server render, useEffect, Swift `.task` и refresh ничего не инициализируют.
4. Если214 прошёл, а218 не прошёл, выбор остаётся сохранённым. Деталь показывает
   состояние требований и «Продолжить подготовку» для допустимого повтора218.
   Не откатывать application, не повторять214 ради исправления218, не добавлять
   ожидание одобрения сотрудником. При `needs_configuration` повтор init не
   предлагает автоматический ремонт или замену старого перечня.
5. При `unavailable` сохранить точные214/218 намерения для повтора. В пределах
   сессии использовать небольшой pending-intent store, привязанный к текущему
   actor/case и точному target, без credentials/файлов/PII. Чтение store не
   отправляет команды. При смене пользователя intent не используется. После
   подтверждённого ответа очищать только соответствующее намерение. После
   перезапуска сначала перечитать сохранённые подготовки; отсутствие локального
   intent не является поводом автоматически создавать новый запрос.
6. `stale_publication` требует обновить сведения и нового явного выбора;
   `intake_closed/expired`, `case_ineligible`, `unsupported_country`, отсутствие
   intake identity показываются по месту. Forbidden не раскрывает чужие данные.
   Ошибка218/214 не заменяется пустым ready-состоянием или fallback успехом.

Не строить новый клиентский алгоритм admission eligibility. Известные закрытые
наборы не предлагают новый выбор. Для срока неизвестный/спорный status и отсутствие
подтверждённой timezone не превращаются в «истёк» через fallback UTC; SQL214
проверяет точный момент. Текущие `universityIntakeStatusKey`/`universityIntakeLabel` и native
`universityIntakeDisplayStatus` в `Services/PortalModels.swift` имеют такое упрощение: в затронутых представлениях убрать ложную достоверность,
не менять SQL. Текущие web Program-фильтры в portal Detail и staff UniversityCatalogue
полностью скрывают unknown/needs_reconfirmation. В новом выборе такие реальные
наборы доступны с пояснением неопределённого срока; старый фильтр нельзя перенести
в selector. Политику видимости целевого native списка сверить так же. Сохранённый `deadlineStateAtSelection=needs_confirmation` остаётся
видимым уточнением срока; это не запрет на уже созданную подготовку.

## Экраны и права

**Student web.** Действие в существующем detail каталога, список подготовок в
`/portal` независимо от Finance, деталь `/portal/preparations/[applicationId]`.
Case берётся из `VerifiedStudentPortalAuthority.studentCaseId`; route ID сверяется
с reader текущего дела. Новый ограниченный UUID-path добавляется в route allowlist.
Старый redirect `/portal/applications` сохраняется. Деталь остаётся доступной
по текущей Student authority, но новый выбор требует active/portal-activated case.
Существующая политика ровно одного дела сохраняется, `.first` не используется.

**CRM.** В `UniversityProgramsTab` добавляется каталоговый picker с конкретным
набором и действие214. Ручной `ApplicationCreateDialog` и legacy applications,
статусы/дедлайны/partner packets остаются. Каталоговый picker отдельно требует
`catalog.read`: его denied/unavailable не закрывает ручной путь и чтение уже
сохранённых подготовок. Новый ограниченный server action использует
`readStaffUniversities(actor, filters, institutionId)`; прежний search action
возвращает только id/name/country и для214 недостаточен, его контракт сохраняется.
Подготовка подключается к существующей application row, без второй визуальной
копии той же заявки. Case видимость не заменяет
`application.manage`; чтение требований требует `document.read.full`, init —
`document.manage`, preview не пишет. Успешный выбор с отсутствующим document.manage
не становится ошибкой всего выбора: сотрудник видит сохранённую заявку, требования
только по доступным правам. Legacy manual application не запускает218 без binding.

**iPhone.** Тот же action в `UniversityDetailView` из каталога, избранного и Home;
передаётся уже разрешённый single-case контекст. Новая selection только из успешно
прочитанного snapshot, не из stale initialItem после ошибки. Список в «Моё
поступление» независим от AdmissionHub Finance. Деталь использует214/218 readers.
Не полагаться на текущий tier, считающий closed/unknown сопровождением: для новой
selection проверять точные active и portalActivatedAt, не менять общий tier вне
среза. Нативные navigation/back/refresh сохраняются.

**Документы.** Состав экрана определяется218 items, не пересечением с глобальным
списком (иначе исчезнет обязательный отсутствующий пункт). Техническая доступность
и staff review показаны отдельно. Существующий web Docs имеет якорь
`#document-<uuid>`; iPhone получает optional focusedSlotId и прокрутку к реальной
строке полного списка. File-missing при целой связи может вести к загрузке;
slot_missing/removed, application_link_missing и metadata_changed не дают ложную
валидную связь/просмотр файла. Маскированные218 поля не восстанавливать из Docs.
При inline reuse controls проверяются case/slot/currentVersionId/currentVersionNo;
простой переход в текущие Docs предпочтительнее второго upload-компонента.
`needs_configuration` сохраняет доступ ко всем документам дела и существующей
помощи, но не скрывает проблему настройки. Никаких копий binary/review/slot.

  точечное подключение в текущий admissions workspace; legacy dialog не заменяется.

  `AdmissionDocumentsView`, передача контекста через текущие catalog/favorites/home

  данные каталога не меняются. Новые dependencies/font/assets не нужны.

Исполнители получают непересекающиеся owned files; общие i18n/pbxproj правки
согласуются. Нельзя откатывать изменения других потоков. Это один функциональный
срез; source-only groundwork не означает пользовательскую готовность.

## Проверка и доступность настоящих данных

До runtime: независимое review pre-code, затем реальный baseline текущего UI и
`craft-floor.md` непосредственно перед UI-правками. Просмотр без write не является
Auth/DB writer permission. Root выделяет окно для любых новых ordinary Auth/DB
действий; A/root схема сейчас может изменяться, поэтому фиксировать фактический
ledger/source SHA перед QA, старые218 receipts не переименовывать новым прогоном.

Существующая local QA содержит настоящий214 preparation с инициализированными218
Фото/Паспортом и прежние ordinary Student/staff учётные записи. Это позволяет
проверить reopen/read/Docs navigation после разрешённого входа. Первый выбор и
положительная первая инициализация в новом UI требуют подходящего ещё не выбранного
реального набора/дела и отдельного разрешённого mutation window. Нельзя удалить
сохранённую подготовку, создать fake case/набор или подменить ответ ради PASS.

Отдельная локальная web-сборка использует текущий local backend и свободный порт,
не останавливает старый33216. Native Local.xcconfig отсутствует в новом worktree. Read-only проверка показала:
AppConfig читает собранный plist; launch-auth hooks отсутствуют; Supabase2.55.2
сохраняет Auth в Keychain с ключом по host без порта. Поэтому QA использует новый
отдельный simulator device, отдельные bundle ID/DerivedData, ignored Local.xcconfig
с явными local Supabase и portal web origins и приватную QA-копию plist с точечным
HTTP ATS-исключением для127.0.0.1. Существующий EVO simulator не переустанавливать,
не разлогинивать, токены не переносить. Production plist/Auth-code не меняются.
Перед установкой проверить собранные bundle/origins/непустоту ключа без его вывода.
После разрешения root — обычный вход прежним QA Student. Наличие listener57495
не доказывает Auth/RPC/HTTP-доступность из нового simulator.
Если isolation или нужный реальный scenario недоступен, записать точную границу
проверки; DTO typecheck не заменяет simulator UI acceptance.

Минимум: scoped typecheck/lint/build изменённых web/Swift путей; ordinary Student
и staff actual UI selection/reopen/requirements/Docs по доступным сценариям;
before/after только затронутых записей и отсутствие дублей. Retry/closed/foreign/
permission/configuration states подтверждать реальными существующими входами или
явно отмечать непроверенными. Не сбрасывать QA, не устраивать полный E2E и не
подменять реальную проверку mocks/fixtures. Снимки desktop/mobile/iPhone, источник,
revision, данные/границы и Impeccable рекомендация→решение→результат идут в QA report.
После exact-head независимого review и required CI — PR, root merge; release отдельно.

Официальные опоры: [Next.js Server Functions](https://nextjs.org/docs/app/api-reference/directives/use-server)
и [mutating data](https://nextjs.org/docs/app/getting-started/mutating-data) требуют
проверять authentication/authorization внутри server function; pending-состояние
отражает выполнение, а не подтверждённый успех. [SwiftUI ScrollViewReader](https://developer.apple.com/documentation/swiftui/scrollviewreader)
даёт переход к элементу по его identity: применяем к существующему slot, не к копии
списка. Эти ссылки подтверждают механизм, не выполненную проверку EVO.

Native QA isolation опирается на [Apple local networking ATS](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking) и [NSExceptionDomains](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAppTransportSecurity/NSExceptionDomains): точечное исключение только в отдельной локальной QA-сборке; реальное соединение ещё не проверено.
