## Результат и границы

Сотрудник открывает конкретную выбранную программу в существующем деле,
составляет её полный список документов, явно выбирает подходящие материалы дела
и сохраняет новую редакцию. Студент видит ту же редакцию на вебе и iPhone,
инструкции, обязательность, доступность файла и решение по его текущей версии.
Выбор программы по-прежнему сразу начинает подготовку; подтверждение полноты
списка не становится новым одобрением выбора или сопровождения.

Это следующий срез после стартовых Фото/Загранпаспорта218. Полный процесс §11
остаётся обязательным: отдельные upload/submit, версионированный пакет, очередь
и решение по комплекту будут следующими блоками. Сохранение требований не
выполняет ни одно из этих действий. Ручные заявки и действующие Docs сохраняются.

B3e работает с требованиями конкретной подготовки214. Массовое распространение
нового шаблона по делам, новый глобальный редактор каталога, перепубликация
университета и автоматическое изменение сроков в этот срез не входят.
Существующие113/137/179 материалы можно явно принять как источник новой редакции;
наличие списка страны не доказывает его полноту для выбранного набора.

## Сохранение программы, версии и сроков

- Case/application и binding214 остаются теми же. Новая редакция требований
  ссылается на точный сохранённый university/publication/program/intake tuple.
  Название, язык или похожий набор не являются идентификаторами.
- Новая версия каталога не обновляет эту подготовку автоматически. Staff-save
  не переписывает application details, publication version или исходный intake.
  Изменение выбранного набора требует отдельного будущего явного действия.
- Дата начала, месяц начала и дедлайн различаются. Существующие
  applicationDeadline/deadlineTime/timezone/sourceUrl/verifiedOn сохраняются
  как сведения выбора; неизвестность или конфликт остаются видимыми.
- B3e не редактирует эти даты через форму требований и не подставляет дату
  из более новой публикации. Дата проверки источника не становится дедлайном.
  Изменение инструкций не считается подтверждением срока.
- Ни сохранение требований, ни пригодность файла не переводят application
  в university-submitted, accepted или rejected и не создают продажу/договор.

## Редакции и явное сопоставление

Источник истины — существующие append-only revisions/items218 с расширением,
которое сохраняет все старые строки и receipts. Новый текущий список — одна
атомарно сохранённая редакция, а не серия частичных правок старых пунктов.
Сервер назначает последовательную revisionVersion; команда передаёт ожидаемую
предыдущую revision ID/version, включая явное отсутствие редакции при первом
принятии legacy. Сохранённая редакция не изменяется и не удаляется. Подтверждённый пустой список
в B3e запрещён: отсутствие пунктов остаётся ненастроенным состоянием. Optional
пункты допустимы; их не включают в число обязательных. Историческая редакция
адресуется по ID, не разрешается только через изменяемое понятие latest.

Новая редакция хранит:

- происхождение `staff_confirmed`, состояние полноты `confirmed`, составителя
  в private audit и время сохранения; это подтверждение списка сотрудником EVO,
  а не решение университета или одобрение файлов;
- точный application/binding и предыдущую редакцию; комментарий причины
  изменения, особенно при исключении ранее обязательного пункта;
- для каждого пункта устойчивый ключ, порядок, обязательность, название,
  группу и конкретную инструкцию; эти тексты не переписывают metadata слота;
- nullable срок отдельного требования: дата, необязательное точное время,
  timezone при времени, источник и дата проверки. Это срок материала этой
  программы, не общий slot deadline и не frozen deadline набора214; неизвестный
  срок остаётся null, дата без времени не получает выдуманную полночь;
- конкретный same-case document slot, происхождение выбора материала,
  source requirement ID при наличии и проверяемый snapshot metadata слота;
- отдельно от названия — основание совместимости. Два эссе с разными заданиями,
  язык/перевод/формат не объединяются по совпадению слов или approved-статусу.

Физическое размещение дополнительных provenance полей в расширении218
уточняется SQL/DTO контрактом до runtime-кода. Не создавать второй параллельный
набор application/Storage/document-version сущностей. Материал остаётся тем же
общим слотом дела; готовый файл повторно не загружается и не копируется.

Каждый пункт должен иметь явное решение: использовать выбранный существующий
слот либо создать отдельный пустой custom slot в той же атомарной команде.
Новый пустой слот не считается файлом. Кандидат может не иметь файла или иметь
технически недоступную версию — это не скрывает обязательный пункт из списка.
Повторное использование не должно требовать предварительного staff approval
файла; пригодность материала и решение по версии — отдельные оси.

Для218 typed photo/passport сохраняется существующее доказуемое происхождение.
Для legacy требуется явный выбор сотрудника; нельзя автоматически сопоставить
по label/group, наличию113 link, extension/MIME или факту старого одобрения.
Provenance задаёт вид источника (`typed_starter`, `country_manifest`,
`application_details`, `staff_entry`), его точный доступный ID/version при наличии
и причину принятия. Для staff-entry требуется содержательное основание; оно не
выдаётся за официальное подтверждение университета. Server проверяет ссылки
источника, same tenant/case, slot version и отсутствие удаления;
совместимость назначения подтверждается scoped staff-действием с provenance.
Сомнительный кандидат остаётся несопоставленным до решения, без fallback.

Один слот может использоваться в разных программах того же дела. Внутри одной
редакции сохраняется уникальность slot и requirement key; один файл не закрывает
два разных обязательных пункта. Смена wording программы не меняет общий slot.
Если metadata/связь/состояние слота изменились после сохранения, reader показывает
конкретную проблему связи и не восстанавливает скрытые file/review поля через Docs.

При adoption113/137/179 сотрудник видит весь прежний относящийся к программе
состав, обязательность и исключения. Неперенесённые пункты перечислены явно;
нельзя незаметно потерять обязательное требование. Изменение списка программы
не отменяет существующий137 guard/exception и не удаляет113 links или179 checklist.
Если изменение требует отдельной действующей команды137, сначала выполнить её
в разрешённом сценарии и перечитать версии; B3e не обходит её права и проверки.
Обычные manual applications без binding214 остаются в действующем процессе.

## Сохранить список ≠ отправить документ ≠ проверить комплект

| Действие | Результат B3e | Чего результат не означает |
|---|---|---|
| Редактировать форму | Локальные несохранённые изменения | Серверный черновик, новую редакцию или отправку |
| Сохранить список | Новая immutable revision и её явные same-case связи | Upload, staff review, отправку в EVO или университет |
| Открыть существующий документ | Существующая строка Docs | Новую версию файла или автоматическое принятие |
| Загрузить в действующих Docs | Существующий upload и его текущая отправка на проверку | Новое раздельное draft/submit поведение |
| Позднее отправить пакет | Будущий отдельный contract с версиями | Не входит в B3e и не подменяется staff-save |

История review остаётся привязана к конкретной document version. Редакция
требований не переписывает старое решение и не создаёт новое approved автоматически.
Если поменялись смысл требования, инструкция или материал, интерфейс показывает
изменение и необходимость проверки применимости прежнего решения. В v2
проверка файла и применимость к текущему требованию — отдельные поля/состояния;
старое approved нельзя преобразовать в безусловно принятое новое требование. Предыдущее
«файл принят» не означает «новый комплект проверен».
В будущем package ссылается на конкретные revision/item/version IDs; новый список
не подменяет состав уже отправленного или принятого комплекта.

## Версия API и старые клиенты

Добавить отдельные Student/staff `application_requirements_v2` readers и новый
staff-save, с TS/Swift DTO одного контракта. V2 читает как прежний starter, так и
новую полную редакцию; различает completeness, обязательность, текущий файл,
его техническую доступность и review. Missing/malformed response — явная ошибка,
а не пустой успешный список. Нельзя ослабить строгую валидацию до произвольного JSON.

V1 wire остаётся неизменным для текущего starter. Если текущая редакция уже full,
старый reader возвращает явную unsupported/client-update ошибку. Он не выбирает
предыдущий starter как якобы текущий и не обрезает новый список до двух пунктов.
Существующие старые web/native error-пути сохраняют доступ ко всем Docs, но
старый клиент не поддерживает полный список — это ограничение прямо учитывается
при включении функции, а не объявляется обратной совместимостью UI.

Initializer218 сохраняет точный replay ранее записанного intent/receipt после
повторной проверки текущей authority. Он возвращает исторический результат этой
команды, не текущий список. Новый init intent при уже полной редакции не создаёт
starter и не выдаёт full revision в старой wire-форме; возвращает явное состояние
невозможности инициализации. Повторная выдача receipt не создаёт новую редакцию.

Порядок включения: сначала v2 readers и все текущие web/CRM/iPhone потребители,
затем full-save/editor. До этого full-write не включается. Managed/production
включение требует согласованного root плана для установленных старых iPhone
клиентов; сборка исходников не доказывает обновление установленных приложений.
Native UI последней B3d сборки ещё не принят: его проверка остаётся реальной
зависимостью общего межплатформенного результата, а не скрытым PASS.

## Authority, конфликт и повтор

Чтение сохраняет действующие Student ownership/portal eligibility и scoped
staff `document.read.full`. Создание редакции/сопоставление — только scoped staff
`document.manage`, с lifecycle guards существующего дела/подготовки: для НОВОЙ редакции
case=active, portal_activated_at присутствует, application=preparation и binding214
подтверждён. Закрытые дела и application после preparation не получают новую
редакцию через этот срез; разрешённое чтение и authorized exact replay остаются.
Preview не получает команду записи. Наличие application.manage или видимость
карточки сами по себе не дают права менять требования.
Student не подтверждает полноту списка и не получает staff-write через v2.
Организация/actor выводятся из текущей authority, не доверяются client payload.

- Одна транзакция сохраняет revision/items/provenance/links, необходимые пустые
  слоты и audit receipt. Любой отказ оставляет нулевой частичный результат.
- Сохраняется полный нормализованный intent и request UUID до отправки.
  Тот же UUID + те же данные даёт тот же receipt; другой payload — conflict.
  После неизвестного ответа новый UUID не генерируется автоматически.
- Фиксированный lock order, совместимый с218/Docs: request → actor → existing
  case/application, затем выбранные слоты
  по устойчивому порядку; authority и versions повторно проверяются под lock.
  При одновременном upload/removal/metadata edit либо непротиворечивый snapshot,
  либо stale conflict; нельзя смешать версии до и после изменения.
- При stale revision/slot пользователь видит, что изменилось, сохраняет ввод
  для сравнения и перечитывает серверный состав. Нет молчаливого перезаписывания
  чужой правки или автоматического принятия нового файла.
- Приватные таблицы, FORCE RLS/ACL, узкие wrappers, schema-qualified relations
  и `search_path=''` для definer сохраняются; JWT/Storage URL/key не попадают в DTO.

Официальная проверка подхода 21.09: row locks удерживаются до конца транзакции,
конкурирующие writers требуют согласованного порядка
([PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html));
для definer важны search_path и явные grants/revokes
([Supabase](https://supabase.com/docs/guides/database/functions)). Это основание
для проектирования; реальное выполнение будущей операции ещё не доказано.

## Impeccable: функциональный и визуальный контракт

Применяется refinement в существующем EVO/Атлас, mode `operate`.
Job сотрудника — увидеть конкретную программу, проверить полный состав и
подходящие документы, сохранить одну понятную правку. Job студента — понять
обязательные материалы и ближайшее действие. Установленные PRODUCT/DESIGN,
Golos, native Dynamic Type, RU/KY, права и полезные функции сохраняются.
Повторное интервью о бренде/компоновке студентов не требуется: решения приняты.

1. В существующей подготовке CRM действие «Настроить список документов».
   Наверху программа/набор и текущая редакция; затем обязательные/дополнительные
   пункты и проблемы настройки. Не открывать глобальный редактор университета.
2. В пункте — требование и инструкция; рядом явный выбор «Использовать документ
   дела» / «Добавить отдельный документ». Кандидаты показывают label/group,
   наличие/версию файла, действующее решение и текущие связи; без скачивания
   личных файлов лишь ради выбора и без автоматического выбора первого совпадения.
3. Перед сохранением краткий diff: добавлено, изменена обязательность/инструкция,
   изменено сопоставление, исключено. Для прежних решений указать влияние правки.
   Одна главная кнопка «Сохранить список», отдельный выход с защитой введённого.
4. После receipt — перечитанная редакция, время и фактический состав. Не показывать
   «Пакет готов» по самому факту сохранения. При stale/unknown outcome форма
   остаётся доступна, есть понятное повторение/перечитывание без дублей.
5. В Student web/iPhone — название программы, набор/срок из214, актуальные
   требования, обязательность, инструкции и отдельные file/review состояния.
   Starter явно остаётся стартовым; confirmed означает состав, а не приём файлов.
   Ошибка настройки не маскируется нулём требований или готовностью100%.

Desktop использует существующий admissions workspace; узкий экран раскрывает
пункт последовательно, без горизонтальной таблицы. Focus возвращается к действию,
ошибки связаны с полями; длинные инструкции/названия и клавиатура не перекрывают
сохранение. iPhone читает тот же результат с нативной типографикой и доступными
touch targets. Общая навигация, шрифты и компоновка Students не перестраиваются.
Перед UI-правками — craft-floor, один реальный baseline и bounded finish review;
старые screenshots подтверждают только прежний экран, не будущий editor.

## Порядок реализации и владение

1. **B3e-1: v2 protocol/read parity.** До кода — точный SQL/TS/Swift wire/error
   contract и независимое review. Новые readers текущего starter и будущей
   полной редакции; обновить web/CRM/native отображение обязательности/completeness.
   Старые clients и исторические receipts проверяются явно; новых full writes нет.
2. **B3e-2: staff revision + mapping.** После merge первого блока — минимальный
   атомарный save, provenance/конфликты, staff editor/diff и все текущие v2 readers.
   Номер миграции выделяет root после проверки актуального общего ledger.
   Включение и реальная QA запись требуют согласованного конкретного окна.
3. **Следующий обязательный блок §11:** раздельные upload/submit, versions/package,
   очередь/решение и исправление. Его точный контракт готовится по завершении B3e,

## Доказательства, необходимые перед закрытием

- Docs-only план: diff review, `git diff --check`, независимый exact-head review,
  PR/CI. Не запускать приложение/БД/полный test suite ради prose.
- Реальный разрешённый local QA: обычный scoped staff + owned Student, пригодная
  существующая preparation и реальные материалы. Если нужного legacy/second
  program/optional сценария нет, зафиксировать gap и согласовать конкретные QA
  изменения; не создавать выдуманную готовность, права или факты университета.
- Save нескольких требований → один новый revision; exact replay без новых
  эффектов; mismatched intent/stale revision/foreign case отклонены. Разрешение
  scoped role проверить реальным actor, без предположений по названию должности.
- Явное принятие legacy и reuse одного подходящего материала в двух программах:
  ни копии бинарного файла, ни metadata/review rewrite; неоднозначное эссе
  не объединено; старые113/137/179 и mandatory guards сохранены.
- Студент web/iPhone читает одинаковые IDs/состав/обязательность. Missing,
  unsafe и удалённый материал не исчезают из списка и не повышают готовность.
  Current-version review не подменён решением по прежнему файлу/требованию.
- Один direct-risk concurrency проход: revision save против slot change и
  второй staff save, с нулём частичных записей. Old v1 на starter работает;
  на full честно unavailable/update-required; old receipt replay неизменён.
- Проверить реальные новый editor/save/reload и Student read на desktop/mobile,
  native новой сборке, RU/KY, light/dark по изменённому scope. Отсутствующая
