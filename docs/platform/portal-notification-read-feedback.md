прочитанными; кнопки показывают ожидание, но локального сообщения при отказе нет.
Ниже сохранено исходное source-обоснование. Последующая реализация и ограниченный
actual описаны отдельными датированными checkpoint, чтобы не смешивать доказательства.

- `NotificationsView.tsx:53–55,115–122` передаёт actions прямо в формы;
  `PortalNotificationReadButton.tsx:10–22` и `PortalMarkAllReadButton.tsx:13–25`
  содержат pending, но не error/retry state.
- `student-portal-actions.ts:15–35` проверяет Student и единственное поле
  `notification_id`, вызывает существующую команду, затем revalidation.
  `portal-source.ts:747–763` выбрасывает ошибку при отказе/некорректном receipt.
- `portal/notifications/page.tsx:21–29` выполняет bulk последовательно,
  останавливаясь на первом исключении. Ранее обработанные записи уже могли

## Предлагаемое поведение — Impeccable harden, режим Operate

1. Сохранить «Атлас», Golos, текущие карточки, порядок, статусы, даты,
   непрочитанное и ссылки на реальные объекты. Добавить компактную ошибку
   непосредственно у отправленной формы. Весь список не становится live-region.
2. Общая небольшая клиентская оболочка формы вызывает тот же action с тем же
   FormData. Отказ показывает `role="alert"`; перед ручным повтором ошибка
   сбрасывается. Pending и блокировка повторной отправки сохраняются, после
   отказа кнопка снова доступна. Автоматического повтора нет.
3. RU: «Не удалось подтвердить отметку о прочтении. Повторите попытку.»
   KY: «Окулганын белгилөө ырасталган жок. Кайра аракет кылыңыз.»
   Для bulk отдельно RU: «Не удалось подтвердить отметку для всех уведомлений.
   Часть могла быть отмечена. Повторите попытку.»
   KY: «Бардык билдирмелердин окулганын белгилөө ырасталган жок. Айрымдары
   белгиленген болушу мүмкүн. Кайра аракет кылыңыз.»
4. Не скрывать строки, не уменьшать счётчик и не показывать успех оптимистично.
   Подтверждённое состояние приходит существующим server revalidation/polling.
   Сбой после записи остаётся неопределённым результатом. При bulk сохраняется
   остановка на первой ошибке; повтор заново читает feed и пропускает прочитанные.
5. Обработать обе формы списка и одиночную форму ответа куратора. Сохранить
   semantic submit, Enter/Space, текущие подписи ожидания и видимый focus.
   При отказе фокус не переносится на верх страницы; сообщение и повтор доступны
   на 320/390 px, длинные RU/KY подписи переносятся без изменения типографики.

## Технические границы и навигация

Предполагаемые изменения: новый `PortalNotificationReadForm.tsx` в
`src/components/portal/admission/`, его подключение в `NotificationsView.tsx`
и `portal/notifications/[notificationId]/page.tsx`, четыре строки admission RU/KY
в `src/lib/portal/i18n.ts`, необходимые обновления существующих wiring checks.
Два submit-компонента сохраняются; их существующий `useFormStatus` получает
pending от той же оборачивающей формы. CSS — только если реальный осмотр выявит
переполнение нового сообщения; новые токены, шрифты или композиция не нужны.

Серверные actions, их `Promise<void>`, Auth guard, RPC, schema/RLS, deterministic
`studentPortalNotificationReadRequestId`, входные поля и revalidation остаются
без изменения. В частности, нельзя заменить throw на `{ok:false}` и оставить
bulk loop без проверки результата: это изменило бы его остановку на отказе.

Клиентский catch обязан пропускать служебные ошибки Next. Установлен Next
16.3.4: `server-action-reducer.js:239–260` отклоняет action promise при redirect;
guard использует `redirect`. Предложение — публичный `unstable_rethrow(error)`
первой строкой catch, до установки локальной ошибки, с освобождением собственного
in-flight guard в finally. Не разбирать digest и не импортировать внутренние
Next-модули. Это **явная зависимость для precode review**: официальный API
помечен нестабильным и не рекомендован для production. До принятия этой детали
координатором реализация не начинается; решение об одобрении зафиксировано
ниже. Нельзя молча проглотить redirect или расширить серверный контракт.

Официальные источники, проверены 2026-09-21:
[Next: обработка ошибок](https://nextjs.org/docs/app/getting-started/error-handling)
описывает локальное состояние для ошибок событий и отдельно ожидаемые серверные
ошибки; [Next: unstable_rethrow](https://nextjs.org/docs/app/api-reference/functions/unstable_rethrow)
объясняет передачу служебных ошибок обратно framework и ограничение стабильности.
Здесь серверный бизнес-контракт не меняется; перехватывается отклонённый вызов
формы, включая потерю связи между браузером и сервером.
