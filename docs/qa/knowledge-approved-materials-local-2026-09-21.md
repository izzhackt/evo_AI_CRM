## Путь и проверка

1. Сверить свежую identity, organization и конкретные capabilities, baseline
   после225, отсутствие дубликатов по заголовкам/body/file hashes.
2. Через существующую форму шаблонов создать ровно два snippets.
3. В корне «Компания» создать две файловые карточки и загрузить по одной
   версии через действующий scanner-gated upload. Создание карточки отдельно
   от загрузки; готовность подтверждается только после Storage finalization.
4. Перечитать оба раздела, проверить IDs/versions/paragraphs, выполнить поиск.
   Скачать каждую новую версию один раз и сверить размер/SHA исходных bytes.
5. Зафиксировать ожидаемые записи и отсутствие изменений старых строк,
   посторонних таблиц/Storage objects, схемы и миграционного реестра.

Реальный ClamAV подготовлен отдельно: официальный engine1.5.4, обновление
сигнатур28109→28129, PING и вызов репозиторного scanBytesWithClamd прошли.
Task-owned контейнер остановлен; перед upload необходим свежий запуск и
проверка. Подмена результата сканирования недопустима. Readiness receipt SHA:
`7e0b3ce9fc82655244278dd18fedf46601ff290c04b987dcd1fff6d0f7c12411`.

Предельный успешный сценарий:2 snippets,2 file metadata,2 versions/objects,
2 upload reservations/bindings/attestations/finalizations и2 downloads.
Download создаёт grants, consumptions, command receipts и audit; это не
нулевая запись. Точные SQL effects сверяются с текущими функциями до действия
и отдельно после него. Обычные Auth sessions учитываются отдельно.

При неоднозначном ответе сохранить исходный request ID и проверить результат
перед повтором. Refresh может выдать новый ID. Не удалять partial shell,
reservation или object и не повторять загрузку вслепую. Успешные QA-записи
сохраняются; массового cleanup нет.
