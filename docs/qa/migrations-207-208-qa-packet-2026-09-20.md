## Что именно изменится при применении

207 добавляет Student read RPC для максимум четырёх недавно опубликованных
вузов. Дата берётся из существующей истории; контент и исторические даты
не переписываются. Вызов требует Student authority и `portal.read.self`.

208 добавляет закрытый ключ роли Sales Manager, связывает его с одной
проверенной существующей ролью и меняет проверки записи продажи, handoff и
исторического редактирования. Admin без этой роли больше не получает
автоматическое разрешение. Продавец и месяц новых продаж берутся из текущего
владельца и signing_date карточки; исторические строки не пересчитываются.
Сохраняются tenant scope, idempotency, audit и блокировки от отзыва роли.

Эти изменения общих функций вступят в силу для работающей CRM сразу после
SQL, даже если новый frontend ещё не выпущен. Отдельная QA-организация
изолирует тестовые бизнес-записи, но не применение общей схемы и новых прав.
Root должен учесть это в решении о времени применения; server release
остаётся отдельным действием.

**Вывод:** не применять shared 208 отдельно ради QA. Перед ним нужны разрешённое
общее окно frontend+SQL по существующему release-контракту, проверенный порядок
перехода и возврата и целевая приёмка до возобновления обычных записей.
Такого release authority сейчас нет; этот пакет его не подразумевает.
207 сама по себе добавляет read RPC, но текущий запрос не разрешает её применение.

Минимальная альтернатива для проверки до выпуска — отдельный одноразовый
локальный PostgreSQL/Auth/PostgREST и Next из #935: применить туда schema и
207/208, использовать обычные QA logins и настоящий UI→RPC→persist/readback.
Никакие production identities или memberships для этого менять не требуется.
Это техническая premerge-проверка, не managed/customer acceptance. Контур и
тестовые записи ещё не создавались; setup/QA выполняются только в явно
согласованной границе, без общего тяжёлого suite. Удаление собственного
одноразового локального контура не требует разрушать общий audit или данные.

## Объём будущего managed-окна, требующий отдельной authority

Следующие действия — только после согласованного frontend+SQL rollout,
не текущая инструкция на самостоятельный SQL apply:

1. Применить ровно сверенные 207, затем 208 одним координатором; проверить
   ledger, RPC/ACL и binding роли. При изменении файлов/реестра пакет пересверить.
2. Подтвердить существующий изолированный QA tenant и staff identities.
   Если их нет, отдельно разрешить одну выделенную QA-организацию, её роли
   и memberships. Нужны сессии Sales Manager, Sales без этой роли, Admin без
   неё и Admissions; новые Auth accounts допустимы только при явном включении
   provisioning в разрешение (не более четырёх выделенных staff identities).
   Сначала использовать только подтверждённые свободные staff QA identities,
   если владелец укажет такие. Существующий Student основной EVO не переносить,
   текущую Admin-сессию пользователя не перепрофилировать.
3. Явно разрешить QA-only создание и изменение минимальных лидов, условий,
   handoff/дел и продаж через настоящий продукт/RPC. Роль QA Sales Manager
   должна получить явный reviewed workflow binding; не выдавать права людям
   основной организации ради теста. Не подменять JWT или RLS.
4. Не включать рассылки, приглашения, оплату у провайдера, Storage uploads,
   изменение клиентских записей, удаление Auth или server deployment.
   QA-артефакты учесть отдельно, сохранять audit; удаление не предполагается.

## Учёт и очистка только созданных QA-артефактов

До первой разрешённой записи сохранить закрытый manifest: точный project,
QA organization ID, новые Auth/profile/membership/resource IDs, request IDs и
квитанции создания. В manifest отдельно отметить переиспользованные identities:
они никогда не являются целью удаления. Перед очисткой сравнить ownership и
фактический набор ссылок с manifest; при чужой ссылке или расхождении остановиться.

Обычная очистка — доступные продуктовые archive/revoke команды только для этих
QA IDs с причиной и сохранением audit. Удаление всей организации или Auth users
не считать простым CASCADE: identity/history используют `ON DELETE RESTRICT`.
Физическое удаление возможно только отдельным явно разрешённым скриптом с
точным списком новых IDs, проверкой FK и read-only preview/counts перед общей
транзакцией. Не использовать LIKE/prefix/name, не отключать triggers/RLS и
не удалять аудит ради успешного cleanup. Такой скрипт пока не подготовлен;
обещание полного физического удаления не входит в готовность этого пакета.
Если оно обязательно для владельца, не создавать managed QA-артефакты до
утверждения исполнимого способа удаления; существующие аккаунты не затрагивать.

Остановиться при расхождении identity/tenant, необходимости клиентской записи,
неожиданном provider-действии, изменившемся ledger или несоответствии SHA.
Это целевая приёмка изменённых функций; общий финальный E2E остаётся отложен.
До её выполнения #935 остаётся draft и не заявляется готовым к merge.
