**Как править.** Одиночный bind mount привязан к inode, поэтому файл
перезаписывается на месте (`cp` в существующий файл), а не заменяется (`mv`
или `cp --remove-destination` дают новый inode, и контейнер остаётся на старом
файле). Порядок: резервная копия рядом, запись на месте с проверкой хэша,
`docker exec evo-edge-caddy caddy validate --config /etc/caddy/Caddyfile
--adapter caddyfile`, и только после успеха `caddy reload` с теми же
аргументами. Контейнер не пересоздавать и не перезапускать (`compose up/down`,
`docker restart` запрещены: порты общие). Не печатать адаптированный JSON и
admin API: в них ключ сайта. Подробная процедура с защитами — шаг C5 в
[`whatsapp-go-live.md`](whatsapp-go-live.md).

`oom_score_adj` 500, `pids_limit` 512, журнал 10 МБ × 3, `restart:
unless-stopped`]. `oom_score_adj` 500 ставили, пока Supabase был копией, чтобы при нехватке памяти
первым погибал он, а не рабочая CRM. С 20.10 Supabase сам рабочая база, а
настройка осталась прежней: при нехватке памяти (16 ГБ, swap нет, раздел 2) ядро
скорее всего снова выберет первым его. Пересмотр лимитов не делался, решение за владельцем.

Studio, `/pg` (meta), аналитика и функции наружу не открыты. Аналитики, vector и
edge functions в нашем слое нет.

**Остановить и запустить.** Это рабочая база: остановка кладёт вход, CRM и приложение
студента, поэтому только по команде владельца. На сервере, из каталога, чтобы
подхватился `.env`:

```bash
cd /opt/evo-supabase && docker compose stop     # остановить, контейнеры и образы остаются
cd /opt/evo-supabase && docker compose start    # запустить обратно
```

**Не** `docker compose down` и **не** `docker system prune` / `docker image
prune`: `down` удаляет контейнеры, и ночная чистка образов (раздел 2) к утру
удалит их образы; тома при этом остаются, но стек придётся тянуть заново. Если
шлюз пересоздан, подключение к `evo_public_web` с алиасом закреплено в
`docker-compose.evo.yml`.
