# Команда EVO: выпуск и начало работы

Обновлено: 2026-09-13. Текущий план: [сотрудники и роли](../design/v3/employee-roles-accounts-run-plan.md).
История командного чата и задач: [team workspace](../design/v3/team-workspace-run-plan.md).
Это инструкция активации, не доказательство production или доставки сообщений.

## Что работает независимо от WhatsApp

- Сотрудник использует собственный вход Supabase Auth в тот же EVO.
- «Командный чат»: Общий — все активные сотрудники, Продажи — Sales/Admin,
  Поступление — Admissions/Admin. Студенты не получают доступ.
- «Задачи»: рабочие задачи без студента и существующие задачи по студентам.
  Чат позволяет открыть предварительную форму задачи; сама переписка не меняет
  дело и не выполняет задачи автоматически.
- Колокольчик содержит внутренние назначения/изменения задач и упоминания.
  В нём нет скрытого текста закрытых сообщений. Просрочка — фильтр задач.
- Никакие сообщения этого чата автоматически не идут клиентам или в WhatsApp.

   schema и один полный CI на окончательном кандидате. Номера миграций и текущий
   release checkpoint брать из [Launch Plan](../EVO_LAUNCH_PLAN.md), не из
   исторического выпуска чата139–142.
2. Используется прежний проект Supabase `iosckaqtovbbnssqcpde`. Не создавать
   новую постоянную базу и не переносить в неё рабочие данные.
3. Соблюдать recovery gate и уже записанные разрешения текущего выпуска в
   Launch Plan. Не повторять вопрос о новом backup: владелец его пока отложил.
   Не делать backup/reset и не расширять разрешённый набор миграций.
4. Применить только новые согласованные миграции, выпустить точный образ через
   штатный release workflow, проверить image/schema/health. Старую базу не reset.
5. Открыть владельцу тот же сервер через `localhost:3000` SSH tunnel после
   проверки занятого порта и актуального адреса app-контейнера. Туннель не
   означает отдельный локальный продукт или вторую базу.

## Приглашения сотрудников

Нужны подтверждённые имя, рабочий email и отдел каждого сотрудника. Пароль
задаёт сам сотрудник; его не отправляют в чат и не показывают администратору.
S2 добавляет редактируемые отделы и бизнес-роли, несколько назначений на человека
и области доступа по отделу, направлению или своим записям. S2 выпущен в
`05585020`; [release evidence](../design/v3/references/2026-09-13-staff-docs-s2-d2-release.md)
отделяет проверенный редактор от ещё не выполненного подключения реальной команды.
Должность — подпись в карточке, она не выдаёт права. Пошаговые действия описаны
в [инструкции Admin](../design/v3/staff-admin-guide.md).

- Admin открывает «Настройки → Сотрудники», проверяет адресата/роль и явно
  подтверждает отправку. Создание Auth-аккаунта само по себе не выдаёт роль.
- Приглашение и выдача membership имеют раздельные подтверждения. При
  неопределённой отправке сначала нажать «Сверить», не отправлять второе письмо.
- Подтверждённый отказ Auth отображается в журнале. После исправления причины
  и паузы можно явно создать новый запрос. Таймаут или неизвестный результат
  не считается подтверждённым отказом и не открывает автоматический retry.
- Для действующего доменного контракта сохранять точные Supabase redirect
  URLs: `https://crm.evoadmissions.com/auth/staff` для сотрудников и
  `https://app.evoadmissions.com/auth/callback` для Student. Не использовать
  общий wildcard и не направлять сотрудника на Student callback.
- Шаблон приглашения/восстановления должен учитывать `{{ .RedirectTo }}`,
  а не направлять все письма на Student-only callback. Прямой вариант:
  `{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=invite` и аналогичный
  `type=recovery`. Сохранить Student callback при изменении общей конфигурации.
- Нельзя заявлять доставку по успешному ответу Auth или наличию timestamp:
  сотрудник должен действительно получить письмо и завершить вход.

Оба домена используют одно приложение, сохраняют публичный Host и host-only
cookies. Старый sslip теперь только GET-only переходы 308; POST отклоняется
с 405, без перенаправления auth POST. Порядок DNS/TLS,
настройки Auth и managed release: [доменный runbook](../../deploy/README.md#canonical-domain-cutover).

Для начала работы нужен настроенный SMTP — сервис отправки писем. Подключить
действующие host, port, user/password и подтверждённый From-адрес в Dashboard,
не в Git или чат. Затем согласовать одного получателя и его назначения, отправить
одно приглашение из EVO и дождаться подтверждённого получения и входа. После
этого подключать остальных. Если SMTP-аккаунта ещё нет, создание сервиса,
подтверждение домена и возможная оплата требуют участия владельца.

Встроенный SMTP Supabase разрешает адреса только команды самого проекта; это
не список сотрудников CRM. Не выдавать сотрудникам доступ к Supabase ради
доставки письма. [Ограничения и настройка SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

Поведение шаблонов и ссылок: [Supabase email templates](https://supabase.com/docs/guides/auth/auth-email-templates).
Отказы провайдера: [Supabase Auth error codes](https://supabase.com/docs/guides/auth/debugging/error-codes).

## Короткая настоящая приёмка

Два согласованных сотрудника с отдельными сессиями, без общего Admin-пароля:

1. Приглашение → собственный пароль → вход. Изменение роли/блокировка
   действительно отнимает старый доступ, последний активный Admin защищён.
2. Сообщение в своём отделе → ответ → упоминание → непрочитанное → refresh.
   Чужой отдел и Student не получают текст по прямому URL/RPC.
3. Сообщение → предварительная форма → одна задача → уведомление исполнителю
   → выполнение. Потерянный ответ и повтор не создают дубликат.
4. Создать вторую задачу по студенту; поиск дела и продолжение страниц не
   смешивают разные запросы. Сетевой сбой сохраняет введённый текст.
5. Проверить клавиатуру и экран393px; при320px действия не теряются.

Реальные аккаунты и сообщения не создавать без подтверждённых адресатов.
Проверка пустой схемы, сборка и review не заменяют этот пользовательский проход.

## Когда появятся WhatsApp-номера

Текущее решение владельца: **WAHA отложен**. Не запускать пункты ниже сейчас.

1. Подтвердить цель: общий sales-номер для клиентов или отдельное дублирование
   корпоративных каналов. Это разные потоки. Внутренний чат уже имеет свои
   аккаунты и не нуждается в рабочих номерах.
2. Для sales подтвердить владельца рабочего номера, доступ к телефону и
   разрешение на pairing/QR. Затем проверить текущую приватную `crm_primary`
   без пересоздания сессий и сохранённых данных.
3. Сверить единственного владельца входящего webhook и исключить двойную
   обработку старым worker. Не включать fallback на замороженный `evo-inbox`.
4. Проверить защищённые настройки и HMAC без вывода ключей; WAHA остаётся
   приватным. Публичные dashboard/порты не открывать.
5. С разрешённым получателем выполнить один входящий и один ручной исходящий
   сценарий. Зафиксировать реальные provider IDs, результат и отсутствие дублей.
   Здоровый контейнер не доказывает подключение WhatsApp или доставку.
6. Только после этого разрешить соответствующий live-поток. Lead-agent/AI
   не получают автономную отправку из факта готовности внутреннего чата.

Корпоративный WhatsApp-мост — отдельный W2 из плана: нужна явная привязка
сотрудник ↔ номер ↔ сессия ↔ разрешённая группа и правила доставки/отзыва.
Он **не реализован и не включён** этим нативным выпуском. Одна WAHA-сессия
отправляет от одного аккаунта, не подменяет каждого сотрудника.
Официальные контракты: [WAHA sessions](https://waha.devlike.pro/docs/how-to/sessions/),
[WAHA groups](https://waha.devlike.pro/docs/how-to/groups/).
