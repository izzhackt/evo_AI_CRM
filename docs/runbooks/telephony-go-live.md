## 2. Правила работы

- Токены, ключи, ссылки на записи, номера и имена не печатаются, не попадают в
  чат, Git, PR и квитанции. Ввод секрета — только `read -rs` (скрытый ввод); в
  командной строке, `echo`, `set -x` и `docker exec -e` секретов нет. В ssh-сессии
  первым делом `set +o history; umask 077`.
- Значения в `.env.production` правятся только на диске, с резервной копией, и
  вступают в силу **только через выпуск** (контроллер запечатывает снимок env).
  Env запущенного контейнера и снимки не править.
- SQL — только чтение и только счётчики (Supabase SQL Editor, как в
  `whatsapp-go-live.md`, G1): колонки с номерами и ссылками и значения `fields` не
  выбираются (имена ключей `fields` — можно).
- Выпуск (процедура **Р**, как `whatsapp-go-live.md`, C3 и `deploy/fast-app-release.md`):
  `main` заморожен, нет `pending-current.json`, чужого выпуска и слияний; локально
  ```bash
  gh variable set EVO_PRODUCTION_RELEASE_ARMED --repo izzhackt/evo_AI_CRM --body true
  gh workflow run evo-platform-ci.yml --repo izzhackt/evo_AI_CRM --ref main -f proof_revision=<полный SHA main>
  # дождаться «EVO fast app release» (gh run watch), затем сразу:
  gh variable set EVO_PRODUCTION_RELEASE_ARMED --repo izzhackt/evo_AI_CRM --body false
  ```
  Проверка: `docker inspect -f '{{index .Config.Labels "org.opencontainers.image.revision"}}' evo-crm-app-1`
  равен SHA, `https://crm.evoadmissions.com/api/health` отвечает 200. Выпуск
  пересоздаёт приложение: **на секунды `contact` недоступен**, поэтому при живом
  подключении выпуски — только в тихое окно и без звонков в этот момент.

Помощники для ssh-сессии на VPS (вставить один раз; секреты они не печатают; нужны
`jq`, `curl`, `awk`, `openssl` — пакеты ставить только с ведома владельца):

```bash
set +o history; umask 077
R=/opt/evo-crm; APP=evo-crm-app-1; ENVF=$R/.env.production; B=/root/evo-config-backups
install -d -m 700 "$B"
backup() { cp -p "$ENVF" "$B/env.production.$(date -u +%Y%m%dT%H%M%SZ)" && ls -1 "$B" | tail -1; }
set_env_value() {  # NEWVAL=… set_env_value FILE NAME — строка NAME= должна быть ровно одна
  local f=$1 n=$2 tmp; tmp=$(mktemp) || return 1
  NAME="$n" awk 'BEGIN{FS=OFS="="} $1==ENVIRON["NAME"]{hit++; print ENVIRON["NAME"] "=" ENVIRON["NEWVAL"]; next} {print} END{if(hit!=1)exit 3}' "$f" > "$tmp" \
    && cat "$tmp" > "$f"; local rc=$?; rm -f "$tmp"; return $rc
}
env_put() {        # env_put FILE NAME VALUE — заменить единственную строку NAME= или добавить её
  if grep -q "^$2=" "$1"; then NEWVAL=$3 set_env_value "$1" "$2"
  else { [ -z "$(tail -c1 "$1")" ] || printf '\n' >> "$1"; } && printf '%s=%s\n' "$2" "$3" >> "$1"; fi
}
envfacts() {       # что видит запущенный контейнер: значение ENABLED и длины остальных (значений нет)
  docker exec "$APP" node -e 'for (const n of ["ENABLED","CRM_TOKEN","CRM_TOKEN_NEXT","PBX_TOKEN","PBX_URL","PBX_HOST"]) {
    const v = process.env["EVO_PLATFORM_TELEPHONY_" + n] ?? ""; console.log(n, n === "ENABLED" ? JSON.stringify(v) : "длина=" + v.length); }'
}
envcheck() {       # контракт env: файлы контракта и примера положены локально командой из шага 1
  node /root/evo-golive/evo-app-env-contract.mjs --example /root/evo-golive/env.production.example --env "$ENVF" --supabase-project-ref "$REF"
}   # ожидается {"ok":true,"code":"valid"}; REF — «gh variable get EVO_SUPABASE_PROJECT_REF» (не секрет)
```

## 3. Предусловия (все обязательны; иначе не начинать)

1. **Уведомление о записи включено** в кабинете ВАТС («Ещё → Запись звонков»):
   стандартная фраза «Обращаем ваше внимание, разговор может быть записан.».
   Владелец проверяет, что она звучит на русском и кыргызском и входит в сценарий,
   включая вызовы, на которые отвечает группа (план §13, §14 шаг 0). Это условие
   юридического решения 17.10; без него не запускаем.
2. **Production ledger содержит 288–301 без дыр.** Читает держатель authority:
   `gh workflow run evo-schema-ledger.yml --repo izzhackt/evo_AI_CRM -f mode=check`
   (читает), при недостающем хвосте — `mode=apply`, затем снова `check`. Сверка
   SQL (только чтение):
   ```sql
   SELECT count(*) AS applied, max(version) AS last_version,
          count(*) FILTER (WHERE version ~ '^(28[89]|29[0-9]|30[01])$') AS v288_301
   FROM supabase_migrations.schema_migrations;   -- ожидается: 301, '301', 14
   ```
3. **Механизм стирания номера есть (миграция 294).** Это жёсткое условие
   `ENABLED=1` (комментарий в `deploy/env.production.example`, PLAN_CHANGES T1a п. 20,
   T11a п. 9). Только чтение:
   ```sql
   SELECT count(*) AS erasure_functions   -- ожидается 2
   FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
   WHERE n.nspname = 'platform' AND p.proname IN ('telephony_erase_person_v1', 'telephony_purge_evidence_v1');
   ```
   Порядок стирания по человеку — `docs/runbooks/account-deletion.md`, шаг «Телефония».
4. **На production выпущен `main` с телефонией** (не старше T10, `cf7945c34`).
   Проверка: revision образа (раздел 2) — потомок этого коммита (локально
   `git merge-base --is-ancestor cf7945c34 <revision>`); `docker exec evo-crm-app-1 ls -l
   /app/telephony-maintenance.mjs` показывает файл; роли «Телефония — менеджер» и
   «Телефония — руководитель» есть в «Настройки → Роли и доступ». Приём при этом
   выключен, ключей телефонии в env нет.
5. **Тихое окно, владелец рядом:** воскресенье либо будний день после 20:00 по
   Бишкеку (шаги с пересозданием приложения при живом подключении — не раньше 21:00,
   план §14 шаг 7). Линия выпусков свободна (`EVO_PRODUCTION_RELEASE_ARMED=false`,
   `main` заморожен). Команду продаж стоит заранее предупредить о тестовых звонках
   и о том, что amoCRM работает как раньше (совет, не условие).
6. **Edge (решение владельца).** Укрепляющая правка edge плана §5.7 (только `POST`,
   предел 32 КиБ и хост `crm.` на пути приёма, заголовок адреса `X-Evo-Telephony-Ip`)
   **в срезы T1–T11a не вошла** и в репозиторном `Caddyfile.evo-edge` её нет; живой
   файл правится только по «давай» (`caddy validate` + `caddy reload`, порядок C5 в
   `whatsapp-go-live.md`, без перезапуска общего edge). Без правки маршрут работает
   (ключ, предел 32 КиБ и ограничитель неудач — в приложении), но: счётчик неудач
   общий для всех адресов (`unknown`), путь отвечает и на хосте студента, edge
   пропускает тело до 105 МБ (приложение режет на 32 КиБ ответом 413). Владелец
   выбирает «идём без правки» или «сначала правка» и это записывается в квитанцию.
7. **Ключи не в руках агента.** Ключ приёма создаётся на машине владельца и живёт в
   буфере обмена и SOPS-архиве (`Секреты и доступы ЭВО`; строки «Beeline ВАТС» в
   реестре ещё нет, её добавляют при внесении ключа); «Ключ для авторизации в АТС»
   видит только владелец в кабинете.

**Отличия.** (1) `ENABLED=1` включается в шаге 1, **до** создания подключения, как в
плане (§14, шаг 7 перед шагом 8): пока подключение живо при `ENABLED=0`, `event` и
`history` получали бы `503`, а реакция ВАТС на это не описана (план §5.1, риск 3).
Отдельной канарейки «сначала только `contact`» нет: `contact` и так отвечает без
базы независимо от `ENABLED`, а приём при выключенном разборе лишь хранит
доказательство и не создаёт звонков, лидов и задач. (2) Таймер — шаг 6, после приёма
и до `projection_enabled` (план §5.3 ставит его до приёма): пока разбор выключен,
повторять нечего, а справочник сотрудников ВАТС таймер заполняет до разбора, как
нужно. (3) Звонки и ноги появляются в базе не в шаге 5, а в шаге 7 после
`projection_enabled`: пока флаг выключен, приём только сохраняет доказательство и
ставит работу в очередь, а разбор выполнит таймер.

## 5. Шаги

### Шаг 1. Ключ приёма и `ENABLED=1`

```bash
# локально (Mac): ключ в буфер, на экран не выводится; сохранить в SOPS-архив; затем вставить на VPS
openssl rand -hex 32 | tr -d '\n' | pbcopy
# локально: положить контракт и пример env из SHA выпущенного main на VPS (один раз)
SHA=<полный SHA выпущенного main>
git show "$SHA:scripts/evo-app-env-contract.mjs" | ssh hermes-vps 'install -d -m 700 /root/evo-golive && cat > /root/evo-golive/evo-app-env-contract.mjs'
git show "$SHA:deploy/env.production.example"    | ssh hermes-vps 'cat > /root/evo-golive/env.production.example'
gh variable get EVO_SUPABASE_PROJECT_REF --repo izzhackt/evo_AI_CRM   # не секрет; это значение — REF на VPS
# после вставки ключа на VPS и в SOPS очистить буфер: printf '' | pbcopy
```
```bash
# на VPS (помощники из раздела 2):
REF=<значение, напечатанное локально>
backup
read -rs -p 'Ключ приёма (вставить): ' T; echo
[[ $T =~ ^[A-Za-z0-9-]{32,64}$ ]] || echo 'СТОП: формат ключа'
env_put "$ENVF" EVO_PLATFORM_TELEPHONY_CRM_TOKEN "$T" && env_put "$ENVF" EVO_PLATFORM_TELEPHONY_ENABLED 1; unset T
awk -F= '$1=="EVO_PLATFORM_TELEPHONY_ENABLED"{print $1"="$2} $1=="EVO_PLATFORM_TELEPHONY_CRM_TOKEN"{print $1" длина="length($2)}' "$ENVF"
envcheck        # {"ok":true,"code":"valid"}; отказ — вернуть файл из $B и не выпускать
```
Затем выпуск (процедура **Р**).

**Проверка маршрута** (на VPS; технический зонд, не приёмка; базу не вызывает, ключ не
печатается — он только в `printf`, встроенной команде, и читается из файла):
```bash
URL=https://crm.evoadmissions.com/api/v2/telephony/beeline/inbound
probe() { curl -sS -m 10 -X POST -H 'Content-Type: application/x-www-form-urlencoded' --data-binary @- -w '  [http %{http_code}, %{time_total}s]\n' "$URL"; }
envfacts                                                    # ENABLED "1", CRM_TOKEN длина=64, остальные длина=0
curl -sS -m 10 -o /dev/null -w 'GET -> %{http_code}\n' "$URL"                       # 405
printf 'cmd=contact&crm_token=wrong-key-probe' | probe                              # {"error":"Invalid token"}  [http 401, …]  (один раз: неверные ключи считает ограничитель, 20 в минуту)
printf 'cmd=contact&crm_token=%s' "$(sed -n 's/^EVO_PLATFORM_TELEPHONY_CRM_TOKEN=//p' "$ENVF")" | probe   # {}  [http 200, …]
docker logs --since 5m "$APP" 2>&1 | jq -rR 'fromjson? | select(.event=="telephony_inbound") | [.status,.reason,.cmd] | @tsv'
```
Ожидается: `405`; `401 invalid_token none`; `200 contact contact`; `time_total` порядка
десятков миллисекунд (план: ответ приложения меньше 200 мс). **С верным ключом не
слать `cmd=event`, `history`, `rating`: при `ENABLED=1` они пишут доказательство.**
Старые публичные пути остаются скрытым 404:
`curl -sS -o /dev/null -w '%{http_code}\n' -X POST https://crm.evoadmissions.com/api/webhooks/telephony`.

**Откат шага 1:** `env_put … ENABLED 0` (ключ можно оставить), `backup` перед правкой,
выпуск. Подключения в кабинете ещё нет, входящие не затронуты.

### Шаг 2. Подключение «Ваша CRM» (кабинет ВАТС, «Интеграция с CRM»)

Подключение **сразу живое**: с момента сохранения каждый входящий звонок на номер
компании вызывает `contact` к EVO. Что делает ВАТС при ошибке или медленном ответе,
не описано (план §17, риск 2, P1) — поэтому только тихое окно и владелец рядом.

До сохранения:
1. **Базовая линия.** Один входящий с номера, известного amoCRM (на чужой номер
   виджет создаст в amoCRM контакт и сделку), принимает менеджер: записать время до
   первого звонка у менеджера и то, что показывает виджет amoCRM.
2. Открыть форму «Интеграция с вашей CRM» → новое подключение «Ваша CRM». Проверить,
   что **«Адрес вашей CRM» принимает путь**, а не только хост (подсказка в поле —
   `domain.kg`). Не принимает — **стоп, не сохранять**: запасной хост с правкой edge и DNS
   (отдельное «давай») либо режим «только сверка» (план §5.6).
3. Прочитать названия двух отметок «Права доступа к управлению ВАТС» и записать
   (только названия) в квитанцию.

| Поле формы | Значение |
|---|---|
| Имя вашей CRM | `EVO CRM` |
| Адрес вашей CRM | `https://crm.evoadmissions.com/api/v2/telephony/beeline/inbound` (в «Настройки → Телефония» есть кнопка копирования) |
| Ключ для авторизации в вашей CRM | ключ приёма из SOPS; **вставляет владелец**, в чат не вводится |
| Сценарий | для всех номеров |
| «Отправлять статус обработки пропущенного звонка в CRM» | **выключено**: перезвон EVO определяет сама (план §5.6); `missedStatus`, если придёт, сохраняется как подсказка |
| «Звонки от клиентов … ответственному менеджеру, указанному в CRM API» | **выключено** до фазы 2 (маршрут входящих не меняется) |
| «Права доступа к управлению ВАТС» | минимум: отметки, без которых чтения и `makecall` отвечают `403`; всё, что позволяет менять сотрудников, отделы, номера, ограничения — не включать, если чтение работает |
| «Адрес АТС» и «Ключ для авторизации в АТС» | генерирует кабинет, только чтение; ключ — для шага 3 |

Сохраняет владелец (или агент при владельце). Подключение amoCRM не трогаем.
**Сразу после сохранения — контрольный входящий (см. шаг 4)**. Звонок задержан,
потерян или виджет сломан — немедленно откат.

**Откат шага 2:** выключить подключение «EVO CRM» в кабинете (или удалить). Больше

### Шаг 3. «Ключ для авторизации в АТС» → env

```bash

backup
```

Адрес и хост берутся из кабинета как есть (в имени тенанта одна «s» в «admissions»,

**Проверка прав ключа** (только чтения, только коды; `makecall` не вызывается):

### Шаг 5. Тестовые звонки: что лежит в базе

Номера — только владельца и сотрудников, знающих о проверке; номер, известный amoCRM.
Чтобы звонки сопоставились с лидом (шаги 7.3, № 2–4), **до первого тестового звонка**
в CRM заводится тестовый клиент с лидом на номер владельца (штатно; после проверок
архивируется, не удаляется). Второй номер владельца, для проверки 7.3 № 5, в EVO не
заводится.

| Звонок | Что проверяется (план §15) |
|---|---|
| Входящий, отвечает менеджер | строка 3; доказательства `event` и `history` |
| Исходящий из amoCRM (WebRTC) на телефон владельца | строка 2 |
| Входящий, звонящий кладёт трубку на приветствии | строка 4 |
| Групповой или с переводом (если есть возможность) | строка 5 |

Только чтение, счётчики (Supabase SQL Editor):
```sql
-- доказательства приёма за два часа: команды, состояния, имена недостающих полей (значений нет)
SELECT cmd, validation_state, count(*) AS n, count(*) FILTER (WHERE has_link) AS with_link
FROM platform_private.telephony_pbx_events WHERE received_at > now() - interval '2 hours' GROUP BY 1, 2 ORDER BY 1, 2;
SELECT e.cmd, k AS field, count(*) AS n   -- какие поля реально шлёт ВАТС (только имена)
FROM platform_private.telephony_pbx_events e, jsonb_object_keys(e.fields) k
WHERE e.received_at > now() - interval '2 hours' AND e.fields IS NOT NULL GROUP BY 1, 2 ORDER BY 1, 2;
-- очередь разбора: пока projection_enabled выключен, всё в queued

```
Ожидается: `event` и `history` есть (число `event` на звонок — образец для квитанции),
`history` с `with_link > 0`, если запись включена; строк `rejected` нет; `queued` равно числу
доказательств, `dead_lettered` нет. **Звонков и ног ещё нет** (`telephony_calls` и
`telephony_call_legs` — 0 строк): разбор выключен, они появятся в шаге 7. В
«Настройки → Телефония» видны «Последнее событие звонка» и «принято N».

**Откат шага 5:** выключить подключение (шаг 8, п. 1). Накопленные доказательства
остаются; удалять их можно только стиранием по человеку (`account-deletion.md`).

видит страницу настроек с единственным разделом «Телефония»; менеджер её не видит.

**7.2. Сопоставление** («Настройки → Телефония» → «Пользователи ВАТС и сотрудники»):

Делается **до** `projection_enabled`: прошлые ноги звонков сопоставление не

владельца (шаг 5); команду продаж стоит предупредить заранее.

```sql
SELECT direction, state, outcome, outcome_source, created_via, match_state, count(*) AS n
FROM platform_private.telephony_calls WHERE started_at > now() - interval '1 day' GROUP BY 1,2,3,4,5,6 ORDER BY 1,2,3;

       count(*) FILTER (WHERE membership_id IS NULL) AS without_staff
FROM platform_private.telephony_call_legs WHERE created_at > now() - interval '1 day' GROUP BY 1,2;
SELECT action, count(*) AS n FROM platform.audit_events
WHERE action LIKE 'telephony.%' AND created_at > now() - interval '1 day' GROUP BY 1 ORDER BY 1;
```
Ожидается: «приветствие» без сотрудника — `missed`, не `answered`; переведённый или групповой
звонок — одна строка (при переводе два звонка со связью), у ног свои сотрудники;
`without_staff = 0`; `created_via` — `webhook` (`dial` не ожидается: связь с набором несёт `dial_request_id`, см. ниже).

**Звонок из «Позвонить» и `missed_task_enabled` (срез T7b, миграция 312).** Звонок из «Позвонить» (`makecall`) привязывается к своему набору (`dial_request_id`): по `callid` из ответа ВАТС при вставке строки звонка и при итоге набора, а при решении автоматики ещё по цепочке переведённых звонков и запасным ключом (сотрудник из набора среди ног, тот же номер клиента, время рядом с набором). ВАТС сначала звонит сотруднику, потом клиенту: если сотрудник не взял СВОЮ трубку, клиенту не звонили, поэтому «Недозвона» и задачи нет (метка автоматики `skipped_dial_unanswered`, результат пуст); если сотрудник взял, а клиент не ответил — обычные правила «Недозвона». Форма событий ВАТС для такого звонка настоящим звонком ещё не проверена (`ACCEPTED` на ноге сотрудника — признак, что он ответил): при включении проверить обе строки (план §15, B 19 и 20) на номере владельца; если «Недозвон» после ответа сотрудника не появляется, а метка стоит `skipped_dial_unanswered`, значит ВАТС не присылает признак ответа на ногу сотрудника — флаг выключить и чинить срез, не включая его вслепую. Проверка (только чтение):
```sql
SELECT c.direction, c.outcome, c.automation_outcome, c.dial_request_id IS NOT NULL AS bound, c.result_code
FROM platform_private.telephony_calls c WHERE c.started_at > now() - interval '1 hour' ORDER BY c.started_at DESC;
```

Потолки автоматики защищают от поддельных событий: не более 10 новых лидов в час и 40
в сутки, 30 задач в час и 120 в сутки. При превышении оба флага автоматики
выключаются сами, горит «Автоматика остановлена по потолку»; снова включает admin
после проверки (повторное включение флага снимает отметку). Ориентир плана: около
четырёх пропущенных входящих в рабочий день и около 0,5 неизвестных номеров в день.

После шага 7 строки A плана §15 (1–14) и B (15–20) закрываются в квитанции по
фактическим результатам; не пройденная строка — флаг выключен, срез чинится.

### Шаг 8. Откат

Порядок важен: пока подключение живо, каждый входящий вызывает `contact`, а правка
env, выпуск и `ENABLED=0` в этот момент задевают входящие.

1. **Владелец выключает подключение «EVO CRM» в кабинете (или удаляет).** Подключение
   amoCRM не трогать. Проверка: следующий входящий идёт по прежнему маршруту, виджет
   amoCRM работает; в EVO новых событий нет; запросы EVO к ВАТС теперь дают `401`
   (`CRM switched off`/`CRM disabled`), «Настройки → Телефония» говорит «Подключение
   выключено в кабинете», а не «ВАТС отклонила ключ»; набор и сверка ждут, ключ не менять.
2. **Флаги** (запись в базу, входящие не затрагивает, в любой момент): сначала
   `unknown_lead_enabled`, `missed_task_enabled`, `backfill_enabled`, затем
   `dial_enabled`, `ui_enabled` и последним `projection_enabled` (автоматика и импорт без
   разбора не сохраняются); `outbound_paused` включить, если нужно остановить запросы к
   ВАТС немедленно.
3. Таймер: `systemctl disable --now evo-telephony-maintenance.timer` (при `ENABLED=0`
   скрипт и так ничего не делает).
4. **Только теперь** env: `backup`; `env_put … EVO_PLATFORM_TELEPHONY_ENABLED 0`; при
   полном откате пустые `PBX_*` (все три) и ключ приёма; `envcheck`; выпуск в тихое
   окно; `envfacts`.
5. Остаётся: накопленные доказательства, звонки и ноги, тестовые лиды и задачи
   (архивируются штатно). amoCRM и маршрут входящих не менялись и не затронуты.
   Данные человека стираются по `account-deletion.md`.

Ротация ключа приёма без простоя: значение в `…_CRM_TOKEN_NEXT` + выпуск (принимаются
оба) → владелец меняет ключ в подключении → после первого запроса с новым ключом
значение в `…_CRM_TOKEN`, `…_NEXT` очистить + выпуск. При подозрении на утечку — то же
сразу, автоматику выключить, просмотреть доказательства с момента подозрения. Ключ АТС
меняется только в кабинете: `outbound_paused` → новый ключ в env + выпуск → снять паузу.

| Где | Что | Действие при отклонении |
|---|---|---|
| «Настройки → Телефония», «Состояние» | приём включён, ключ задан, «Связь с ВАТС: на связи», последнее событие не старше двух суток (вс — меньше звонков), сверка не отстаёт больше чем на 3 часа, «не сопоставлено 0», «отклонённых после проверки ключа 0» | «ВАТС отклонила ключ» / «Подключение выключено в кабинете» / «У ключа ВАТС нет прав на метод» — см. шаги 3 и 8; «Автоматика остановлена по потолку» — найти причину, включать самому не спеша |
| «Настройки → Телефония», здоровье записи | «Запись в ВАТС выключена»; «Сотрудников без записи разговоров: N» | записи нет — слушать нечего; сообщить владельцу |
| «Расхождений со сверкой за сутки: N» | звонки, пришедшие только из истории ВАТС, а не событиями | растёт — вебхуки теряются: проверить подключение; входит в критерий выхода из фазы 1 |
| Журнал приложения (`telephony_inbound`; команда шага 4 с `--since 24h`) | `503` и `429` в норме 0 (`reason=database_unavailable` / `disabled` / `rate_limited`); `401 invalid_token` — зонды, всплеск = подбор ключа; `parse_failed` | 503 — база; при подозрении на подбор ротация ключа (шаг 8) |
| `journalctl -u evo-telephony-maintenance.service` | `"status":"ok"`, `"pbx":"ready"`, `retry_dead = 0`, нет `automation_failed`/`intake_failed`, `error_…` в `users`/`probe`/`reconcile`; `systemctl is-failed` — нет | единичный сбой в минуту выпуска — норма (контейнер пересоздавался) |
| SQL, счётчики (запросы шагов 5 и 7 с окном `'1 day'` и запрос ниже) | `telephony_event_work`: нет `dead_lettered` и старых `queued`; доля `incomplete` в доказательствах; `needs_review` и несопоставленные звонки | `dead_lettered` — разобрать причину по `last_error_code` |
| Автоматика | задач и лидов за сутки против потолков и ориентира плана; дубли у менеджеров (amoCRM делает свои) | дубли — вопрос команде, не ошибка кода (план §17, риск 6) |
| Звонки из CRM | число наборов против лимитов (150 на сотрудника в сутки, 60 в час и 400 в сутки на всех) | рост стоимости — `outbound_paused`, разобраться |
| Записи | «Слушать» играет; состояния «ещё не готова» / «удалена по сроку хранения» | первая настоящая запись может быть отвергнута строгим шаблоном пути ссылки (PLAN_CHANGES T6, п. 7): ответ `recording_temporarily_unavailable` — сообщить, шаблон не ослаблять на ходу |

```sql
SELECT count(*) AS calls, count(*) FILTER (WHERE needs_review) AS needs_review,
       count(*) FILTER (WHERE match_state <> 'matched') AS not_matched
FROM platform_private.telephony_calls WHERE started_at > now() - interval '1 day';
```
Сроки: первые удаления записей у Beeline ожидаются около 22–28.10.2026 (план §7.5,
§17, риск 11) — первичный импорт ссылок (7.3, № 6) не откладывать без причины. Очистка
доказательств старше 12 месяцев не расписана (T11b): в первую неделю не нужна.

Через неделю, по строкам §15 (A и B), агент готовит квитанцию запуска отдельным
документом (не частью этого файла): что пройдено, какие числа, образцы форм (без
значений), решения по предусловию 6 и по `missed_task_enabled`, что не проверено.
Критерий выхода из фазы 1 — по плану §4.
