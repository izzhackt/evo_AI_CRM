## Решения владельца (06.10.2026)

Вопросы к go-live, ответы владельца в чате:

- Окно — **7 дней**, сначала **пилот** (по умолчанию).
- Импортированные чаты — **только диалоги**; лид появляется, когда клиент напишет
  снова (по умолчанию, `lead_mode promote`).
- ИИ сейчас **выключен**; черновики Gemini с проверкой человеком — после запуска
  (к импорту не относится).
- **Личных чатов на телефоне продаж нет** — отдельного просмотра чатов владельцем и
  списка исключений нет: загружаются все чаты (`--all-chats`).
- Чаты, где в окне писали только мы, **тоже загружаются** — во всех командах
  `--include-outbound-only` (в самом загрузчике по умолчанию выключен: консервативно;
  здесь он указывается явно, каждый раз).
- Отвечать из CRM, по решению владельца, должны мочь **все сотрудники** (отдельного
  «ответственного за ответы» нет). Импорт этого не делает и не проверяет: это
  делает отдельный draft PR [#1141](https://github.com/izzhackt/evo_AI_CRM/pull/1141)
  «WhatsApp: отвечать могут все сотрудники» (миграция 261, без смены ролей); порядок
  слияния #1137 → #1139 → #1141. До его выката отвечают только сотрудники, чья область
  совпадает с диалогом; после — все, у кого есть нужные права — см. «Кто видит и
  отвечает из CRM» ниже.
- Дублей действующих клиентов не ожидается: в платформе клиентов пока нет.
  `chats_existing_client_match` в предпросмотре должен быть **0**; если нет —
  остановиться и спросить владельца.

## Кто видит и отвечает из CRM (прочитано по коду; в боевой работе не проверялось)

Решение владельца «отвечать могут все» выполняет не импорт, а draft PR
[#1141](https://github.com/izzhackt/evo_AI_CRM/pull/1141) (миграция
`261_platform_whatsapp_team_inbox.sql`, порядок слияния #1137 → #1139 → #1141): он
расширяет `staff_access_evaluate`, и роли менять не нужно. Импорт от него не зависит и
работает в обоих состояниях.

- Импортированный диалог принадлежит владельцу приёма
  (`EVO_PLATFORM_WAHA_INTAKE_SALES_MEMBERSHIP_ID`, очередь «продажи»). Системные
  администраторы отвечают во всех диалогах.
- **После применения миграции 261 (#1141):** каждый активный сотрудник (не студент), у
  чьей роли есть оба права, `communication.read.full` и `communication.manual.send`,
  видит и может ответить в **любом диалоге очереди «продажи»** независимо от области
  «свои» / «подразделение» / «вся организация». Правило привязано к очереди `sales`,
  а не к сессии WAHA; чаты куратора, лиды и дела студентов оно не меняет. По чтению
  production 06.10.2026 (только агрегаты, без имён) оба права есть у всех 5 активных
  сотрудников, то есть «все могут» выполняется для каждого из них. Сотрудник без
  одного из этих двух прав доступа по этому правилу не получит.
- **До применения 261** (сейчас, пока #1141 не выкатили) отправку даёт право
  `communication.manual.send` **с областью**: «вся организация» — любой диалог,
  «подразделение» — диалоги, чей ответственный в этом подразделении, «свои» — только
  диалоги, где сотрудник ответственный (`platform_private.staff_context_can_access`,
  миграция 155; отправка проверяет право на этот диалог). Видимость диалога в Inbox
  идёт по тем же областям. По тому же чтению production назначения с правом отправки
  имеют **разные** области, не только «вся организация»: сотрудник с областью «свои»
  не отвечает в импортированном диалоге владельца приёма, а с областью «подразделение»
  — только если владелец приёма в его подразделении. Отдельной смены ролей для этого
  не требуется: достаточно выката #1141 после #1139.
- **Остаётся верным и после 261:** отправка из CRM — ответ на **последнее входящее
  сообщение клиента в открытом диалоге**: кнопка «Отправить» выключена, а база
  отклоняет отправку (`Manual send source must be the latest inbound message in an
  open conversation`, миграция 050), пока во входящих пусто. Поэтому в импортированном
  чате, где писали только мы (`--include-outbound-only`), ответить из CRM **нельзя**,
  пока клиент не напишет; до этого сотрудники пишут с телефона продаж, а сообщения с
  телефона живой приём показывает в том же диалоге. Так сделано сознательно: из CRM
  только отвечают клиенту, холодных отправок по импортированным чатам нет (заодно
  меньше риск блокировки номера WhatsApp). Это свойство отправки из CRM, не импорта.

## Что делает и чего не делает

- Читает историю из REST API WAHA: после привязки телефона GOWS сохраняет
  синхронизированную историю и отдаёт её по запросу; вебхуками она **не**
  приходит. Только `GET`, всегда `downloadMedia=false`; никаких `POST/PUT/DELETE`,
  `read/seen`, отправки и скачивания медиа. Запрос вне списка из трёх разрешённых
  `GET` не уходит из процесса.
- Импортирует **прямые** чаты (`@c.us`, `@lid`) с клиентами: диалог целиком (оба
  направления, время сообщений — время WhatsApp), как живой. С флагом
  `--include-outbound-only` (решение владельца: он стоит во всех командах ниже) —
  **и чаты, где в окне писали только мы**: такой чат становится диалогом с нашими
  сообщениями с первого из них, без клиента, лида и передачи. Без флага такие чаты
  пропускаются и считаются (`skip_outbound_only`). Группы, Status, каналы, рассылки,
  чат с собственным номером, отправки самой CRM (`source=api`) не импортируются
  никогда.
- Медиа — типизированная заметка «📎 Фото — откройте в WhatsApp продаж», как у
  живых сообщений; файлы не скачиваются.
- Длинный текст импортируется целиком, без обрезки: БД отказывает только телу
  длиннее 100 000 знаков (`invalid`; WhatsApp допускает около 65 000), а загрузчик
  отбрасывает (`messages_dropped_oversize`) только сообщение больше одной страницы
  RPC (3 МиБ) — для текстового сообщения это недостижимо.
- Клиента, лида и передачу сотруднику импорт **не создаёт** — и для чата только из
  наших сообщений тоже. Когда клиент напишет уже после запуска, первое живое
  входящее сообщение в импортированном чате создаёт клиента и лида **ровно один раз**
  (`lead_mode promote`, по умолчанию; `--lead-mode none` — без этого); сообщения,
  которые телефон продаж отправляет в такой чат после запуска, попадают в тот же
  диалог и лида не создают. (Проверено набором `supabase/tests/platform_waha_history_import.sql`,
  раздел 8b.)
- Сообщения, отправленные с телефона после включения приёма и **до** импорта в чат,
  у которого ещё нет диалога, живой приём откладывает (миграция 259: исходящее само
  диалог не создаёт). Импорт, создавая диалог чата, добавляет их в него — по одному
  разу, после сообщений самой страницы (id, который есть и в истории, и среди
  отложенных, остаётся одной строкой).
- Доказательство: строки `history.message` / `missing` / `api_history`
  («прочитано из API, не подписано»), личность сообщений
  `private_waha_history_binding`. Это не «проверенный вебхук» и так не выглядит.

## Окно: `--window-to` — один и тот же на всех шагах

`--days N` (1–31, по умолчанию 7) и `--window-to ISO` (с часовым поясом, `Z`).
Для реального `apply` `--window-to` **обязателен** (`window_to_required`):
значения по умолчанию нет. Без него берётся «сейчас» только у `sync-status`,
`preview` и `apply --dry-run` (в ответе `window_to_defaulted: true`), и для
реального импорта это не годится. Правило в общем виде:

- `window_to` = **момент `WORKING` после привязки** — первый переход в
  `WORKING` после pairing; если сессию привязывали несколько раз, берётся
  последний (максимальный) такой момент. Сообщения до него приходят в CRM
  только через импорт (номер ещё не был привязан, вебхуков не было), после
  него — живым приёмом;
- и `window_to` **не позже первой отправки из CRM** (отправка CRM, прочитанная из
  истории раньше собственной привязки, импортировалась бы как сообщение
  сотрудника).

Отсечка по времени включения приёма (release с
`EVO_PLATFORM_WAHA_INGRESS_ENABLED=1`) — ошибка, если приём включён раньше
привязки (так и было по go-live): окно закончилось бы раньше `WORKING`, и
сообщения, пришедшие на телефон между выпуском и привязкой, не попали бы ни в
импорт, ни в живой приём. Пример 06.10: оба прогона (`c1831744…`, `59f9f226…`) шли с
`--window-to 2026-10-06T07:41:06Z`.

Зафиксируйте значение один раз и передавайте его в `sync-status`, `preview` и
каждый `apply`: файл `preview` помнит окно, и `apply` с другим окном отказывается
(`list_window_mismatch`). БД принимает только прошедшее окно не длиннее 31 дня.

## Порядок

Команды выполняются в контейнере приложения (`--max-old-space-size=512`:
окно держится в памяти в сокращённом виде, но потолок задаём явно). Ничего из
вывода команд не вставляется в чат, кроме чисел и кодов; **тексты сообщений,
номера и имена не копируются никуда**.

```bash
CLI='docker exec evo-crm-app-1 node --max-old-space-size=512 scripts/waha-history-import.mjs'
WINDOW='--window-to 2026-10-06T07:41:06Z'   # момент WORKING после привязки 06.10
OPTS='--include-outbound-only'   # решение владельца: чаты только из исходящих тоже; во ВСЕХ командах, кроме sync-status
```

`$OPTS` (то есть `--include-outbound-only`) передаётся в `preview`, пилот, остальной
`apply` и проверку — одинаково. Это важно: кандидаты `apply` зависят от флага, а
защита `--preview-file` требует, чтобы каждый кандидат был в просмотренном файле. Файл,
сделанный **без** флага, не покроет `apply` **с** флагом (`chat_not_reviewed`,
ничего не начато); наоборот безвредно. Параметры запуска (`include_outbound_only`,
`lead_mode`) записываются в БД с прогоном, и возобновление (`--resume`) требует тех
же.

### Как переносить файлы (файл предпросмотра и список пилота)

Файлы живут **в контейнере** приложения, в `/tmp` (это tmpfs на 64 МиБ: хватает с
запасом, исчезает при перезапуске контейнера). Права везде 0600; на хосте — только в
каталоге с закрытыми правами, не в облачной папке, не в чате и не в git.

```bash
# положить файл в контейнер (umask 077 внутри контейнера => права 0600):
docker exec -i evo-crm-app-1 sh -c 'umask 077; cat > /tmp/pilot.txt' < pilot.txt

# вынести файл предпросмотра из контейнера в файл 0600 на хосте:
( umask 077; docker exec evo-crm-app-1 cat /tmp/history-preview.jsonl > history-preview.jsonl )

# проверить права: должно быть -rw-------
docker exec evo-crm-app-1 ls -l /tmp/history-preview.jsonl /tmp/pilot.txt
ls -l history-preview.jsonl

# удалить (шаг 7): внутри контейнера и на хосте
docker exec evo-crm-app-1 rm -f /tmp/history-preview.jsonl /tmp/pilot.txt
rm -f history-preview.jsonl pilot.txt
```

### 0. Подождать, пока WAHA дозагрузит историю (`sync-status`)

У WAHA нет сигнала «история синхронизирована». Эвристика (только эвристика):
сессия `WORKING` не менее 10 минут и два снимка окна с одинаковыми счётчиками с
паузой не менее 3 минут.

```bash
$CLI sync-status $WINDOW --working-since 2026-10-06T07:41:06Z --watch
```

`--working-since` — время, когда вы увидели `WORKING` после привязки. Вывод — одна
строка JSON: счётчики (`window_rows`, `kept_messages`, `direct_chats`, `inbound`,
`outbound`) и `heuristic.stable` с причинами (`working_since_unknown`,
`working_under_10_minutes`, `counts_changed`, `interval_under_3_minutes`,
`no_second_snapshot`). Код выхода 0 — стабильно, 3 — нет; повторяйте, пока
`stable: true`. Если `kept_messages` подозрительно мал для недели переписки,
остановитесь и разберитесь с WAHA: глубина истории — свойство WAHA и телефона.

### 1. Сухой прогон-список (`preview`)

```bash
$CLI preview $WINDOW $OPTS --out /tmp/history-preview.jsonl
```

(файл создаётся внутри контейнера; вынос на хост — командой из раздела «Как
переносить файлы»)

В stdout — только итоги: число чатов, исходы по ответу БД (`import_new`,
`import_existing`, `skip_*`), пропуски по причинам, `chats_existing_client_match`
(номер совпал с активным клиентом — этих людей CRM уже знает; по ответу владельца
клиентов в платформе пока нет, ожидается **0**, иначе — остановиться и спросить).
С флагом чаты только из исходящих — кандидаты (`chats_outbound_only` в итогах — это
чаты, которые флаг **не** взял; при `$OPTS` обычно 0). Файл
`--out` создаётся **эксклюзивно с правами 0600** (существующий не перезаписывается)
и содержит по строке на чат: непрозрачная ссылка `c-…`, имя в WhatsApp, последние
4 цифры, число входящих/исходящих, первое и последнее время в окне, исход.
**Это персональные данные**: файл не копировать, не коммитить, не пересылать;
после шага 6 удалить и в контейнере, и на хосте (шаг 7).

Ссылки `c-…` стабильны для одного ключа сервиса (HMAC от ключа Supabase); если
ключ сменили между шагами, ссылки перестанут совпадать — загрузчик остановится
(`list_ref_unmatched`), а не импортирует лишнее.

### 2. Оператор выбирает чаты для пилота (формы чатов)

Просмотра чатов владельцем и списка исключений нет: личных чатов на телефоне продаж
нет (ответ владельца 06.10). Оператор выбирает чаты для пилота **из файла
предпросмотра: по одному-два каждой формы, всего не больше 6**. Без этого формы,
которые владелец выбрал (чат только из наших сообщений, `@lid`, длинный чат в
несколько страниц), он впервые увидел бы после необратимого `--all-chats`.

| Форма | Признак в файле | Что проверить в CRM после пилота |
|---|---|---|
| `ordinary` | `inbound > 0`, `kind = c_us`, `pages = 1` | порядок по времени WhatsApp, фото/голос — заметкой, клиента и лида нет |
| `outbound_only` | `inbound = 0` | диалог «WhatsApp ••••NNNN» из наших сообщений, клиента, лида и передачи нет |
| `lid` | `kind = lid` | название по телефону (если WAHA его знает) или «WhatsApp контакт #…», числа из цифр LID нет |
| `multi_page` | `pages > 1` (больше 200 сообщений) | все сообщения на месте и по порядку, особенно на стыке страниц |

На хосте, где лежит файл предпросмотра, команда печатает кандидатов по формам (без
имён и номеров: форма, время последнего сообщения, ссылка, число входящих/исходящих,
число страниц). Берутся только чаты с исходом `import_new` и без совпадения с
действующим клиентом:

```bash
jq -r '
  select(.outcome == "import_new" and (.existing_client_match | not))
  | [ (if .inbound > 0 and .kind == "c_us" and .pages == 1 then "ordinary" else empty end),
      (if .inbound == 0 then "outbound_only" else empty end),
      (if .kind == "lid" then "lid" else empty end),
      (if .pages > 1 then "multi_page" else empty end) ] as $shapes
  | $shapes[] as $shape
  | [$shape, .last_at, .ref, .inbound, .outbound, .pages] | @tsv
' history-preview.jsonl | sort -t"$(printf '\t')" -k1,1 -k2,2r
```

Из каждой формы берутся одна-две верхние ссылки (самые свежие); один чат может
закрывать две формы. Ссылки идут в `pilot.txt`, по одной на строку (после пробела
можно комментарий). Если в окне нет чатов какой-то формы (например, ни одного `@lid`),
то этой формы просто нет: пилот берёт имеющиеся, а оператор записывает, каких форм
не было. Число ссылок: `grep -c '^c-' pilot.txt` — **не больше 6**.

Положить `pilot.txt` в контейнер (команда выше). Файл без единой ссылки (пустой или из
одних комментариев) загрузчик **отвергает** (`list_file_empty`).

### 3. Пилот

Сначала сухой прогон по тому же списку: ничего не пишет, показывает, что будет
сделано.

```bash
$CLI apply $WINDOW $OPTS --only-chats-file /tmp/pilot.txt --max-chats 6 --dry-run
```

Проверить: `selection.only_list: true`; `totals.chats_selected` равно числу ссылок в
`pilot.txt`; `totals.by_outcome.import_new` — столько же; `chats_multi_page` не 0,
если выбран длинный чат; `chats_existing_client_match` — 0. Иначе — исправить список.
Потом сам пилот:

```bash
$CLI apply $WINDOW $OPTS --only-chats-file /tmp/pilot.txt --max-chats 6
```

Вывод: `state: completed`, `totals` (чатов, страниц, сообщений, пропусков по
причинам, `deferred_phone_sent_*`), `run_id`.

Пилот делается **только** через `--only-chats-file` со ссылками, выбранными человеком
по файлу предпросмотра. Импорт необратим, поэтому ограничение числа чатов выбора не
заменяет: `--max-chats 6` — **страховка** от опечатки (список из 300 ссылок импортирует
не больше 6 чатов), а не способ выбрать чаты. `--max-chats` один выбора не делает
(`selection_required`) и допускается **только вместе с `--only-chats-file`** (урезает
выбранный список); с `--exclude-chats-file` и `--all-chats` он отвергается
(`max_chats_needs_only_list`): ограниченный импорт непросмотренных чатов невозможен.

### 4. Владелец смотрит пилот в CRM

В Inbox, по таблице форм выше: диалоги на месте, порядок по последнему сообщению
WhatsApp, исходящие до первого сообщения клиента на месте, голосовые/фото —
заметками, клиента и лида нет (у чата только из наших сообщений — тоже), длинный чат
целиком. Реальному клиенту **тестовых сообщений не отправлять**: поэтому пилотом
проверяется только то, что кнопка «Отправить» доступна в диалоге, где клиент писал
(не нажимая её), а если #1141 уже выкачен, то и под учётной записью сотрудника с
областью «свои» (диалог должен быть виден и кнопка доступна: см. «Кто видит и отвечает
из CRM»); в чате только из наших сообщений отправки из CRM нет по построению. Если
что-то не так — **стоп**: уже импортированное удалить нельзя, дальше только
исправление кода.

### 5. Остальные чаты

```bash
$CLI apply $WINDOW $OPTS --all-chats --preview-file /tmp/history-preview.jsonl
```

`--all-chats` — явный выбор «все», без списка исключений (личных чатов нет).
`--preview-file` включает защиту: каждый кандидат окна должен быть в просмотренном
файле, иначе `chat_not_reviewed` (появился чат, которого не было в предпросмотре, или
предпросмотр сделан без `--include-outbound-only`).
Уже импортированные пилотом сообщения считаются (`already_bound`) и не
дублируются. Без явного выбора (`--only-chats-file`, `--exclude-chats-file` или
`--all-chats`) `apply` не запускается (`selection_required`).
Во время работы в stderr идут строки прогресса (только числа).

Прерванный прогон (Ctrl-C, сеть, перезапуск) ставится на паузу; курсор хранится в
БД. Продолжить: тот же набор флагов плюс `--resume <run_id>` (обязателен явный
`--window-to`). Без `--resume` незавершённый прогон не подхватывается
(`unfinished_run_exists`, в ошибке — `run_id`).

### 6. Проверка

```bash
$CLI apply $WINDOW $OPTS --all-chats --dry-run
```

`totals.first_page_would_import` должен быть **0**, все выбранные чаты —
`skip_nothing_eligible`. Сверьте `run_totals` и `totals` последнего `apply` с
числами предпросмотра (`projected` ≈ входящие + исходящие выбранных чатов, медиа
учтены, `skipped` объяснён). Сообщения, которые телефон отправил после включения
приёма в чаты без диалога, в `projected` и в предпросмотр **не входят**: их считают
`totals.deferred_phone_sent_found` (найдено отложенных), `_imported` (добавлено в
созданные диалоги) и `_dropped` (не добавлено: берутся только 200 самых свежих на
чат; `_dropped > 0` — сообщить владельцу, число и есть доказательство, в чат оно
не попадёт). Эти три числа загрузчик считает **по каждому запуску CLI**, а не по
прогону: в `run_totals` из БД их нет, и каждый новый запуск (пилот, полный `apply`,
каждый `--resume`) начинает с нуля. Поэтому **просуммируйте** их по выводам всех
запусков пилота и полного импорта (в выводе `--dry-run` этих чисел нет). Итого
сообщений в CRM ≈ `projected` + сумма `deferred_phone_sent_imported` по всем запускам.
Если `would_import` не 0 (WAHA отдавал хвосты страницы при равных метках времени) —
повторите `apply`: он идемпотентен.

### 7. Убрать следы

```bash
docker exec evo-crm-app-1 rm -f /tmp/history-preview.jsonl /tmp/pilot.txt
rm -f history-preview.jsonl pilot.txt   # копии на хосте
```

## Как загрузчик читает WAHA (проверено по исходникам WAHA 2026.9.2)

| Параметр | Значение | Источник |
|---|---|---|
| Путь | `GET /api/crm_primary/chats/all/messages` (chatId `all` — все чаты, GOWS не фильтрует по jid) | `src/api/chats.controller.ts:51,126-145`; `src/core/engines/gows/session.gows.core.ts:2731` |
| Окно | `filter.timestamp.gte` / `.lte`, Unix **секунды**, включительно | `src/structures/chats.dto.ts:35,44`; `session.gows.core.ts:2749-2756` |
| Предел | `limit` всегда передаётся (по умолчанию у WAHA 10; верхней границы в DTO нет); сортировка `timestamp` по возрастанию | `chats.dto.ts:102-123` |
| Короткие и пустые страницы | реакции, голоса опросов, служебные сообщения отбрасываются **после** SQL `LIMIT/OFFSET` — страница может быть короче или даже пустой посреди окна, а число скрытых строк не видно | `session.gows.core.ts:2785`, `:2950-2976` |
| Равные метки времени | хранилище gows-plus сортирует **только** по метке времени с точностью до секунды (без вторичного ключа): строки с равной меткой могут менять порядок между запросами, и постраничное чтение по `offset` теряет и повторяет их | gows-plus `src/storage/sqlstorage/message.go:83-84` (проверено на теге v1.0.48, который закрепляет WAHA 2026.9.2) |

Поэтому загрузчик **не листает по `offset`** (всегда `offset=0`), а режет окно на
непересекающиеся срезы по целым секундам (`--waha-slice-seconds`, 3600) и читает
каждый срез с растущим пределом: 200, затем 1000, 5000 и 12 500 (×5). Срез принят,
когда два соседних предела вернули **один и тот же набор id**; иначе предел растёт
дальше, а срез, не устоявшийся на самом большом пределе (или слишком большой
ответ), делится пополам. Граница для одной секунды: чтобы устояться, ей нужны два
равных соседних чтения, а наибольший предел — 12 500, поэтому секунда, в которой
больше **~5 000** строк, не устоится и даёт `scan_unstable` (читаются 5000 и
12 500, и они различаются); больше 5 000 сообщений в одну секунду для
живой переписки нереалистично. Метка времени читается как целая секунда
`floor(timestamp)`, как её читает БД: запрос идёт `gte=начало`, `lte=конец+1`
(границы WAHA только целые), строка ровно в `конец+1` остаётся следующему срезу, так
что дробная метка внутри последней секунды среза не теряется и не читается дважды.
Одна секунда, которая не устоялась; id, встретившийся в
двух срезах или дважды в одном ответе (после двух повторов запроса); ответ с
сообщением вне среза (сервер игнорирует фильтр) — это `scan_unstable`/
`waha_response_invalid`, а не тихая потеря. Правила «остановиться на пустой
странице» нет: каждая секунда окна принадлежит ровно одному срезу. Остаточный
риск: сотни подряд идущих «служебных» строк внутри одного часа, прячущих
настоящие сообщения от двух соседних пределов сразу.
| Медиа | `downloadMedia=false` всегда | `chats.dto.ts:123` |
| Чат | у прямого чата GOWS `from` = чат в обе стороны, `to` = `null`; `source` = `app`/`api` по устройству | `session.gows.core.ts:3487-3495`, `:3186-3195` |
| `@lid` | телефон: `GET /api/crm_primary/lids/{lid}` → `{lid, pn\|null}`; `pn`, равный собственному номеру, игнорируется; телефон передаётся в БД как `_data.Info.SenderAlt`/`RecipientAlt` | `src/api/lids.controller.ts:69-90`; `session.gows.core.ts:2599-2610` |
| Сессия | `GET /api/sessions/crm_primary`: `status`, `engine`, `me {id, lid, jid}` | `src/api/sessions.controller.ts:80`; `src/structures/sessions.dto.ts:469-484` |

Не проверено на живом WAHA (нужен один реальный образец на движок): совпадение
полей REST с вебхуком (`source`, медиа-поля, id сообщений), глубина истории,
порядок сообщений с равной меткой времени (закрыт срезами, но не проверен на
живых данных).

## Ограничения и риски

- **Необратимо:** сообщения, привязки и диалоги неизменяемы; поэтому
  preview → пилот → остальные. Ошибочно импортированный чат убрать нельзя.
- Страница в БД — не более 500 сообщений и 5 МиБ; первая страница чата
  расширяется до первого входящего сообщения клиента (иначе исходящие до него
  потерялись бы). Если первое входящее глубже 500-го сообщения чата, чат
  пропускается целиком (`chats_first_inbound_unreachable`); если БД не сочла
  первую страницу началом диалога (`skip_outbound_only`), остаток чата не
  отправляется, а курсор переносится дальше.
- Неотвеченные импортированные чаты честно показываются как «ждут ответа» с
  многодневным ожиданием; они не попадают в «новые заявки».
- Чат только из наших сообщений (`--include-outbound-only`): имя клиента неизвестно
  (его даёт сообщение клиента), поэтому диалог называется по последним 4 цифрам
  номера, а `@lid`-чат без телефона — «WhatsApp контакт #…» (никогда числом из цифр
  LID). До первого сообщения клиента лида нет, в списках лидов такого чата нет.
- Ответ из CRM — на последнее входящее сообщение клиента: в чате только из наших
  сообщений он невозможен, пока клиент не напишет (сознательно: только ответы, без
  холодных отправок). Кто может ответить: после #1141 (миграция 261) все сотрудники с
  правами чтения и отправки, до него — по областям ролей (см. «Кто видит и отвечает из
  CRM»).
- `@lid`-чат без известного телефона и тот же человек позже как `@c.us` без LID —
  два диалога (известное ограничение миграции 259).
- Загрузчик держит окно в памяти (до 200 000 сообщений, сокращённый вид без
  вложений); больше — сократите `--days`. Запускайте его с
  `node --max-old-space-size=512`.
- Нагрузка: последовательное чтение WAHA (каждый срез минимум два запроса) с
  паузой 150 мс и паузы между страницами БД; параллельных запросов нет. Неделя
  окна — порядка 340 запросов на скан.
- Повторяющиеся риски чтения: см. «Как загрузчик читает WAHA» (равные метки времени,
  скрытые служебные строки). Неудавшееся чтение (`scan_unstable`) ничего не
  импортирует; частично применённый прогон добирается повторным `apply`.
- Повышение до клиента и лида при первом живом сообщении (`lead_mode promote`)
  не должно терять живое сообщение: при неподходящем владельце импортированного
  диалога владельцем лида становится живой intake-участник, а при конфликте
  идентичности (уникальность, проверка, внешний ключ) сообщение сохраняется,
  повышение пропускается (в результате проекции `identity_promotion_skipped`) и
  повторяется со следующим проверенным сообщением клиента. Любая другая ошибка
  по-прежнему ломает событие, как любая ошибка проекции.
