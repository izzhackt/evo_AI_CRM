# WhatsApp: импорт истории переписок (последние 7 дней) в Inbox CRM

Обновлено: 2026-10-05. Статус: **процедура, не выполнялась.** Документ ничего не
разрешает: каждый шаг, который пишет в production (миграция 260, release, запуск
загрузчика), выполняется только после явного «давай» владельца в чате и только в
его границах. Загрузчик читает WAHA и пишет в CRM; откатить импорт внутри
приложения нельзя.

Код: draft PR [#1139](https://github.com/izzhackt/evo_AI_CRM/pull/1139) — слой
базы данных (миграция `260_platform_waha_history_import.sql`) и загрузчик
`scripts/waha-history-import.mjs` (он ставится в образ приложения, как
`scripts/waha-runtime-binding.mjs`). Приём живых сообщений — #1137, go-live —
`docs/runbooks/whatsapp-go-live.md` (#1138); этот документ идёт **после**
приёмки go-live.

## Что делает и чего не делает

- Читает историю из REST API WAHA: после привязки телефона GOWS сохраняет
  синхронизированную историю и отдаёт её по запросу; вебхуками она **не**
  приходит. Только `GET`, всегда `downloadMedia=false`; никаких `POST/PUT/DELETE`,
  `read/seen`, отправки и скачивания медиа. Запрос вне списка из трёх разрешённых
  `GET` не уходит из процесса.
- Импортирует **личные** чаты (`@c.us`, `@lid`), где в окне есть хотя бы одно
  входящее сообщение клиента: диалог целиком (оба направления, время сообщений —
  время WhatsApp), как живой. Чаты только из исходящих — по флагу
  `--include-outbound-only`. Группы, Status, каналы, рассылки, чат с собственным
  номером, отправки самой CRM (`source=api`) не импортируются никогда.
- Медиа — типизированная заметка «📎 Фото — откройте в WhatsApp продаж», как у
  живых сообщений; файлы не скачиваются.
- Клиента, лида и передачу сотруднику импорт **не создаёт**. Когда клиент напишет
  снова уже после запуска, первое живое входящее сообщение в импортированном чате
  создаёт клиента и лида (`lead_mode promote`, по умолчанию; `--lead-mode none` —
  без этого).
- Доказательство: строки `history.message` / `missing` / `api_history`
  («прочитано из API, не подписано»), личность сообщений
  `private_waha_history_binding`. Это не «проверенный вебхук» и так не выглядит.

## Предусловия (все обязательны)

1. Миграция 260 применена (release после merge #1137 → #1139); go-live принят.
2. Сессия `crm_primary` в `WORKING`, движок **GOWS** (или NOWEB с SQL/Mongo-хранилищем;
   WEBJS/WPP историю целиком не отдают — загрузчик откажется: `engine_unsupported`).
3. Vault-binding ключа WAHA готов (`waha-runtime-binding.mjs check` из go-live);
   ключ загрузчик берёт оттуда сам — не из аргументов и не из окружения.
4. В окружении приложения есть `EVO_PLATFORM_WAHA_INTAKE_SALES_MEMBERSHIP_ID`
   (владелец импортированных диалогов — тот же, что у живого приёма).
5. Известен **момент включения приёма** (`EVO_PLATFORM_WAHA_INGRESS_ENABLED=1`,
   release №2 из go-live) — это и есть `--window-to` (ниже).

## Окно: `--window-to` — один и тот же на всех шагах

`--days N` (1–31, по умолчанию 7) и `--window-to ISO` (с часовым поясом, `Z`).
Без `--window-to` берётся «сейчас» (в ответе `window_to_defaulted: true`) —
**так нельзя** для реального импорта: окно должно заканчиваться **не позже
момента включения приёма и не позже первой отправки из CRM** (отправка CRM,
прочитанная из истории раньше собственной привязки, импортировалась бы как
сообщение сотрудника). Зафиксируйте значение один раз
(`2026-10-06T08:30:00Z`) и передавайте его в `sync-status`, `preview` и каждый
`apply`: файл `preview` помнит окно, и `apply` с другим окном отказывается
(`list_window_mismatch`). БД принимает только прошедшее окно не длиннее 31 дня.

## Порядок

Команды выполняются в контейнере приложения. Ничего из вывода команд не
вставляется в чат, кроме чисел и кодов; **тексты сообщений, номера и имена не
копируются никуда**.

```bash
CLI='docker exec -i evo-crm-app-1 node scripts/waha-history-import.mjs'
WINDOW='--window-to 2026-10-06T08:30:00Z'
```

### 0. Подождать, пока WAHA дозагрузит историю (`sync-status`)

У WAHA нет сигнала «история синхронизирована». Эвристика (только эвристика):
сессия `WORKING` не менее 10 минут и два снимка окна с одинаковыми счётчиками с
паузой не менее 3 минут.

```bash
$CLI sync-status $WINDOW --working-since 2026-10-06T07:50:00Z --watch
```

`--working-since` — время, когда вы увидели `WORKING` после привязки. Вывод — одна
строка JSON: счётчики (`window_rows`, `kept_messages`, `direct_chats`, `inbound`,
`outbound`) и `heuristic.stable` с причинами (`working_since_unknown`,
`working_under_10_minutes`, `counts_changed`, `interval_under_3_minutes`,
`no_second_snapshot`). Код выхода 0 — стабильно, 3 — нет; повторяйте, пока
`stable: true`. Если `kept_messages` подозрительно мал для недели переписки,
остановитесь и разберитесь с WAHA: глубина истории — свойство WAHA и телефона.

### 1. Сухой прогон-список (`preview`)

```bash
$CLI preview $WINDOW --out /tmp/history-preview.jsonl
```

В stdout — только итоги: число чатов, исходы по ответу БД (`import_new`,
`import_existing`, `skip_*`), пропуски по причинам, `chats_existing_client_match`
(номер совпал с активным клиентом — этих людей CRM уже знает). Файл
`--out` создаётся **эксклюзивно с правами 0600** (существующий не перезаписывается)
и содержит по строке на чат: непрозрачная ссылка `c-…`, имя в WhatsApp, последние
4 цифры, число входящих/исходящих, первое и последнее время в окне, исход.
**Это персональные данные**: файл не копировать, не коммитить, не пересылать;
после шага 5 удалить (`rm /tmp/history-preview.jsonl`).

Ссылки `c-…` стабильны для одного ключа сервиса (HMAC от ключа Supabase); если
ключ сменили между шагами, ссылки перестанут совпадать — загрузчик остановится
(`list_ref_unmatched`), а не импортирует лишнее.

### 2. Владелец отмечает личные чаты

Владелец открывает файл (на сервере или по защищённому каналу, не в чате),
выписывает ссылки **личных** чатов (семья, друзья, поставщики) в
`/tmp/personal.txt` — по одной на строку, можно с комментарием после пробела.

### 3. Пилот на 3 чатах

Три ссылки обычных клиентских чатов — в `/tmp/pilot.txt`.

```bash
$CLI apply $WINDOW --only-chats-file /tmp/pilot.txt
```

Вывод: `state: completed`, `totals` (чатов, страниц, сообщений, пропусков по
причинам), `run_id`. Альтернатива без списка — `--max-chats 3` (первые три чата
по свежести).

### 4. Владелец проверяет пилот в CRM

В Inbox: диалоги на месте, порядок по последнему сообщению WhatsApp, исходящие до
первого сообщения клиента на месте, голосовые/фото — заметками, клиента и лида
нет, ответ из CRM в такой диалог уходит как обычно. Если что-то не так —
**стоп**: уже импортированное удалить нельзя, дальше только исправление кода.

### 5. Остальные чаты

```bash
$CLI apply $WINDOW --exclude-chats-file /tmp/personal.txt --preview-file /tmp/history-preview.jsonl
```

`--preview-file` включает защиту: каждый чат окна должен быть в просмотренном
файле, иначе `chat_not_reviewed` (появился чат, который владелец не видел).
Уже импортированные пилотом сообщения считаются (`already_bound`) и не
дублируются. Без явного выбора (`--only-chats-file`, `--exclude-chats-file`,
`--max-chats` или `--all-chats`) `apply` не запускается (`selection_required`).
Во время работы в stderr идут строки прогресса (только числа).

Прерванный прогон (Ctrl-C, сеть, перезапуск) ставится на паузу; курсор хранится в
БД. Продолжить: тот же набор флагов плюс `--resume <run_id>` (обязателен явный
`--window-to`). Без `--resume` незавершённый прогон не подхватывается
(`unfinished_run_exists`, в ошибке — `run_id`).

### 6. Проверка

```bash
$CLI apply $WINDOW --exclude-chats-file /tmp/personal.txt --dry-run
```

`totals.first_page_would_import` должен быть **0**, все выбранные чаты —
`skip_nothing_eligible`. Сверьте `run_totals` и `totals` последнего `apply` с
числами предпросмотра (`projected` ≈ входящие + исходящие выбранных чатов, медиа
учтены, `skipped` объяснён). Если `would_import` не 0 (WAHA отдавал хвосты
страницы при равных метках времени) — повторите `apply`: он идемпотентен.

### 7. Убрать следы

```bash
rm -f /tmp/history-preview.jsonl /tmp/personal.txt /tmp/pilot.txt
```

## Флаги

| Команда | Флаги |
|---|---|
| все | `--days N` (7), `--window-to ISO`, `--waha-page-size N` (200), `--waha-pause-ms N` (150), `--max-window-messages N` (200000) |
| `sync-status` | `--working-since ISO`, `--watch`, `--interval-seconds N` (180) |
| `preview` | `--out FILE` (обязателен), `--include-outbound-only`, `--lead-mode`, `--page-size N`, `--rpc-pause-ms N` |
| `apply` | `--only-chats-file`, `--exclude-chats-file`, `--preview-file`, `--max-chats N`, `--all-chats`, `--dry-run`, `--include-outbound-only`, `--lead-mode promote\|none`, `--resume RUN_ID`, `--page-size N` (200, максимум 500), `--rpc-pause-ms N` (100) |

Окружение (уже есть в контейнере): `NEXT_PUBLIC_SUPABASE_URL`,
`EVO_PLATFORM_SUPABASE_SECRET_KEY`, `EVO_PLATFORM_ORGANIZATION_ID`,
`EVO_PLATFORM_WAHA_INTAKE_SALES_MEMBERSHIP_ID` (для `apply`).
Код выхода: 0 — готово, 1 — ошибка (одна JSON-строка в stderr: `error_code`,
иногда `sqlstate` и `run_id`), 2 — ошибка аргументов, 3 — `sync-status` не стабилен.

Коды ошибок: `session_not_working`, `engine_unsupported`, `session_me_missing`
(WAHA не сообщил собственный аккаунт — без него собственный номер мог бы стать
клиентом), `waha_binding_missing`/`waha_binding_invalid` (нет Vault-binding),
`waha_key_rejected`, `waha_unreachable`, `window_invalid`, `window_too_large`,
`rpc_unauthorized`/`rpc_forbidden` (ключ сервиса, владелец приёма), `rpc_not_found`
(схема не на 260), `rpc_rejected` + `sqlstate`, `list_*`, `chat_not_reviewed`,
`selection_required`, `unfinished_run_exists`, `resume_mismatch`, `interrupted`.

## Как загрузчик читает WAHA (проверено по исходникам WAHA 2026.9.2)

| Параметр | Значение | Источник |
|---|---|---|
| Путь | `GET /api/crm_primary/chats/all/messages` (chatId `all` — все чаты, GOWS не фильтрует по jid) | `src/api/chats.controller.ts:51,126-145`; `src/core/engines/gows/session.gows.core.ts:2731` |
| Окно | `filter.timestamp.gte` / `.lte`, Unix **секунды**, включительно | `src/structures/chats.dto.ts:35,44`; `session.gows.core.ts:2749-2756` |
| Страницы | `limit` всегда передаётся (по умолчанию у WAHA 10), `offset` растёт на запрошенный `limit`; сортировка `timestamp` по возрастанию | `chats.dto.ts:106,114` |
| Короткие страницы | реакции, голоса опросов, служебные сообщения отбрасываются **после** SQL `LIMIT/OFFSET` — страница может быть короче или даже пустой посреди окна; скан кончается после **двух** пустых страниц подряд или когда страница целиком за окном | `session.gows.core.ts:2785`, `:2950-2976` |
| Медиа | `downloadMedia=false` всегда | `chats.dto.ts:123` |
| Чат | у прямого чата GOWS `from` = чат в обе стороны, `to` = `null`; `source` = `app`/`api` по устройству | `session.gows.core.ts:3487-3495`, `:3186-3195` |
| `@lid` | телефон: `GET /api/crm_primary/lids/{lid}` → `{lid, pn\|null}`; `pn`, равный собственному номеру, игнорируется; телефон передаётся в БД как `_data.Info.SenderAlt`/`RecipientAlt` | `src/api/lids.controller.ts:69-90`; `session.gows.core.ts:2599-2610` |
| Сессия | `GET /api/sessions/crm_primary`: `status`, `engine`, `me {id, lid, jid}` | `src/api/sessions.controller.ts:80`; `src/structures/sessions.dto.ts:469-484` |

Не проверено на живом WAHA (нужен один реальный образец на движок): совпадение
полей REST с вебхуком (`source`, медиа-поля, id сообщений), глубина истории,
порядок сообщений с равной меткой времени между страницами.

## Ограничения и риски

- **Необратимо:** сообщения, привязки и диалоги неизменяемы; поэтому
  preview → пилот → остальные. Ошибочно импортированный чат убрать нельзя.
- Страница в БД — не более 500 сообщений и 5 МиБ; первая страница чата
  расширяется до первого входящего сообщения клиента (иначе исходящие до него
  потерялись бы). Если первое входящее глубже 500-го сообщения чата, чат
  пропускается целиком (`chats_first_inbound_unreachable`); если БД не сочла
  первую страницу началом диалога (`skip_outbound_only`), остаток чата не
  отправляется, а курсор переносится дальше.
- Неотвеченные импортированные чаты честно показываются как «ждут ответа» с
  многодневным ожиданием; они не попадают в «новые заявки».
- `@lid`-чат без известного телефона и тот же человек позже как `@c.us` без LID —
  два диалога (известное ограничение миграции 259).
- Загрузчик держит окно в памяти (до 200 000 сообщений, сокращённый вид без
  вложений); больше — сократите `--days`.
- Нагрузка: одно последовательное чтение WAHA с паузой 150 мс и паузы между
  страницами БД; параллельных запросов нет.

## Откат и остановка

Остановить: прервать команду (Ctrl-C); прогон ставится на паузу, уже импортированное
остаётся, продолжить можно через `--resume`. Отката нет. Исправление данных —
отдельное решение владельца и отдельная миграция.
